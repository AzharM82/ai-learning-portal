Security basics: OWASP top 10 for builders

Most web apps are not broken by exotic zero-days. They are broken by the same ten families of mistakes, ranked by OWASP from real vulnerability data: a missing permission check, a query built from user input, a default password, an unpatched library. Learn the ten as builder habits, not as a compliance list, and you close the doors attackers actually walk through.

02 The one-idea version

The OWASP Top 10 is a map of broken trust boundaries, not a trivia list. Every category is a place where your app trusted something it should not have: the browser to enforce permissions, the user to send harmless input, a default setting to be safe, a library to be clean. Security basics means moving every one of those checks to a place the attacker does not control — the server, the design, and the pipeline.

03 The 2025 list, as a request flowing through gates

The OWASP Developer Guide lists the 2025 edition as the latest: A01 Broken Access Control, A02 Security Misconfiguration, A03 Software Supply Chain Failures, A04 Cryptographic Failures, A05 Injection, A06 Insecure Design, A07 Authentication Failures, A08 Software or Data Integrity Failures, A09 Security Logging and Alerting Failures, A10 Mishandling of Exceptional Conditions. 04 How it works

Six builder mechanics that cover the ten categories, in the order you apply them.

1

Authorize on the server, for every object and every function — deny by default (A01)

Broken Access Control is the #1 risk because it is a design habit, not a typo: the app checks logged in? but never allowed to touch this record? Change an ID in the URL (/invoices/124 instead of 123) and a stranger's data comes back — that is an insecure direct object reference. Fix it structurally: a server-side permission check on every handler, scoped queries (WHERE owner_id = current_user), and default-deny for anything not explicitly allowed.

2

Never let input become code: parameterize queries, encode output (A05)

Injection is one bug with many interpreters: SQL, OS commands, templates, and the browser itself (XSS). The root cause is always the same — user input glued into a string that something then executes. Parameterized queries / prepared statements send the query and the data separately, so input can never change the query's meaning. For output, encode for the context (HTML, attribute, JavaScript) so data stays data when the browser renders it.

3

Use proven crypto, and never store secrets like an amateur (A04)

Cryptographic Failures are usually absences, not bad math: passwords in plain text or fast hashes, no TLS, secrets checked into git, home-grown encryption. Use the platform standards: hash passwords with a dedicated password hash (Argon2 or bcrypt), encrypt in transit with TLS everywhere, encrypt sensitive data at rest, keep secrets in a secret store — and rotate anything that ever touched a repo or a log.

4

Harden the config and the supply chain you ship on (A02, A03, A08)

Three categories, one discipline: know what you run. Misconfiguration (A02) is default credentials, debug mode in production, verbose errors, and unused features left on — fix with hardened, reviewed, environment-specific config. Supply-chain failures (A03) expand the old vulnerable-components problem: pin and patch dependencies, generate an SBOM, and scan in CI. Integrity failures (A08) are trusting updates and data without verification — verify signatures and never deserialize untrusted data.

5

Design for abuse before you build, and make authentication boring-strong (A06, A07)

Insecure Design (A06) means the flaw was in the plan: a password-reset flow anyone can abuse cannot be patched at the code level. Threat-model first — who would abuse this flow, and what stops them? Authentication Failures (A07) are the implementation side: allow strong passwords, rate-limit and lock out credential stuffing, offer MFA, expire sessions, and never ship default credentials. If a control is not in the design, code review will not invent it.

6

Log, alert, and fail closed — never fail open or leak internals (A09, A10)

You cannot respond to attacks you never see: log authentication and access-control failures, alert on them, and keep logs attackers cannot tamper with (A09). And when something unexpected happens, mishandling it is its own category (A10): return a generic error to the user, keep stack traces and SQL errors in the server log, and make the failure state the safe state — a crashed permission check must deny, never allow.

05 Code sketch

One handler applying gates 1–3 and failing safely: ownership check, parameterized query, generic errors, and a log line on denial.

import logging
log = logging.getLogger("app")

def get_invoice(db, user, invoice_id):
    # A05: parameterized — invoice_id is data, never SQL
    row = db.execute(
        "SELECT owner_id, total FROM invoices WHERE id = ?",
        (invoice_id,),
    ).fetchone()
    if row is None:
        # A10: generic message, no internals leaked
        return 404, {"error": "not found"}
    # A01: authorize THIS object for THIS user, server-side
    if row[0] != user.id and not user.is_admin:
        # A09: denials are security events — log them
        log.warning("access denied user=%s invoice=%s",
                    user.id, invoice_id)
        return 403, {"error": "forbidden"}
    return 200, {"id": invoice_id, "total": row[1]}

# Missing on purpose: any string-built query, any check
# that lives only in the UI, any plaintext secret.

06 Failure modes

Five ways builders ship a Top-10 bug — and the one-line fix for each.

1

Checking login, not permission (IDOR)Fix: authorize the specific object on the server for every request — scope the query by owner.

The endpoint requires a session, so it feels protected. But any logged-in user can increment an ID and read everyone else's records. Authentication is who you are; authorization is what you may touch — A01 is #1 precisely because teams ship the first and forget the second.

2

Building queries by string concatenationFix: parameterized queries / prepared statements everywhere — no exceptions for “internal” tools.

"... WHERE name = '" + name + "'" hands the attacker the keyboard to your database. Escaping by hand always misses a case; parameterization removes the whole class by separating code from data.

3

Plain-text passwords, home-grown crypto, secrets in gitFix: Argon2/bcrypt for passwords, TLS everywhere, secrets in a secret store — and rotate anything exposed.

A fast hash (or none) turns a leaked database into everyone's password. A secret committed once lives in history forever, even after you delete the line. Crypto failures are silent until the breach report.

4

Debug mode, defaults, and dependencies left to rot in productionFix: hardened reviewed config per environment, defaults changed, dependencies pinned, patched, and scanned in CI.

Misconfiguration (A02) and supply-chain failures (A03) are the highest risers in the 2025 list because modern apps are mostly configuration and other people's code. The exploit for a known-vulnerable library is public — patching late is volunteering.

5

Silent failures: no logs, and stack traces as the error pageFix: log and alert on auth and access failures, return generic errors, and fail closed.

Without logging (A09) a breach runs for months unnoticed. With verbose errors (A10) every failure teaches the attacker your schema, paths, and versions. Both are one-line habits set at the framework level — set them once, correctly.

08 Sample prompts

Copy one into your AI assistant and apply it to your own code.

AUDIT AGAINST THE TOP 10

Audit this web app code against the OWASP Top 10 (2025). For each category A01–A10 say: not present, present with file/line evidence, or cannot tell from this code. For every present finding, show the smallest concrete fix. Start with broken access control and injection — do not give generic advice.

FIND THE IDOR

Review these API handlers for broken access control. For each handler that loads an object by an ID from the request, tell me: does it verify the current user owns or may access that object, on the server? List every handler that only checks authentication, and rewrite it with a scoped query or an explicit ownership check.

THREAT-MODEL THE FLOW

Threat-model this user flow (for example password reset or checkout) the way OWASP's Insecure Design category demands: list the abuse cases an attacker would try, which Top 10 categories each abuse maps to, and the design-level control that stops it — not code patches, design decisions.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

Broken Access Control (A01:2025)
The #1 risk: users acting outside their permissions — IDOR, forced browsing, privilege escalation. Fix: server-side check per object, deny by default.
Injection (A05:2025)
User input interpreted as code — SQL, OS commands, or script in a page (XSS). Fix: parameterize queries and encode output; input is data, never code.
Parameterized query
Query structure and data sent separately (placeholders like ?). The database never parses input as SQL, so injection has nothing to grab onto.
Cryptographic Failures (A04:2025)
Sensitive data exposed by missing or misused crypto: plain-text passwords, no TLS, secrets in code. Fix: proven algorithms, Argon2/bcrypt, secret stores.
Security Misconfiguration (A02:2025)
Default credentials, debug mode in prod, verbose errors, unused features left on. Fix: hardened, reviewed config per environment, changed defaults.
Software Supply Chain Failures (A03:2025)
The 2025 expansion of vulnerable components: unpatched libraries, compromised packages, unsafe build pipelines. Fix: pin, patch, SBOM, scan in CI.
Insecure Design (A06:2025)
The flaw is in the plan, not the code — an abusable flow no patch can save. Fix: threat-model abuse cases before building, design the control in.
Authentication Failures (A07:2025)
Weak passwords allowed, no rate limiting or MFA, sessions that never expire, default credentials. Fix: boring-strong identity — limits, MFA, expiry.
Logging & Alerting Failures (A09:2025)
Attacks nobody sees: auth and access failures unlogged, no alerts, tamperable logs. Undetected breaches run for months. Log denials; alert on them.
Fail closed (A10:2025)
Mishandling exceptional conditions leaks internals and opens doors. On error: deny, return a generic message, keep the details in the server log.

11 Reach for this when…

You are about to ship any endpoint that loads data by an ID — run the A01 test first: log in as a second user, change the ID, and confirm the server says no. If it does not, nothing else on the list matters yet.
A code review touches a query, a login flow, a file upload, or a new dependency — walk the relevant Top 10 categories for that surface (A05, A07, A03) and check the cheat sheet before approving.
Someone says “we will add security later” — point at A06: insecure design cannot be patched later. The abuse-case conversation costs an hour now and a redesign later.
