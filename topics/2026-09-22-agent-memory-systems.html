Agent memory systems: short-term, long-term, episodic

A model on its own has no memory between turns — so without a memory system, your agent forgets everything the moment the task runs long or the session ends. Memory isn't something the model has; it's a system you build around the model: a working window for this run, a scoped store that survives sessions, and two policies — WRITE and READ — that are the entire craft.

02 The one-idea version

The context window is the agent's desk: session-scoped, finite, wiped clean when the run ends. Long-term memory is the filing cabinet beside it — a dated journal (episodic: what happened), index cards (semantic: facts and preferences), and a taped-up how-to (procedural: rules). The craft is two librarians — one filing (WRITE: what to store, when, and how to update it) and one fetching (READ: recall just-in-time, ranked by relevance × recency) — plus an honest third one who throws out the stale cards.

04 How it works

Seven mechanics: the two memory scopes, the three long-term kinds, and the two policies plus the honest one.

1

Short-term memory is the running window — keep it lean, don't trust it between sessions

Short-term is thread-scoped: the message history and agent state for one run, persisted via a checkpointer (LangGraph) so the thread can resume. It dies with the thread. A checkpointer does not give you cross-session recall — that's the most common misconception to kill early. Manage the window actively: trim old tool outputs, summarize long stretches, filter stale messages (see 2026-09-14 on context engineering). A finite window is a distraction budget.

2

Long-term memory lives OUTSIDE the window in a namespace-scoped store

Long-term memory is saved under custom namespaces — similar to folders — with a distinct key per memory, like a file name. LangGraph stores them as JSON documents; namespaces typically include user_id or org_id plus labels so memories organize hierarchically, with cross-namespace search and content filters. The question for every fact you write: who may read this later, and where? Answer that before the store call, not after.

3

Split long-term into three kinds: semantic (facts), episodic (experiences), procedural (rules)

Borrowed from human memory (the CoALA taxonomy). Semantic = facts and preferences ("user prefers sans-serif dashboards"), stored as a continuously-updated profile (JSON document) or a collection of narrowly-scoped documents. Episodic = past experiences: what was tried, in what order, what worked — in practice recalled as few-shot examples or searchable past threads. Procedural = rules for how to act: the system prompt, skills, instructions the agent may refine about itself (via reflection on feedback). Three drawers, three access patterns — don't mash them into one blob.

4

Own the WRITE policy: decide what to store, and choose hot-path vs background

Never store the raw transcript — distill. The two write strategies: hot-path (the agent writes during the conversation, e.g. ChatGPT's save_memories tool) — memories are available immediately, but it adds latency and makes the agent multitask; background ("sleep time compute": a separate consolidation agent runs on a cron, extracts facts, merges them into the store) — zero user-facing latency, but memories appear next session. The canonical consolidation decision per new info is ADD / UPDATE / DELETE / NOOP. Match consolidation cadence to how often users actually talk to the agent — consolidating hourly for weekly users just burns tokens on no-ops.

5

Own the READ policy: recall just-in-time, ranked by relevance × recency

Don't load the whole cabinet every turn. The READ policy: retrieve just-in-time — a top-k slice via semantic search plus content filters over the namespace, ranked by relevance × recency. Two load patterns from the Deep Agents playbook: load into the system prompt at startup for facts and preferences, or on-demand retrieval for skills (read only the skill descriptions at startup; read the full skill file when a task matches it). Context stays lean until a capability is needed.

6

Forgetting is a feature: TTLs, decay, supersede-don't-delete

Memory that never decays becomes a liability. Give facts TTLs, let unused memories decay, evict what the consolidation agent flags as stale. Temporal knowledge-graph systems (Zep/Graphiti) are bi-temporal: when a fact changes, the old version is superseded, not deleted — so the agent can answer "what did we believe in March?" correctly. And the poison rule: if a tool returned stale data, the agent may have written it as fact — verify-before-trust for consequential values, with provenance on every stored fact so you can ask where it came from.

7

Scope by user by default — shared memory is an injection surface

Default to the (user_id,) namespace: one user's preferences never leak into another user's run. Agent-scoped (shared across all users) and organization-scoped memory have real uses — the agent's own persona, company policies — but shared state one user can write and another user reads is a prompt-injection channel. Rule: shared/org memory is read-only (populated by application code, writes denied declaratively), and writes to sensitive paths go through human-in-the-loop approval. Treat shared memory like shared filesystem permissions: least privilege wins.

05 Code sketch

The whole architecture in 24 lines: a checkpointer for this thread's window, a namespace-scoped store for everything that survives it.

from langgraph.store.memory import InMemoryStore
from langgraph.checkpoint.memory import MemorySaver

store = InMemoryStore()          # LONG-term: survives across threads
checkpointer = MemorySaver()     # SHORT-term: this thread's state only

user_ns = ("memories", "user_42")   # namespace scopes WHO this belongs to

# WRITE — semantic fact, distilled (never the raw transcript)
store.put(user_ns, "pref-dashboards",
          {"fact": "user prefers sans-serif dashboards",
           "kind": "semantic", "source": "turn-118"})  # provenance!

# WRITE — episodic: how a past bug was fixed, searchable later
store.put(user_ns, "ep-2026-08-flaky-ci",
          {"episode": "flaky e2e traced to 30s docker timeout; fix: bump to 120s",
           "kind": "episodic"})

# READ — just-in-time: top-k, relevance × recency, never the whole cabinet
hits = store.search(user_ns, query="dashboard style preference")
mem_block = "\n".join(h["value"]["fact"] for h in hits[:5])

messages = checkpointer.load(thread_id="t-7")["messages"][-20:]  # desk: last 20 only
prompt = system_prompt + mem_block + messages                 # desk + fetched index cards

06 Failure modes

Named pitfalls, each with a one-line fix. Most memory bugs are a scope problem, a freshness problem, or the whole transcript saved verbatim.

✕

Saving the raw transcript as "memory" Fix: distill — write facts, episodes, and rules as narrowly-scoped documents (ADD/UPDATE/DELETE/NOOP per new info), and let a consolidation agent merge duplicates on a cron.

A transcript dump is all noise and no retrieval: the read side can't rank it, the context bill explodes, and duplicates compound. Memory is a distilled index, not a log file — logs belong in audit storage, not the recall path.

✕

One shared bucket, no scoping Fix: namespace per user_id by default; organization/agent memory is read-only and populated by application code, never by the agent's writes.

Without scoping, user A's "draft the layoff memo" style preference leaks into user B's run — and worse, a malicious user can inject instructions into state another user will read. Shared writable memory is a prompt-injection channel with a friendly name.

✕

Loading the whole cabinet onto the desk every turn Fix: retrieve just-in-time — top-k by relevance × recency; keep skills on-demand (descriptions at startup, full files only when a task matches).

Every turn pays the full-memory token tax and the model gets distracted by irrelevant cards. Memory retrieval should look like a search call, not like opening every drawer and dumping the contents on the desk.

✕

Stale cards treated as truth Fix: TTLs, supersede-don't-delete (bi-temporal), and provenance on every fact — verify-before-trust for consequential values; re-read live facts at task time.

The poisoned-premise failure: a tool returned stale data once, the agent filed it as fact, and every later step built on it. A stored note says what someone said last week; it does not prove the account balance, permission, or policy is still the same today.

✕

Memory writes on the hot path of a latency-sensitive loop Fix: write hot-path only what the next turn needs; move consolidation to a background agent on a cron cadence that matches how often users actually interact.

The agent multitasking between answering and filing produces slower answers AND worse memories. Sleep-time compute exists for exactly this: a separate agent that reviews recent conversations and merges key facts while the user isn't waiting.

08 Sample prompts

Copy-paste starters. One designs the memory system, one audits the write policy, one recovers a lost episode.

THE MEMORY ARCHITECT

Design the memory system for my agent. Context: {{describe the agent, its users, how often it runs, and what it must remember between sessions}} Decide: (1) short-term strategy — what stays in the window, thread scoping, trim/summarize rules; (2) long-term store — namespace scheme (user/agent/org), the three kinds (semantic facts, episodic experiences, procedural rules) with 3 example entries each for MY agent; (3) WRITE policy — hot-path vs background consolidation and the cadence; (4) READ policy — just-in-time top-k, what loads at startup vs on-demand; (5) forgetting — TTLs and the supersede rule; (6) permissions — what is read-only and why. Flag the injection surface in my shared state.

THE WRITE-POLICY AUDITOR

Audit my agent's memory write policy. Below is a dump of what's currently in the store (or the code that writes to it). For each entry check: (1) is it a distilled fact/episode/rule, or a raw transcript fragment that should never have been stored? (2) which ADD/UPDATE/DELETE/NOOP decision does it imply — and is there a duplicate or contradiction that consolidation missed? (3) does it carry provenance (where did this come from, when)? (4) does it have a TTL, or will it go stale silently? (5) is the namespace scoped correctly — could one user's memory leak into another user's run? Return the keep / rewrite / delete verdict for each entry with the one-line reason.

THE EPISODIC RESCUE

My agent keeps re-solving a problem it has solved before — the episodic memory is failing. Here's how memory retrieval currently works: {{paste the retrieval code or describe it}}. Diagnose: (1) are past episodes even searchable (threads, task logs, episode documents)? (2) is the retrieval query capturing the problem signature or just the surface words? (3) would the winning pattern be better distilled into a procedural rule (skill/system-prompt line) instead of left as an episode? Propose the smallest change that makes "we fixed this class of bug before" retrievable — episode retrieval or procedural promotion — and show the before/after.

11 Reach for this when…

Your agent starts every session from zero — users re-explain preferences, and the agent repeats mistakes it made last week. The desk is fine; it's the filing cabinet that's missing.
You're stuffing everything into the context window — user profile, past tickets, style guides — and paying the full token tax plus distraction cost every turn. Move it to a namespace-scoped store and fetch just-in-time.
The agent's "memory" is one shared bucket anyone can write — leakage between users, or a poisoning surface for injected instructions. Scope by user, make shared memory read-only, give facts TTLs.
