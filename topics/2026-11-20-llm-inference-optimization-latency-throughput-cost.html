LLM inference optimization: latency, throughput, and cost per token

Training is a one-time bill; inference is the bill on every request. You cannot optimize it in one dimension — you trade time to first token for one user against tokens per second for all users, and both against cost per token.

02 The one-idea version

Inference is two different workloads sharing one GPU. Prefill processes the whole prompt at once — compute-bound, it sets time to first token (TTFT). Decode generates one token at a time, re-reading all weights and the KV cache each step — memory-bound, it sets time per output token (TPOT). Almost every optimization is either making prefill cheaper, making decode move fewer bytes, or packing more requests into each weight read — and cost per token is simply GPU cost divided by the throughput you actually deliver inside your latency target.

03 The picture: prefill, decode, and the trade-off triangle

One request, two phases — and three numbers that pull against each other.

04 How it works

Seven mechanics: measure the right numbers, split the phases, keep the GPU busy, and move fewer bytes.

1

Measure four numbers first — at production concurrency, on the tail

Record TTFT (queue + prefill, the first delay a user feels), TPOT / ITL (decode gap between tokens; TPS ≈ 1 / TPOT), end-to-end latency (E2E ≈ TTFT + TPOT x (output tokens - 1)), and throughput in tokens/sec and requests/sec. Report p50 and p95/p99, never just averages, and track goodput — throughput delivered inside your latency SLO. A single idle-server request measures nothing about load; NVIDIA's GenAI-Perf and vLLM's metrics exist precisely to sweep concurrency and draw the latency-throughput curve.

2

Diagnose by phase: prefill is compute-bound, decode is memory-bound

Long prompt, slow first token? That is prefill: shorten or cache the prompt, use a faster attention kernel (FlashAttention), or chunk the prefill. Fast first token, slow streaming? That is decode: each step re-reads all weights plus the KV cache, so the ceiling is roughly batch x memory bandwidth / model size in bytes. Together AI's worked example: Llama 3.1 8B in bf16 is ~16 GB; an H100's 3.35 TB/s gives a ~210 tokens/sec single-stream ceiling before cache and kernel overhead. Optimizing the wrong phase wastes the whole effort.

3

Batch continuously — and chunk long prefills so they do not stall decode

Static batching runs a fixed group to completion: short requests wait for the longest, new arrivals wait for the batch. Continuous (iteration-level) batching re-forms the batch every step — finished sequences leave, queued ones join — so one weight read serves many tokens. In vLLM, tune max_num_seqs (concurrency cap) and max_num_batched_tokens (token budget per step): smaller values (~2048) favour ITL, larger values (>8192) favour TTFT and throughput. Chunked prefill — on by default in vLLM V1 — splits a long prompt and interleaves it with pending decodes, prioritising decode so streams slow slightly instead of stalling.

4

Treat the KV cache as the concurrency budget: page it, prefix-cache it, cap it

Every active request's KV cache grows with every token, and it often caps concurrency before weights do. PagedAttention stores KV in fixed-size blocks (16 tokens by default) allocated on demand through a block table — OS-style paging that cuts the 60-80% waste of reserving contiguous space for the maximum length. Enable prefix caching when requests share a system prompt or tool schema so that prefill is computed once. Set max_model_len to what the product actually needs, watch for preemptions (KV exhaustion forces recompute in vLLM V1), and if preemptions are frequent, raise gpu_memory_utilization, lower concurrency, or shard across more GPUs.

5

Move fewer bytes per token: quantize, speculate, or shrink the model

Because decode is bandwidth-bound, fewer bytes = faster tokens. Quantization to FP8 (usually near-lossless on Hopper/Blackwell) halves weight bytes vs bf16; INT8/AWQ and 4-bit go further at higher quality risk — always gate on your own evals. Speculative decoding is exact: a small draft model proposes several tokens, the target verifies them in one pass, and only accepted tokens are kept — typically 1.5-3x when acceptance is high, shrinking at large batch sizes. The cheapest lever of all is often a smaller model or routing easy requests to one: an 8B reads roughly 9x fewer bytes per token than a 70B at the same precision.

6

Pick parallelism and the operating point from the Pareto curve, not by habit

Tensor parallelism shards each layer across GPUs (lower per-GPU memory and latency, communication every layer); pipeline parallelism distributes layers (helps across nodes, can add latency); data parallelism replicates the model to scale throughput; expert parallelism spreads MoE experts. Then benchmark across concurrency and precision (bf16 / FP8 / FP4) and plot throughput vs TTFT/TPOT: keep only Pareto-optimal points — highest throughput at a given latency — discard everything that violates your SLO (e.g. TTFT ≤ 250 ms for interactive chat), and choose the highest-throughput survivor. That point, not the peak benchmark number, is your capacity per instance.

7

Compute cost per token from goodput — and pick the pricing model that matches traffic

For dedicated GPUs: cost per 1M tokens = GPU $/hr / (tokens/sec at SLO x 3600) x 1,000,000, with instances needed = peak requests/sec ÷ achievable requests/sec per instance at the SLO. Serverless per-token pricing (output typically 3-4x input, because decode is the expensive phase) wins when traffic is spiky or low; dedicated wins when volume is steady and high enough that the GPU is not idle. Cache repeated inputs (prompt/prefix and semantic caching) and cap output length — output tokens dominate both latency and cost on long generations.

05 Code sketch

Measure TTFT/TPOT from a stream, find the decode ceiling, and price a token at your SLO.

import time

def measure_stream(chunks, t0):
    # chunks: iterator of (timestamp, token_count) from a streamed response
    ttft, last, n = None, t0, 0
    for ts, c in chunks:
        if ttft is None: ttft = ts - t0
        last, n = ts, n + c
    e2e = last - t0
    tpot = (e2e - ttft) / max(n - 1, 1)
    return {"ttft_s": ttft, "tpot_s": tpot, "e2e_s": e2e, "tokens": n}

def decode_ceiling_tps(batch, bandwidth_gb_s, model_gb):
    # Memory-bound bound: tokens/sec <= batch * bandwidth / model size
    return batch * bandwidth_gb_s / model_gb  # 1 x 3350 / 16 ~= 209 for 8B bf16 on H100

def cost_per_1m_tokens(gpu_usd_per_hr, tps_at_slo):
    return gpu_usd_per_hr / (tps_at_slo * 3600) * 1_000_000

# $3/hr GPU sustaining 2,000 goodput tokens/sec -> ~$0.42 per 1M tokens
print(cost_per_1m_tokens(3.0, 2000))

06 Failure modes

Six ways inference work goes wrong — each with a one-line fix.

1

Optimizing the average while the p99 breaks the productFix: set SLOs and alerts on p95/p99 TTFT and TPOT, and size capacity on goodput — throughput inside the SLO — not raw tokens/sec.

Queueing gives latency a long tail. Averages look fine while agent tool loops and chat users hit timeouts.

2

Cranking batch size / max_num_seqs until throughput peaksFix: sweep concurrency, find the knee where per-request TPOT starts climbing, and cap just before it — peak throughput past the knee is unusable latency.

Every added request eventually slows the step for everyone; the benchmark maximum is rarely the production operating point.

3

One long prompt stalls every streaming responseFix: enable chunked prefill (default in vLLM V1), prioritise decode, and consider prefill/decode disaggregation for very long-context workloads.

Without chunking, a naive scheduler runs the whole compute-bound prefill before the next decode step.

4

KV-cache preemptions and OOMs under loadFix: lower max_num_seqs / max_num_batched_tokens or max_model_len, raise gpu_memory_utilization, or add tensor parallelism — and alert on the preemption counter.

Oversubscribing concurrency does not create capacity; vLLM evicts and recomputes requests, which destroys tail latency.

5

Quantizing (or shrinking the model) without an eval gateFix: run your regression eval suite on the quantized/smaller candidate first — FP8 is usually safe, 4-bit varies by model and task.

The speedup is real and so is the quality regression; without evals you discover it from users.

6

Paying GPU-hours for an idle or wrongly-sized fleetFix: do the crossover math — tokens/day where dedicated beats per-token pricing — autoscale to demand, and re-benchmark after every model, precision, or traffic-mix change.

Dedicated GPUs charge whether or not traffic arrives; serverless charges per token whether or not you needed the headroom.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

TTFT
Time to first token: queueing + prefill. Mostly decided by prompt length and scheduling. The first delay a chat or voice user feels.
TPOT / ITL
Time per output token (inter-token latency): the decode gap between streamed tokens. TPS ≈ 1 / TPOT — 20ms per token is 50 tokens/sec per stream.
Prefill vs decode
Prefill: whole prompt in one pass, compute-bound, sets TTFT. Decode: one token per step, re-reads weights + KV cache, memory-bound, sets TPOT.
Decode ceiling
tokens/sec ≤ batch size x memory bandwidth (GB/s) / model size (GB). Fewer bytes (quantization), fewer weights (MoE, smaller model), or more tokens per read (batching) raise it.
Continuous batching
Iteration-level scheduling: the batch re-forms every decode step — finished sequences exit, queued ones enter — instead of waiting for a whole static batch to drain.
PagedAttention
KV cache stored in fixed-size blocks (16 tokens default) allocated on demand via a block table — OS paging for GPU memory. Cuts reservation waste from 60-80% to a few percent.
Chunked prefill
Split a long prompt into chunks interleaved with pending decodes, prioritising decode. Streams slow slightly instead of stalling behind one large prefill.
Speculative decoding
A small draft model proposes tokens; the target verifies them in one pass and keeps only accepted ones. Exact (output distribution unchanged), typically 1.5-3x when acceptance is high.
Goodput
Throughput delivered inside the latency SLO. Size capacity and compute cost per token on goodput — a token delivered late did not serve the user.
Cost per token
For dedicated GPUs: hourly GPU cost / tokens served per hour at the SLO operating point. Output tokens cost more than input because decode, not prefill, is the slow phase.

11 Reach for this when…

Users say the model feels slow, but the dashboard average looks fine — split TTFT from TPOT, look at p95/p99 at real concurrency, and diagnose prefill vs decode before changing anything.
The GPU bill grows faster than usage, or one GPU saturates while answers crawl — sweep the latency-throughput curve, enable continuous batching + PagedAttention + prefix caching, and re-price cost per token on goodput.
You are choosing a model size, precision, or hosting model for production — benchmark bf16 vs FP8, dedicated vs serverless, at your real prompt/output mix and SLO; the cheapest option is the one that passes evals at the lowest cost per goodput token.
