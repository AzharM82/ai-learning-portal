Infrastructure as code from zero

Stop clicking clouds into existence. Infrastructure as code (IaC) means you declare the environment you want in versioned text files, a tool diffs that declaration against reality, shows you a plan you can review like a code change, and then makes reality match — the same way, every time, in every environment.

02 The one-idea version

Infrastructure is a desired state you declare, not a sequence of clicks you remember. Microsoft Learn puts it plainly: just as the same source code always generates the same binary, an IaC model generates the same environment every time it deploys. You edit the source, not the target — the tool computes the diff, and applying it is idempotent: run it twice, get the same result once.

03 The loop: write, plan, apply, detect drift

HashiCorp names Terraform’s core workflow Write → Plan → Apply. Add the two bookends that make it a team practice — version control before, and drift detection after — and you have the whole discipline:

04 How it works

Seven mechanics, in the order you meet them on your first real project.

1

Declare the end state; do not script the steps

Declarative IaC (Terraform, Bicep, ARM, CloudFormation) describes what should exist — a network, two subnets, a VM of this size — and the tool works out creation order from the dependency graph. That is what makes it idempotent, per Microsoft Learn: applying the same model always lands the same configuration, whatever the starting state. Imperative scripts (do A, then B, then C) break the moment reality is not where the script assumed. Reach for a real programming language (Pulumi, AWS CDK) only when you genuinely need loops and abstractions a declarative file cannot express.

2

Learn the vocabulary: providers, resources, variables, outputs, modules

A provider is the plugin that translates your declarations into one platform’s API calls (AWS, Azure, GCP, Kubernetes, even GitHub). A resource is one managed object. Variables are inputs, outputs are the values other code consumes, and a module is a reusable folder of declarations — your “standard web tier” used twenty times instead of copy-pasted twenty times. References between resources (subnet_id = aws_subnet.web.id) are how the tool learns the dependency order for free.

3

Version it exactly like application code

Commit the files to git, review changes in pull requests, and pin provider and module versions (with the lock file committed). HashiCorp’s point is that the configuration is the infrastructure topology, readable in one place — so a PR diff is an infrastructure review, git log is your audit trail, and rolling back is checking out the previous version and applying it. If a change did not go through a PR, it did not happen — that rule is what kills snowflake environments.

4

Treat state as a database, not a file

The tool needs memory: Terraform’s state file maps each declared resource to its real cloud ID, which is how the next plan knows what already exists. Keep state in a remote backend with locking (so two applies cannot race), back it up, restrict who can read it — state can contain sensitive values in plain text — and never edit it by hand or commit it to git. Most beginner disasters are state disasters: a lost or corrupted state file makes the tool forget it owns production.

5

Plan first, read the plan, then apply the saved plan

init downloads providers, plan is the dry run, apply makes it real, destroy tears it down. The discipline is in the middle step: read every create / update / destroy in the plan, save that exact plan in CI, and apply the saved plan — not a freshly generated one. An unexpected destroy or replace of a database is visible in the plan for free; it is only a surprise if nobody looked. Never use auto-approve on production.

6

One codebase, many environments — parameterize, never fork

Dev, staging, and prod should differ only in variable values (instance size, replica count, domain) and state, never in copied code. Copy-pasted environment folders drift apart within a month and double every fix forever. Keep the shared shape in modules, keep each environment thin (a backend + a variables file), and keep the blast radius small by splitting state along boundaries that change independently — network, platform, app — rather than one giant state for everything.

7

Run it from the pipeline, guard it with policy, watch for drift

Mature IaC runs in CI/CD: format and validate on every PR, plan posted as a PR comment, apply only from the pipeline with a short-lived cloud identity (OIDC, not a permanent access key pasted into a secret). Add policy-as-code checks for the expensive mistakes (public storage, unencrypted disks, missing tags), keep secrets in a secret store referenced — never written — in code, and run a scheduled plan: a non-empty plan on an unchanged repo is drift, and drift means someone bypassed the loop.

05 Code sketch

The whole idea in Python: desired state as data, a plan as a diff against recorded state, and an apply that is safe to re-run. Real tools (Terraform, Pulumi) do this against cloud APIs — the shape is identical.

# desired state is data you version in git
desired = {
    "web-vm":  {"type": "vm", "size": "small", "replicas": 2},
    "web-lb":  {"type": "lb", "public": True},
}
state = load_state()          # ledger: what we managed last apply

def plan(desired, state):
    actions = []
    for name, want in desired.items():
        if name not in state:
            actions.append(("create", name))
        elif state[name] != want:
            actions.append(("update", name))
    for name in state:
        if name not in desired:
            actions.append(("destroy", name))  # read this line twice
    return actions

for action, name in plan(desired, state):
    print(action, name)       # a human / pipeline approves THIS list
# apply(plan) calls provider APIs in dependency order and saves
# the new state. Re-running with no changes plans zero actions:
# that is idempotence.

06 Failure modes

Five ways IaC projects hurt themselves — and the one-line fix for each.

1

ClickOps drift: “just one quick console fix”Fix: edit the code, not the target — and run a scheduled plan so drift is caught the same day.

A hotfix in the console feels faster, but now code and reality disagree. The next unrelated apply silently reverts the hotfix — usually during another incident. AWS and Microsoft both name drift as the core problem IaC exists to solve; bypassing the loop recreates it.

2

State committed to git, kept on one laptop, or hand-editedFix: remote backend with locking and backups, restricted access, and state surgery only via the tool’s own commands.

State in git leaks sensitive values and conflicts on every merge. State on one laptop is a single point of losing production’s map. A hand edit corrupts the ledger so plans lie. Treat state like a production database, because it is one.

3

Applying without reading the planFix: save the plan, review creates / updates / destroys, and apply that saved plan — no auto-approve in prod.

Renaming a resource or changing one attribute can force a destroy-and-recreate of a database or load balancer. It was all printed in the plan. The plan is the cheapest code review in engineering; skipping it converts a typo into downtime.

4

Copy-pasted environments and one giant stateFix: modules + per-environment variables, and split state by blast radius (network / platform / app).

Three copied folders become three different infrastructures within a month, and every fix has to be made three times. One giant state has the opposite problem: every apply can touch everything, locking blocks everyone, and one corruption takes the whole estate with it.

5

Secrets hardcoded in code — and sitting in stateFix: reference secrets from a secret store, use short-lived pipeline identity (OIDC), and restrict + encrypt state access.

A password in a .tf file lives in git history forever, and many tools also store resource attributes — including secrets — in state in plain text. IaC multiplies both the power and the leak surface; design for it from day one, not after the first rotation panic.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

Infrastructure as code (IaC)
Defining and deploying infrastructure (networks, VMs, load balancers, databases) in versioned, machine-readable files instead of manual console or hardware processes.
Declarative vs imperative
Declarative: declare the end state, the tool computes the steps (Terraform, Bicep). Imperative / general-language: specify steps or program them (scripts, Pulumi, CDK).
Idempotence
Applying the same declaration always produces the same configuration, regardless of the starting state. Re-running a converged apply plans zero changes.
Provider
The plugin that translates your declarations into one platform’s API calls — AWS, Azure, GCP, Kubernetes, GitHub, and thousands more in registries.
State file
The tool’s ledger mapping declarations to real resource IDs. Remote, locked, backed up, restricted — never committed to git, never hand-edited.
Plan
The dry-run diff of code vs state + reality: create / update / destroy, in dependency order. Review it, save it, apply that exact plan.
Drift
Reality no longer matches code — usually a manual console change. A scheduled plan detects it; resolve it in code or by reverting, never by ignoring it.
Module
A reusable folder of declarations with variables in and outputs out — the standard shape (web tier, database tier) instantiated many times without copy-paste.
Snowflake environment
An environment built and maintained by hand until it is unique and cannot be reproduced automatically — the failure mode IaC was invented to eliminate.
Edit the source, not the target
Microsoft Learn’s rule for every IaC change: change the versioned model and let the pipeline configure the environment — never change the environment directly.

11 Reach for this when…

You are about to create a second environment, or rebuild one after an incident — if rebuilding depends on someone’s memory or a wiki checklist, codify it now: the first IaC project pays for itself at the first rebuild.
Someone says “dev works but staging doesn’t” or proposes a console hotfix — that is drift talking. Put the environments under one codebase and route the hotfix through a PR, even a fast one.
An auditor, a new teammate, or future-you asks “why is it configured like this?” — with IaC the answer is a git history: who changed it, when, in which reviewed PR, and how to roll it back.
