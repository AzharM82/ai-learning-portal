Spec-driven development: specs as the source of truth for AI-built features

A vague prompt forces a coding agent to guess thousands of unstated requirements — and some guesses will be wrong. Spec-driven development flips the order: you agree the specification first, in versioned files an agent can execute against, and code becomes the compiled output of that spec. Change the requirement? Edit the spec, regenerate the affected work, and check the code back against it.

02 The one-idea version

Specifications don’t serve code — code serves specifications. Traditional development treats specs as scaffolding to discard once coding starts; spec-driven development makes the spec executable and primary. Per GitHub’s Spec Kit docs, the spec defines the what before the how, and maintaining software means evolving spec.md and plan.md — when something is wrong, you first ask whether the spec or the code diverged.

03 The picture: constitution to convergence

One gated pipeline. You review and approve each artifact before the next one is built on top of it — ambiguity is resolved in markdown, not discovered in a diff:

04 How it works

Seven mechanics, following the Spec Kit workflow — shorter path for small features, full path with clarify / checklist / analyze gates for production work.

1

Set the constitution once per project

Before any feature, write constitution.md: the non-negotiable principles every later artifact is judged against — security rules (validate all input), architecture style, testing and documentation standards, your design system. In Spec Kit this is /speckit-constitution, run once and stored under .specify/memory/ so specify, plan, and tasks all read it. It is the difference between re-arguing standards on every feature and stating them once, durably.

2

Specify the what and why — and keep the tech stack out

/speckit-specify turns a natural-language description into spec.md: user stories and journeys, functional requirements, success criteria, edge cases, and explicit non-goals. The quickstart is explicit: focus on what and why, not the tech stack. A spec that names a database in paragraph one has smuggled a decision past review; a spec that says “a locked-out user can regain access without a support ticket” can be judged by product, engineering, and the agent alike.

3

Clarify before you plan — fold answers back into the spec

Run /speckit-clarify next: the agent asks targeted questions about whatever is underspecified — token expiry, permission boundaries, what happens on partial failure — and folds your answers into spec.md instead of leaving them in chat history. This is the cheapest bug fix in the whole pipeline: an ambiguity costs a sentence here, and a sprint if the agent guesses it during implementation.

4

Plan the how in a separate artifact

Only now does implementation detail belong: /speckit-plan generates plan.md — stack, architecture, data model, API contracts — derived from the approved spec and constrained by the constitution. Keeping spec.md (intent) and plan.md (approach) separate is what lets you re-plan the same feature for a different stack, or generate two candidate implementations from one spec and compare them, without rewriting the requirements.

5

Break the plan into dependency-ordered, testable tasks

/speckit-tasks produces tasks.md: small, actionable steps ordered by dependency, each small enough for an agent to implement and a human to verify. Gate it on production work with /speckit-checklist — a requirements-quality checklist, “unit tests for your requirements” — and /speckit-analyze, which reports conflicts, gaps, and ambiguities across spec, plan, and tasks before any code exists. Fix inconsistencies at the source document, not in the implementation.

6

Implement in order — then converge, don’t just finish

/speckit-implement executes tasks.md in dependency order. The step most teams skip is the last one: /speckit-converge checks the codebase against the spec, plan, and tasks; if it finds gaps it appends new tasks, and you implement and converge again until it reports Converged. “The agent stopped typing” is not done — “the code provably covers the spec” is.

7

Choose your persistence level — and evolve the spec when reality changes

Thoughtworks / Fowler research names three levels: spec-first (spec guides one task, then is archived), spec-anchored (spec persists and evolves with the feature — the sweet spot for most teams), and spec-as-source (humans edit specs, never code; code is regenerated). Whichever level you pick, the rule is the same: when requirements change, edit the spec first, re-plan the affected slice, and let the change propagate — never patch code and leave the spec lying about the system.

05 Code sketch

A spec as data: acceptance criteria you can check mechanically, so “converged” is a test result, not a vibe.

# spec_check.py — converge = every criterion has evidence
from dataclasses import dataclass

@dataclass
class Criterion:
    id: str
    text: str                 # from spec.md, what + why only
    test: str                 # test / check that proves it

@dataclass
class Spec:
    feature: str
    version: int              # bump when requirements change
    criteria: list[Criterion]

def converge(spec: Spec, passing: set[str]) -> list[Criterion]:
    """Return unmet criteria — non-empty means: append tasks, re-implement."""
    return [c for c in spec.criteria if c.test not in passing]

password_reset = Spec("password-reset", version=2, criteria=[
    Criterion("FR-1", "Locked-out user resets via emailed link", "test_reset_happy"),
    Criterion("FR-2", "Link expires after 30 minutes", "test_link_expiry"),
    Criterion("FR-3", "Old sessions are revoked on reset", "test_session_revoke"),
])

if __name__ == "__main__":
    missing = converge(password_reset, {"test_reset_happy", "test_link_expiry"})
    print("Converged" if not missing else f"Gaps: {[c.id for c in missing]}")

06 Failure modes

Five ways spec-driven work goes wrong — and the one-line fix for each.

1

The vague spec — the agent guesses the missing thousandsFix: run clarify, name edge cases and non-goals explicitly, and never plan on top of unanswered ambiguity.

Spec-driven development does not remove the need for precision; it moves where precision pays. Thoughtworks is blunt: incomplete or ambiguous requirements produce poor AI output. If your spec could describe three different features, the agent will build one of them — fluently, and possibly the wrong one.

2

Write the spec, build the code, throw the spec awayFix: default to spec-anchored — keep spec.md in the repo, versioned and reviewed with the code it describes.

Spec-first-and-discard recreates the old failure with new tooling: six months later nobody knows why the system behaves as it does, and the next agent session re-derives intent from code. The spec only becomes a source of truth if it outlives the implementation session.

3

Tech stack in the spec, intent in the planFix: enforce the split — spec.md holds what/why and acceptance criteria; stack, schema, and contracts live in plan.md.

Mixing the layers destroys the main leverage: you can no longer re-plan the same intent, compare implementations, or tell whether a change is a requirement change or an approach change. Reviewers should reject a spec whose first page is a framework choice.

4

The sledgehammer workflow for a one-line fixFix: scale the path to the risk — shorter path (specify → plan → tasks → implement) for small features, full gated path for production or ambiguous work; skip SDD for trivial, well-understood fixes.

Thoughtworks warns current SDD frameworks can be rigid: a heavy multi-step ceremony turns a small bug into dozens of acceptance criteria. The methodology serves the work, not the reverse — proportionality is a skill, not a violation.

5

Skipping analyze and converge — drift with extra stepsFix: treat checklist + analyze as pre-implementation gates and converge as the definition of done; when code and spec disagree, fix the source artifact and re-run.

Without the cross-checks, spec, plan, tasks, and code quietly diverge — the exact disease SDD was meant to cure, now with four documents lying instead of one. LLMs are also non-deterministic: the same spec can yield different code on re-runs, which is why verification against criteria, not trust in generation, closes the loop.

08 Sample prompts

Copy one into your AI assistant and apply it to your own work.

TURN A VAGUE FEATURE INTO A SPEC

Do not write code or choose a tech stack. Turn this feature idea into a spec.md: [paste idea]. Include user stories with the why, numbered functional requirements, measurable success criteria, edge cases, and explicit non-goals. Wherever the idea is ambiguous, do not guess — list it as an open question for me to answer, and fold my answers back into the spec when I reply.

CHECKLIST + ANALYZE MY SPEC, PLAN, AND TASKS

Review these three artifacts for consistency before any implementation: [paste spec.md, plan.md, tasks.md]. Act as the checklist and analyze gates: flag every requirement with no task, every task with no requirement, contradictions between spec and plan, and any acceptance criterion that is not testable as written. Report findings grouped by severity, and tell me which source document to fix for each — do not edit the code or invent missing requirements.

CONVERGE: AUDIT CODE AGAINST THE SPEC

Audit this implementation against its spec: [link / paste spec.md + the diff or repo]. For each numbered requirement and success criterion, state covered / partial / missing with the file and test that prove it. Where code and spec disagree, say which one should change and why. End with either “Converged” or the exact additional tasks, in dependency order, needed to converge.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

Spec-driven development (SDD)
An approach where structured specifications — not code — are the primary source of truth for AI-assisted development. The spec defines what and why; AI generates, validates, and maintains code against it.
Executable specification
A spec precise, complete, and unambiguous enough to generate a working implementation from — not a guide the coder interprets loosely, but an artifact an agent executes against and a checker can verify.
Constitution
Spec Kit’s once-per-project principles file (.specify/memory/constitution.md): security, architecture, testing, and documentation non-negotiables that every specify / plan / tasks step must comply with.
spec.md vs plan.md
spec.md holds intent: user journeys, requirements, success criteria — no tech stack. plan.md holds approach: stack, architecture, data model, contracts. Separating them lets you re-plan the same intent or compare implementations.
tasks.md
The dependency-ordered breakdown of the plan into small, actionable, individually verifiable steps. /speckit-implement executes them in order; each task traces back to a requirement in the spec.
Clarify
The Spec Kit step (/speckit-clarify) where the agent asks targeted questions about underspecified areas and folds the answers into spec.md — resolving ambiguity before planning, when it is cheapest.
Analyze + checklist gates
Pre-implementation quality gates: checklist generates “unit tests for your requirements” (completeness, clarity, consistency); analyze is a read-only cross-check of spec.md, plan.md, and tasks.md for conflicts and gaps.
Converge
The closing step (/speckit-converge): check the codebase against spec, plan, and tasks. Gaps become new tasks; you implement and converge again until it reports Converged. This — not “agent finished” — is the definition of done.
Spec-first / anchored / as-source
Three maturity levels: spec-first = spec guides one task then is archived; spec-anchored = spec persists and evolves with the feature; spec-as-source = humans edit only specs and code is regenerated. Most teams should live at spec-anchored.

11 Reach for this when…

An AI-built feature keeps coming back “working but wrong” — the code compiles and the intent was never written down: stop re-prompting, write the spec, clarify it, and make the agent implement and converge against it.
Multiple people or agents will build against the same requirements — product, frontend, backend, and QA need one versioned artifact that decides disagreements: a spec-anchored spec.md reviewed like code, in the repo.
You expect the feature to change, be regenerated, or be ported — brownfield modernization, a stack migration, or parallel implementation experiments: intent in the spec survives; only the plan and code get replaced.
