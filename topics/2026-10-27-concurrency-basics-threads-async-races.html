Concurrency basics: threads, async, races

Most programs do not need to be faster. They need to stop waiting badly: ten network calls in a row, a UI frozen on one slow request, a counter that loses updates for no visible reason. The fix is picking the right way to overlap work — and the wrong pick is how you get a fast-looking program that is wrong, or a correct program that is slow.

02 The one-idea version

Concurrency is dealing with many things at once; parallelism is doing many things at once. One chef juggling ten orders is concurrent; ten chefs cooking at once is parallel. Everything else — threads, async, processes, locks — is just a mechanism for juggling, and the bugs arrive when two jugglers grab the same pan at the same time.

03 Waits or computes? Pick the mechanism

One question decides the tool. If the job spends its time waiting, overlap the waiting. If it spends its time computing, add cores.

04 How it works

Six mechanics, in the order you actually use them.

1

Ask “waits or computes?” before you pick a tool

I/O-bound means the program spends its time waiting: HTTP calls, database queries, file reads. CPU-bound means it spends its time computing: math, parsing, encoding. Async and threads fix waiting; only processes (more cores) fix computing. Picking async for a CPU-bound job is the most common wasted optimization in this whole topic.

2

Threads share memory; the kernel does the switching

A thread is a second execution path inside one process, sharing the same memory. The operating system preempts threads at any point — including mid-statement — so any shared mutable state can be observed halfway through an update. That is why threads are powerful for blocking I/O and dangerous for shared counters: the switch points are invisible.

3

Async shares one thread; you do the switching, at await

An async def coroutine runs until it hits await, then hands control back to the event loop, which runs another task. Switching only happens at await points you can see — so between two awaits, your code cannot be interrupted. That makes async far easier to reason about than threads, and it is exactly why a blocking call inside async code is so damaging: nothing else runs until it returns.

4

Processes have separate memory and true parallelism

Each process gets its own memory, so a child process changing a variable never affects the parent — but it also means processes must pass data explicitly (queues, pipes, shared memory). In standard CPython, the Global Interpreter Lock (GIL) also means threads do not run Python bytecode in parallel, so CPU-bound Python work genuinely needs processes (or a free-threaded build) to use more than one core.

5

Guard shared state with a lock, or stop sharing it

counter += 1 is read, modify, write — three steps. Two threads can both read 0, both add 1, and both write 1, losing an update. A threading.Lock used as with lock: makes the whole read-modify-write atomic: one thread at a time, released even if the block raises. The better fix, when you can take it, is to not share at all: give each worker its own accumulator and combine results at the end.

6

Launch together, wait together, bound the fan-out

Sequential await runs tasks one after another — use asyncio.gather() (or a task group) to run them concurrently, and always await or join what you start, or failures vanish silently. And bound the fan-out: a semaphore (say, 10 in flight) keeps 1,000 URLs from becoming 1,000 open connections. Unbounded concurrency is a self-inflicted denial of service.

05 Code sketch

Fetch many URLs concurrently, at most 10 in flight — and note where a lock would (and would not) be needed.

import asyncio
import httpx

async def fetch(client, sem, url):
    async with sem:  # at most 10 requests in flight
        r = await client.get(url, timeout=10)
        return url, r.status_code

async def main(urls):
    sem = asyncio.Semaphore(10)
    async with httpx.AsyncClient() as client:
        # gather runs all fetches concurrently; one slow
        # URL no longer blocks the other 999.
        results = await asyncio.gather(
            *(fetch(client, sem, u) for u in urls))
    return results

# No lock needed here: each task writes only its own
# result slot, and gather collects them. A lock would
# be needed only if tasks mutated one shared counter.
asyncio.run(main(["https://example.com"] * 5))

06 Failure modes

Five ways concurrent code goes wrong — and the one-line fix for each.

1

A blocking call inside the event loopFix: move blocking work to a thread with asyncio.to_thread(), or use an async library.

A synchronous HTTP call, a time.sleep(), or a heavy parse inside a coroutine freezes every task on the loop. The symptom is everything stalling at once with no error — the hardest kind of outage to spot.

2

Async wrapped around CPU-bound workFix: send CPU work to a process pool (ProcessPoolExecutor) and await the result.

Async does not make computation faster. A regex, a big JSON parse, or model inference inside a coroutine blocks the loop just like a network call would — except no await ever yields, so nothing else runs at all.

3

A race on shared stateFix: guard every read-modify-write with the same lock, via with lock: — or give each worker its own state.

Two threads read the same counter, both add one, one update is lost. The bug is timing-dependent, so it passes every test and fails in production under load. If you cannot reproduce it, suspect a race first.

4

A coroutine that is never awaitedFix: await it, gather it, or create a task for it — and treat “coroutine was never awaited” warnings as errors.

Calling an async def function does not run it — it returns a coroutine object that sits idle. The work silently never happens, and the only clue is a runtime warning that is easy to miss.

5

Deadlock from lock orderingFix: always acquire locks in the same global order, hold each lock for the shortest possible time, and never await while holding a lock you do not own.

Thread A holds lock 1 and wants lock 2; thread B holds lock 2 and wants lock 1. Both wait forever. The program does not crash — it just stops, which is worse, because monitoring often reports it as healthy.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

Concurrency
Dealing with many tasks at once — overlapping their waiting, even on one core. Juggling, not cloning.
Parallelism
Doing many tasks at the same instant, on multiple cores. Needs real hardware parallelism — one core cannot fake it.
Thread
A second execution path inside one process, sharing its memory. The kernel preempts it at invisible points.
Event loop
The scheduler at the heart of asyncio: it runs tasks until they await, then switches to a task that is ready.
Coroutine
An async def function. Calling it does nothing — it returns a coroutine object that only runs when awaited or scheduled.
Race condition
The result depends on timing: two threads interleave a read-modify-write and one update is lost. Passes tests, fails under load.
Lock (mutex)
A two-state guard: one holder at a time. Use with lock: so it releases even if the block raises. Keep the guarded section tiny.
Deadlock
Two threads each hold a lock the other wants, and both wait forever. Fix: one global lock order, shortest possible hold time.
GIL
CPython’s Global Interpreter Lock: only one thread runs Python bytecode at a time. Threads help waiting, not computing.
Semaphore
A counter that caps how many tasks enter a section at once — e.g. at most 10 requests in flight. Bounds the fan-out.

11 Reach for this when…

Requests run one after another while each waits on a network call — overlap the waiting with async or threads. Ten half-second waits should take 0.5 s, not 5 s.
A shared counter, cache, or balance looks wrong only under load — suspect a race before anything else: find the read-modify-write and guard it with a lock, or stop sharing the state.
Someone proposes async to speed up heavy computation — stop and ask waits-or-computes. Computing needs processes and cores; async on top of it just blocks the loop more politely.
