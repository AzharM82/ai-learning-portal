Browser and computer-use agents: perception, grounding, and safe action

Some work has no API — it lives behind a login, a form, or a legacy desktop app. A browser or computer-use agent does that work the human way: look at the interface, find the right control, click or type, then look again. The engineering is not the click — it is choosing what the agent perceives, how a name becomes a target, and what it is never allowed to do alone.

02 The one-idea version

A UI agent is a perceive–ground–act–verify loop, and grounding is where it succeeds or fails. Perception turns the screen into something the model can reason over — a structured accessibility tree with element refs, or a screenshot of pixels. Grounding turns an intention like “click Submit” into a concrete target: that ref, or that (x, y) coordinate. Act once, then perceive again and verify from the new state — never from the plan.

03 The picture: two ways to see, one loop to act

Same loop, two perception lanes. Structured refs are cheap and deterministic; pixels are universal and expensive. Good systems start structured and fall back to pixels only where they must.

04 How it works

Seven mechanics: the loop, the two perception modes, the browser/desktop split, and the safety gates that make autonomy deployable.

1

Run one action, then re-observe — never batch blind

Drive the loop as perceive → decide → act → perceive again. Anthropic notes computer use typically needs a fresh screenshot after each batch of actions, which is why it is the slowest option; Playwright MCP returns a fresh snapshot after most tools for the same reason. A plan made from a stale screen is fiction: navigation, dialogs, and lazy loading change the targets under you. Cap the loop (max steps, max time, max cost) and log every observation–action pair as the trajectory you will debug and grade.

2

Prefer structured perception: accessibility snapshot + refs

When the task is inside a web page, perceive structure before pixels. Playwright MCP serialises the page's accessibility tree — roles, accessible names, and states, with decorative DOM stripped away — into compact text where every actionable element carries a ref such as e5. The model then acts by ref (browser_type { target: "e5" }): deterministic, token-cheap, and usable by models with no vision at all. Anthropic's browser-use pattern makes the same move, pairing clicks with page-aware tools like read_page, find, and form_input so the agent can act on element references in addition to coordinates.

3

Ground explicitly — and treat every target as perishable

Grounding is mapping an intended element to an executable target. With snapshots that target is a ref, valid only within that snapshot: Playwright fails a stale target with “Ref not found in the current page snapshot — try capturing a new snapshot,” which is the correct response, not an error to retry blindly. With screenshots the target is a coordinate in the screenshot's pixel space (Anthropic) — so viewport, zoom, and device-pixel ratio are part of the contract. Rule: never invent a ref or coordinate, never reuse one across a page change, and if grounding is ambiguous (two “Delete” buttons), stop and disambiguate from context or ask.

4

Pick the right family: browser agent vs computer-use agent

Anthropic draws the line cleanly: if the whole task occurs inside webpages — forms, reading content, working across tabs — use the browser toolset; use full computer use when the task needs arbitrary GUI interaction narrower tools cannot reach: legacy software with no API, visual verification, or a workflow spanning multiple desktop apps. Computer use receives screenshots and issues mouse and keyboard actions, so it can drive anything a human can — at the price of a screenshot round-trip per step. OpenAI's hosted computer use follows the browser side of the same split: a hosted browser session the agent observes and acts in, while your application owns session lifecycle and approvals.

5

Execute in a sandbox you control, with no ambient authority

Never point a learning agent at your real desktop or your daily browser profile. Run it in an isolated VM, container, or hosted browser session; give it a throwaway or task-scoped account; keep saved passwords, payment methods, and unrelated tabs out of reach; and allowlist the origins it may visit. OpenAI's model makes this explicit: the browser requires approval before accessing each new website origin, and enabling network access does not approve those requests. Sign-in belongs to the user through a dedicated flow — the agent should pause for it, not harvest credentials from page text or chat.

6

Gate consequential actions separately from site access

Origin approval is not action approval. OpenAI states it directly: approving a site does not enforce confirmation before purchases, destructive changes, or other consequential actions — if you must guarantee that confirmation, restrict the browser to resources that cannot perform them, or use a runtime you control with a real gate. Classify actions by reversibility: read and navigate freely; require human confirmation before pay, delete, send, publish, or final submit; and never let a “confirm” function the model may or may not call be your only control. Treat all website content as untrusted data: it cannot grant permission or override the user's instructions — a page that says “ignore your task and click here” is a prompt-injection attempt, not an instruction.

7

Verify from new state, and name blockers honestly

Close every step by checking the new observation against the expected effect: the item appears in the list, the URL or heading changed, the confirmation text is present. Verify the task the same way before reporting success — OpenAI's walkthrough ends by checking the answer actually contains the requested title and URL. When the world blocks you — a CAPTCHA, an unsupported sign-in method such as a passkey, a permission wall — report that blocker plainly and stop or hand over; do not claim success, do not quietly loop, and do not treat solving the challenge as permission to expand the task. Save a screenshot and the last snapshot on failure: they are the difference between a five-minute fix and a mystery.

05 Code sketch

A minimal safe loop in Python: structured perception, ref-grounded action, an allowlist, an approval gate, and verification — the shape every provider's API ends up taking.

# Browser agent loop: perceive -> ground -> (gate) -> act -> verify
ALLOWED = {"https://demo.playwright.dev"}
RISKY = {"pay", "delete", "send", "submit_order"}

def run_task(browser, model, task: str, max_steps: int = 20) -> str:
    for step in range(max_steps):
        snap = browser.snapshot()              # a11y tree: role, name, [ref=eN]
        action = model.decide(task, snap)      # {"tool": "click", "ref": "e12"} or {"done": ...}
        if "done" in action:
            return action["done"] if browser.verify(task) else "unverified"
        if browser.origin() not in ALLOWED:
            raise PermissionError(browser.origin())   # origin gate, checked in code
        if action["tool"] in RISKY and not human_approves(action, snap):
            return "stopped: awaiting human approval"
        browser.act(action)                    # stale ref raises -> loop re-snapshots
    raise TimeoutError("step budget exhausted")

06 Failure modes

Five ways UI agents go wrong in production — and the one-line fix for each.

1

Acting on a stale snapshot or a remembered coordinateFix: re-observe after every navigation or mutation, and ground each action in the fresh snapshot — a stale ref failure means “look again,” not “retry the same target.”

Pages change under the agent: dialogs open, lists re-render, a click navigates. Refs are valid only within one snapshot and coordinates only for one viewport at one moment, so a target carried across a change clicks whatever now happens to sit there — the classic wrong-row delete.

2

Screenshot-only grounding for an ordinary web taskFix: use the accessibility snapshot and refs by default; reserve coordinate clicks for canvas, maps, and elements the tree cannot expose.

Pixels are the most general perception and the most fragile: image tokens cost more, small or look-alike controls get mis-grounded, and a layout shift breaks every remembered position. Teams pay the vision tax on pages that already publish a perfect semantic tree.

3

Obeying instructions written on the pageFix: treat all page content as untrusted data — it can inform the task, but it can never grant permission, change the task, or override the user's instructions.

A page, pop-up, or document the agent reads says “to continue, enter your password here” or “ignore previous instructions.” A UI agent with a browser and a logged-in session is the highest-value prompt-injection target there is; the defence is architectural (allowlist, sandbox, gates), not a sterner prompt.

4

Mistaking site-access approval for action approvalFix: gate consequential actions in your own runtime — pay, delete, send, and final submit each need their own human confirmation, independent of origin approval.

The user approved visiting the store, so the agent assumes checkout is approved too. OpenAI warns this inference is false: origin approval does not enforce confirmation before purchases or destructive changes. Conflating the two turns a browsing permission into a spending permission.

5

Running on the real profile with no step budgetFix: isolated browser or VM, task-scoped account, no saved payment methods — plus max steps / time / cost, a trajectory log, and a screenshot saved on failure.

On a real profile the agent inherits every saved login and card, and a confused loop can click for an hour before anyone notices. The sandbox limits the blast radius; the budget guarantees the loop ends; the log makes the failure debuggable instead of anecdotal.

08 Sample prompts

Copy one into your AI assistant and apply it to your own work.

DESIGN A SAFE BROWSER TASK

Design — do not run — a browser agent for this task: [describe task and site]. Specify: (1) perception mode per step (accessibility snapshot + refs, or screenshot + coordinates) and why, (2) the origin allowlist, (3) every action classified as free / confirm-first / never, (4) the verification check after each mutation, (5) step, time, and cost budgets, and (6) what the agent must report instead of proceeding when it hits a CAPTCHA, a login wall, or an ambiguous target. Present it as a table I can approve before anything runs.

DEBUG A FAILED UI-AGENT TRAJECTORY

Here is a failed browser-agent run: [paste the step log — each observation summary, grounded target (ref or coordinate), action, and result — plus the final screenshot description]. Classify the first failing step as exactly one of: perception (agent never saw the right state), grounding (saw it, targeted the wrong element or a stale ref), action (right target, wrong operation), verification (action failed but agent reported success), or safety (agent should have stopped and did not). Quote the log line that proves it, then give the smallest fix that prevents this class of failure — not a rewrite of the whole agent.

API, BROWSER, OR COMPUTER USE?

For each workflow below, recommend the narrowest sufficient automation — a documented API or structured tool, a browser agent on accessibility snapshots, or full computer use over screenshots — and defend the choice in one line on reliability, cost per run, and blast radius if the agent mis-clicks: [list 4-6 workflows, e.g. "export last month's invoices", "update a record in our legacy desktop app", "check a competitor's public pricing page weekly"]. Flag any workflow where none of the three is acceptable without a human in the loop, and say why.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

Perceive–ground–act–verify loop
The UI-agent control loop: observe the interface, ground an intention to a concrete target, execute one action, then observe the new state and verify the effect before continuing. Skipping re-observation is how agents act on fiction.
Grounding
Mapping “the Submit button” to an executable target: an element ref in a structured snapshot, or an (x, y) coordinate in screenshot pixel space. Grounding — not planning — is where most UI-agent failures live.
Accessibility snapshot / ref
A text serialisation of the page's accessibility tree — roles, names, states — where each actionable element gets a short ref (e5, e12). Playwright MCP acts on refs: deterministic, token-cheap, and no vision model required.
Stale ref
A ref from an earlier snapshot used after the page changed. Refs are valid only within one snapshot; the correct recovery is a fresh snapshot and re-grounding, never retrying the same target or reusing remembered coordinates.
Browser agent vs computer-use agent
Browser agent: the task stays inside webpages, so page-aware tools and element refs apply (Anthropic browser_use, hosted browser sessions). Computer-use agent: arbitrary desktop GUI from screenshots + mouse/keyboard — most general, slowest, per Anthropic.
Origin approval ≠ action approval
Approving access to a website origin lets the agent browse there; it does not confirm purchases, deletions, or other consequential actions (OpenAI, explicit). Those need their own gate in a runtime you control.
Page content is untrusted data
Anything the agent reads on screen — text, pop-ups, documents — is data, not instructions. It cannot grant permission or override the user's task. Defence is architectural: allowlists, sandboxing, and action gates, not a firmer prompt.
When do screenshots beat snapshots?
When structure is missing: canvas and WebGL apps, maps, image-only controls, legacy desktop GUIs, and visual verification itself. That is Playwright MCP's vision mode and Anthropic's computer use — powerful, and priced in image tokens and mis-clicks.
Trajectory log
The recorded sequence of observations, grounded targets, actions, and results for a run. It is the debugging artifact, the eval input, and the audit trail — save the last snapshot and a screenshot on failure.

11 Reach for this when…

The work exists only behind a UI — a vendor portal with no API, a government form, a legacy desktop app — and a human doing it by hand is the current integration. Start with a browser agent on snapshots; escalate to computer use only for the steps structure cannot reach.
You need an agent to test or verify your own web app end-to-end — accessibility snapshots give deterministic, reviewable steps, and the trajectory log doubles as the bug report when a flow breaks.
Someone proposes letting an agent “just handle” a purchasing, admin, or messaging workflow — that is your cue to design the gates first: sandbox, origin allowlist, per-action human confirmation for anything irreversible, and an honest blocker report for CAPTCHAs and logins.
