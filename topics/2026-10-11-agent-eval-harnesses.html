Agent eval harnesses: tasks, graders, scoring loops

Unit tests check whether code behaves. An eval harness checks whether an agent behaves — across tasks with defined success criteria, graders that score outcomes, and a scoring loop that turns a single flaky run into a trustworthy pass rate. The uncomfortable finding that makes this mandatory: when agents fail, most failures look like successes from the outside — the transcript reads fine while the world state is wrong. A harness is how you catch them before your users do.

02 The one-idea version

An eval is a task plus a grader; a harness is the machinery that runs tasks in isolation, grades every trial, and aggregates the results into a score you can trust. Start small with 20–50 tasks drawn from real failures, grade the outcome in the environment (not the agent’s words), run enough trials to measure reliability not luck, and wire the loop shut: every failure becomes a new task, and every change runs the suite.

03 The loop, visually

The harness is a closed loop, not a one-shot score. Failures flow back in as new tasks; scoreboards flow out to CI gates.

04 How it works

Imperative, concrete. Do these in order when standing up an agent eval program.

1

Start with 20–50 tasks from real failures

Don’t wait for a perfect suite. Turn your manual pre-release checks, support tickets, and production incidents into tasks: defined inputs + objective success criteria. Two reviewers looking at the same result must reach the same pass/fail. If a capable agent fails a task at 0% over many trials, the task or grader is broken — fix those first.

2

Reset a clean, isolated environment for every trial

Leftover files, cached data, and shared history corrupt scores — they cause correlated failures or give the agent an unfair head start. Seed fixture data (a template database you clone per run), then destroy the trial environment when the run ends. An eval is only as trustworthy as its isolation.

3

Run each task several times, not once

Agents are non-deterministic: one trial is an anecdote. Run multiple trials and report the metric that matches your stakes: pass@k (at least one success in k attempts — fine for exploration) vs pass^k (all k succeed — what a customer-facing agent needs). At 75% per-trial success, pass³ is only about 42%.

4

Grade the outcome in the environment, not the agent’s words

A transcript can read perfectly while the world is wrong: the agent says “refund processed” but never called the refund tool. Assert on end state — database rows, files, tickets — not on the final message. Also diff for side effects the task didn’t ask for: wrong values, missing effects, and unintended extra effects are three different failure kinds.

5

Combine code-based, model-based, and human graders

Match the grader to the layer: deterministic checks for tool selection, arguments, and state; an LLM judge with an explicit rubric for open-ended quality; humans for judgment calls and for calibrating the judge against real labels. Score outcome and trajectory separately — a pass with a red trajectory is a different signal than a clean pass.

6

Keep capability evals and regression evals apart

Capability evals ask “what can this do?” — they should start at a low pass rate and be your hill to climb. Regression evals ask “does it still do what it did?” — they should hold near 100% and gate every merge. Hard tasks that saturate “graduate” into the regression suite; saturated capability tasks get replaced with harder ones.

7

Read failing transcripts, then close the loop

A scoreboard never tells you whether you measured the right thing. Read a sample of failing transcripts to learn whether the agent failed or the grader did — bad graders and ambiguous tasks are endemic — then convert each real failure into a new task. The loop is test → measure → diagnose → improve, and evals make it automatic.

05 Code sketch

The whole harness idea in miniature: clean environment per trial, several trials per task, outcome-graded, aggregated into pass rates.

# A minimal eval harness: tasks x trials x graders
from dataclasses import dataclass

@dataclass
class Task:
    name: str
    prompt: str              # defined inputs
    seed_env: callable       # returns a FRESH isolated environment
    graders: list            # functions: env -> (ok: bool, reason: str)

def run_harness(agent, tasks, trials=5):
    results = {}
    for task in tasks:
        passes = 0
        for _ in range(trials):            # one trial = one clean env
            env = task.seed_env()          # isolation: no shared state
            transcript = agent.run(task.prompt, env)
            ok = all(g(env, transcript)[0] for g in task.graders)
            passes += ok                  # grade OUTCOME, not words
        results[task.name] = passes / trials     # pass^k ≈ (this)^k
    return results

06 Failure modes

Named, with a one-line fix each. Most eval programs die from these, not from bad models.

F1

Grading the reply instead of the recordFix: assert on environment end-state — database rows, tickets, files — never on the final message alone.

The refund agent did nine careful tool calls, documented the timeline, closed the ticket as solved — and never actually changed the ticket state. A state-check harness measured 67% of failures in one benchmark as “clean runs that ended wrong.” The agent’s words are a claim; the database is the evidence.

F2

Grading the path instead of the outcomeFix: default to outcome checks; enforce specific steps only when the order is genuinely required.

You assert the agent must call search then read then update. It finds a valid shortcut and solves the problem — marked failed. Frontier agents regularly invent better approaches than the task author imagined; rigid trajectory checks punish exactly the capability you hired the agent for.

F3

Single-trial scores as “the” numberFix: run multiple trials per task and report pass@k or pass^k matched to your stakes.

One green run can be luck; one red run can be noise. A model at 75% per attempt fails a 3-invocation workflow more than half the time, but a single trial hides that completely. Report the pass rate with its run count and spread, never a bare percentage.

F4

Leaky trial environmentsFix: every trial starts from a seeded template environment; destroy it at run end.

The agent reads the git history left by the previous trial and “solves” the task. Or leftover caches make every run after the first slower, and you conclude your change regressed. Shared state measures your infrastructure’s flakiness, not your agent’s skill.

F5

The 98% suite nobody learns fromFix: keep it as a regression guard, and add harder capability tasks for the hill ahead.

Your scoreboard is green and flat. That suite is doing regression duty, not telling you where to improve — and every change now “passes,” which feels like safety but is just silence. A capability eval at 98% should graduate into regression and be replaced with tasks the agent actually fails.

F6

An uncalibrated judge is a vibe check with a spreadsheetFix: give the judge an explicit rubric, shuffle answer order, use a different model family, and calibrate against human labels.

LLM judges have known biases — toward answers shown first, longer answers, and their own model family’s outputs. A judge without calibration will happily certify a broken agent. Read its disagreements with humans; that’s where your rubric is wrong.

08 Sample prompts

Copy-paste starters. Use the copy button; each one is a full working prompt.

PROMPT 1 · DESIGN THE TASK SET

You are an evaluation engineer. I am building an agent that does this: [describe the agent's job, its tools, and what success looks like]. Draft 20-30 eval tasks: for each, give the task name, the exact inputs/prompt the agent receives, the fixture setup needed (seeded records, files, API stubs), and objective pass/fail criteria that two reviewers would agree on — assert on end state, not on the agent's words. Include: happy paths, known edge cases, cases where the correct behavior is to escalate/refuse/ask, and at least three "awkward" fixtures (nonexistent record, duplicate records, empty lookup results). Flag any task whose criteria are ambiguous and tighten them before I approve the set.

PROMPT 2 · WRITE THE JUDGE RUBRIC

Write an LLM-judge rubric for grading this open-ended agent behavior: [describe the behavior and the transcript format]. The rubric must: define PASS and FAIL as explicit, observable criteria (not vibes); give 2-3 few-shot examples per side with short rationales; specify what the judge should do when evidence is insufficient (abstain, don't guess); require the judge to cite the transcript lines supporting its verdict. Then propose a calibration plan: how many human-labeled samples, how we measure judge-human agreement, and the disagreement threshold at which we rewrite the rubric instead of trusting the judge.

PROMPT 3 · DIAGNOSE A FAILING RUN

Diagnose this failing eval run. First decide whether the failure is (a) a real agent failure, (b) a broken grader (rejecting a valid approach, asserting a brittle step order, checking words instead of state), or (c) a broken task (unsolvable as written, ambiguous criteria, missing fixture). Read the transcript below, name the failure layer — reasoning, action, or overall execution — then recommend the smallest fix: to the agent, the grader, or the task. End with a concrete regression task derived from this failure so it can't recur silently. Task definition and graders: [paste]. Transcript: [paste].

10 Flashcards

Click a card to flip it. Tab to a card and press Enter or Space.

Task
One test with defined inputs and objective success criteria. A good starting suite is 20–50 tasks drawn from real failures.
Trial
One attempt at a task, run in a clean isolated environment. Multiple trials per task measure reliability, not luck.
Grader
Logic that scores an aspect of performance. Three families: code-based (deterministic), model-based (rubric judge), human (spot checks and calibration).
Transcript (trajectory)
The complete record of a trial: outputs, tool calls, reasoning, intermediate results. Read failing ones to learn whether the agent or the grader failed.
Outcome
The final state of the environment at trial end. Grade this, not the agent's words — the database is the evidence.
Evaluation harness
The infrastructure that runs evals end-to-end: provides instructions and tools, runs tasks in isolation, grades outputs, aggregates results.
pass@k vs pass^k
pass@k: at least one success in k attempts. pass^k: all k attempts succeed — the reliability metric for customer-facing agents. 75%³ ≈ 42%.
Capability vs regression evals
Capability: "what can it do?" — starts at low pass rates, your hill to climb. Regression: "does it still?" — holds near 100%, gates every change.
LLM judge calibration
Judges have position, length, and self-preference biases. Counter with explicit rubrics, shuffled order, a different model family, and agreement checks against human labels.

11 Reach for this when…

Users say the agent “got worse” after a change and you can’t tell why. Without a baseline suite you are flying blind: a prompt tweak, a tool description edit, or a model version bump can silently regress behavior. Evals turn “feels worse” into a measured diff you can bisect.
Your agent mutates real state — tickets, records, money. Then transcript-only review is blindness: assert on end state, fingerprint tables for unintended side effects, and require pass^k across repeated trials before anything ships.
You’re about to change the model, prompt, or tool surface. Freeze the current suite as a regression gate first, so the change is graded against the bar your users already enjoy — and every new production failure becomes a new task in the suite.
