Code review craft: reviewing like a senior

A senior’s approval means something: I read this, I understand what it does, and I would run it in production. That is a different job from hunting typos or counting style violations. Senior review is a disciplined pass over intent, correctness, tests, and the things the diff does not show — done fast enough that authors still want your review tomorrow, and kind enough that they learn from it.

02 The one-idea version

A code review is not a proofread — it is a second pair of eyes vouching for a change. Read for what the change is supposed to do, then for whether it actually does it safely, then for whether a future reader can maintain it. Automate everything below that bar (formatting, lint, basic checks) so human attention goes where only a human can go: intent, edge cases, and judgment.

03 The senior review pass

Six gates, in order. Do not start at line 1 of the diff — start at the purpose, and stop early if an early gate fails.

04 How it works

Seven mechanics. Order matters: the first three keep you from wasting the last four.

1

Read the intent before the code

Read the title, description, and linked issue first, and restate the goal in one sentence. If the PR does not solve the stated problem — or the problem itself is wrong — say so now. Reviewing line by line before you know the destination is how reviewers approve elegant solutions to the wrong problem.

2

Move from general to specific

Find the core change first — usually the largest or most central files — and understand the design before the details. Ask: is this the simplest design that works? Does it belong here, or is it a new abstraction for one use? Only then descend into functions, branches, and edge cases, and start with the test files: they show what the author believes the code should do.

3

Interrogate the tests, not just the code

Ask the one question that separates real tests from decoration: would this test fail if the code were broken? Check that tests cover the happy path, the edge cases, and the failure path; that assertions are specific (not “result is truthy”); and that tests were added in the same change, not promised for later. A test suite that passes on broken code is worse than none — it manufactures confidence.

4

Check what the diff does not show

The most expensive bugs live outside the visible lines: unhandled errors swallowed silently, a loop that becomes N+1 queries at scale, a race when two requests interleave, unsanitized input, a migration with no rollback, a secret or credential in the diff, a feature with no flag or kill switch. For each change, ask: what happens when this fails, when it is called twice, when it is called concurrently, and when the input is hostile?

5

Label severity on every comment

Use explicit labels — blocker, suggestion, nit, question, praise — so the author knows what must change and what is optional. Never block on personal style: if a formatter or linter can enforce it, let the machine say it. Unlabelled comments all read as blockers, and a PR full of apparent blockers reads as hostility.

6

Verify when it matters; do not just read

For risky changes, check the branch out, run the tests, and try the unhappy path yourself. Reading a diff proves the author’s logic looks right; running it proves it works in the real environment. This is also how you catch semantic merge conflicts — a diff that is correct alone but breaks against what landed on main since the branch was cut. Test the merge result, not just the diff.

7

Write comments that teach, and review fast

Explain why, offer a direction (not always the full solution — the PR is the author’s responsibility), and name at least one thing done well. Aim to review within one business day: a PR that waits a week loses the author’s context, and a slow review queue quietly teaches the team to skip review altogether. Speed and care are not opposites — a focused 60-minute session beats three distracted days.

05 Code sketch

A tiny pre-review triage: it sorts a change into blockers, suggestions, and nits before a human ever opens the diff — the same severity split a senior reviewer applies by hand.

#!/usr/bin/env python3 — review_triage.py (illustrative, not a substitute for reading)
import re

def triage(files, diff):
    blockers, suggestions, nits = [], [], []
    if sum(f["lines"] for f in files) > 400:
        suggestions.append("PR >400 lines: ask author to split it.")
    if not any(f["path"].startswith("test") for f in files):
        blockers.append("No tests in this change.")
    if re.search(r"api_key\s*=\s*['\"][^'\"]+", diff):
        blockers.append("Possible hard-coded secret in diff.")
    if re.search(r"except.*:\s*\n\s*pass", diff):
        blockers.append("Swallowed exception: except: pass hides failures.")
    for m in re.finditer(r"for .*:\n.*execute\(", diff):
        suggestions.append("Query inside a loop — check for N+1.")
    return {"blockers": blockers, "suggestions": suggestions, "nits": nits}

print(triage([{"path": "app.py", "lines": 120}],
    "except Exception:\n    pass"))

06 Failure modes

Five ways reviews go wrong, each with the fix.

!

The 30-second rubber stampFix: if you cannot explain what the change does, you have not reviewed it — read the intent, the core files, and the tests, or decline the review.

Approving a 400-line PR at a glance is not trust, it is abdication: your approval is a public statement that the code is safe. Every careless approval also spends your credibility — the next time you raise a real concern, it carries less weight.

!

The 50-comment avalancheFix: rank your comments, lead with the one or two that matter, and label the rest suggestion or nit. A review the author dreads is a review they stop reading.

Fifty comments turn a review into an adversarial audit: the author stops learning and starts defending. Most of those comments are usually style or preference — exactly what linters exist to say, without the social cost.

!

Blocking on style, approving on substanceFix: automate formatting and linting in CI; spend human review time on design, correctness, security, and tests — never the reverse.

Teams that argue about brace placement in reviews while missing a swallowed exception have their priorities backwards. If a machine can check it, a machine should check it, so humans check what machines cannot.

!

Reviewing the code, not the changeFix: start from the PR description and the tests, and ask what the change is for. A beautifully written function that solves the wrong problem still fails the review.

Line-by-line reading without intent produces reviews that are technically accurate and strategically useless: every line correct, the feature wrong. The design question — should this exist, here, like this — must come before the line question.

!

The review that arrives a week lateFix: review within one business day, or hand it off. A stale review costs the author their context and the team its momentum.

By day seven the author has moved on, the branch has drifted from main, and the review itself becomes a merge conflict. Slow reviews do not buy quality — they buy resentment and, eventually, a culture that routes around review entirely.

08 Sample prompts

Copy-paste these into your AI assistant when you’re reviewing — or asking it to review — a change.

REVIEW: SENIOR PASS

Review this pull request as a strict senior reviewer. First restate the intent in one sentence from the PR description. Then report only, grouped by severity (blocker / suggestion / nit): 1. Intent or design problems — does it solve the right problem the right way? 2. Correctness bugs and edge cases that would break in production 3. Tests that are missing, weak, or would pass on broken code 4. Invisible risks: swallowed errors, races, N+1 queries, security issues, migrations without rollback For each issue give the file, the line, and why it matters. Do not rewrite the code.

COMMENT: MAKE IT LAND

Rewrite these review comments so they land well: [paste your draft comments]. Rules: lead with the why, not the verdict; phrase disagreements as questions where I am genuinely unsure; label each comment blocker / suggestion / nit / question / praise; add one genuine praise comment for something done well; keep the tone respectful and about the code, never the person.

PREPARE: MAKE IT REVIEWABLE

Before I open this pull request, review it as if you were my reviewer: [paste the diff summary or key files]. Tell me: (1) what is unclear about the intent from the description alone; (2) the three most likely reviewer objections, in severity order; (3) whether the change should be split, and where; (4) which tests a skeptical reviewer would ask for. Give me the fixes, not a rewrite.

10 Flashcards

Click or press Enter/Space to flip.

Approval
A vouch: “I read this, I understand it, and I would run it in production.” Not a rubber stamp — Google’s bar is that the change definitely improves overall code health.
Intent first
Read the title, description, and issue before any code. If the change solves the wrong problem, line-level feedback is wasted work.
General to specific
Core design first, details second. Start with the central files and the test files — they show what the author believes the code should do.
Would the test fail?
The test-quality question: would this test fail if the code were broken? A test that passes on broken code manufactures false confidence.
Blocker / suggestion / nit
Label every comment. Blocker must change; suggestion is the author’s call; nit is optional polish and never blocks. Unlabelled comments all read as blockers.
Invisible risks
What the diff does not show: swallowed errors, races, N+1 queries, unsanitized input, migrations without rollback, secrets in the diff, no kill switch.
Semantic merge conflict
Git merges text, not meaning. A diff correct alone can break main if main moved underneath it — always test the merge result, not just the diff.
One business day
Google’s review-response rule: a PR should not wait more than one working day. Slow reviews cost the author’s context and teach the team to route around review.
Mentor, not examiner
Explain why, offer a direction, leave the fix to the author, and praise something done well. Reviews are where senior engineers grow the rest of the team.

11 Reach for this when…

You are about to click Approve on a PR you skimmed — stop. Restate its intent in one sentence; if you cannot, you have not reviewed it yet.
Your review comments keep sparking arguments about taste — label severity, move style to the linter, and argue only about things with technical consequences.
Reviews sit for days, or authors dread them — the process, not the people, is broken: set a one-day response rule, keep PRs under ~400 lines, and lead with the one comment that matters.
