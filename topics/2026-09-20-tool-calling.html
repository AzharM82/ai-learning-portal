Tool calling / function calling done right

The whole point of AI agents fits in one sentence: the model never runs your code — it just asks. You hand it a menu of tools described as JSON schemas; it emits a structured call — "run get_weather with location=Paris"; your application validates and executes it, then feeds the result back in. Give the model verbs, and keep every side effect behind your own code.

02 The one-idea version

Tool calling is a structured request, not remote execution. The model looks at your JSON-schema menu and emits a call — a name plus JSON arguments — and then stops. Your code decides whether that call is allowed, runs it, and returns the result as a tool_result tied to the call by ID. The loop repeats until the model answers. The LLM is the decision-maker; your code is the only thing that touches the world.

03 The visual

One loop, two owners: the model picks and describes; your application validates, executes, and returns. The red line is the trust boundary — nothing crosses it except structured text.

04 How it works

Six mechanics — one per step of the loop — plus the controls that keep it from running away.

1

Describe each tool as a JSON-schema menu — the description is the model's only manual

Name, what it does, when to use it, and a JSON schema for the arguments. The model never sees your implementation — only this description. OpenAI's official best practices: write clear, detailed names and parameter descriptions, and use the system prompt to say exactly when (and when not) each function should be used. Vague tools get vague callers.

2

The model emits a structured call, never code — then stops

On OpenAI that's a tool_calls entry with a function name and JSON arguments; on Anthropic it's a tool_use block with stop_reason: "tool_use". This is strictly better than the old ReAct trick of parsing free-text "Action:" lines: structured output can't drift formatting mid-sentence. Parsing text is fragile; a schema-shaped call is a contract.

3

Your code dispatches: allow-list the name, validate the args, then execute

Look the tool name up in a registry you control — never eval or dynamically import by model-supplied string. Validate arguments against the schema, and use enums to make invalid states unrepresentable: OpenAI's own example is that toggle_light(on: bool, off: bool) allows nonsense, while an enum doesn't. The model proposes; your code authorizes.

4

Return a tool_result tied to the call by ID, and append the full turn history

Each result must carry the original call_id (OpenAI) / tool_use_id (Anthropic) so the model knows which call the result answers — especially when several calls fly in one turn. Then send back the whole transcript: the original prompt, the model's call, and your result. The model continues the loop: another call, or the final answer.

5

Run the loop with a hard budget: max iterations, timeout, token cap

An agent loop is a while with a model in the condition — it can spin. OpenAI's tool_choice gives you five gears: auto (model decides), required (must call something), force one specific function, restrict to an allowed subset, or none (chat only). On top of that, your loop needs a step limit and a cost ceiling. An unbounded loop is a credit card with a keyboard.

6

Keep the menu small: aim for fewer than 20 active tools per turn

Every tool definition is injected into the model's context and billed as input tokens — and accuracy degrades as the menu grows. OpenAI's guidance: fewer than 20 functions at the start of a turn (a soft target), offload burden into code (don't make the model fill arguments you already know), and merge functions that are always called in sequence. If you have hundreds of tools, defer-load them: let the model search for and load tools on demand instead of listing the whole catalog.

7

Handle parallel calls: the model can emit several in one turn

"Compare flights to Tokyo and Osaka" is two independent lookups — both providers let the model emit them together. Execute them concurrently, build one tool_result per call ID, and return all of them. Parallelism is free latency; the only hard part is pairing each result with the right ID so the model doesn't mix up the cities.

05 Code sketch

The whole pattern in 27 lines: the model asks, your code runs, the loop is bounded. Validation and permission checks go where the comment says.

import json

TOOLS = {
    "get_weather": {
        "schema": {"type": "function", "name": "get_weather",
            "description": "Current temperature for a city.",
            "parameters": {"type": "object",
                "properties": {"location": {"type": "string"}},
                "required": ["location"]}},
        "fn": get_weather,  # your real implementation, in your process
    }
}

def agent_loop(messages, max_steps=8):
    for _ in range(max_steps):          # the loop has a budget
        msg = client.chat.completions.create(
            model="gpt-4o-mini", messages=messages,
            tools=[t["schema"] for t in TOOLS.values()]).choices[0].message
        messages.append(msg)
        if not msg.tool_calls:          # no call requested → final answer
            return msg.content
        for call in msg.tool_calls:       # the model ASKS; your code RUNS
            # TODO: validate call.function.arguments against the schema,
            # check permissions, then dispatch ONLY from this registry
            result = TOOLS[call.function.name]["fn"](
                **json.loads(call.function.arguments))
            messages.append({"role": "tool",
                "tool_call_id": call.id, # pair result to the call
                "content": json.dumps(result)})
    raise RuntimeError("tool loop exceeded its budget")

# every production agent is this loop with validation, permissions,
# retries, and logging bolted on. the shape never changes.

06 Failure modes

Named pitfalls, each with a one-line fix. Every one of them is a hole in the trust boundary.

✕

Parsing free text instead of using native tool calls Fix: use the provider's structured tool-call output (tool_calls / tool_use blocks) — it's a contract, not a hope.

The ReAct-era trick of regexing "Action: search(...)" out of model prose breaks the moment the model rephrases, reorders, or adds a stray quote. Native tool calling exists precisely because text parsing is fragile.

✕

Hallucinated arguments reach your real functions Fix: validate every argument against the schema, use enums for closed sets, and return validation errors as tool_results so the model retries — don't crash, converse.

The model will invent enum values, drop required fields, and pass "ASAP" where you expected an ISO date. Treat every argument as user input: it is. A returned error message is just another turn of the loop.

✕

A 60-tool menu and the model picks wrong (or never picks) Fix: aim for fewer than 20 active tools per turn; offload arguments you already know into code; defer-load rare tools with tool search.

Tool selection accuracy falls as the menu grows — and every schema costs input tokens on every turn. A sprawling menu is the tool-calling equivalent of a 200-item restaurant menu: nobody orders well.

✕

The loop never ends: spin, retry-storm, budget gone Fix: max iterations + wall-clock timeout + cost ceiling; back off and surface a partial answer instead of spinning forever.

A model that keeps calling tools "just to check" is an agent with no exit condition. The while loop in the sketch has a budget for a reason — put one in before the first production call.

✕

Side-effectful tools with no human in the loop Fix: least-privilege tool permissions, explicit confirmation for destructive or irreversible actions, and idempotent tool implementations.

delete_account should not sit on the same menu, with the same permissions, as get_weather. The model decides what to propose — you decide what it's allowed to propose, and what needs a human's yes first.

08 Sample prompts

Copy-paste starters. One designs tool schemas, one reviews your dispatch code, one debugs a misbehaving tool menu.

THE TOOL DESIGNER

Design the tool menu for my agent. My application's capabilities: {{list what your code can actually do, e.g. look up orders, issue refunds, send emails}} For each capability, write a tool definition: a clear snake_case name, a description that says exactly when to use it (and when NOT to), and a JSON schema for its arguments. Apply the rules: enums for closed sets (no invalid states), required vs optional fields marked deliberately, no arguments the model can't know or that my code already has, and merge any two functions that are always called in sequence. End with the one tool you'd cut if I had to ship tomorrow.

THE DISPATCH REVIEWER

Review my tool-calling dispatch loop for safety and correctness. The code is pasted below. Check for: (1) tool names dispatched only from an allow-list registry — no dynamic eval/import by model-supplied string; (2) arguments validated against the schema before execution; (3) tool_result paired with the correct call_id; (4) a hard bound on iterations, plus timeout and cost ceiling; (5) side-effectful tools gated behind permission checks or human confirmation; (6) the full transcript (prompt, call, result) sent back each turn. List every gap as: the exact line, what the model could do through it, and the smallest fix.

THE MENU DEBUGGER

My agent's tool calling misbehaves. Symptoms: {{e.g. it never calls the right tool / it calls the wrong one / it calls tools in an endless loop / arguments come back malformed}} My tool menu (name + description + schema per tool): {{paste it}} Diagnose across: vague descriptions vs a decisive one, menus over ~20 tools, arguments the model can't know, missing enums, and tool_choice / system-prompt steering. For each issue: the one-line evidence in my menu, and the smallest change — cheapest fix first.

The model's structured request: a tool name plus JSON arguments. It proposes — it never executes.
tool_result + call_id
Your application's reply: the tool's output, tied to the original call by ID — so the model knows which result answers which call, especially when several fly in one turn.
The tool menu
Every tool described as name + description + JSON schema for its arguments. The description is the model's only manual — it's all it ever sees of your implementation.
The agent loop
Model emits a call → your code validates, dispatches, executes → you return tool_result → model continues or answers. Every production agent is this loop with validation, permissions, and logging bolted on.
tool_choice
How much freedom the model gets: auto (model decides), required (must call something), force one specific function, restrict to a subset — or none for plain chat.
The intern test
OpenAI's bar for a tool description: could a human intern use this function correctly given nothing but what you gave the model? If not, the questions they'd ask you belong in the description.
Enums over booleans
Use enums and object structure to make invalid states unrepresentable: toggle_light(on: bool, off: bool) allows nonsense; a mode enum doesn't. Design the schema so the model can't be wrong.
Allow-list dispatch
Look the model-supplied tool name up in a registry you control — never eval or dynamic-import by model string. The model proposes the verb; your code decides whether it exists and may run.
Parallel tool calls
The model can emit several independent calls in one turn. Execute them concurrently, return one tool_result per call_id — the pairing is the only hard part.
Client vs server tools
Anthropic's split: client tools (your functions) run in your application and return a tool_result; server tools (web search, code execution) run on the provider's infrastructure — no handler code from you.

11 Reach for this when…

The model needs facts newer than its training data or inside your systems — weather, prices, order status, your database. If the answer isn't in the weights, don't make it guess: give it a tool.
You want natural language to trigger real actions — refunds, emails, ticket creation, deployments. The loop turns "cancel my order" into a validated, permission-checked function call instead of a hallucinated confirmation.
You need structured data out of messy text — entity extraction, classification, form filling. Force a specific tool via tool_choice and the model becomes a reliable JSON emitter for your pipeline.
