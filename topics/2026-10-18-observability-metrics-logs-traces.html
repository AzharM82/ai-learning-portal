Observability: metrics, logs, traces

At 2 AM, nobody reads dashboards — they interrogate telemetry. Observability is the discipline of emitting the right telemetry ahead of time so that any question about a live system can be answered fast: metrics to notice something is wrong, traces to find where, and logs to see exactly what happened.

02 The one-idea version

Observability is the ability to ask any question about system behavior from the telemetry you emit — not from the dashboards you pre-built. Monitoring tells you a known bad thing happened; observability lets you diagnose an unknown bad thing. The mental model: metrics, logs, and traces are three views of the same events — metrics aggregate behavior over time (cheap, coarse, for alerting), logs record individual events (rich, expensive, for debugging), and traces connect events across service boundaries (causal — spans plus context propagation).

03 One request, three views

A single checkout request flows through three services. The trace-id travels on every arrow (W3C traceparent header), so all three views join on it. Metrics answer "how many / how slow", logs answer "exactly what happened", traces answer "why slow — which span".

04 How it works: six mechanics

Imperative, concrete, no fluff. These are the moves that turn "we emit telemetry" into "we can diagnose anything".

1

Emit the three signals deliberately — never rely on one

Metrics notice that something is wrong, traces locate where, logs explain exactly what happened. A system with only metrics can alert but not diagnose; with only logs it drowns in volume before it notices; with only traces it lacks the long-term aggregates that show trends. Instrument all three for every request path that matters, using the vendor-neutral OpenTelemetry SDK so you are not married to one backend.

2

Record metrics as histograms; aggregate with percentiles, not averages

Record each latency observation into a histogram (buckets computed by the backend) instead of pre-averaging. Alert on p50 / p95 / p99, never on the mean: an average latency of 95 ms can hide a p99 of 800 ms — the 1% of users in real pain — and when a page needs three such backends, that tail becomes the frontend's median. Google's SRE book calls this "worrying about your tail" for a reason.

3

Log events as structured JSON, not sentences

Log {"event":"checkout_completed","trace_id":"4bf92f35","request_id":"req_123","duration_ms":712,"outcome":"success"} — never "User clicked checkout button". Fields are filterable, groupable, and joinable to traces by trace_id; sentences are only greppable, and only by the author who remembers the exact wording. Write for the reader who debugs this at 3 AM three months from now: every log line should answer what happened, to which entity, how long it took.

4

Propagate trace context across every service boundary

A trace is a tree of spans — one unit of work each — linked by parent IDs under a shared trace-id. That context rides the W3C traceparent header on every outgoing call: the sending side injects it, the receiving side extracts it and continues the trace. Instrument the HTTP client and server frameworks once (OpenTelemetry auto-instrumentation) rather than hand-rolling headers — one un-instrumented hop kills the waterfall exactly where you need it most.

5

Keep label cardinality bounded — no unbounded values as labels

Every unique label-value combination creates a new time series. user_id, email, or request_id as a Prometheus label means an unbounded series explosion that blows up storage and query cost. Bounded labels: service, endpoint, status code. High-cardinality identity belongs in logs and traces (where you query it ad hoc), not in metric labels (which you aggregate forever).

6

Alert on symptoms, not causes — and name a runbook action

The four golden signals — latency, traffic, errors, saturation — are symptoms users feel. Page a human when a symptom is bad (p95 checkout latency > 800 ms for 5 minutes); ticket the causes (CPU > 80% on db-03) for investigation during work hours. Every page must name the runbook action the on-call takes; an alert with no action is noise that trains people to ignore the pager — including during the real incident.

05 Code sketch: instrument one request

24 lines, stdlib only, in OpenTelemetry style: one span per unit of work, latencies recorded into a histogram (never averaged), and a structured JSON log line carrying the same trace_id the traceparent header would carry downstream.

import json, logging, time, uuid
from datetime import datetime, timezone

# OpenTelemetry-style: span = one unit of work; trace_id rides the
# traceparent header across services; logs carry the same id to join on.
logger = logging.getLogger("checkout")

def handle_checkout(request_id):
    trace_id = uuid.uuid4().hex       # one id, metrics + logs + traces
    latencies = []                    # histogram: record, never average
    start = time.perf_counter()
    for step in ("auth", "inventory", "payment"):
        s = time.perf_counter()
        ...                       # real work here
        latencies.append((time.perf_counter() - s) * 1000)
    p95 = sorted(latencies)[int(len(latencies) * 0.95)]
    logger.info(json.dumps({
        "event": "checkout_completed", "request_id": request_id,
        "trace_id": trace_id, "duration_ms": round((time.perf_counter() - start) * 1000, 2),
        "step_p95_ms": round(p95, 2), "outcome": "success",
    }))
    return trace_id   # propagate to the next hop

if __name__ == "__main__":
    logging.basicConfig(format="%(message)s")
    handle_checkout("req_123")

06 Failure modes: five ways telemetry lies or dies

Each one is a named pitfall plus its one-line fix.

F1

Averaging latencies Fix: record histograms and alert on p50/p95/p99. The average hides the 1% of users in pain — and when your page needs three backends, one backend's p99 becomes your frontend's median.

F2

Logging free text ("User clicked checkout") Fix: emit structured events with fields (trace_id, request_id, duration_ms) so logs are filterable and joinable — greppable sentences are only readable by whoever wrote them.

F3

Trace propagation dying at one hop Fix: instrument the HTTP clients/servers with the framework's OpenTelemetry integration so the traceparent header rides every boundary — a hand-rolled client that forgets the header splits your waterfall exactly where the bug lives.

F4

Unbounded label cardinality (user_id as a metric label) Fix: keep metric labels bounded (service, endpoint, status); put unbounded identity in logs and traces where it is queried ad hoc instead of stored as infinite time series.

F5

Alerting on every cause Fix: page on symptoms (the four golden signals: latency, traffic, errors, saturation), ticket on causes, and require every alert to name a runbook action — otherwise pager fatigue teaches the team to ignore the real incident.

10 Flashcards

Click or press Enter/Space to flip.

Observability vs monitoring
Monitoring answers pre-chosen questions (dashboards, known-bad alerts). Observability is the ability to ask ANY question about system behavior from emitted telemetry — diagnosing the unknown bad thing, not just the known ones.
The three signals
Metrics aggregate behavior over time (cheap, coarse — for alerting). Logs record individual events (rich, expensive — for debugging). Traces connect events across service boundaries (causal — spans + context propagation). Three views of the same events.
Histogram + p95/p99
Record each latency observation into buckets; the backend computes percentiles. p99 = the latency only 1% of requests exceed. Never alert on the mean — the average hides the tail, and one backend's p99 becomes the frontend's median.
Structured log
An event with named fields — {"event":"checkout_completed","trace_id":"…","duration_ms":712} — filterable, groupable, joinable to traces. Sentences like "User clicked checkout" are only greppable by whoever wrote them.
Span and trace
A span is one unit of work (name, start/end, parent span, attributes). A trace is the tree of spans one request created across services — the waterfall that shows which span burned the time.
W3C traceparent
The standard header (trace-id + span-id + flags) that carries trace context across service boundaries. Inject on every outgoing call, extract on every incoming one — one hop that forgets it kills the waterfall exactly where you need it.
Cardinality
The number of unique label-value combinations a metric produces — each becomes a time series. Unbounded values (user_id, email, request_id) as labels = series explosion and storage death. Keep metric labels bounded; put identity in logs/traces.
The four golden signals
Latency, traffic, errors, saturation — the user-facing symptoms. If you can only measure four things and page when one goes bad, your service is at least decently covered. (Google SRE Book, ch. 6.)
Symptoms vs causes
Symptoms = what's broken (users feel it: "p95 latency > 800 ms") — page on these. Causes = why ("CPU > 80% on db-03") — ticket and investigate. Paging on causes trains the team to ignore the pager, including during the real incident.

11 Reach for this when…

You're debugging a live incident and the averages look fine — pull p95/p99, filter structured logs by trace_id, and open the span waterfall. The tail and the slow span are where the incident lives, not the mean.
You're designing telemetry or reviewing instrumentation in a PR — walk the six mechanics: three signals, histograms not averages, structured events, traceparent on every boundary, bounded labels, symptom alerts with runbook actions.
Someone proposes alerting on CPU, disk, or "something seems weird" — redirect to the four golden signals and demand a runbook action per alert. A page without an action is noise that will mask the real page at 3 AM.
