Coding agents in practice: Copilot agent mode, task decomposition, repo-scale changes

Autocomplete suggests the next line. A coding agent takes a whole task: it plans the steps, edits files across the repo, runs commands, reads the errors, and iterates until the work is done — or until you stop it. The skill is not prompting harder; it is decomposing work so an agent can succeed and you can verify it did.

02 The one-idea version

A coding agent is a loop, not a suggestion. Per GitHub’s docs, in agent mode Copilot takes a high-level task, decides which files to change, makes the edits, and runs commands as needed, iterating to remediate issues until the task is complete. Your job moves up a level: decompose the work into verifiable chunks, supply the context the loop needs, and be the reviewer at the end of it.

03 The picture: decompose, loop, verify

One large request becomes several small, checkable tasks. Each task runs the same loop, and nothing merges without a human review of the diff:

04 How it works

Seven mechanics, in the order a good agent session actually runs.

1

Pick the mode that matches the job

Use Ask to understand code without changing it, Edit for targeted changes in files you name, Plan to agree an approach before any code, and Agent when the task is multi-step and you want Copilot to determine the steps, edit across files, run commands, and iterate on errors. For self-contained work you can hand off entirely, assign the issue to the cloud coding agent instead — it works asynchronously and returns a draft pull request. Choosing Ask for a repo-wide refactor, or Agent for a one-line question, wastes the tool either way.

2

Write the task like an issue a junior teammate could pick up

GitHub’s best-practices guide is blunt: Copilot does better on clear, well-scoped tasks. An ideal task states the problem to solve, complete acceptance criteria (what “done” looks like — including whether tests are expected), and directions about which files need to change. Think of the issue description as a prompt, because for the agent it literally is one. “Fix the login bug” is not a task; “users with expired tokens see a 500 on /refresh — return 401, add a regression test in auth/tests” is.

3

Decompose before you delegate — plan first on anything large

If the task is large or ambiguous, the agent-mode docs recommend drafting an implementation plan first. Split along natural boundaries: one subtask per independently testable outcome, one branch per subtask, no two parallel agents editing the same files. Good first delegations are deliberately modest — fix a bug, improve test coverage, update docs, improve accessibility, address a piece of technical debt — so you learn what the agent is good at before you trust it with cross-repo design work.

4

Give the repo a memory: custom instructions and setup steps

Do not re-explain your project in every prompt. Put build, test, and lint commands, coding standards, and repo structure in .github/copilot-instructions.md (plus path-scoped files under .github/instructions/), and pre-install dependencies with a copilot-setup-steps.yml so the cloud agent does not burn its session on trial-and-error setup. An agent that can build, test, and validate its own changes in its environment produces pull requests that merge quickly; one that cannot is guessing.

5

Isolate the work: branch, working set, and least privilege

Never let an agent work directly on your main line. Locally, work on a feature branch and scope the working set to the files that should change; in the cloud, the agent already works on its own copilot/ branch and can only return a PR — it cannot merge or deploy. Keep terminal-command approval on by default, extend tools via MCP only as far as the task needs, and use custom agents (a testing specialist, a docs expert) with narrowed tool access for recurring kinds of work.

6

Run the loop — and steer it while it runs

Agent mode is interactive, not fire-and-forget. Watch edits stream in, confirm or reject each terminal command it proposes, send a follow-up prompt to redirect it before it finishes, and undo edits you do not want. On a cloud PR, batch your feedback: use Start a review and submit all comments at once, mentioning @copilot, so the agent works on the whole review in one pass instead of reacting comment-by-comment.

7

Verify like a reviewer, not a fan

The agent’s summary is a claim; the diff is the evidence. Read every changed file, run the build and the test suite yourself, check that acceptance criteria are actually met (including the new tests passing for the right reason), and look for the classic agent extras: unrelated refactors, weakened assertions, and plausible-but-wrong edge-case handling. If it is not right, iterate on the PR exactly as you would with a human author — the process to mergeable is the same.

05 Code sketch

Decomposition as data: break a feature into verifiable subtasks, then gate each one on its own check before the next starts.

# decompose.py — a task is only delegable if "done" is checkable
from dataclasses import dataclass, field

@dataclass
class Subtask:
    title: str
    files: list[str]
    acceptance: str          # what a reviewer can verify
    check: str               # command that must pass
    branch: str = ""

def decompose(feature: str) -> list[Subtask]:
    tasks = [
        Subtask("Add token-refresh endpoint",
                ["auth/refresh.py"], "Expired token returns 401, not 500",
                "pytest auth/tests/test_refresh.py -q"),
        Subtask("Wire client retry on 401",
                ["client/session.py"], "One transparent retry, then surface error",
                "pytest client/tests -q"),
    ]
    for i, t in enumerate(tasks):   # one branch per subtask: no shared files
        t.branch = f"copilot/{feature}-{i+1}"
        assert not any(t.files == o.files for o in tasks[:i])
    return tasks

if __name__ == "__main__":
    for t in decompose("token-refresh"):
        print(f"{t.branch}: {t.title} | done when: {t.acceptance} | {t.check}")

06 Failure modes

Five ways coding-agent sessions go wrong — and the one-line fix for each.

1

The vague mega-taskFix: decompose into well-scoped subtasks, each with acceptance criteria and named files, before delegating.

“ modernize the auth system” gives the agent no done state, so it optimizes for looking busy: a huge, design-inconsistent diff across dozens of files. GitHub’s own guidance lists complex, broadly scoped, cross-repository refactoring among the tasks to keep for yourself — or break down first.

2

No tests, no criteria — “it works” by assertionFix: state acceptance criteria in the task and require the agent to run (and add) tests it can validate against.

Without a checkable definition of done, the loop’s only stopping rule is the model’s confidence. The fix is structural: criteria in the issue, build/test commands in the repo instructions, and a setup-steps file so the agent can actually run them.

3

Working on main, or parallel agents in the same filesFix: one branch / worktree per task, disjoint file ownership, and merge one PR at a time.

Agents do not coordinate with each other. Two sessions editing the same module produce conflicts and silently overwritten work, and an agent editing your working tree directly leaves you no clean undo. Isolation is what makes delegation cheap to reject.

4

Auto-approving every terminal commandFix: keep per-command approval on by default; auto-approve only a narrow, named allowlist.

The agent proposes commands; you are the permission boundary. The docs note commands run automatically only if you or your admin configure it so — leave that off for anything destructive, networked, or credential-bearing, especially on sensitive, security, or production-critical tasks, which the guidance says not to delegate casually at all.

5

Reviewing the summary instead of the diffFix: read every hunk, run the tests yourself, and batch PR feedback into one review for the agent to act on.

Agent summaries are fluent whether the code is right or not, and they omit the unrelated refactor three files down. The PR process is identical to a human’s for a reason: diff, tests, criteria — then merge, or send it back with specific comments.

08 Sample prompts

Copy one into your AI assistant and apply it to your own work.

PLAN BEFORE YOU CODE

Do not write code yet. For this task — [describe the change] — produce an implementation plan: the subtasks in order, the files each subtask touches, the acceptance criteria and the exact test or command that proves each one done, and any risks or open questions. Keep each subtask independently reviewable and on its own branch. I will approve or edit the plan before you implement anything.

WRITE AN AGENT-READY ISSUE

Rewrite this rough task as an issue I can assign to a coding agent: [paste rough task]. Include a clear problem statement, complete acceptance criteria (including what tests must exist and pass), the files or areas likely to change, explicit constraints and non-goals, and how to build and test. Flag anything ambiguous instead of guessing — if it is too broad for one agent task, split it into sequenced sub-issues.

REVIEW AN AGENT’S PR LIKE A SENIOR

Review this agent-generated pull request against its issue: [link / paste issue + diff]. Check, in order: does the diff actually satisfy every acceptance criterion, are there changes outside the task scope, do the new tests pass for the right reason (not weakened assertions), and are there edge cases, security, or auth implications the agent missed? Give me a merge / iterate / reject verdict with the specific comments I should batch into one review.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

Agent mode
Copilot’s autonomous IDE mode: given a task, it decides which files to change, edits them, runs commands (with your approval by default), and iterates on errors until the task is complete.
Cloud coding agent
The asynchronous Copilot agent on GitHub: assign it an issue, it works on a copilot/ branch in its own environment, runs tests, and opens a draft PR for your review. It cannot merge or deploy.
Task decomposition
Splitting a large request into small, independently testable subtasks — each with its own acceptance criteria, files, and branch — so an agent can succeed and a human can verify each piece.
Well-scoped task
GitHub’s bar for delegation: a clear problem description, complete acceptance criteria, and directions about which files need to change. Think of the issue as a prompt — because it is one.
Plan mode
Drafting an implementation plan with the agent before any code is written. The docs recommend it when a task is large or ambiguous — agree the approach, then execute.
copilot-instructions.md
Repo-level custom instructions at .github/copilot-instructions.md: build/test/lint commands, standards, and structure every Copilot session in the repo follows. Path-scoped variants live under .github/instructions/.
copilot-setup-steps.yml
A setup file that pre-installs a repo’s dependencies before the cloud agent starts, so it can build and test immediately instead of discovering setup by slow, unreliable trial and error.
Custom agent
A specialized agent profile (Markdown) for a recurring kind of work — testing specialist, documentation expert — with focused instructions and narrowed tool access. Least privilege, packaged.
Batch your PR feedback
On an agent PR, use Start a review and submit all comments at once with @copilot. The agent starts on each comment as it lands, so one batched review gets one coherent fix pass.

11 Reach for this when…

A change spans several files but each step is mechanical once understood — a rename with call-site updates, a framework migration, a test-coverage pass: decompose it, delegate the subtasks, review the diffs.
You have a backlog of small, well-defined issues — bug fixes, accessibility and docs improvements, technical debt with clear criteria: assign them to the cloud agent and spend your own time on design and review.
You are exploring an unfamiliar repo and need a change, not just an explanation — start in Plan mode to agree the approach from the agent’s research, then let Agent mode execute it on a branch you can discard.
