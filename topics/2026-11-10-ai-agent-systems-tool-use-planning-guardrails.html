AI agent systems: tool use, planning loops, and guardrails

An agent is not a smarter prompt. It is a model in a loop: plan a step, request a tool, let your code validate and run it, read the real result, and decide again. That loop is where the power comes from — and where every failure lives. Build the loop deliberately, scope the tools narrowly, and put the guardrails in code, not in a polite request to the model.

02 The one-idea version

An agent is a model using tools in a loop, and your code — not the model — owns the loop. Anthropic draws the line by who decides the next step: in a workflow, your code paths decide; in an agent, the model dynamically directs its own process from environmental feedback. Either way, the model never executes anything. It emits a structured tool request, your runtime validates, authorises, and runs it, and the observation that comes back is the ground truth the next decision must answer to. Autonomy is earned inside budgets and guardrails, never granted by a prompt.

03 The picture: the loop your code owns

One run, end to end. The model proposes; the runtime disposes — at the validation gate, at the budget check, and at the human gate.

04 How it works

Six mechanics: simplest system first, tools as an interface, the loop, stopping, guardrails in code, and approval plus evaluation.

1

Start with the simplest system that works — workflow before agent

Ask who must decide the next step. If the steps are known in advance, build a workflow: prompt chaining, routing, parallelisation, orchestrator-workers, or evaluator-optimiser, all on predefined code paths. Reserve a free-running agent for open-ended work where the number and order of steps cannot be predicted — and accept its price: more latency, more cost, and compounding errors. Anthropic and OpenAI give the same advice: a single well-built agent (or one optimised LLM call) beats a premature multi-agent system almost every time.

2

Design tools as the agent-computer interface — the model only requests

The model never runs your code. It emits a tool name plus JSON arguments matching a schema you published; your runtime does everything else. So design tools like a UI for the model (Anthropic’s ACI): few, distinct, non-overlapping tools at natural task size; names and descriptions with examples and edge cases; argument formats the model cannot easily mangle (absolute paths, not relative ones); and return values that are concise and cite their source. Split OpenAI’s three kinds consciously: data tools that fetch, action tools that change state, and orchestration tools that call other agents.

3

Run the planning loop: think, act, observe — with ground truth each turn

Use ReAct as the default rhythm: a short thought, one tool call, then the observation appended to the transcript before the next thought, so reality corrects the plan instead of the plan hallucinating forward. For reviewable or parallelisable work, prefer plan-and-execute: write the full plan first (a human can inspect it), then execute step by step and replan only on failure. Make planning transparent — show the steps — because a loop you cannot read is a loop you cannot debug, grade, or trust.

4

Give the loop explicit stopping conditions, enforced before every step

Never let “the model stopped calling tools” be your only exit. Enforce, in code and before each iteration: a hard max_steps cap, a cost / token budget, and a wall-clock timeout; an explicit done signal (a final-answer output or a finish tool); loop detection (the same tool + same arguments repeating); and no-progress detection (steps adding no new information). On budget exhaustion, force a finalisation: answer from what the run has, or fail explicitly — never return silence, and never let a retry double-send a side effect (use idempotency keys).

5

Put guardrails in code, in layers — never only in the prompt

Layer them, as OpenAI’s guide prescribes: input guardrails (relevance, moderation, injection screening — tool results and web pages are data, never instructions), tool guardrails (validate arguments against the schema, authorise with the caller’s permissions — never the model’s assertion — and scope credentials per task, read-only by default, minutes-long), and output guardrails (schema, policy, and groundedness checks before anything reaches a user or another system). A guardrail that lives only in the system prompt is a suggestion an injected instruction can talk its way past.

6

Gate irreversible actions, checkpoint the run, and evaluate outcomes

Classify every tool as auto, approval-required, or never-automated — by reversibility and blast radius, in the runtime, not by the model. On a gated action, pause, persist the full state (messages, plan, budget, step), present the exact action and its preview, and resume on approve / edit / reject without re-running completed steps. Trace every model call, tool call, argument, result, token count, and timing, and grade the run on whether the task actually succeeded — an eval harness over real tasks, not on whether the final paragraph sounded confident.

05 Code sketch

A minimal owned loop: the model requests, code validates and authorises, budgets stop the run, and irreversible tools wait for a human.

def run_agent(goal, model, tools, *, max_steps=12, budget_usd=1.00):
    messages = [{"role": "user", "content": goal}]
    seen_calls = set()
    for step in range(max_steps):              # hard cap, checked every turn
        if spent(messages) > budget_usd:
            return finalize(messages, reason="budget")   # answer from what we have
        reply = model(messages, tool_schemas(tools))
        if not reply.tool_calls:
            return reply.text                       # explicit done: no tool requested
        for call in reply.tool_calls:
            key = (call.name, str(sorted(call.args.items())))
            if key in seen_calls:                  # loop detection
                result = {"error": "repeated call blocked; change approach"}
            else:
                seen_calls.add(key)
                tool = tools[call.name]
                validate(call.args, tool.schema)          # raises -> error result, not a crash
                authorize(tool, caller_perms)             # caller's rights, not the model's
                if tool.irreversible and not human_approved(call):
                    result = {"error": "awaiting human approval"}
                else:
                    result = tool.run(call.args, idempotency_key=key)
            messages.append(tool_result(call, result))    # observation = ground truth
    return finalize(messages, reason="max_steps")

06 Failure modes

Five ways agent systems fail in production — each with a one-line fix.

1

An agent where a workflow would doFix: if the steps are predictable, hard-code the path (chain, route, parallelise) and give the model only the step it is good at.

Building a free-running loop for a fixed three-step task buys 10× the cost, compounding error, and a debugging story nobody wants — for flexibility the task never uses. Complexity must be earned by the problem, not by the demo.

2

The god tool and the overlapping toolboxFix: split into few, distinct, schema-typed tools at natural task size, with examples in the description — and delete tools the evals never need.

One do_anything tool, or fifteen tools that half-overlap, leaves the model guessing which to call and inventing plausible arguments. Tool-selection errors look like reasoning errors but are interface errors — they are fixed in the ACI, not with a bigger model.

3

The runaway loopFix: enforce max steps, cost and time budgets before every iteration, detect repeated identical calls, and force a finalisation on exhaustion.

Without hard stops, a confused agent retries the same failing call forever, burns the budget, and — if a tool has side effects — repeats the damage. “It will figure it out eventually” is not a stopping condition.

4

Guardrails that live only in the promptFix: move every real limit into code — schema validation, caller-based authorisation, scoped credentials, and approval gates the model cannot bypass.

“Never refund over $500” in the system prompt fails the first time an injected web page, a jailbreak, or a confident hallucination argues otherwise. Instructions and data share one text channel; only the runtime sits outside it.

5

Flying blind: no trace, no eval, self-graded successFix: trace every step, checkpoint at gates, and grade runs on task outcomes in an eval harness — never on the agent’s own claim that it finished.

An agent that reports success in fluent prose while the tool call failed, the record never updated, or the wrong account was charged is worse than one that crashes loudly. Without traces you cannot find the bad step; without outcome evals you cannot tell a fix from a regression.

08 Sample prompts

Copy one into your AI assistant and apply it to your own work.

DESIGN AN AGENT SYSTEM

Design an agent system for this task: [task, tools available, what success looks like]. First argue honestly whether this should be an agent at all: if a fixed workflow (chaining, routing, parallelisation, orchestrator-workers, evaluator-optimiser) solves it, design that instead and say why. If an agent is justified, give me: (1) the tool list — few, distinct, schema-typed, split into data / action / orchestration, (2) the planning style (ReAct or plan-and-execute) and why, (3) stopping conditions in code: max steps, cost and time budgets, loop and no-progress detection, (4) guardrails per layer (input, tool, output) plus which actions need human approval, and (5) how we will eval the run on task outcomes. Flag any tool that is too broad to be safe.

AUDIT MY TOOL SURFACE

Audit this agent tool surface like an interface designer, not a fan: [paste tool names, descriptions, and schemas]. For each tool check: is it at natural task size or a god tool? Does it overlap another tool enough to confuse selection? Could the model mangle its argument format (relative paths, free-text dates, ambiguous IDs)? Does its return value waste context or hide errors? Is it read-only by default, and are its credentials scoped to this task? Rewrite the surface: rename, split, merge, or delete tools, and write model-ready descriptions with one example and one edge case each. Show the before / after tool count.

STRESS-TEST MY LOOP AND GUARDRAILS

Stress-test this agent design before I build it: [paste the loop, stopping conditions, guardrails, and approval gates]. Attack it in five passes: (1) runaway — how could it loop, retry, or spend without bound? (2) injection — a tool result or web page tells it to ignore its instructions; what, in code, stops that? (3) authority — can it perform any irreversible action with more privilege than the caller has? (4) duplicates — if a step is retried or a run resumes, can a side effect happen twice? (5) evidence — from the traces alone, could I prove what it did and grade whether the task succeeded? For each hole, give the smallest code-level fix, not a prompt edit.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

Agent
A system where the model dynamically directs its own process: it plans, requests tools, reads observations, and decides the next step and when to stop — inside budgets and guardrails your code enforces.
Workflow
LLMs and tools orchestrated through predefined code paths: chaining, routing, parallelisation, orchestrator-workers, evaluator-optimiser. Predictable — and the right answer whenever the steps are known in advance.
Tool call
A structured request the model emits — a tool name plus JSON arguments matching a published schema. The model never executes it; the runtime validates, authorises, runs it, and returns the result.
ACI (agent-computer interface)
Everything the model sees of its tools: names, descriptions, schemas, return formats, error messages. Anthropic’s point: design and test it as carefully as a human UI — most “reasoning” errors start here.
ReAct
Reasoning + Acting: thought, action (one tool call), observation, repeat. The observation is ground truth that corrects the next thought, instead of a long plan hallucinating forward unchecked.
Plan-and-execute
Write the full plan first, then execute it step by step, replanning only on failure. Easier for a human to review before anything real happens; less adaptive than interleaved ReAct when results keep surprising you.
Guardrail (in code)
A limit enforced by the runtime, not requested in a prompt: schema validation, caller-based authorisation, scoped credentials, budget checks, approval gates. Layered at input, tool, and output.
Least privilege
Give the agent only the tools, data, and credentials this task needs: read-only by default, per-task scoped tokens with short lifetimes, egress only to named hosts. What it cannot reach, it cannot be tricked into misusing.
Stopping condition
How a run ends on purpose: an explicit done signal, a max-steps cap, a cost / time budget, or loop / no-progress detection — with a forced finalisation that answers from what it has or fails explicitly.
Human-in-the-loop gate
A pause before an irreversible or high-blast-radius action: checkpoint the state, show the exact action and preview, resume on approve / edit / reject. The tool’s risk class — set in code — decides, not the model.

11 Reach for this when…

The steps depend on what you find — investigation, support, coding, and research tasks where step three cannot be written until step two answers. That mid-task decision is the agent loop’s signature; a fixed pipeline cannot make it.
A demo agent is heading for production — before it ships, move its limits into code: budgets, validation, least-privilege credentials, approval gates, traces, and outcome evals. If a safeguard is only a sentence in the prompt, it is not yet a safeguard.
You are choosing between frameworks and patterns — decide workflow vs agent, ReAct vs plan-and-execute, and single vs multi-agent from the task’s shape first. The framework is the last choice, and the simplest pattern that passes your evals wins.
