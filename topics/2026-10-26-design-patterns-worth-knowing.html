Design patterns worth knowing (and ones to skip)

You do not need all 23 Gang of Four patterns. You need a handful, learned deeply, and a habit: start from the pain, name what keeps changing, and pick the smallest structure that makes that change easy. A pattern is a named, reusable solution to a recurring design problem — not a library, not a badge of seniority, and never the starting point.

02 The one-idea version

A pattern is a name for a recurring shape of change: something varies, something stays stable, and the pattern draws the boundary between them. So the question is never “which pattern can I use here?” It is “what keeps changing, and what would make that change easy?” Answer that first, and the pattern — or the plain function that beats it — picks itself.

03 Start from the pain, not the pattern

The same decision, every time. If the plain version is not hurting yet, do not upgrade it.

04 How it works

Seven mechanics: six patterns worth knowing, and the discipline for skipping the rest.

1

Name what varies before you name a pattern

Patterns fall into three families: creational (how objects are made), structural (how objects are composed), and behavioral (how objects communicate). Classify the pain first — creation, composition, or communication — and you have already narrowed 23 patterns to a handful. If nothing is varying yet, you have no pattern problem; you have a working function.

2

Strategy: swap the algorithm, not the code

When a behavior has several variants — shipping rates, discount rules, pricing tiers — pull each variant behind one shared interface and inject the one you need. Adding a variant then means adding a class, not editing an if-chain in five places. In Python, a plain function often is the strategy; reach for a class only when the variant carries state or configuration.

3

Factory: hide the creation decision in one place

When callers should not know which concrete class they get — a payment provider by region, a parser by file type — put that decision in one factory function behind a shared interface. Callers depend on the interface, so a new variant lands in one place. A factory with no real decision to hide is just indirection: if there is only ever one class, construct it directly.

4

Observer: notify without coupling

When many things must react to one event — an order placed, a config changed — let the subject keep a list of listeners and call notify on each. The subject never learns who is listening, so inventory, email, and analytics can each subscribe independently. This is the same idea behind DOM events, message queues, and pub-sub; always provide an unsubscribe, or listeners leak.

5

Adapter and Facade: tame what you did not write

Adapter translates one interface into the one your code expects: every shipping vendor’s API becomes one ship() method. Facade simplifies a whole subsystem behind one friendly entry point: one checkout() call instead of five subsystem calls in the right order. Both keep foreign complexity at the border instead of letting it leak through your codebase.

6

Decorator and Builder: compose and construct cleanly

Decorator layers optional behavior by wrapping an object — caching, logging, auth around a service — without a subclass for every combination, and without editing the core. Each layer must call through to the wrapped object, or behavior silently vanishes. Builder replaces a 10-parameter constructor with a readable step-by-step build, so a complex object can be assembled in different configurations without a telescoping constructor.

7

Skip list: know the cost before you pay it

Singleton as a global is the classic trap: hidden dependencies, untestable code, state that survives tests. Prefer dependency injection — pass the instance in, and let the container manage one shared instance if you truly need one. Abstract Factory pays off only for families of related products. Visitor, Mediator, and Memento are powerful and rarely worth their indirection; Flyweight earns its complexity only when memory pressure is measured, not guessed.

05 Code sketch

Strategy + Factory in under 30 lines: a new shipping rule is a new class plus one factory entry — never an edit to checkout.

# Strategy: one interface, one class per algorithm
class Standard:
    def cost(self, weight): return 5 + 0.5 * weight
class Express:
    def cost(self, weight): return 15 + 1.5 * weight

# Factory: the creation decision lives in exactly one place
def shipping_for(name):
    return {"standard": Standard(), "express": Express()}[name]

# Checkout depends on the interface, never on a concrete class
def checkout(weight, method):
    return shipping_for(method).cost(weight)

assert checkout(10, "standard") == 10.0
assert checkout(10, "express") == 30.0
print("standard:", checkout(10, "standard"), "express:", checkout(10, "express"))

06 Failure modes

Five ways patterns go wrong, each with the fix.

!

Pattern-first designFix: write the plain version first; introduce the pattern only when the second variant, second vendor, or second rule actually arrives.

Starting from “let’s use Abstract Factory here” inverts the decision: the code now serves the pattern instead of the problem. YAGNI is the antidote — a pattern adopted before its pain is speculation with a class diagram.

!

Singleton as a global variable in a suitFix: inject the dependency through the constructor; let a DI container own the single instance, so tests can substitute a fake.

Global access hides dependencies, couples every caller to one implementation, and makes tests order-dependent because state survives between tests. A singleton is defensible only for a truly unique, stateless, process-local resource — and even then, injection is usually cleaner.

!

Observer leaks and surprise orderingFix: always provide unsubscribe, and never let listeners depend on notification order — order is an implementation detail, not a contract.

Forgotten subscriptions keep objects alive and fire handlers long after the listener is gone; listeners that assume they run first or last break silently when a new subscriber registers. Treat the listener list as a set, not a sequence.

!

Decorator stacks that swallow behaviorFix: every decorator must call through to the wrapped object; keep stacks shallow and name each layer by what it adds.

A decorator that forgets to delegate drops behavior silently — the worst kind of bug, because nothing errors. Deep stacks (logging around caching around auth around retry) also become unreadable; if you cannot name the stack in one sentence, flatten it.

!

Strategy classes for what a function could doFix: in Python, start with functions as strategies; promote to a class only when the variant carries state or needs configuration.

Not every pattern needs its textbook shape. First-class functions, closures, and dicts-of-functions are Strategy and Factory in miniature — less code, same boundary. A class per one-line algorithm is ceremony, not design.

08 Sample prompts

Copy-paste these into your AI assistant when a design decision is on the table.

NAME THE PAIN FIRST

Here is my code: [paste the code]. Do not suggest a design pattern yet. First tell me: what keeps changing (or is about to change) in this code, and is it creation, composition, or communication? Then name the smallest structure that makes that change easy — a plain function, a parameter, or a pattern — and why. If a pattern, name its cost too.

REFACTOR TO STRATEGY

This if-chain keeps growing every time we add a variant: [paste the code]. Refactor it to the Strategy pattern: one shared interface, one class (or function) per variant, and a factory that picks the variant. Show me exactly where a future variant would be added, and confirm no existing behavior changes.

AUDIT: PATTERN OR OVER-ENGINEERING?

Review this design for over-engineering: [paste the code or design]. For each pattern used, say: what pain does it actually solve today, what would break if I removed it, and what is the simpler alternative? Flag Singleton-as-global, factories with a single product, and abstractions with only one implementation. Give a verdict: keep, simplify, or remove — per pattern.

10 Flashcards

Strategy
Interchangeable algorithms behind one interface. Swap the object, not the code — a new variant is a new class, not an if-chain edit.
Factory
One place decides which concrete class to create, behind a shared interface. Callers never learn the concrete type. No real decision? No factory.
Observer
A subject notifies a list of listeners without knowing who they are. Always provide unsubscribe, and never depend on notification order.
Adapter
Translates one interface into the one your code expects. Keeps a foreign API’s quirks at the border instead of leaking them through your code.
Decorator
Layers behavior by wrapping an object: caching, logging, auth — without subclass explosion. Every layer must call through to the wrapped object.
Builder
Step-by-step construction of a complex object, replacing a telescoping constructor. Different configurations, one readable build.
Facade
One simple entry point over a whole subsystem. One checkout() call instead of five subsystem calls in the right order.
Singleton trap
One instance + global access = hidden dependencies and order-dependent tests. Prefer dependency injection; let a container own the single instance.
Three families
Creational: how objects are made. Structural: how objects are composed. Behavioral: how objects communicate. Classify the pain first.
Pattern-first smell
Choosing the pattern before the pain is over-engineering. Plain code first; the pattern earns its place when the second variant arrives.

11 Reach for this when…

An if-chain grows with every new variant — pull each variant behind one interface (Strategy) and let a factory pick it. New variants become additions, not edits.
A foreign API or a messy subsystem leaks into your code — put an Adapter or Facade at the border: one interface your code owns, quirks contained on the other side.
Someone proposes a pattern before naming the pain — stop and ask what keeps changing. If a function, a parameter, or a dict already makes that change easy, that is the design.
