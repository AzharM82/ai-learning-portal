Agent frameworks compared: LangGraph, Semantic Kernel, and the Microsoft Agent Framework

Every agent framework is a bet about control: who decides the next step — an explicit graph you drew, a kernel that lets the model pick plugins, or a unified agent-plus-workflow runtime? LangGraph, Semantic Kernel, and Microsoft Agent Framework make three different bets. Pick by workflow shape, ecosystem, and where your code must run in two years — not by demo speed.

02 The one-idea version

Frameworks differ first in their control model, not their model list. LangGraph makes control explicit: you define shared State, Nodes that do work, and Edges that decide what runs next. Semantic Kernel centers a Kernel holding services and plugins, with a different agent class per provider. Microsoft Agent Framework — described by Microsoft as the next generation of both Semantic Kernel and AutoGen — unifies that into one Agent type plus graph-based Workflows when the steps are known in advance.

04 How it works

Seven mechanics: one selection rule, the three frameworks in their own terms, and how to commit without regret.

1

Map the workflow before you name a framework

Microsoft Agent Framework’s own guidance is the cleanest test: use an agent when the task is open-ended or conversational and a single LLM call with tools may suffice; use a workflow when the process has well-defined steps, needs explicit execution order, or must coordinate several agents — and if a plain function handles the task, write the function instead of an agent. Sketch states, branches, loops, human approvals, and failure exits on paper first. That sketch, not a vendor chart, is your selection criteria.

2

LangGraph: define State, add Nodes and Edges, then compile

Per the LangChain Graph API docs, a graph is three things: State (a TypedDict or Pydantic schema shared by all steps, with a reducer per key deciding how updates merge — e.g. add_messages appends), Nodes (plain Python functions that receive state and return a partial update — an LLM call or ordinary code), and Edges (fixed transitions or conditional routers that inspect state). You compile() the StateGraph — which checks for orphaned nodes and attaches checkpointers and breakpoints — then invoke it. Nodes do the work; edges tell what to do next.

3

LangGraph in production: checkpointers, interrupts, and subgraphs

The graph model pays off operationally: a checkpointer persists state after each super-step keyed by thread_id, so runs pause, resume, and can be inspected; interrupt() pauses for a human and Command resumes with an approval or an edit; the Send API fans work out dynamically; and a node can itself be a compiled subgraph, so teams compose tested pieces. The cost is honesty: every branch you want must be drawn — there is no hidden planner to improvise a path you did not model.

4

Semantic Kernel: build a Kernel, register plugins, pick an agent class per service

Semantic Kernel’s center is the Kernel: a container for AI services and plugins — functions decorated [KernelFunction] / @kernel_function that the model can call. Its Agent Framework then gives you a different class per provider: ChatCompletionAgent for chat-completion services, OpenAIAssistantAgent, AzureAIAgent, and OpenAIResponsesAgent, each with its own thread type you create and manage. Multi-agent work is expressed as named orchestration patterns — Sequential, Concurrent, Handoff, Group Chat, and Magentic — each constructed and invoked through a shared pattern API.

5

Microsoft Agent Framework: one Agent type, sessions, and building blocks around it

Agent Framework collapses SK’s per-service classes into a single Agent / ChatClientAgent type over a unified model-client interface (Foundry, Azure OpenAI, OpenAI, Anthropic, Ollama, and more), in .NET, Python, and Go. State moves from manually-created threads to an AgentSession you create with agent.create_session(). Around the agent sit the composable blocks SK and AutoGen pioneered, now first-class: context providers for memory and RAG, middleware that intercepts runs, calls, and tool calls, built-in MCP clients, telemetry, and a batteries-included Harness agent for long multi-step tasks. Tools register directly at agent creation — no Kernel required.

6

Microsoft Agent Framework workflows: executors and edges when steps are known

When the path is defined, Agent Framework switches abstraction: a WorkflowBuilder connects executors (agents or functions) with edges, supports sequential, concurrent, group-chat, and handoff patterns, checkpointing, and human-in-the-loop — and any workflow can be wrapped with .as_agent() so callers use the same run API as for a single agent. That dual model is the real difference from SK: agent and workflow are peers in one runtime, not an agent framework with orchestration bolted on.

7

Choose on ecosystem and migration, then prove it with an eval slice

Decide the tie-breakers explicitly: LangGraph if you are Python/JS, provider-agnostic, and need fine-grained cyclic control plus mature checkpointing; Microsoft Agent Framework if you are on Azure / Foundry / .NET, want sessions, middleware, and telemetry built in, or are migrating from Semantic Kernel or AutoGen (Microsoft publishes a step-by-step SK→Agent Framework migration guide: namespaces, agent creation, sessions, tool registration); Semantic Kernel itself mainly to maintain existing systems while you plan that move. Whichever you pick, implement one real slice — one loop, one tool, one approval, one failure — in the finalist and grade it with your eval harness before committing the codebase.

05 Code sketch

The same triage idea in three dialects — notice what each one makes you name: state and edges, a kernel and an agent class, or just an agent and its session.

# --- LangGraph: state, nodes, edges, compile ---
from langgraph.graph import StateGraph, START, END, MessagesState
def triage(state): return {"route": "billing" if "refund" in state["messages"][-1].content else "support"}
g = StateGraph(MessagesState); g.add_node("triage", triage); g.add_node("act", act_node)
g.add_edge(START, "triage"); g.add_conditional_edges("triage", lambda s: s["route"]); g.add_edge("act", END)
app = g.compile(checkpointer=saver)  # resume / interrupt by thread_id

# --- Semantic Kernel: kernel + plugin, agent class per service ---
from semantic_kernel.agents import ChatCompletionAgent
sk_agent = ChatCompletionAgent(service=azure_service, kernel=kernel_with_plugins,
                               name="Triage", instructions="Route the request, then act.")

# --- Microsoft Agent Framework: one Agent type + session ---
from agent_framework import Agent
maf_agent = Agent(client=foundry_client, name="Triage",
                  instructions="Route the request, then act.", tools=[refund_tool])
session = await maf_agent.create_session()
result = await maf_agent.run("Where is my refund?", session=session)

06 Failure modes

Five ways framework choices go wrong — and the one-line fix for each.

1

Picking the framework from a demo, not from your workflow shapeFix: draw states, branches, approvals, and failure exits first; choose the framework whose native control model matches that drawing.

A chat demo makes every framework look identical — one prompt, one tool, one answer. Production exposes the difference: loops, retries, parallel fan-out, and human gates are either native (drawn edges, workflow executors) or hand-built scaffolding you now own forever.

2

The mega-node: a LangGraph graph with one node that does everythingFix: split by decision point — one node per step that can fail, branch, or be checkpointed independently.

Wrapping an entire prompt-chain inside a single node keeps the code but discards the framework: no conditional routing, no per-step checkpoint, no interrupt in the middle. If your graph has no meaningful edges, you did not need a graph — or you have not modeled the workflow yet.

3

Greenfielding on Semantic Kernel as if it were the destinationFix: for new Microsoft-stack work, start on Microsoft Agent Framework; reserve SK work for maintenance and a planned migration.

Microsoft states it plainly: Agent Framework is the direct successor to Semantic Kernel and AutoGen, built by the same teams, with a published migration guide. New features, the unified agent type, and graph workflows are landing there — an SK greenfield today is a migration project scheduled for tomorrow.

4

Confusing agent and workflow — in any frameworkFix: agent for open-ended work the model must plan; workflow / graph for defined steps that must execute in order; plain function if neither is needed.

Giving an autonomous agent a fixed compliance pipeline invites improvised step order; hard-coding a graph for an open-ended research task forces you to anticipate every branch. Both errors look like ‘the model is unreliable’ when the real fault is the abstraction choice.

5

Assuming provider portability you never testedFix: keep model clients behind the framework’s abstraction, avoid provider-specific message types in shared state, and smoke-test a second provider early.

All three frameworks claim multi-provider support, but hosted threads, service-side history, and tool formats differ — SK even encodes them in separate agent classes, and Agent Framework’s migration guide consolidates them precisely because they diverged. Portability is a tested property, not a logo grid.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

LangGraph State / Node / Edge
State is the shared schema (TypedDict or Pydantic, with a reducer per key). A Node is a function that reads state and returns a partial update. An Edge — fixed or conditional — decides which node runs next. Nodes do the work; edges tell what to do next.
Reducer (LangGraph)
The per-key function that merges a node's update into existing state: left argument = accumulated value, right = new update. Default replaces; add_messages appends and updates by message ID. Returning an empty list does not clear a merging field — use Overwrite.
Checkpointer / thread_id (LangGraph)
The persistence layer that saves graph state after each super-step under a thread_id. It is what makes pause, resume, human-in-the-loop interrupts, and inspection of past states possible — attach it at compile().
Kernel + plugin (Semantic Kernel)
The Kernel is SK's container for AI services and plugins. A plugin is a set of functions decorated [KernelFunction] / @kernel_function that the model can invoke. Every SK agent depends on a Kernel, even an empty one.
Per-service agent classes (SK)
SK ships a different agent class per provider — ChatCompletionAgent, OpenAIAssistantAgent, AzureAIAgent, OpenAIResponsesAgent — each with its own thread type. Microsoft Agent Framework consolidates these into one Agent / ChatClientAgent type.
Orchestration patterns
Named ways to coordinate agents: Sequential (pipeline), Concurrent (broadcast and collect), Handoff (control passes by context or rules), Group Chat (manager-coordinated conversation), and Magentic (generalist group collaboration, from Magentic-One). SK implements them as orchestrations; Agent Framework as workflows.
AgentSession (Microsoft Agent Framework)
Agent Framework's unit of conversation state, created with agent.create_session() — replacing SK's manually-created, provider-specific AgentThread types. Sessions carry multi-turn history, locally or service-side where the provider supports it.
Context provider (Agent Framework)
A composable component that supplies an agent with memory or retrieved information at run time — the framework's plug-in point for long-term memory and RAG, instead of hand-stuffing everything into the prompt.
Middleware (Agent Framework)
Hooks that intercept agent runs, chat completions, and tool calls to log, modify, guard, or measure behavior — SK's filters / telemetry ideas, made a first-class building block alongside MCP clients.
Agent vs workflow
Agent: open-ended or conversational work where the model plans and picks tools. Workflow: a defined process — fixed steps, explicit order, multiple executors — drawn as a graph. If a plain function does the job, use neither.

11 Reach for this when…

You are starting an agent project and the framework debate is blocking the design — draw the workflow (states, branches, approvals, crash points) first, then pick the framework whose native shape matches: graph, kernel, or agent + workflow.
You run Semantic Kernel or AutoGen in production — you are on a predecessor stack: read Microsoft’s migration guide, map threads to sessions and plugins to registered tools, and route new work to Microsoft Agent Framework.
Your agent needs loops, parallel fan-out, human interrupts, and resumable state you can inspect — that is explicit-graph territory: LangGraph’s StateGraph with checkpointers, or an Agent Framework workflow, drawn — not prompted.
