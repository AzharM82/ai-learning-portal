Analytics engineering: dbt, semantic layers, and metric definitions

Raw tables do not make a business metric. Analytics engineering is the discipline in between: model raw data in dbt with software-engineering discipline — layers, tests, lineage — then define each metric once in a semantic layer so every dashboard, API and AI agent returns the same number.

02 The one-idea version

Define the metric once, in code, and let machines generate the SQL. A metric like revenue is not a column or a dashboard formula — it is a governed definition (grain, filters, time dimension, aggregation) stored in git. dbt builds the tested tables underneath it; the semantic layer (MetricFlow) turns a request for ‘revenue by month by region’ into correct SQL from that one definition. Change the definition in one reviewed place, and every consumer moves together.

03 The picture: from raw tables to one governed metric

Transform in layers, test at every step, then stop letting consumers re-define metrics.

04 How it works

Seven mechanics: layered dbt models, tests as code, and a semantic layer on top.

1

Declare sources, never hardcode raw tables

Define every raw table once with source() in YAML, with owner, freshness and description. Models select from sources, not from raw_db.schema.table strings — so a source rename, a loading change, or a freshness alert lands in one place and lineage starts at the true origin.

2

Stage 1-to-1: rename, cast, clean — nothing else

Build one staging model per source table (stg_<source>__<table>). Rename to your conventions, cast types, convert cents to dollars — and stop. No joins, no filters that drop business rows, no aggregates. Staging is a cleaned mirror; all business logic lives downstream where it can be reused.

3

Use ref() everywhere and let the DAG order the build

Reference other models only with ref(). dbt builds the dependency DAG from those calls, runs models in the right order, swaps dev/prod schemas automatically, and draws lineage. A hardcoded relation breaks all four — and hides a dependency from tests and docs.

4

Layer into intermediate and marts at a declared grain

Intermediate models (int_) hold reusable joins and logic no BI tool should see. Marts are fct_ (one row per event/transaction, at a stated grain) and dim_ (one row per entity). Say the grain in the description and test it — grain drift is how revenue quietly doubles.

5

Test like software: generic, singular, and in CI

Attach unique, not_null, accepted_values and relationships tests in YAML, add singular SQL tests for business rules (a test passes when it returns zero rows), and run dbt build in CI on changed models plus their children. A red test blocks the merge, not the Monday dashboard.

6

Define the metric once in the semantic layer

On top of marts, define semantic models in YAML — entities (join keys), dimensions (slice/filter), measures (aggregations) — then define metrics (simple, ratio, cumulative, derived) on them. MetricFlow generates the SQL and the joins from entities, so Tableau, Sheets, an API and an AI agent all compute ‘revenue’ the same way.

7

Version, document, and review metrics like code

Models, tests, semantic models and metrics all live in git, change in pull requests, and ship with descriptions that become the docs site and lineage graph. A metric change is a product change: it needs an owner, a review, and a note on which dashboards and agents it will move.

05 Code sketch

A tiny CI guard in Python: a metric defined twice, or without a description, fails the build.

# audit_metrics.py — one definition, or it does not ship
import yaml, sys, pathlib
defs = {}
for f in pathlib.Path("models").rglob("*.yml"):
    doc = yaml.safe_load(f.read_text()) or {}
    for m in doc.get("metrics", []):
        name = m["name"]
        if name in defs:
            sys.exit(f"DUPLICATE metric {name}: {defs[name]} and {f}")
        if not m.get("description") or not m.get("label"):
            sys.exit(f"UNDOCUMENTED metric {name} in {f}")
        defs[name] = f
print(f"OK: {len(defs)} metrics, each defined exactly once")
# Run in CI next to `dbt build`: duplicate or undocumented
# metric definitions fail the pull request, not the board meeting.

06 Failure modes

Five ways analytics stacks quietly lose trust — each with a one-line fix.

!

Two dashboards, two revenuesFix: Each BI tool re-implements the metric in its own SQL/calculated field. Fix: define the metric once in MetricFlow and make every tool query the semantic layer.

!

Business logic buried in stagingFix: Joins and filters in stg_ models get copied, diverge, and cannot be reused safely. Fix: keep staging 1-to-1 and move logic to intermediate/marts.

!

Join fan-out inflates the metricFix: Joining a fact to a one-to-many table duplicates rows before aggregation. Fix: aggregate to the fact grain before joining, test grain uniqueness, and let MetricFlow entities choose join paths.

!

Renaming a column breaks five consumers silentlyFix: No tests, contracts or lineage on the mart. Fix: add column tests, document consumers in exposures, and run dbt build in CI before merge.

!

A metric with no owner, grain, or time dimensionFix: ‘Active users’ means three things and no one can say which. Fix: require owner, description, primary time dimension and filters in the metric YAML — no definition, no publish.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

Analytics engineering
Applying software-engineering practice — version control, tests, review, docs, CI — to the SQL that turns raw warehouse data into trusted models and metrics.
dbt model
One SQL SELECT in a file that dbt materializes as a view or table. Models reference sources with source() and other models with ref().
Staging / intermediate / marts
Staging: 1-to-1 cleaned mirror per source. Intermediate: reusable joins/logic, not exposed to BI. Marts: fct_ and dim_ tables analysts and dashboards query.
Grain
What one row represents — one order, one order line, one customer-day. State it, test it; most metric bugs are grain bugs.
Semantic layer
A governed layer where metrics are defined once (in dbt, via MetricFlow) and every BI tool, API and agent queries the same definition instead of re-writing SQL.
MetricFlow
dbt’s SQL-generation engine for the semantic layer: it reads semantic models and metric definitions in YAML and generates the correct joins and SQL per query.
Entity / dimension / measure
Entity: a join key. Dimension: a field to slice or filter by. Measure: a quantitative aggregation. Together they describe a semantic model.
Metric types
Simple (one measure), ratio (measure / measure), cumulative (running window), derived (expression over other metrics), conversion (event-to-event within a window).
dbt data test
A query that returns the rows breaking a rule — zero rows means pass. Generic: unique, not_null, accepted_values, relationships. Singular: custom SQL for a business rule.
Fan-out
When a one-to-many join duplicates fact rows before aggregation, inflating sums and counts. Prevent by aggregating to grain first and testing uniqueness.

11 Reach for this when…

Two reports disagree on the same metric — the definition lives in two tools; move it into the semantic layer and point both at it.
An AI agent or self-serve tool answers data questions — give it governed metrics to query, not raw tables to guess SQL over.
SQL transformations are copied between dashboards and notebooks — promote them into layered, tested dbt models with lineage.
