Caching strategies: layers and invalidation

Every repeated expensive read is a tax you choose to keep paying. A cache pays it once and serves the answer from memory — but a cached answer is a copy, and copies go stale. The whole discipline is one decision per entry: how stale may this be, and what forces it back to fresh?

02 The one-idea version

A cache is a bet that the future looks like the recent past: the same questions get asked again, so you store the answers where they’re cheapest to reach and accept that they’re copies. Speed comes from the copy being close; correctness comes from deciding, per entry, when the copy must die — by TTL, by invalidation, or by versioned keys. Every caching bug is a disagreement between the copy and the truth.

03 The request gauntlet

One request for /product/42, walking down through the layers. A hit anywhere short-circuits the walk and the answer comes straight back up; a full miss walks the whole gauntlet to the source of truth. The dashed red line is the expensive path — a stampede is thousands of requests walking it at once.

04 How it works

Seven mechanics. Pick the pattern per write path, and the TTL per data contract.

1

Cache-aside (lazy loading): the default

The application checks the cache; on a miss it queries the database and stores the result with a TTL. Simple, resilient — if the cache dies the app just reads the database (slow, not broken) — and it only ever caches data someone actually asked for.

2

Write-through vs write-behind: choose per write path

Write-through writes the cache and the database together: reads stay fresh, every write pays for two operations. Write-behind acknowledges the write on the cache alone and persists to the database later in batches: the fastest writes, but a crash before the flush can lose data the user was told was saved. Reserve it for counters and metrics you can afford to lose.

3

TTL is a staleness budget, not a vibe

Set it from the business rule — how stale may this be? Minutes for content pages, hours for rarely-changed settings, seconds (or don’t cache) for money and inventory at checkout. Every key gets a TTL: it is the safety net that bounds damage when an invalidation is missed.

4

Invalidate by key on the write path: delete, don’t overwrite

When a record changes, delete its cache key in the same code path as the write. Deleting can’t go wrong under concurrency; overwriting can — two writers can apply cache updates in the opposite order of their database commits, permanently caching the older value. The next read simply rebuilds from the truth.

5

Version and namespace your keys

A key like prod:v3:product:42 carries environment, schema version, entity, and id. Versioning makes deploys safe by construction — new code reads keys only it could have written — and a predictable format is what makes “delete every affected key” possible at all.

6

Layer from closest to farthest

Browser → CDN edge → app cache (Redis) → database. Each layer catches repeats before they reach the next one down. The HTTP layers are coordinated by headers — Cache-Control, ETag, s-maxage — not by application code.

7

Guard the hot path against stampedes

A hot key expiring means hundreds of requests miss at once and all run the same slow query. Collapse them with a per-key lock (singleflight) so one request rebuilds while the rest wait, jitter TTLs so keys never expire in lockstep, and cache brief “not found” results against penetration by bots.

05 Code sketch

Cache-aside with a TTL, per-key locks to collapse stampedes, and delete-on-write. About 25 lines, no dependencies.

import threading, time, random

class Cache:
    def __init__(self, ttl=300):
        self.ttl, self.store, self.locks = ttl, {}, {}
        self._guard = threading.Lock()

    def get(self, key, loader):
        now = time.monotonic()
        hit = self.store.get(key)
        if hit and hit[1] > now:      # fresh hit: serve the copy
            return hit[0]
        with self._guard:
            lock = self.locks.setdefault(key, threading.Lock())
        with lock:                     # one rebuild per key: no stampede
            hit = self.store.get(key)  # re-check; a waiter may have filled it
            if hit and hit[1] > now:
                return hit[0]
            value = loader()           # miss: pay for the expensive call
            jitter = random.uniform(0, self.ttl * 0.2)
            self.store[key] = (value, now + self.ttl + jitter)
            return value

    def invalidate(self, key):
        self.store.pop(key, None)      # delete, don't overwrite

06 Failure modes

Six ways caches bite, each with its one-line fix.

1

Cache stampede (thundering herd)Fix: per-key lock (singleflight) so one request rebuilds while the rest wait; jitter TTLs so keys never expire in lockstep.

A hot key expires and hundreds of requests miss at the same instant — all run the same slow query and stall the database.

2

Stale reads from TTL-only freshnessFix: delete the key on the write path. The TTL is the safety net, never the correctness plan.

The write path never invalidates, so an updated profile serves the old name until the TTL dies — minutes of visibly wrong data.

3

Hot keys melt one nodeFix: a small in-process cache with a seconds-long TTL in front of Redis; replicate the celebrity key.

One key takes most of the traffic and saturates its single cache node — sharding doesn’t help when every request wants the same key.

4

Cache penetrationFix: cache the “not found” result with a short TTL; a Bloom filter in front for very large key spaces.

Bots hammer IDs that don’t exist. Nothing is ever cached, so every request reaches the database — a miss that can’t be filled.

5

Old shapes poison new deploysFix: version the key namespace (v3:product:42) so new code only reads keys it wrote.

A deploy changes the serialized JSON; new code reads old entries and breaks. Versioned keys make deploys safe by construction.

6

Caching on vibesFix: track hit rate and p95 latency before and after. Under ~80% hit rate, the TTL or key strategy is wrong — or the data shouldn’t be cached.

A cache gets added, nobody measures, and it quietly adds complexity and stale-data risk for no visible gain.

10 Flashcards

Click or press Enter/Space to flip.

Cache-aside
App checks the cache; on a miss it reads the DB and fills the cache with a TTL. The default pattern — the app owns consistency, and a dead cache degrades to slow, not broken.
Read-through
The cache layer loads from the database itself on a miss — the app never talks to the DB. Same result as cache-aside, cleaner call sites, needs a supporting library.
Write-through
Every write updates the cache and the database together, synchronously. Reads almost always hit and stay fresh; every write pays for two operations.
Write-behind
Writes hit the cache, get acknowledged immediately, and persist to the DB later in batches. Fastest writes — but a crash before the flush can lose acknowledged data.
TTL
The staleness budget: how long a copy may live before it must die. Every key gets one; jitter it so cohorts of keys don’t expire in the same second.
Cache stampede
A hot key expires and hundreds of requests miss at once, all running the same slow query. Fix: per-key lock (singleflight) + jittered TTLs.
Cache penetration
Requests for IDs that don’t exist never get cached, so every one hits the DB. Fix: cache the “not found” briefly, or a Bloom filter for large key spaces.
Hot key
One key takes a huge share of traffic and saturates its single cache node. Fix: a small in-process cache with a seconds-long TTL in front of Redis; replicate the key.
Versioned keys
Key format like v3:product:42: deploys read a new namespace, so old shapes can never poison new code. Old entries expire untouched.
Cache-Control
HTTP headers (max-age, s-maxage, stale-while-revalidate, ETag) that tell browsers and CDNs how long to keep a copy — how the outer layers get invalidated without app code.

11 Reach for this when…

The same expensive query or endpoint runs hundreds of times a minute with mostly identical results, and the data tolerates being seconds or minutes old — cache-aside with a TTL sized to the staleness budget, and delete the key on the write path.
Database CPU or origin latency climbs under traffic while a few hot keys would serve most requests — add a Redis/app layer, watch the hit rate climb past ~80%, and keep measuring: the cache has to earn its complexity.
Static assets or full API responses travel the world on every request — CDN edge cache with Cache-Control/s-maxage, and version asset filenames so deploys never need an invalidation request.
