Observability for LLM apps: traces, token accounting

Your AI feature can fail while every dashboard stays green — a wrong answer is still a 200 OK. So stop debugging with a stopwatch: model every request as a trace (the whole play-by-play), break it into spans (each model call, tool call, retrieval), and record token counts on every span so cost is just multiplication. A log tells you the request finished. A trace tells you what the AI actually did.

02 The one-idea version

Traditional monitoring watches services; AI observability watches decisions. A single user request fans out to a chain of hidden steps — retrieval, model calls, tool calls — and the failure hides in one of them. A trace records that chain as nested spans, each stamped with its tokens, latency, model, and outcome; sum the tokens across spans and you have cost. If your agent can't be traced, it can't be trusted — and you can't bill it either.

03 One request, seen whole

This is what an agent run looks like as a trace: a waterfall of spans, each carrying its own tokens and time. The two chat spans dominate both.

04 How it works

Six mechanics. Together they turn "the AI did something" into an inspectable, billable, alertable system.

1

Model every request as a trace; every step as a span

A trace is the whole request, from the user message to the final answer. A span is one step inside it: an LLM call (chat {model}), a tool run (execute_tool {tool}), an agent invocation (invoke_agent), a retrieval. Each span records what went in, what came out, how long it took, and how many tokens it burned. That tree is the play-by-play.

2

Emit the standard gen_ai.* attributes

OpenTelemetry's GenAI semantic conventions are the shared vocabulary: gen_ai.operation.name (chat, execute_tool, embeddings), gen_ai.provider.name, gen_ai.request.model vs gen_ai.response.model, gen_ai.usage.input_tokens / output_tokens, gen_ai.response.finish_reasons, gen_ai.tool.name. Emit the standard names and any OTel-native backend — Phoenix, Langfuse, Jaeger, your existing APM — can render them without re-instrumentation.

3

Account for tokens at the span level — that is your cost ledger

Cost = ∑(input tokens × input price + output tokens × output price) per span, grouped by tenant, feature, or user. Keep a price table keyed by gen_ai.request.model and join it at query time, not at emission time — prices change and rewrites of history are a lie. Alert on spend per tenant per hour before the invoice does.

4

Leave prompt/completion capture off in production

Content attributes (gen_ai.input.messages, gen_ai.output.messages) are opt-in for a reason: turned on, your spans carry raw user input and model output, which for most products is regulated data. The token counts, model, and finish reasons give you the debugging signal without the content. Gate content capture behind sampling + redaction, never on by default.

5

Export through a collector; decide sampling and redaction there

Point your SDK at an OpenTelemetry Collector, not straight at the backend. The collector is where three policies live: tail-based sampling (keep 100% of error traces, a fraction of clean ones), redaction processors (strip prompt text before anything leaves your network), and attribute enrichment (add app.tenant.id once, centrally, instead of in every service).

6

Ask the four questions on a rolling window

The dashboard answers: is it slow (p99 latency per span type, not the average)? Is it expensive (tokens × price per tenant)? Is it failing (error rate per tool, per model)? And the one traditional monitoring never had — is it right? Feed sampled traces into your eval harness (LLM-as-judge or code graders) so quality joins cost and latency on the same screen.

05 Code sketch

Minimal OpenTelemetry instrumentation for one model call: the span carries the gen_ai.* attributes, the collector does the rest.

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter

trace.set_tracer_provider(TracerProvider())
trace.get_tracer_provider().add_span_processor(
    BatchSpanProcessor(OTLPSpanExporter(endpoint="http://collector:4317")))
tracer = trace.get_tracer("agent.runtime")

def chat(model, messages, step, tenant):
    # span name follows the spec: "{op} {model}"
    with tracer.start_as_current_span(f"chat {model}") as span:
        span.set_attribute("gen_ai.operation.name", "chat")
        span.set_attribute("gen_ai.provider.name", "openai")
        span.set_attribute("gen_ai.request.model", model)
        # ... call the model here ...
        resp = call_model(model, messages)
        span.set_attribute("gen_ai.response.model", resp.model)
        span.set_attribute("gen_ai.usage.input_tokens", resp.usage.prompt_tokens)
        span.set_attribute("gen_ai.usage.output_tokens", resp.usage.completion_tokens)
        span.set_attribute("gen_ai.response.finish_reasons", resp.finish_reason)
        # spec omits these — you own them
        span.set_attribute("agent.loop.iteration", step)
        span.set_attribute("app.tenant.id", tenant)
        return resp.text

06 Failure modes

Five ways observability silently lies to you — and the fix for each.

1

Attribute-name driftFix: pin the semconv version you target and assert attributes land on a live trace after every library upgrade.

Your instrumentation emits gen_ai.system; your dashboard queries gen_ai.provider.name (the current spec name). Nothing errors. Half your data is silently invisible until someone notices the provider facet is empty.

2

Streaming calls drop token counts on errorFix: count tokens from streamed chunks client-side, or log a partial-usage estimate, so failures aren't the one cost you can't see.

Usage attributes are recorded when the call completes. A streaming call that errors or is cancelled mid-stream records no tokens — so your cost dashboard undercounts exactly the failures you most want to inspect.

3

Orphaned child spansFix: propagate trace context through the agent loop explicitly, then verify one end-to-end trace shows nested spans before shipping.

Trace context isn't threaded through the planning loop, so execute_tool and retrieval spans detach from the parent chat span. The trace reads as unrelated fragments and you can't see which tool the model called, or in which iteration.

4

Sampling hides the incidentFix: tail-based sampling at the collector — keep 100% of error traces, sample clean ones — so you always review the runs that mattered.

Head sampling decides up front and keeps a fixed fraction of whole traces, so set it low and rare failures are dropped at the same rate as routine runs. You will review the wrong runs.

5

Prompt text in traces becomes a PII pipelineFix: content capture off by default; add a collector redaction processor and run evals on a separate access-controlled content path.

Turn on content capture once and your spans carry raw user input and model output to wherever your exporter points. Metadata (tokens, tool names, finish reasons) gives you the debugging signal without the content — redact the rest.

08 Sample prompts

Copy, adapt, and ask your coding assistant. Each one applies today's skill card.

PROMPT 1 · INSTRUMENT A CHAT CALL

My Python agent calls the OpenAI chat API in a loop with tool calls. Write minimal OpenTelemetry instrumentation following the current GenAI semantic conventions: one span per model call named "chat {model}" with gen_ai.operation.name, gen_ai.provider.name, gen_ai.request.model, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens, and gen_ai.response.finish_reasons. Add agent.loop.iteration and app.tenant.id as custom attributes. Export via OTLP to a collector. No prompt/completion content capture. Show the full runnable file, and list what I must verify on a live trace after installing it.

PROMPT 2 · TRACE REVIEW DEBRIEF

I am pasting one production trace of my agent as a span tree (span names, durations, token counts, tool names). Do three things: (1) identify which step dominates latency and which dominates token cost, (2) compute the "loop tax" — how much extra token spend comes from re-sending conversation history across steps, and (3) point out any span that smells like a stuck loop or a retry storm. Then recommend the single cheapest change that would cut this trace's cost in half, with reasoning.

PROMPT 3 · ALERT DESIGN

Design a minimal alerting scheme for my LLM app's observability pipeline. I emit OpenTelemetry traces with gen_ai.usage.input_tokens, gen_ai.usage.output_tokens, gen_ai.request.model, and app.tenant.id on every model span, exported to a collector. Define exactly four alerts: a per-tenant hourly token-budget alert, a tool error-rate alert, a p99 latency alert per span type, and a correctness-drop alert fed by sampled eval scores. For each: the query logic in words, sensible starting thresholds, who gets paged vs notified, and one failure mode that would make the alert fire falsely and how to prevent it.

10 Flashcards

Click or press Enter/Space to flip. Ten terms worth owning.

Trace
The full play-by-play of one request: a tree of spans from the user's input to the final answer.
Span
One step inside a trace — an LLM call, a tool call, a retrieval — stamped with input, output, latency, and tokens.
gen_ai.operation.name
The standard attribute naming the operation a span represents: chat, execute_tool, embeddings, invoke_agent.
gen_ai.provider.name
Which provider served the call (openai, anthropic, aws.bedrock). Replaces the older gen_ai.system — drift between them is a classic failure.
gen_ai.usage.input_tokens / output_tokens
Token counts per span. Multiplied by your price table, they are your cost ledger — the whole of token accounting.
Trace context propagation
How child spans link to their parent. Break it in the agent loop and you get orphaned fragments instead of one connected trace.
Head vs tail sampling
Head decides up front and can drop incidents; tail decides after the trace completes, keeping 100% of error traces.
Collector-side redaction
Strip prompt/completion text at the OpenTelemetry Collector so metadata survives while raw content never leaves your boundary.
agent.loop.iteration
A custom attribute the spec doesn't define but you need: which iteration of the agent loop a span belongs to. Without it, loops are invisible.
The token trap
Agents re-send the entire conversation on every step: a 10-step agent pays ~10× and a stuck loop can burn 50× normal cost with no error anywhere.

11 Reach for this when…

A user says "it gave the wrong answer." Open the trace: was the retrieval wrong, the tool wrong, or the model wrong? Stop guessing which stage failed.
The bill jumps but usage didn't. Sum tokens per span per tenant — find the loop tax, the retry storm, or the context duplication before the invoice lands.
You're shipping to production for the first time. Trace one feature end to end tonight, add the token-budget alert, and you've bought yourself the cheapest insurance an AI app has.
