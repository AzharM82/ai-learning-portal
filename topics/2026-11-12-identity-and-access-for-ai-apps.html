Identity and access for AI apps: OAuth, scoped tokens, and agent permissions

An AI agent that can read mail, send mail, move money, or call tools is only as safe as the credential it carries. Give it the user’s password or a long-lived master key and every prompt injection inherits the whole account. Give it a valet key instead — a short-lived OAuth token, consented to by the user, bound to one service, carrying only the scopes this task needs, checked on every call — and a compromised agent has a small, expiring, revocable blast radius.

02 The one-idea version

Never hand an agent the master key — hand it a valet key. OAuth is delegated authorization: the user consents on the authorization server’s own page (the agent never sees the password), and the agent receives an access token that names one audience, carries only named scopes, and expires soon. OpenID Connect answers who the user is; OAuth answers what this client may do — and your own code still decides, per tool and per record, whether this action by this user is allowed.

03 The picture: the valet key, end to end

One delegated grant for one task. The token is checked on every call, and a token minted for a different service is rejected — not forwarded.

04 How it works

Six mechanics: split identity from authorization, use the one safe flow, scope tightly, bind and validate every token, manage lifetimes, and enforce agent permission in code.

1

Separate “who” from “what” — OIDC for identity, OAuth for access

OAuth 2.0 is an authorization framework: its access token says what a client may do at a resource server, and its audience is that resource server. OpenID Connect adds the identity layer on top: the ID token proves who signed in, and its audience is your client app. Never send an ID token to an API, never treat an access token as proof of identity in your UI, and never let an agent “log in as the user” — it acts on behalf of the user, with the user’s sub carried in the token it presents.

2

Use Authorization Code + PKCE for every client — no exceptions for agents

Run the authorization code flow with PKCE (S256) for web, mobile, SPA, CLI, and agent clients alike. PKCE binds the code exchange to the client that started the flow, so an intercepted code is useless. The implicit grant and the password grant are deprecated — removed in OAuth 2.1 and called out in RFC 9700, the OAuth Security Best Current Practice. Add state (and nonce in OIDC) against CSRF and mix-up, validate the iss in the authorization response (RFC 9207), and match redirect URIs exactly.

3

Design scopes as least-privilege, and step up instead of hoarding

Name scopes resource.operation and split reads from writes: mail.read is not mail.send, and neither is *.ReadWrite.All. Request only the scopes the current operation needs — Microsoft’s guidance is explicit: developers should always abide by the principle of least privilege. When a call comes back 403 insufficient_scope, run a step-up authorization for just the extra scope instead of requesting everything up front. For MCP servers, take the scopes from the 401 WWW-Authenticate challenge first; that challenge set is authoritative for the operation.

4

Bind every token to one audience, and validate it on every request

A token is minted for one resource server. The client names it with the RFC 8707 resource parameter on both the authorization and token requests (in MCP, the server’s canonical URI); the resource server then verifies, on every request: signature against the issuer’s JWKS, iss, aud (must be itself), exp, and the scope the operation requires. The MCP specification states the hard rule plainly: servers must only accept tokens issued for their own resources and must not accept or transit any other tokens — forwarding a received token upstream is the token-passthrough anti-pattern.

5

Keep lifetimes short, refresh safely, and keep tokens out of the model’s sight

Access tokens live minutes to about an hour; refresh tokens are the long-lived secret, so rotate them on every use, detect reuse (a replayed old refresh token means theft — revoke the family), and sender-constrain high-value tokens with DPoP (RFC 9449) or mTLS (RFC 8705) so a leaked token is useless without the client’s key. Store tokens server-side or in a backend-for-frontend vault — never in localStorage, URLs, logs, or the model’s context. The agent asks for a tool call; your harness attaches the token outside the prompt, so the token never becomes text the model can leak or be tricked into repeating.

6

Enforce agent permission in your own code — per tool, per record, per action

Scopes are client-level and coarse; they do not say whether this user may touch this record. Behind the token check, enforce a second layer: an allowlist of tools per agent and per task, an ownership / policy check on every object (token sub must own the resource it acts on), and a human approval gate for irreversible or high-blast-radius actions (send, pay, delete, publish). Watch for the confused deputy: an agent holding its own privileged service credential must not spend that privilege on a user request — use on-behalf-of / token exchange so downstream calls keep the user’s identity and limits. Log sub, client, scope, tool, and outcome for every call, and make each agent’s grant independently revocable.

05 Code sketch

A resource server’s tool gate in Python: validate the token properly first, then check scope, then check ownership — three distinct decisions.

import jwt
from jwt import PyJWKClient

JWKS = PyJWKClient("https://login.example.com/.well-known/jwks.json")
ISSUER = "https://login.example.com/"
AUDIENCE = "https://api.example.com"  # this server only (RFC 8707)

def require_scope(token: str, needed: str) -> dict:
    claims = jwt.decode(
        token, JWKS.get_signing_key_from_jwt(token).key,
        algorithms=["RS256"], audience=AUDIENCE, issuer=ISSUER,
    )  # raises on bad signature, wrong iss/aud, or expiry
    granted = set(claims.get("scope", "").split())
    if needed not in granted:
        raise PermissionError("403 insufficient_scope: step up")
    return claims

# Tool handler: scope check first, ownership check second,
# human approval before anything irreversible actually sends.
def send_mail_tool(token: str, draft: dict, approved: bool) -> str:
    claims = require_scope(token, "mail.send")
    assert claims["sub"] == draft["owner_id"]  # act only for the owner
    if not approved:
        return "held for human approval"
    return mail_api.send(as_user=claims["sub"], **draft)

06 Failure modes

Five ways identity and access fail in AI apps — each with a one-line fix.

1

The master-key agentFix: per-user OAuth grants — short-lived, scoped tokens issued after consent, revocable per user and per agent.

The agent runs on one long-lived API key, a shared service password, or the user’s own credentials pasted into a config file. It works in the demo, and then any prompt injection, log leak, or rogue tool call inherits the entire account, for every user, forever.

2

Token passthrough and the confused deputyFix: validate audience and never transit a received token; use on-behalf-of / token exchange so downstream calls carry the user’s identity and limits.

Your MCP server or agent forwards the token it received to an upstream API, or quietly uses its own broader service credential to fulfil a user’s request. Either way the downstream service can no longer tell who really authorized the call — and a token stolen in one place becomes a key everywhere.

3

Scope hoardingFix: request the minimal scope per operation and step up on 403 insufficient_scope instead of pre-collecting broad grants.

The app requests .default, Mail.ReadWrite, and admin-flavoured scopes at first sign-in “to avoid friction later.” Consent screens get scarier, admins refuse the app, and when the token leaks the attacker inherits permissions the feature never used.

4

Wrong token, no validationFix: verify signature, iss, aud, exp, and required scope on every request — and reject ID tokens at APIs outright.

The API accepts an ID token (audience: some other client), skips audience checking, or trusts a token because it “looks like a JWT.” Any token from any app in the tenant — or from a lookalike issuer — now opens your endpoints.

5

Tokens where the model can see themFix: hold tokens in a server-side vault / BFF, attach them in the harness outside the prompt, send them header-only, and redact them from logs and traces.

Access and refresh tokens end up in prompts, tool results, browser localStorage, query strings, and debug logs. Anything in the context window can be exfiltrated by injection, and anything in a log tends to live forever — the token’s short expiry stops mattering once the refresh token leaks with it.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

OAuth 2.0
A delegated authorization framework: a client obtains limited access to a resource on a user’s behalf — after the user consents at the authorization server — without ever handling the user’s password. Its output is an access token.
OpenID Connect (OIDC)
The identity layer on top of OAuth 2.0. It adds the ID token — audience: your client — so the app can verify who signed in. OAuth alone never tells the app who the user is.
Access token vs ID token
Access token: for the resource server (API), carries scopes, checked on every call. ID token: for the client, proves identity at sign-in. Sending an ID token to an API — or reading identity off an access token — mixes up the two audiences.
Scope
A named permission string the client requests and the user (or admin) consents to, e.g. mail.read vs mail.send. Scopes slice a resource’s functionality into least-privilege chunks; the resource server enforces them per operation.
PKCE
Proof Key for Code Exchange (RFC 7636, pronounced “pixy”): the client sends a hash of a secret (code_challenge) with the authorization request and the secret itself (code_verifier) at redemption — so a stolen code is worthless. Mandatory, S256, for MCP clients and best practice everywhere.
Audience & resource indicator
Every token is minted for one audience (aud). RFC 8707’s resource parameter lets the client name that target — in MCP, the server’s canonical URI — on both authorize and token requests. The server rejects tokens whose aud is not itself.
Refresh token rotation
Each use of a refresh token returns a new one and invalidates the old. If an old token is ever replayed, someone has a copy — revoke the whole token family. Rotation (or DPoP / mTLS sender-constraining) is what makes long-lived refresh tokens survivable.
Step-up authorization
Start with minimal scopes; when a call returns 403 insufficient_scope, run a fresh consent for just the extra scope that operation needs. It replaces up-front scope hoarding — in MCP, the 401 challenge’s scope parameter tells the client what to ask for.
Token passthrough / confused deputy
Two faces of one bug: a server forwards a token it received to an upstream service (passthrough), or a privileged agent spends its own credential on a user’s behalf (confused deputy). Both destroy attribution — validate audience, never transit, exchange on-behalf-of instead.
Sender-constrained token (DPoP)
A token cryptographically bound to a key the client holds (DPoP, RFC 9449; or a certificate via mTLS, RFC 8705). A stolen token alone no longer works — the thief also needs the private key. The upgrade path when plain bearer tokens are too replayable.

11 Reach for this when…

Your AI app touches a user’s data in another service — mail, calendar, files, CRM, code. The moment the app acts on behalf of a person, it needs delegated, consented, scoped access — not a shared API key and never the user’s password.
Your agent can write, send, pay, or delete — read-only mistakes are embarrassing; write mistakes are incidents. Split read and write scopes, put irreversible tools behind per-record checks and a human approval gate, and make the grant revocable per agent.
You expose an API or MCP server to clients you do not control — third-party agents will present tokens. Publish Protected Resource Metadata, require PKCE and audience-bound tokens, validate on every call, and never pass a received token through to your own upstreams.
