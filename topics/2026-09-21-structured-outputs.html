Structured outputs: JSON mode, grammars, and validation

The moment a model's answer feeds your code, free prose becomes a bug. The fix is a schema-shaped hole cut into the decoder: your JSON schema is compiled to a grammar, and at every generation step the tokens that would violate it are masked out before sampling. The output is schema-valid by construction — no regex, no retry loop, no json.loads() crash at 2 AM.

02 The one-idea version

Structured output is constrained decoding, not better prompting. Your JSON schema is compiled into a grammar that predicts which tokens are legal next; the sampler is only allowed to pick from those. JSON mode guarantees valid JSON; structured outputs guarantee your schema. But a schema controls the shape, never the truth — hallucinations just arrive in valid JSON.

04 How it works

Seven mechanics: what each level buys you, how the mask works, and the three-line schema discipline that makes it strict.

1

Know the three reliability levels — and what each one promises

Prompt-only ("return JSON only") works sometimes and fails often. JSON mode (response_format: json_object) guarantees syntactically valid JSON but no schema: keys can be missing, types can be wrong, enums can be invented. Structured outputs guarantee your declared schema. When a downstream tool, DB column, or UI expects exact fields, only level 3 is production.

2

Constrained decoding masks invalid tokens before sampling — the shape becomes unbreakable

Your JSON schema is compiled into a grammar (a finite-state machine over the token vocabulary). At each generation step, the engine computes which next tokens the grammar allows and zeroes out (logit → −∞) all the rest. If the schema expects a number, tokens that would start a string or object are simply never sampled. The invalid output is never generated, not corrected afterward.

3

Turn on strict with three schema rules: strict, required, no extra keys

For hard guarantees on OpenAI: strict: true, list every expected key in required, and set additionalProperties: false so the model can't smuggle in a surprise "confidence": 0.98 your API will reject. Note: the first request with a new schema pays extra latency while the API compiles it — subsequent identical requests don't.

4

Write schemas as code, not JSON: Pydantic models → schema, then parse the reply back into them

Never hand-write raw JSON Schema if your SDK can do it: define a BaseModel, let .model_json_schema() generate the schema, and call .parse() / responses.parse() so the validated, typed object comes back — event = response.output_parsed. Type hints, defaults, and docstrings become the contract, and your editor and tests can see them too.

5

Open models get the same guarantee from grammar libraries: XGrammar, Outlines, Guidance

Constrained decoding isn't a closed-API trick. Libraries like XGrammar (used inside vLLM and SGLang), Outlines, and Guidance compile your JSON schema or regex/CFG grammar into a token mask for open engines. Same idea as the diagram: the mask is rebuilt per step, the model can only emit legal tokens — on your own GPU, no API required.

6

Design schemas the model can actually satisfy: clear names, descriptions, enums for closed sets

Name keys clearly, put plain-language descriptions on important fields, and use enum for anything with a fixed set of values — a unit enum of celsius/fahrenheit beats hoping the model won't invent kelvin. Keep schemas as small as the consumer needs; giant schemas raise the chance of a refused or truncated generation.

7

Validate on your side anyway — and handle refusals and truncation as separate cases

Constrained decoding guarantees structure, but a safety refusal won't follow your schema (OpenAI returns a refusal field instead), and a max-tokens cutoff leaves the JSON half-written. Both are detectable programmatically — branch on them explicitly instead of treating every odd response as a "schema failure". Belt, suspenders, and a label for each kind of tear.

05 Code sketch

The whole pattern in 24 lines: schema as a Pydantic model, one parse call, a typed object back. No json.loads, no regex.

from pydantic import BaseModel, Field
from enum import Enum
from openai import OpenAI

client = OpenAI()

class Unit(str, Enum):          # closed set → enum, not hope
    celsius = "celsius"
    fahrenheit = "fahrenheit"

class Weather(BaseModel):
    city: str
    temp: float = Field(description="current temperature")
    unit: Unit                        # unrepresentable states stay unrepresented

resp = client.responses.parse(        # schema comes from Weather
    model="gpt-4o-mini",
    input="Weather in Paris in Celsius",
    text_format=Weather,
)
weather = resp.output_parsed          # typed Weather object — no json.loads
print(weather.city, weather.temp, weather.unit.value)

06 Failure modes

Named pitfalls, each with a one-line fix. Every one of them is a shape problem disguised as a model problem.

✕

JSON mode trusted like a schema Fix: reach for strict structured outputs whenever code consumes the answer — JSON mode only promises valid JSON, never your fields.

{"type": "json_object"} happily returns {"weather": "nice"} when you needed {"city": ..., "temp": ...}. The failure shows up three layers downstream as a KeyError, not at the call site.

✕

"Optional" fields that strict mode won't allow Fix: strict schemas require all keys in required — model optionality with a union against null (["type", "null"]) instead of omitting the key.

In strict mode every key must be declared and required, so "may be absent" has to become "may be null". Designing this after the schema is wired in means rewriting every consumer.

✕

Refusals and truncation treated as schema failures Fix: check the refusal field and the incomplete/max-tokens status explicitly — they're separate outcomes with separate handling (show the refusal, retry with more tokens).

A safety refusal doesn't follow your schema by design, and a max-tokens cutoff leaves JSON half-written. Lumping both into "the schema broke" hides the real cause and the real fix.

✕

Schema-valid but factually wrong output trusted blindly Fix: schema guarantees shape, never truth — validate values (ranges, enums, cross-checks), and gate anything consequential with evals or a second source.

{"price": 999999.99} passes every schema check. Constrained decoding keeps hallucinations inside the schema; it does not remove them. Structure is a channel, not a fact-checker.

✕

Exotic schema features silently unsupported Fix: stay inside the supported schema subset (objects, arrays, enums, simple types) and keep schemas small — check the provider's supported-schemas list before shipping the clever combinators.

Recursive types, complex oneOf/anyOf webs, and heavy regex patterns may be rejected or degraded by the grammar compiler. The fancier the schema, the earlier you should test it against the real API.

10 Flashcards

Click a card — or tab to it and press Enter — to flip it.

Structured outputs
Model responses constrained to adhere to your declared JSON schema — by construction, via constrained decoding. The evolution of JSON mode.
JSON mode
response_format: json_object — guarantees syntactically valid JSON, but NOT your schema: keys, types, and enums can all be wrong. Never trust it where code consumes the answer.
Constrained decoding
The mechanism under structured outputs: your schema compiles to a grammar, and at each generation step tokens that would violate it are masked out before sampling. Invalid output is never generated.
Token mask
The per-step allow-list of tokens the grammar permits next; everything else has its logits zeroed. Rebuilt at every generation step as the parse state advances.
strict: true
The flag that turns schema adherence into a hard guarantee. Pairs with every key in required and additionalProperties: false — the three rules of a fully-closed schema.
additionalProperties: false
Blocks the model from emitting keys not in your schema — like a surprise "confidence": 0.98 that a downstream API would reject. No smuggled fields.
The Pydantic pattern
Define the schema as a BaseModel, let .model_json_schema() generate it, and parse the reply back into a typed object (responses.parse → output_parsed). Never hand-write raw JSON Schema, never json.loads model output.
XGrammar / Outlines
Constrained-decoding libraries for open models: they compile your JSON schema or grammar into a token mask inside vLLM, SGLang, or your own loop. Same guarantee as closed APIs, on your own GPU.
Refusal
A safety-based refusal does not follow your schema by design — OpenAI reports it in a separate refusal field. Handle it as its own outcome (show it in the UI), not as a schema failure.
Shape vs truth
Structured outputs guarantee the SHAPE of the answer, never its factual correctness. {"price": 999999.99} is schema-valid and completely wrong. Validate values, not just structure.

11 Reach for this when…

Model output feeds code, a tool, a database, or a UI — extraction, classification, form filling, generative UI. Anywhere a missing key or wrong type is a production bug, not a cosmetic one.
You're retrying or regex-parsing LLM output today — json.loads crashes, missing keys, invented enum values. Structured outputs delete that whole validation-and-retry layer by making the shape unbreakable.
Agents hand outputs to other agents — one agent's free text is the next agent's unparseable input. A shared schema at every handoff keeps multi-agent pipelines from breaking in production.
