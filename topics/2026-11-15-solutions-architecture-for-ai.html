Solutions architecture for AI: patterns, trade-offs, and reference designs

A demo proves a model can answer. A reference architecture proves a system can answer safely, reliably, and affordably for everyone, every day — with identity, grounding, guardrails, evaluation, and fallbacks designed in from the start, not bolted on after the first incident.

02 The one-idea version

Solutions architecture for AI is trade-off design under uncertainty: the model is one replaceable component inside a system you control. Rank the quality attributes first (quality, latency, cost, safety, reliability), pick a pattern whose failure modes you can contain, and keep every consequential decision — routing, retrieval, tool use, price — in code and configuration around the model. If you cannot draw the gateway, the grounding source, the guardrail, the eval, and the fallback on one page, you do not have an architecture yet.

03 The picture: a reference design in five layers

Every production AI design, on any cloud, answers the same five questions in order.

04 How it works

Six mechanics: rank attributes, pick the simplest pattern, gateway everything, ground it, guard it, and design for failure.

1

Start from quality attributes, constraints, and the workload class — not from a model

Write the ranked list before any diagram: target quality (eval score), p95 latency, cost per successful task, data residency, safety risk, and availability. Then classify the workload — chat/RAG, document processing, prediction, or agent — because each class has a different reference design. AWS frames this as scoping first in its Generative AI Lens (6 lifecycle phases from scoping to iterating); Google's AI/ML perspective does the same across operational excellence, security, reliability, cost, and performance. A design without ranked attributes cannot be reviewed — every trade-off looks equally good.

2

Choose the simplest pattern that can meet the bar: prompt → RAG → workflow → agent

Escalate only on evidence. Prompting fixes format and behaviour the model already has. RAG supplies fresh, citable facts. A deterministic workflow (your code decides the next step) handles known sequences reliably. An agent (the model decides the next step) earns its cost and risk only when the path truly cannot be enumerated. Record the pattern, why the simpler ones failed an eval, and the exit criterion — patterns are reversible decisions, not identities.

3

Put a gateway in front of every model: one front door for policy, routing, and budgets

Never let product code call a provider directly. The gateway enforces identity and least-privilege scopes, routes by task difficulty to the cheapest model that passes evals, applies timeouts, bounded retries and circuit breakers, caps spend per user/tenant, and logs tokens and latency in one place. Azure's guidance explicitly covers using a gateway in front of Foundry and other models for custom auth and advanced monitoring; the same box is what makes a provider swap a config change instead of a rewrite.

4

Design grounding and data architecture as part of the AI architecture

Separate offline ingestion (extract, chunk, embed, index with ACL fields) from online retrieval (rewrite, hybrid search, rerank, security-trim to the caller's permissions). Version the corpus, stamp freshness, and require citations to retrieved sources for factual answers. Treat prompts, indexes, and datasets as versioned artifacts alongside code and models — Google's perspective stresses version control for code, models, and data together, because a silent index change is a behaviour change.

5

Make guardrails, evaluation, and human gates architectural — not prompt text

Place input and output checks in code around the model: content safety, prompt-injection screening on retrieved content, schema validation, and groundedness checks. Gate consequential tool actions behind approval by reversibility and blast radius. Before launch, require an eval suite (golden tasks, code graders, a calibrated judge) and in production sample live traffic into that suite. A guardrail that lives only in the system prompt is a suggestion, not a control.

6

Design for failure, cost, and change from day one

Assume the model times out, throttles, drifts, and gets deprecated. Give every request a deadline budget, isolate dependencies with bulkheads, degrade gracefully (cached answer, smaller model, human handoff), and make retries idempotent. Price the design per successful task — tokens in/out, retrieval, retries, and eval sampling — and set alerts on cost and quality drift, not just errors. Pin model versions, test the successor against your evals before promotion, and keep a rollback path.

05 Code sketch

A gateway-shaped call: route, ground, generate, validate — with a budget and a fallback.

def answer(request, user):
    budget = Deadline(seconds=20)               # one budget for the whole request
    route = router.pick(task=request.kind,       # cheapest model that passes evals
                        quality_bar=0.85)
    chunks = retrieve(request.query,             # hybrid search, ACL-trimmed
                      acl=user.permissions, top_k=6, deadline=budget)
    if not chunks:
        return escalate_to_human(request)        # no grounding, no guessing
    draft = route.model.generate(
        prompt=build_prompt(request, chunks), timeout=budget.remaining())
    checked = validate(draft, schema=Answer, sources=chunks)
    return checked if checked.ok else fallback_cached_or_human(request)

06 Failure modes

Five ways AI architectures fail — each with a one-line fix.

1

Model-first designFix: start from ranked quality attributes and the workload class; choose the model last, inside the gateway, against evals.

The team picks the biggest model, builds around its quirks, then discovers latency, cost per task, and data-residency needs it cannot meet. Every later decision is a workaround for the first one.

2

Agent by defaultFix: use a deterministic workflow until an eval proves the path cannot be enumerated; add agency one bounded step at a time.

An autonomous loop where a fixed pipeline would do multiplies token cost (multi-agent work is measured at many times chat cost), hides who decided what, and fails in ways a flowchart never would.

3

Direct provider calls scattered through the codebaseFix: force all model traffic through one gateway with routing, budgets, timeouts, breakers, and token logging.

Each feature invents its own retry, timeout, and key handling. A provider outage, price change, or deprecation becomes a repo-wide hunt instead of one config change.

4

RAG without permission trimming or freshnessFix: store ACLs on chunks, filter at retrieval time to the caller, version the index, and show citations and age.

The assistant happily summarises documents the user may not see, or answers from a stale index with total confidence. Grounding without governance is a leak with citations.

5

No eval gate — the demo was the testFix: require a golden-set eval in CI and sampled production evals; block promotion when quality, cost, or safety regresses.

A prompt tweak, model upgrade, or index refresh silently degrades real answers. Without a suite, you learn about it from users, one complaint at a time.

08 Sample prompts

Copy one into your AI assistant and apply it to your own work.

DRAFT A REFERENCE ARCHITECTURE

Draft a reference architecture for this AI use case: [describe users, task, data sources, latency and volume]. Give me: (1) ranked quality attributes with numeric targets (quality, p95 latency, cost per successful task, safety, availability), (2) the workload class and the simplest pattern that fits (prompt, RAG, workflow, or agent) with why simpler patterns fail, (3) a one-page layer diagram in text — gateway, orchestration, grounding, model, guardrails, observability — with the contract between each layer, (4) the three biggest trade-offs and which side we take and why, and (5) the eval and fallback plan. Flag every assumption.

REVIEW MY DESIGN LIKE A WELL-ARCHITECTED REVIEW

Review this AI architecture as a Well-Architected review: [paste design]. Score it pillar by pillar — operational excellence, security, reliability, performance, cost, sustainability — and for each give: the top risk, the evidence in my design, and the smallest fix that removes it. Then list: any direct model calls bypassing a gateway, any retrieval without permission trimming, any consequential action without a human gate or idempotency, and any place with no eval, no deadline budget, or no fallback. End with the five changes you would make before launch, in order.

PRICE AND STRESS THE DESIGN

Price and stress this AI design: [paste architecture, expected requests/day, average prompt and retrieval sizes]. Give me: (1) cost per successful task broken down by model tokens, retrieval, retries, and eval sampling, at current and 10x volume, (2) a latency budget table — gateway, retrieval, model, validation — that sums to the p95 target, (3) the failure rehearsal: model throttling, slow retrieval, bad index deploy, model deprecation — detection signal and degraded behaviour for each, and (4) which single component you would simplify first to cut cost or risk, and what we lose by simplifying it.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

Reference architecture
A proven, production-shaped design for a workload class — components, contracts, and cross-cutting controls included — that you adapt, not invent from scratch. Example: Azure's baseline Foundry chat architecture.
Quality attributes
The ranked non-functional targets a design must meet: quality, latency, cost per task, safety, reliability, residency. Ranking them is what makes trade-offs reviewable.
Pattern escalation ladder
Prompt → RAG → deterministic workflow → agent. Move up only when an eval proves the simpler pattern cannot meet the bar; each step adds cost, risk, and opacity.
LLM gateway
The single front door for model traffic: identity and policy, routing, budgets, timeouts, retries, circuit breakers, and token/latency logging. Provider swaps become config changes.
Grounding
Supplying the model with retrieved, citable facts at query time — with permission trimming and freshness stamps — instead of relying on what it memorised in training.
Bulkhead / circuit breaker
Reliability patterns from the video: bulkheads isolate a dependency so it cannot consume all capacity; breakers stop calling an unhealthy dependency so the system degrades instead of cascading.
Eval gate
A launch and promotion rule: no prompt, model, or index change ships unless the golden-set eval holds quality, cost, and safety. Demos do not gate; suites do.
Cost per successful task
The unit economics of an AI feature: all tokens, retrieval, retries, and eval sampling divided by tasks that actually succeeded — the number to optimise, not cost per call.
Well-Architected lens
A cloud's structured review for a workload type: AWS GenAI Lens (6 pillars × 6 phases), Azure reference architectures, Google AI/ML perspective. Use one as your design checklist.

11 Reach for this when…

A demo works and someone says 'ship it' — run the reference-design check: gateway, grounding with permissions, guardrails in code, eval gate, deadline and fallback. Whatever is missing is the launch plan.
Two smart people argue model A vs model B — park the argument, rank the quality attributes, and let an eval behind a gateway decide. If swapping models would take more than a config change, fix that first.
A design review has boxes but no trade-offs — ask for the ranked attributes, the pattern-ladder justification, the cost per successful task, and the failure rehearsal. Architecture is the trade-offs, documented.
