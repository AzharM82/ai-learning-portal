API design: contracts that survive contact with clients

Code you can refactor on a Tuesday; a contract you will be living with in five years, because somebody else’s software already depends on it. API design is therefore contract design: shape, semantics, representation, and change — decided in that order, because that is the order of how expensive a mistake gets.

02 The one-idea version

An API is a promise, not code. The test that settles every design argument is: would a client written last year, untouched, still work? If not, you are not evolving — you are breaking. So design the contract first, make it boring enough for a stranger to guess, and remember that every field, status code, and URL you ship is a commitment you will honor long after the code behind it is rewritten.

03 The contract is four decisions

Most API advice stops at “use nouns, not verbs” — that is the first ten minutes of a job that lasts years. The four decisions below are ordered by how expensive a mistake gets: your code you can rewrite, your contract you live with. Follow the animated request path.

04 How it works: six mechanics

Imperative, concrete, no fluff. These are the moves that turn “JSON over POST” into an API that survives contact with real clients.

1

Name resources, not actions

URLs are nouns: /orders (collection, plural) and /orders/42 (item). The verbs already live in HTTP — GET /orders/42 reads, DELETE /orders/42 deletes — so /getOrder and /deleteOrder say the same thing twice. Keep nesting shallow (never deeper than collection/item/collection); beyond that, link related resources in the response body instead. Google’s API design guide calls this resource-oriented design: model the nouns, attach a small fixed set of verbs.

2

Use the HTTP contract honestly

Learn the two axes: safe (changes nothing: GET, HEAD) and idempotent (repeatable without new side effects: GET, PUT, DELETE, PATCH-with-full-replacement). POST is neither — that is exactly why a lost response causes double charges. Pair creation with 201 Created plus a Location header pointing at the new resource; long-running work with 202 Accepted and a job resource the client polls. And never return 200 OK with an error buried in the body — caches, retries, and monitoring all read the status line, not your JSON.

3

Treat every field as a promise

The moment a client parses a field, its name, type, and meaning are contractual. Additive changes are free — a new optional field breaks nobody. Breaking changes cost a version — renaming, retyping, removing, or changing the meaning of an existing field. Two traps: null vs absent (absent means “unknown/unchanged”, null means “explicitly empty” — pick one and document it), and mirroring your database schema in the response (exposes internals and turns every migration into a breaking change).

4

Errors are part of the contract

Design the error path with the same care as the success path: a stable machine-readable code (e.g. insufficient_funds, never a sentence clients regex-match), a human message, and a request ID the client can quote back to you in support tickets. The industry shape is application/problem+json (RFC 9457). Distinguish 400 (client sent garbage) from 422 (well-formed but semantically invalid), 401 (who are you?) from 403 (you may not), and use 429 with a Retry-After instead of silently dropping clients at the rate limit.

5

Design for retries and races

The network will retry you, so make retries safe. Non-idempotent POSTs take an Idempotency-Key header: the server stores the key with the first response and replays it for duplicates. Lists use cursor pagination (?cursor=abc&limit=50 with a stable ordering), never offset — inserts above the offset silently shift every page and clients skip or duplicate rows. Concurrent writes use ETag + If-Match: a stale writer gets 412 Precondition Failed and re-reads instead of silently overwriting.

6

Version the change, not the conversation

For public APIs, put the version in the path (/v1/orders) — it is visible, cacheable, and unambiguous. A published version is a promise: never break it in place; run v1 and v2 side by side and migrate on a timeline. Announce the timeline with the standard headers: Deprecation: true and Sunset: <date>, plus a migration guide. Keep one entrypoint client written last year can still use, and the “last-year test” passes: would that untouched client still work? If yes, you evolved. If no, it is a new version — whatever the ticket calls it.

05 Code sketch: idempotency key + cursor pagination

The two retry-safety patterns that prevent the most expensive production incidents — double charges and skipping pages — in under 30 lines of FastAPI.

from fastapi import FastAPI, Header
app = FastAPI()
idem_store = {}          # key -> first response (persist in Redis/DB)
ORDERS = [{"id": i, "total": i * 10} for i in range(1, 1000)]

@app.post("/v1/orders", status_code=201)
def create_order(payload: dict, idempotency_key: str = Header(...)):
    if idempotency_key in idem_store:     # retry -> replay, don't double-charge
        return idem_store[idempotency_key]
    order = {"id": len(ORDERS) + 1, **payload}
    ORDERS.append(order)
    idem_store[idempotency_key] = order
    return order                     # 201 + Location: /v1/orders/<id> in prod

@app.get("/v1/orders")
def list_orders(cursor: int = 0, limit: int = 50):
    page = ORDERS[cursor : cursor + limit]  # cursor = stable offset here
    nxt = cursor + limit if cursor + limit < len(ORDERS) else None
    return {"orders": page, "next_cursor": nxt}  # client follows next_cursor

06 Failure modes: five ways APIs die

Each one is a named pitfall plus its one-line fix.

F1

Verbs in URLs Fix: rename /getOrder/42 to GET /orders/42. Nouns name the thing, HTTP names the action — saying it twice doubles the learning cost for every endpoint.

F2

200 OK with an error in the body Fix: return the honest status code (400/404/409/422) with a stable machine code and request ID. Everything downstream — caches, retries, alerts — reads the status line, not your JSON.

F3

Offset pagination on a moving list Fix: paginate with an opaque cursor over a stable ordering (e.g. created_at, id). Inserts no longer shift pages out from under the client.

F4

Renaming a field “because it’s cleaner” Fix: ship the new field additively, keep the old one, and mark it deprecated with a Sunset date. Old mobile clients you cannot force-upgrade are the ones that read your changelog the least.

F5

Last-write-wins concurrency Fix: return an ETag on GET and require If-Match on writes. A stale writer gets 412 Precondition Failed and re-reads — silent overwrites become explicit retries.

10 Flashcards

Click or press Enter/Space to flip.

Safe vs. idempotent methods
Safe = changes nothing (GET, HEAD). Idempotent = repeatable without new side effects (GET, PUT, DELETE). POST is neither — the network will retry you, so POST needs an idempotency key.
POST vs. PUT, correctly
POST: the server assigns the resource URI; not idempotent; used for creation and processing. PUT: the client supplies the full URI and representation; idempotent — repeating it replaces the same state, creating or updating.
201 + Location
The response to a successful POST that creates a resource: 201 Created, with a Location header pointing at the new resource's URI — and ideally the representation of the resource in the body to save the client a round trip.
400 vs. 422
400 Bad Request: the request is malformed garbage (bad JSON, wrong types). 422 Unprocessable Entity: well-formed but semantically invalid (a date in the past, an expired card). Both are client errors; 422 says "I understood you, and the answer is no."
401 vs. 403
401 Unauthorized: the server doesn't know who you are — authenticate. 403 Forbidden: it knows exactly who you are, and you may not. 401 = identity problem; 403 = permission problem.
Cursor vs. offset pagination
Offset (?offset=500) is a moving target: inserts above it shift every page, so clients skip or duplicate rows. Cursor (?cursor=abc) anchors to a stable ordering, so pages stay consistent while the list grows. Cursors for lists; offsets only for static snapshots.
Idempotency-Key
A client-generated header on unsafe requests (POST). The server stores the first response against the key and replays it for retries instead of executing again. Turns "was my order created?" into a safe question. Keys must be unique per operation, not per client.
problem+json (RFC 9457)
The standard error shape: type (a URI identifying the error class), title (short human summary), status (the HTTP code), detail (this-instance specifics), instance (the request URI). Stable machine codes clients can switch on, plus a request ID for support.
ETag / If-Match / 412
GET returns an ETag (a version fingerprint). The writer sends it back in If-Match. If the resource changed since, the server answers 412 Precondition Failed — the client re-reads and retries instead of silently overwriting someone else's edit.
"Add freely, remove never"
The evolution rule: adding an optional field or endpoint breaks nobody; renaming, retyping, removing, or changing meaning breaks every client that parsed it — and requires a new version, both versions running, Deprecation/Sunset headers, and a migration guide.

11 Reach for this when…

You’re about to define an endpoint — shape, semantics, representation, then change: name the resource as a noun, pick the honest verb and status code, and ask what the contract promises before writing the handler.
Someone proposes an “improvement” to a live field or URL — run the last-year test: would an untouched client still work? If not, it is a version with a timeline, not a patch.
You’re reviewing a PR that touches the API surface — check the four layers: is anything renamed/removed (shape), does the status line lie (semantics), are errors stable codes with request IDs (representation), is deprecation announced (change).
