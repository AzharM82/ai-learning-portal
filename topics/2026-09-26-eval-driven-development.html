Eval-driven development for AI features

TDD made the test the spec for deterministic code. Eval-driven development does the same for AI features: before you touch the prompt, the model, or the tools, you write down what "good" means as a dataset of real tasks plus graders — and every change gets scored against it like CI. Ship only what the evals green-light; harvest every production failure back into the dataset.

02 The one-idea version

In test-driven development, the test defines done before the code. In eval-driven development, a fixed, labeled dataset of tasks plus graders defines "good" before any prompt, model, or tooling change — so every change becomes a measurable experiment, regressions get caught before shipping, and the suite keeps improving because production failures get harvested back into it. Evals are not a QA checkbox; they are the CI pipeline for AI.

04 How it works

Seven mechanics. Each is one concrete move.

1

Write the failing case before the change (red-green for AI)

Like TDD, the eval comes first: before you touch the prompt, the model, or a tool, turn the desired behavior into a task (input + success criterion) and add it to the dataset. An eval written after the fix tends to just bless whatever the system already does — the whole point of going first is that the suite can actually fail.

2

Build the dataset from production, not imagination

Sample real production traces and edge cases — an eval suite that doesn't match the production distribution is a museum, not a measurement. Use error analysis (bucketed failures) to pick cases, and generate synthetic cases only to fill gaps the real data leaves. Every case is an input with expected success criteria — the "data" half of every eval.

3

Layer the graders: code, then judges, then humans

Deterministic code graders (assertions, regex, schema checks, tool-call verification) are always preferred where the criterion can be codified — fast, free, zero ambiguity. Calibrated LLM judges handle what code can't (tone, faithfulness). Humans spot-check and calibrate. Anthropic's vocabulary: a task is one test case, a trial is one attempt, a grader scores an aspect, the transcript is the full record — evaluate the transcript AND the outcome.

4

Split capability evals from regression evals

Capability (quality) evals ask "what can it do well?" — start them at LOW pass rates so there's a hill to climb. Regression evals ask "does it still do everything it used to?" — these must stay near 100%, and any dip is a bug. When a capability eval climbs high enough, graduate it into the regression suite. One suite drives ambition; the other guards the base.

5

Run the suite in CI on every change — and let it block

Evals run automatically on every prompt, model, or tooling change, with per-version score tracking so regressions get attributed. This is what makes new-model adoption take days instead of weeks: run the suite against the new model, see exactly where it wins and regresses, tune, then ship. An eval suite that can't block a deploy is documentation, not CI.

6

Harvest production failures back into the dataset

The highest-signal eval cases are the ones users already found for you: complaints, thumbs-downs, escalations, support tickets. A clean path from "user complained about X" to "X is now a permanent eval case" is one of the strongest operational signals of eval competence — the regression suite grows out of reality instead of guessing at it.

7

Keep a holdout you never optimize against

Teams game their own suites — Goodhart's law bites evals too. Hold out a labeled set the team can't tune against, re-sample the dataset as production drifts, and re-check judge-vs-human agreement on cadence. Evaluate the whole harness (prompt + tools + model), and track latency, token usage, and cost per task alongside quality — a "better" answer that costs 10x isn't automatically a win.

05 Code sketch

A minimal eval harness in ~25 lines: dataset of tasks, a run function, code graders, and a CI-style score report.

import json

# tasks: inputs + success criteria. graders: code checks, no judge needed here.
DATASET = [
    {"input": "Return policy?",
     "must_contain": ["30 days"], "must_not_contain": ["90 days"]},
    {"input": "Cancel order #4815",
     "must_call_tool": "cancel_order"},   # agent-style: grade the action
]

def run_feature(prompt, model): # your system under test (prompt+tools+model)
    return prompt.dispatch(model=model)   # returns {"text": ..., "tool_calls": [...]}

def grade(task, output):
    checks = []
    for s in task.get("must_contain", []):
        checks.append(s in output["text"])
    for s in task.get("must_not_contain", []):
        checks.append(s not in output["text"])
    if "must_call_tool" in task:
        checks.append(task["must_call_tool"] in output["tool_calls"])
    return all(checks)

results = [grade(t, run_feature(prompt_v2, "gpt-5")) for t in DATASET]
score = sum(results) / len(results)
print(f"prompt_v2: {score:.0%} ({sum(results)}/{len(results)})")
assert score >= 0.95, "BLOCKED: regression suite must stay green"

06 Failure modes

Five named pitfalls, each with a one-line fix.

1

Evals written after the fixFix: add the task to the dataset BEFORE changing the prompt/model/tools — red first.

An eval authored to describe what the system already does can never catch a regression; it just canonizes current behavior. If the suite can't fail, it's a mirror, not a measurement.

2

Dataset drift from productionFix: re-sample cases from live traces on a cadence; synthesize only for coverage gaps.

The suite still passes green while users hit failures you never test for — your distribution and production's have quietly parted ways. The suite becomes a museum of last year's problems.

3

Goodharting the gradersFix: held-out set you never tune against, plus periodic human spot-checks and judge re-calibration.

The system learns to please the judge — shorter answers, keyword stuffing, citing more — while real quality stalls. When a measure becomes a target, it stops being a good measure.

4

Gate theater: the suite runs but never blocksFix: wire regression dips to block deploys; post score deltas on every PR.

A CI job everyone ignores is ceremony, not engineering. If red scores ship anyway, the loop teaches the team that evals don't matter — the exact opposite of the culture you need.

5

Evaluating the model instead of the systemFix: evaluate the full harness — prompt, tools, retrieval, and model — and track cost/latency/tokens per task too.

Swapping to a newer model changes behavior through your prompt and tools, not in isolation — and a "better" output that costs 10x or takes 30s longer can be a loss. Score what you ship.

08 Sample prompts

Copy, adapt, run. Each is a complete working artifact.

EDD SPEC WRITER

I want to change my AI feature's behavior. Before I touch anything, write the eval that defines done. FEATURE: [one sentence — what the feature does] CHANGE: [one sentence — what I'm about to change] CURRENT FAILURES: [2-3 real user complaints or bad traces, pasted] For the CHANGE above, produce: 1. FIVE eval tasks as JSON: {"input": "...", "success_criteria": "...", "grader_type": "code|judge|human"}. At least one must be a regression task the CURRENT system already passes. 2. For each judge-graded task, the one-dimension rubric (PASS/FAIL/UNKNOWN, reasoning first). 3. A one-line CI rule: the exact score threshold and what blocks the deploy. Output only the JSON tasks, the rubrics, and the CI rule. No prose.

DATASET BUILDER

I have 60 recent production traces from my AI assistant (pasted below). Build eval dataset cases. For EACH trace: 1. Write a one-sentence note on the FIRST thing that went wrong, or "no failure". 2. Bucket the notes into failure-mode categories and COUNT each bucket. Then, for each of the top 3 buckets, write 4 eval tasks as JSON: {"input": "realistic user request", "success_criteria": "observable condition", "grader_type": "code|judge|human"}. Prefer "code" wherever the criterion can be an assertion or regex. Do not invent failures that aren't in the traces. If the traces have no failures in a category, say so instead of filling the bucket. [Paste traces]

GOODHART AUDIT

Audit my eval suite for Goodhart risk. I grade my AI feature with the graders below. [Paste: each grader — what it checks, how it scores, what "pass" means] For EACH grader, answer: 1. If the team optimized ONLY for this grader for a month, what degenerate behavior would emerge? Be specific. 2. Which real production failure would this grader miss entirely? 3. One concrete countermeasure: a held-out check, a human spot-check cadence, or a grader edit. Rank the graders by Goodhart risk (highest first). One sentence per answer, no hedging.

Every AI change is a coin flip. Prompt tweaks ship on vibes, and you're never sure whether quality moved up, down, or sideways.
You're about to touch the prompt, model, or tools. Write the failing eval first — red-green for AI — so the change becomes a measurable experiment.
