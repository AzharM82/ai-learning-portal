LLM evals and LLM-as-judge: building trust in outputs

You cannot improve what you cannot measure — and stochastic outputs need measuring differently. An eval is a repeatable bet about what "good" means, built from real failures, not vibes. Code checks what code can check; an LLM judge grades what only judgment can grade — but the judge itself is a model, so it stays on probation until it agrees with humans.

02 The one-idea version

Traditional tests ask "does it still work?" Eval harnesses ask "is it getting better?" — across prompts, models, and tooling changes. Error analysis tells you which evals to write; deterministic code graders catch the objective failures; an LLM judge catches the subjective ones. And a judge is just another model output, so it earns trust the same way: measured against human labels, iterated 3–4 times, re-validated every time the rubric or judge model changes.

04 How it works

Seven mechanics. Each is one concrete move.

1

Start from real failures, not metric dashboards

Pull ~100 real production traces and read them with your own eyes. Write a one-sentence note on the first thing that went wrong in each trace, bucket the notes, count the buckets. The tallest buckets become your eval roadmap — error analysis tells you which evals to write, which is the decision most teams skip and get burned by.

2

Grade with code first for anything objective

Format validity, JSON schema conformance, tool-call correctness, citation presence, length bounds — a regex or assertion runs in <1ms, costs nothing, and never hallucinates. Code-based graders are always preferred where the criterion can be codified; they are the tripwire layer that catches obvious regressions.

3

Reach for the LLM judge only for the subjective rest

For tone, faithfulness, helpfulness — anything no regex can express — prompt a strong model with the output plus a rubric. Three flavors: pointwise (score one output), pairwise (pick A vs B — more reliable for rankings), reference-based (grade against a gold answer — the most anchored, needs curated golds).

4

Write the judge prompt like a spec, not a vibe

One dimension per judge. PASS/FAIL binary verdict per failure mode — not 1–5 "helpfulness" scores, which are noisy and uncalibrated. Include explicit criteria with 2–4 few-shot examples of PASS and FAIL. Make the judge reason (chain-of-thought) before the verdict — reasoning-first judges are measurably more accurate than score-first ones. Give the judge an UNKNOWN escape hatch for thin evidence.

5

Validate the judge against human labels — or don't trust it

Hand-label 30–50 examples yourself (binary PASS/FAIL per failure). Run the judge on the same set and measure true-positive rate and true-negative rate — not raw agreement, which a judge can game by always passing. Expect to iterate 3–4 rounds, sharpening the rubric each time, until the judge agrees with humans. Zheng et al. (MT-Bench) showed a strong judge can reach ~80% human agreement — about the level humans agree with each other — after this work is done.

6

Neutralize the judge's known biases

Position bias: pairwise judges favor whichever answer is shown first — run both orderings and average. Verbosity bias: judges reward longer answers — add an explicit anti-verbosity instruction. Self-preference: models favor their own outputs — use a different model family as judge than the one being evaluated wherever feasible. Treat instability across orderings as a low-confidence signal.

7

Run evals on every change; keep a calibration set held out

Evals run automatically on every prompt, model, or tooling change — they are CI, not a quarterly ceremony. Track scores per version so regressions get attributed. Maintain a held-out, human-labeled calibration set and re-run it whenever you change the judge model, the rubric, or the surrounding prompt infrastructure; a drop in judge-human agreement is a blocking issue, not a footnote.

05 Code sketch

A binary LLM judge in ~25 lines: reason first, then a structured PASS/FAIL verdict.

import json
from openai import OpenAI

client = OpenAI()
JUDGE_SYSTEM = """You are an evaluator for a support assistant.
Grade ONE dimension: did the answer invent facts not in the source docs?
Reason step by step FIRST, then give the verdict."""

def judge_faithfulness(question, answer, sources):
    resp = client.chat.completions.create(
        model="gpt-5",
        response_format={"type": "json_object"},   # structured output: verdict by construction
        messages=[
            {"role": "system", "content": JUDGE_SYSTEM},
            {"role": "user", "content":
             f"QUESTION:\n{question}\n\nANSWER:\n{answer}\n\nSOURCES:\n{sources}\n\n"
              "Respond with JSON: {\"reasoning\": \"...\", \"verdict\": \"PASS|FAIL\", "
              "\"quote\": \"invented claim or null\"}"},
        ],
    )
    return json.loads(resp.choices[0].message.content)

r = judge_faithfulness("Return policy?",
                       "90 days, plus a full refund",
                       "Source: returns within 30 days of purchase.")
# r["verdict"] == "FAIL" — "90 days" and "full refund" are not in the source

06 Failure modes

06 Failure modes

Five named pitfalls, each with a one-line fix.

1

Vibe-check iterationFix: read ~100 real traces and do error analysis before writing any eval.

Prompt tweaks that "feel better" silently break other cases, and nobody notices for weeks. Without measurement, every change is a coin flip wearing a lab coat.

2

The unvalidated judgeFix: probation loop — 30–50 hand labels, TPR/TNR, iterate 3–4 rounds before trusting it.

An LLM judge with no human-calibration check is just a confident guess with an API bill. Its verdicts compound into false confidence across your whole iteration loop.

3

Scale scores (1–5 "helpfulness")Fix: binary PASS/FAIL per failure mode, one dimension per judge.

Numeric scales drift across runs, judges, and prompts — nobody agrees on what a "3" means, so regressions hide inside the noise. Binary verdicts on specific failures stay comparable.

4

Judge bias treated as noiseFix: swap pairwise order and average, add anti-verbosity instructions, use a different judge family than the generator.

Position bias, verbosity bias, and self-preference are systematic — they push every comparison the same direction. Untouched, they quietly crown longer, first-listed, self-generated answers.

5

Metric drift without re-calibrationFix: keep a held-out human-labeled calibration set; re-run on every judge/rubric/prompt change, and block on drops.

The judge that agreed with humans last month silently disagrees after you swap the model or tweak the rubric. Trust decays with every unmeasured change.

08 Sample prompts

Copy, adapt, run. Each is a complete working artifact.

ERROR ANALYSIS STARTER

I have 100 recent conversation traces from my AI support assistant. For EACH trace, do the following and nothing more: 1. Read the full trace. 2. Write ONE sentence naming the FIRST thing that went wrong (or "no failure" if none). 3. Do not score, rate, or rewrite anything. After all 100, bucket the one-sentence notes into failure-mode categories, COUNT the traces in each bucket, and return a ranked table: category | count | one example trace id. The top 3 categories are my eval roadmap — say nothing else.

JUDGE PROMPT TEMPLATE

You are an evaluator for an AI assistant. Grade ONE dimension only: DIMENSION: [e.g. faithfulness — does the answer invent facts not present in the sources?] RUBRIC: - PASS: every factual claim in the answer is supported by the sources below. - FAIL: at least one factual claim contradicts the sources or appears nowhere in them. - UNKNOWN: the sources are missing or too thin to check. EXAMPLES: PASS example: [paste a real PASS pair] FAIL example: [paste a real FAIL pair] INSTRUCTIONS: reason step by step FIRST, quoting the specific claims you checked. Then output exactly one JSON line: {"reasoning": "...", "verdict": "PASS|FAIL|UNKNOWN", "evidence": "quote or null"} Do not consider tone, length, or style — dimension only.

JUDGE CALIBRATION REPORT

I hand-labeled 40 traces as PASS or FAIL for one failure mode. The judge's verdicts are below alongside my labels. For each DISAGREEMENT, diagnose: was my label ambiguous, was the rubric vague, or was the judge wrong — in one sentence each. Then propose exactly three concrete edits to the rubric or few-shot examples that would fix the systematic disagreements, ranked by how many disagreements each edit resolves. Do not re-run anything; report only. [Paste: trace id | my label | judge verdict | judge reasoning]

11 Reach for this when…

Quality is "vibe-checked." You're iterating on prompts by feel and have no number that would catch a regression tomorrow.
You changed the prompt, model, or tools and need to know whether quality moved — up, down, or sideways — before it reaches users.
A subjective quality bar must scale. No regex can express it, humans can't grade the volume — so you need a judge, and that judge needs its probation loop.
