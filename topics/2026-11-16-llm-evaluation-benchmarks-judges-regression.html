LLM evaluation: benchmarks, judges, and regression suites

Public benchmarks tell you what a model can do in general. Your own regression suite tells you whether your system still works after the last change. Learn to separate the two, grade with code first and a calibrated judge second, and gate every release on evidence — not vibes.

02 The one-idea version

An eval is a test that asserts a property, not an exact string: give the system an input, run it, and apply grading logic to the transcript and the final outcome. Benchmarks measure a model in isolation on someone else's tasks; a regression suite measures your system on your users' tasks and must stay near 100%. The judge is just another classifier — it earns trust only by agreeing with human labels on a held-out set.

03 The picture: three layers, one gate

Benchmarks inform a choice. Your suite decides a release.

04 How it works

Six mechanics: separate the suites, start from failures, grade in order, calibrate the judge, run trials, gate the release.

1

Separate three meanings of “eval” — and never substitute one for another

OpenAI distinguishes industry benchmarks (MMLU, SWE-bench Verified — models in isolation), standard scores (ROUGE, BERTScore), and your own application tests. Benchmarks help you shortlist a model; they say nothing about your prompts, retrieval, or tools. HELM-style holistic reporting is a reminder: report accuracy alongside robustness, fairness, and cost, never a single leaderboard number.

2

Start from error analysis on real traces, with 20–50 tasks

Read 50–100 real transcripts, have one domain expert note what went wrong in plain language, and group the notes into failure modes. Anthropic and OpenAI both say 20–50 simple tasks drawn from real failures are a great start. Include typical, edge, adversarial, and should-refuse cases. Split into dev (tune on it), held-out test (release decisions), and challenge sets — and protect the held-out set from prompt tuning.

3

Split capability evals from regression evals

Capability evals ask “what can it do now?” — they start low and give you a hill to climb. Regression evals ask “does it still do what it used to?” — they should pass at nearly 100%, and any drop is a blocker. When a capability task becomes reliably passed, graduate it into the regression suite. LangSmith makes the same split operational: benchmarking, unit tests, regression tests, and backtesting on historical production data, plus online monitoring after launch.

4

Grade in order: code first, model second, human for the hard cases

Use the fastest reliable grader. Code graders check what code can check: schema validity, exact fields, tool calls, final state in the database, tests passing. Model graders (LLM-as-judge) handle semantic equivalence, tone, and groundedness with a narrow rubric — pointwise scoring or pairwise “A vs B”, which models and humans both do more reliably. Human graders calibrate both and adjudicate high-stakes ambiguity. Grade the outcome, not just what the agent says it did.

5

Calibrate every judge like a classifier — and report its agreement

Build 50–100 human-labelled cases, split train/dev/test, tune the judge prompt only on train/dev, and measure on the untouched test set. Report true-positive and true-negative rates separately, plus agreement (accuracy, Cohen's kappa, or Spearman for scores) alongside every judge-derived metric. Control known biases: swap order in pairwise judging (position bias), watch length and self-preference bias, allow “Unknown”, and recalibrate whenever the judge model or rubric changes.

6

Run multiple trials and wire the suite into CI as a gate

Outputs vary, so one run is an anecdote. Report pass@k (at least one of k trials succeeds — capability) and pass^k (all k succeed — reliability); 75% per trial becomes about 42% at pass^3. Run a small fast suite on every PR, the full suite nightly or on model/prompt/index changes, and sample production traffic with online evaluators. Harvest every new production failure into the dataset — continuous evaluation, in OpenAI's workflow, is step five, not an afterthought.

05 Code sketch

A minimal regression gate: code grader first, judge second, agreement reported.

def grade(case, output, state):
    if not valid_schema(output): return Fail("schema")  # code grader
    if state.reservation != case.expected: return Fail("outcome")
    return judge(case, output)  # calibrated LLM judge, rubric-scored

def run_suite(cases, system, trials=3):
    rows = [{"case": c.id, "pass^k": all(grade(c, *system.run(c)).ok
             for _ in range(trials))} for c in cases]
    rate = sum(r["pass^k"] for r in rows) / len(rows)
    assert rate >= 0.99, f"regression gate: {rate:.2%} < 99%"  # block release
    return {"pass^k": rate, "judge_agreement_kappa": 0.81}  # always report it

06 Failure modes

Five ways evals lie — each with a one-line fix.

1

Benchmark shoppingFix: shortlist on public benchmarks, decide on your own held-out suite run under your harness, budget, and tools.

The team picks the model with the highest MMLU or SWE-bench score, then discovers it fails on their documents, latency budget, and tool format. The same model can swing many points with a different scaffold or token budget.

2

Uncalibrated judge trusted on sightFix: label 50–100 cases by a domain expert, tune on dev only, and publish TPR/TNR and kappa with every score.

A judge prompt copied from a template produces authoritative-looking 4/5 scores that hide failures — overall accuracy can look fine while failure detection is poor.

3

Contamination and held-out leakageFix: keep a private, versioned held-out set, decontaminate against training data, and never tune prompts on test failures case-by-case.

Public benchmark items leak into training data, and engineers who inspect every test failure turn the test set into a dev set. Scores rise while real quality does not.

4

Single-trial, single-score reportingFix: run multiple trials, report pass@k and pass^k by slice (task type, length, language), with cost and latency alongside quality.

One lucky run ships, one unlucky run blocks, and an average hides that a critical slice — refunds, refusals, long documents — is broken.

5

Suite that never growsFix: turn every production failure and anomaly flagged by online evaluators into a new regression case before fixing it.

The suite passes forever because it only contains last quarter's problems. Each fix breaks something the suite never covered, in the reactive loop Anthropic describes.

08 Sample prompts

Copy one into your AI assistant and apply it to your own work.

DESIGN MY REGRESSION SUITE

Design a regression suite for this AI feature: [describe feature, users, and 5 recent failures]. Give me: (1) a table of 25 starter tasks grouped by failure mode, each with input, expected outcome (final state, not just text), and grader type (code, judge, or human) with why, (2) which tasks are capability vs regression and the pass bar for each suite, (3) the dev / held-out test split and how we protect the held-out set, and (4) the CI gate: what runs on PR, what runs nightly, and what blocks a release. Flag any task where the expected outcome is ambiguous.

CALIBRATE MY LLM JUDGE

Here is my LLM judge prompt and rubric: [paste]. Help me calibrate it like a classifier: (1) rewrite the rubric so each criterion is independently checkable and binary where possible, with an explicit Unknown option, (2) design the human labelling set — how many cases, which slices, and the train/dev/test split, (3) list the bias checks to run (position swap for pairwise, length, self-preference) and how to run each, and (4) give me the exact report format: TPR, TNR, agreement/kappa on the untouched test set, reported alongside every judge score. Tell me what agreement level you would require before this judge can gate a release.

AUDIT A BENCHMARK CLAIM

Audit this benchmark claim for my decision: [paste model, benchmark, score, and who reported it]. Give me: (1) what the benchmark actually measures and its grader, (2) who ran it, under what harness, scaffold, token budget and number of attempts, (3) saturation and contamination risks for this benchmark, (4) which of my own tasks it does and does not predict, and (5) the smallest experiment on my own data that would settle the choice. End with: trust this number for shortlisting, for deciding, or for neither — and why.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

Benchmark vs regression suite
Benchmark: public tasks, model in isolation, for comparison and shortlisting. Regression suite: your tasks, your full system, must stay near 100% — it gates releases.
Capability eval
Asks what the system can do now. Starts at a low pass rate and gives a hill to climb. When reliably passed, tasks graduate into the regression suite.
Task · trial · grader · transcript · outcome
Anthropic's anatomy: a task is one test case, a trial is one attempt, a grader scores an aspect, the transcript is the full record, and the outcome is the final state in the environment.
LLM-as-judge
A model scoring outputs against a rubric — pointwise (score one output) or pairwise (which of two is better). Scalable for semantic quality, but biased and non-deterministic until calibrated.
Judge calibration
Validate the judge like a classifier: human-labelled train/dev/test, tune only on dev, report TPR, TNR and agreement (kappa) on untouched test — with every judge-derived metric.
pass@k vs pass^k
pass@k: at least one of k trials succeeds (rises with k, measures capability). pass^k: all k succeed (falls with k, measures reliability). 75% per trial is ~42% at pass^3.
Position bias
A judge favouring whichever answer appears first (or second) in pairwise comparison. Fix: run both orders and count a win only when the verdict survives the swap.
Contamination
Test items leaking into training data, or a held-out set leaking into tuning. Scores inflate without real improvement. Keep test sets private, versioned, and untouched during development.
Error analysis
Reading real traces and noting failures in plain language before choosing any metric. It is where good evals come from — each failure mode becomes a task and a grader.
Online evaluation
Scoring sampled production traffic (judge or code) for monitoring and anomaly detection. Flagged failures feed back into the offline dataset — the production feedback loop.

11 Reach for this when…

Someone says the new model “feels worse” — stop arguing from impressions: run the regression suite, compare by slice against the baseline, and let pass^k decide.
You are choosing between two models on leaderboard scores — shortlist on benchmarks, then run both on your 25-task held-out set under your harness and pick on quality per successful task, cost, and latency together.
A production failure surprises you — before fixing it, add it as a regression case that fails today. The fix is done only when the new case passes and the rest of the suite stays at ~100%.
