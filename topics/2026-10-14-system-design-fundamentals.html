System design fundamentals: thinking in trade-offs

There is almost never one correct architecture — only trade-offs between scalability, availability, consistency, latency, cost, and complexity. System design is the discipline of writing down what matters most for this workload, doing the capacity arithmetic, and adding components only when a failure demands them.

02 The one-idea version

Every component in a distributed system exists because something simpler stopped working. System design is therefore a two-step habit: first name the quality attributes you are optimizing — you cannot have infinite scale, perfect correctness, and zero downtime at once — then let failures, not fashion, dictate which boxes and arrows you add. A design review that never asks “what did you give up?” is not finished.

03 How systems grow: one failure at a time

Start with one box and one database. Each stage below adds exactly one component, and every addition is a response to a specific failure of the stage before it. Follow the animated request path.

04 How it works: six mechanics

Imperative, concrete, no fluff. These are the moves that separate a real design from boxes-and-arrows theater.

1

Requirements come before design

Split requirements into functional (what it does: post photo, follow user) and non-functional (how it must behave: 10k QPS, p99 < 300ms, 99.99% uptime, 5-year retention). The NFRs are the design — two teams with the same features but different NFRs will build different systems. Ask the five questions first: how many users, how much data, read/write ratio, latency target, consistency target.

2

Name the quality attributes, in priority order

Scalability (handle growth without proportional cost), availability (fraction of time the system responds — the nines), reliability (correctness under stress and failure), latency (p95/p99, not averages), consistency (do all readers see the same data?), cost and operability. Rank them for this workload and make the ranking explicit: a bank ranks reliability first; a social feed ranks availability first. The AWS and Google Cloud Well-Architected Frameworks exist to make this ranking a checklist instead of an argument.

3

Do the capacity arithmetic on a napkin

avg QPS = DAU × requests/user/day ÷ 86,400; plan for 2–3× peak. storage = DAU × bytes/user/day × retention days × 3 for replication. bandwidth = QPS × avg response bytes. Rules of thumb: 1M requests/day ≈ 12 QPS; a single tuned server handles low-thousands of QPS; replication always triples storage. Do this before choosing anything — it tells you whether you need one box or ten regions.

4

Keep the app tier stateless; push state down

Stateless servers scale horizontally with a load balancer and survive restarts, because any request can land on any instance. Sessions, carts, and partial progress go into the data layer (cache, database, object store), not process memory. The health check on each instance is what lets the balancer route around a dead one. This one decision buys you most of your scalability and most of your availability.

5

Scale reads and writes with different tools

Read-heavy (>80% reads): cache the hot paths, add read replicas, push static content to a CDN. Write-heavy: scale the app tier horizontally, shard the database, and put a queue in front of bursty writers so spikes become a backlog, not an outage. Mixed traffic with divergent needs is what CQRS (separate read and write paths) is for. Match the tool to the bottleneck — a cache does nothing for a write storm.

6

Every partition forces a CAP choice — make it deliberately

When the network splits, a distributed data store can either refuse requests (consistency) or serve possibly-stale answers (availability); it cannot do both. Pick C for money, inventory, and billing (banking takes brief downtime over wrong balances) and A for feeds, counters, and caches (serve slightly stale, reconcile later). Then design the degraded mode: fail gracefully, disable non-critical features, keep the core path up. Availability without a degradation plan is just optimism.

05 Code sketch: capacity arithmetic

The entire “estimation” step of a system design interview, in one function. Run the numbers before drawing boxes.

DAU = 2_000_000            # daily active users
REQ_PER_USER_DAY = 50      # actions per user per day
BYTES_PER_REQ = 20_000     # avg response: 20 KB
RETENTION_DAYS = 365       # 1 year of data

def capacity(dau, req_day, bytes_req, retention):
    avg_qps = dau * req_day / 86_400        # 1 day ≈ 86.4k s
    peak_qps = avg_qps * 2.5                # plan for 2-3x peak
    storage_tb = dau * req_day * bytes_req * retention * 3 / 1e12
    # x3 = replication factor; x5-10 write-cost if write-heavy
    bandwidth_gbps = peak_qps * bytes_req * 8 / 1e9
    return f"avg {avg_qps:,.0f} QPS | peak {peak_qps:,.0f} QPS | " \
           f"storage {storage_tb:,.1f} TB | bandwidth {bandwidth_gbps:,.1f} Gbps"

print(capacity(DAU, REQ_PER_USER_DAY, BYTES_PER_REQ, RETENTION_DAYS))

06 Failure modes: five ways designs die

Each one is a named pitfall plus its one-line fix.

F1

Designing for nines nobody needs Fix: budget availability like money — 99.9% allows 8.8h/yr downtime, 99.99% allows 52min. Price each extra nine before you buy it.

F2

Microservices on day one Fix: start a modular monolith; split only when a team, a scaling need, or a failure domain demands it. Distribution is a cost, not a feature.

F3

Cache stampede Fix: a hot key expires and every request hits the database at once. Stagger TTLs with jitter, coalesce identical requests, or serve stale-while-revalidating.

F4

The single database primary with no replica Fix: one machine is one failure away from data loss. Run a replica with automated promotion and test failover before you need it.

F5

Averaging latency Fix: a 50ms average hides a 2s p99 that torches user experience. Design, alert, and capacity-plan on p95/p99 per endpoint.

08 Sample prompts

PROMPT 1 · RUN THE NAPKIN MATH

I want to practice capacity estimation. Give me a scenario (e.g. a social feed, a URL shortener, a food-delivery app) with: DAU, average actions per user per day, average response size, and retention requirement. Then ask me to estimate avg QPS, peak QPS, storage over the retention period (with 3x replication), and bandwidth. Check my math, correct my mistakes, and explain which numbers drove the architecture choice.

PROMPT 2 · GRILL MY DESIGN

Act as a senior staff engineer reviewing my system design. I will describe an architecture (I'll start with a monolith + single Postgres). After each description, ask exactly one question targeting the weakest point: capacity limits, single points of failure, consistency vs availability, or operational cost. Do not propose the fix — make me propose it, then judge whether my fix creates a new problem.

PROMPT 3 · NAME THE TRADE-OFF

Give me five short design scenarios (one per message): a bank transfer service, a viral short-video feed, an e-commerce checkout on Black Friday, a multiplayer game leaderboard, and a hospital records system. For each, I must name the top-priority quality attribute, the CAP choice, and what I am deliberately sacrificing. Confirm or challenge each answer with one sentence of reasoning.

10 Flashcards

Click or press Enter/Space to flip.

Scalability vs. availability vs. reliability
Scalability: handle growth without proportional cost. Availability: fraction of time the system responds (the nines). Reliability: correct behavior under stress/failure. A checkout can be up (available) yet broken (unreliable).
What the "nines" actually buy
99% ≈ 3.7 days/yr downtime. 99.9% ≈ 8.8 hrs. 99.99% ≈ 52 min. Each extra nine costs roughly an order of magnitude more — price it before promising it.
CAP theorem, one sentence
During a network partition, a distributed data store can guarantee consistency (refuse requests) or availability (serve possibly-stale answers) — not both. Money → C; feeds → A.
Vertical vs. horizontal scaling
Vertical: bigger machine (simple, hard ceiling, single point of failure). Horizontal: more machines behind a load balancer (no ceiling, needs stateless app tier, more moving parts).
Why stateless app tiers win
Any request can hit any instance → the load balancer scales freely and routes around dead servers. Sessions and partial state live in the data layer (cache/DB/store), not process memory.
Read-heavy vs. write-heavy playbook
Read-heavy (>80% reads): cache + read replicas + CDN. Write-heavy: horizontal app tier + DB sharding + a queue to absorb spikes. Cache the right bottleneck — a cache won't fix a write storm.
Cache stampede
A hot key expires and every request slams the database at once. Fixes: jitter the TTLs, coalesce identical in-flight requests (request collapsing), or serve stale-while-revalidating.
Graceful degradation
Plan what to turn off first under failure: shed non-critical features (recommendations, analytics) to keep the core path up. Availability is a design, not an accident.
p99, not the average
A 50 ms average can hide a 2 s tail that ruins user experience. Design, alert, and capacity-plan on p95/p99 latency per endpoint.
The review question that matters
Every component must name the failure it fixes. A box that can't is deleted. And every trade-off is documented: what you sacrificed and why.

11 Reach for this when…

You’re about to draw an architecture — requirements, NFR ranking, and napkin math happen before any box does.
Someone proposes a distributed solution — ask what failure it fixes, what it sacrifices (CAP, latency, cost), and whether a bigger box would do.
You’re in a design review — check the trade-off log: each box names its failure, each nine is priced, each partition has a chosen CAP side.
