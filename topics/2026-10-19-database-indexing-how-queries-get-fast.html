Database indexing: how queries get fast

A table with ten million rows answers WHERE email = ? in under a millisecond instead of seconds — not because of better hardware, but because of a second, sorted data structure built alongside the table. An index turns the database’s default move — reading every row — into a walk down a shallow, balanced tree.

02 The one-idea version

Without an index, a database can find rows only one way: scan every row and test the predicate — O(N) work that doubles when the table doubles. An index is the table’s shadow, sorted the way your queries look it up: a B-tree mapping searched values to row locations, so the engine descends a few levels (3–4 page reads even at a billion rows) and fetches only the matching rows. The work stops growing with the table.

04 How it works

Seven mechanics. Indexing is a design decision you make per query pattern, not per column.

1

The planner’s default move is the sequential scan

With no usable index, the only access path is: read every page, test every row against the predicate. That is Seq Scan in EXPLAIN output. An index doesn’t change the query — it gives the planner a second access path, and the planner picks whichever costs less.

2

The B-tree is wide, shallow, and sorted

Each node holds hundreds of keys and fits in one disk page (8 KB in PostgreSQL). A 100-million-row table needs only 3–4 levels, so any lookup costs 3–4 page reads. Leaves are linked in sorted order, so a range query (BETWEEN, >, LIKE 'Al%') finds its start point, then walks sideways — no re-descending the tree.

3

Index the access pattern, not the column

Start from the queries you actually run: the columns in WHERE, JOIN, and ORDER BY of your slowest and most frequent queries. Indexing a column nothing filters on buys nothing. One CREATE INDEX on the right column is routinely a 100–1000× speedup; one on the wrong column is pure write tax.

4

Composite indexes read left to right

An index on (last_name, first_name) is sorted by last name first, then first name within each last name — it serves WHERE last_name = ? and WHERE last_name = ? AND first_name = ?, but never WHERE first_name = ? alone (the leftmost-prefix rule). Put equality columns first, the range or sort column last: (status, created_at), not (created_at, status).

5

Covering indexes answer without touching the table

If the index holds every column the query needs, the planner never fetches the table rows — an Index Only Scan, the fastest access path. In PostgreSQL, CREATE INDEX ON users (email) INCLUDE (user_id) adds payload columns without sorting on them. Use it for your hottest few-column queries, not everywhere: wider indexes mean fewer entries per page.

6

The planner decides from statistics — verify with EXPLAIN

You don’t choose the index; you propose it. The planner estimates selectivity (what fraction of rows a filter keeps) from table statistics and picks index scan vs sequential scan. Run ANALYZE after bulk loads so stats stay fresh, and read EXPLAIN: Seq Scan means your index lost or doesn’t exist, Index Scan means it won.

7

Every index taxes writes and space

Each INSERT, UPDATE, and DELETE must maintain every index on the table, and each index consumes disk plus cache memory. A write-heavy table (event logs, telemetry) deserves few indexes; a read-heavy one (dashboards, catalogs) deserves more. Indexes that the planner never uses are pure cost — find them and drop them.

05 Code sketch

A pocket model of the planner’s decision: sequential pages vs. index descent plus one fetch per matching row. Watch the crossover — selective filters pick the index, unselective ones don’t.

# planner_cost.py — why the planner sometimes ignores your index
import math

ROWS_PER_PAGE = 100          # ~8KB pages, modest rows
FETCH_FACTOR = 1.2           # random page fetch > sequential read

def btree_depth(rows):
    return math.ceil(math.log(max(rows, 2), ROWS_PER_PAGE))

def compare(rows, selectivity):
    seq = rows / ROWS_PER_PAGE
    idx = btree_depth(rows) + rows * selectivity * FETCH_FACTOR
    pick = "INDEX SCAN" if idx < seq else "SEQ SCAN"
    return seq, idx, pick

for sel, label in [(1e-7, "unique email"),
                   (0.02, "city"),
                   (0.50, "status flag")]:
    seq, idx, pick = compare(10_000_000, sel)
    print(f"{label:14} seq={seq:,.0f}  idx={idx:,.1f}  -> {pick}")

# unique email   seq=100,000  idx=5.2        -> INDEX SCAN
# city           seq=100,000  idx=240,004.0  -> SEQ SCAN  (borderline IRL —
#                                                 bitmap scans blur the line)
# status flag    seq=100,000  idx=6,000,003.0 -> SEQ SCAN

06 Failure modes

Five ways indexing goes wrong — each with the one-line fix.

F1

Indexing a boolean (or any low-cardinality column)Fix: drop it. If only the rare value is ever queried, use a partial index instead: CREATE INDEX ... WHERE is_active = true.

A filter that keeps half the rows can’t win: fetching 5 million rows through random index lookups costs far more than one sequential pass. The planner knows this and ignores the index — so the index is pure write tax.

F2

Wrapping the indexed column in a functionFix: build an expression index on the same expression, e.g. CREATE INDEX ON users (LOWER(email)), or rewrite the predicate to use the stored form.

WHERE LOWER(email) = 'a@b.com' can’t use an index on email — the tree stores the original values, not the lowercased ones. Same trap with WHERE DATE(created_at) = ...: rewrite as a range (>= day AND < day+1) instead.

F3

Composite with the range column firstFix: equality columns first, range/sort column last: (status, created_at), not (created_at, status).

The tree is sorted by the leftmost column. With (created_at, status), a query filtering status = 'active' AND created_at > X can range-scan on the date but must check status row by row inside that range. Flip the order and the equality pins the start of the scan.

F4

Type mismatch in the predicateFix: match the column’s type exactly — WHERE user_id = 42, not '42'.

WHERE int_col = '42' forces the database to cast every row’s value before comparing, which disqualifies the index. ORMs generate these silently when a string sneaks into an integer filter — check the generated SQL, not just the model code.

F5

The index graveyardFix: query pg_stat_user_indexes for idx_scan = 0 and drop the dead weight — every unused index still taxes every write.

Indexes added for one-off investigations or long-deleted features accumulate silently. On a write-heavy table each one slows every insert. Audit quarterly: if the planner hasn’t touched it in months, it’s not an asset.

10 Flashcards

Click or press Enter/Space to flip.

Sequential scan
The planner's default access path: read every page, test every row. Cost is O(N) — it doubles when the table doubles.
B-tree
The default index structure: sorted, balanced, wide-and-shallow. Any lookup costs ~3–4 page reads even at 100M+ rows; linked leaves make range queries a sideways walk.
Selectivity
The fraction of rows a filter keeps. The number the planner uses to pick index scan vs sequential scan — highly selective (few rows) favors the index.
Composite index
One index on two or more columns, searched left to right. Put equality columns first, the range or sort column last.
Leftmost-prefix rule
A composite index (a, b, c) serves queries on a, or a+b, or a+b+c — never on b or c alone. Like a phone book sorted by last name: no good for searching by first name.
Covering index (Index Only Scan)
An index holding every column the query needs, so the planner never fetches table rows. PostgreSQL's INCLUDE adds payload columns without sorting on them.
EXPLAIN
Shows the planner's chosen access path and cost estimates. Seq Scan = full table scan; Index Scan = index plus row fetches; Index Only Scan = answered from the index alone.
Expression index
An index on a function's output, e.g. CREATE INDEX ON users (LOWER(email)). The fix when a predicate wraps the indexed column in a function.
Partial index
An index over a subset of rows (CREATE INDEX ... WHERE ...). Small, cheap, and perfect for the hot slice — e.g. only the active orders.
Write amplification of indexes
Every INSERT/UPDATE/DELETE must maintain every index on the table. Unused indexes are pure write tax — find them via pg_stat_user_indexes (idx_scan = 0) and drop them.

11 Reach for this when…

A query that was fast in dev is slow in prod, and EXPLAIN shows Seq Scan on a large table — design the index for that query's WHERE/JOIN/ORDER BY, then re-run EXPLAIN to confirm the planner picks it.
You're adding a filter, join, or sort to a hot query path — choose the index together with the query: composite, left-to-right, equality columns first and the range/sort column last.
Write latency is climbing on a table with a dozen indexes — audit which ones the planner actually uses and drop the dead weight. An index nobody reads is a tax everybody pays.
