Inference optimization: quantization, vLLM, batching

A model that answers one user in a notebook is a demo. A model that answers thousands of users without renting a data center is a product. The bridge between the two is inference optimization: making every GPU byte smaller (quantization), wasting none of it (PagedAttention), and never letting the GPU sit idle (continuous batching).

02 The one-idea version

LLM serving is a memory-bandwidth problem, not a compute problem: decoding reads the entire weight set once per generated token, so the wins come from smaller weights (quantization), zero-waste memory (PagedAttention pages the KV cache like an OS pages RAM), and zero-idle scheduling (continuous batching fills every freed slot instead of waiting for the slowest request).

04 How it works

Six mechanics. Each is a concrete action, not a slogan.

1

Measure which phase you are in

Prefill (processing the prompt) is compute-bound; decode (token-by-token generation) is memory-bound. Most serving cost is decode. So profile decode tokens/second/GPU first — if that number is low, more FLOPs won't help you; less memory movement will.

2

Shrink the weights with quantization

Store each parameter in fewer bits: FP16 → 2 bytes, FP8/INT8 → 1 byte, INT4 → half a byte. Fewer bytes per parameter means the model fits on cheaper GPUs and each decode step moves less data. Match the format to hardware: AWQ/GPTQ INT4 on consumer NVIDIA cards, native FP8 on Hopper/Ada, GGUF k-quants for CPU and Apple Silicon.

3

Don't forget the KV cache

Weight quantization leaves the KV cache at full precision — and in long-context serving the cache dominates memory. vLLM's kv_cache_dtype="fp8" compresses it separately. Treat the cache as its own quantization decision, not an afterthought.

4

Page the KV cache (PagedAttention)

Traditional serving pre-allocates one contiguous KV block per request — sequence lengths vary, so 60–80% of that memory is wasted on fragmentation and over-reservation. PagedAttention splits the cache into fixed-size blocks mapped through a block table, exactly like OS virtual memory. Waste drops below 4%, freed blocks return instantly, and copy-on-write lets parallel samples share prompt blocks.

5

Batch continuously, not statically

Static batching makes new requests wait for the longest sequence in the batch to finish. Continuous batching (Orca, 2022) schedules at iteration granularity: the moment one request finishes, another takes its slot. Long generations no longer hold the GPU hostage while short requests queue.

6

Cache prefixes, chunk long prefills

Requests that share a system prompt can reuse the same KV blocks — enable prefix caching so you never recompute them. And when a long prompt arrives, chunk its prefill (Sarathi-style) so decode requests don't stall waiting behind one giant prompt.

05 Code sketch

Size the job before buying hardware: weights + KV cache, then serve with vLLM.

# 1. Memory math: does the model + context fit on one GPU?
params     = 70e9          # 70B model
bytes_p    = 0.5           # INT4 weights ≈ half a byte per param
weights_gb = params * bytes_p / 1e9   # ≈ 35 GB

layers, d_model = 80, 8192
seq_len, batch = 8192, 16            # 8k context × 16 concurrent requests
# K+V per token = 2 × layers × d_model values
kv_gb = 2 * layers * d_model * seq_len * batch * 2 / 1e9  # ≈ 34 GB at FP16
print(weights_gb + kv_gb)       # ≈ 69 GB → won't fit an 80GB A100 with headroom
print(weights_gb + kv_gb / 2)   # ≈ 52 GB with FP8 KV cache → fits comfortably

# 2. Serve it: vLLM with FP8 weights + FP8 KV cache
from vllm import LLM, SamplingParams
llm = LLM(model="meta-llama/Llama-3.1-70B-Instruct",
          quantization="fp8",        # native FP8 on H100/H200
          kv_cache_dtype="fp8",     # compress the KV cache too
          max_model_len=8192)
out = llm.generate(["Explain quantization in one sentence:"],
                   SamplingParams(max_tokens=64, temperature=0))
print(out[0].outputs[0].text)

06 Failure modes

Named pitfalls, each with a one-line fix.

F1

Chasing bits without quality gatesFix: validate quantized checkpoints on perplexity AND the downstream benchmarks your users actually care about — perplexity can look flat while coding accuracy drops 30%.

F2

Turning on FP8 where no FP8 hardware existsFix: FP8 on A100-or-older falls back to emulation and the speedup disappears; use SmoothQuant-style W8A8 for full INT8 throughput on pre-Hopper GPUs.

F3

Expecting weight-only INT4 to speed up servingFix: weight-only quantization saves VRAM — the math still runs at FP16, so generation speed barely moves; latency wins need full (W8A8/FP8) quantization with matching tensor-core kernels.

F4

Quantizing the weights, ignoring the KV cacheFix: long contexts make the cache dominate — budget cache bytes per token in the memory math and quantize the cache (e.g. FP8) alongside the weights.

F5

Cranking batch size until first-token latency explodesFix: throughput and latency trade off — chunk long prefills so decodes keep flowing, and size max_num_seqs against a TTFT SLO, not vibes.

F6

Recomputing the same system prompt on every requestFix: enable prefix caching so shared prefixes reuse identical KV blocks instead of burning prefill compute per request.

10 Flashcards

Click or press Enter/Space to flip each card.

KV cache
The cached key and value tensors of every previous token, kept in GPU memory so decoding doesn't recompute them. It's what makes generation fast — and what eats memory at long contexts.
Prefill vs decode
Prefill processes the whole prompt in one parallel pass (compute-bound). Decode generates one token at a time, re-reading weights and cache each step (memory-bound). Optimize each differently.
PagedAttention
KV cache stored in fixed-size blocks mapped through a block table — virtual memory for attention. Memory waste drops from 60–80% to under 4%, and blocks can be shared copy-on-write.
Continuous batching
Scheduling requests at iteration granularity instead of waiting for a whole batch to finish. A finished request's slot is immediately reused (Orca, 2022) — no more waiting behind the longest generation.
Weight-only quantization
Compress weights to INT4/INT8, decompress to FP16 at compute time (GPTQ, AWQ, GGUF). Saves VRAM so bigger models fit — but barely speeds up generation, since the math is still full precision.
W8A8
Both weights AND activations quantized to 8 bits. Needs FP8-capable hardware (Hopper/Ada) or SmoothQuant's activation smoothing on older GPUs. This is what actually buys throughput, not just memory savings.
FP8: E4M3 vs E5M2
E4M3 (4 exponent, 3 mantissa) = higher precision, narrow range — used for weights, activations, KV cache. E5M2 (5 exponent, 2 mantissa) = wider range, lower precision — used for gradients in training.
Prefix caching
Requests sharing an identical prompt prefix (e.g. the same system prompt) reuse the same KV blocks instead of recomputing them. Big win when most of your traffic shares a long prompt.
Chunked prefill (Sarathi)
Split a long prompt's prefill into chunks so decode requests don't stall behind one giant prompt. The fix for "big prefill holds every small request hostage" — latency stays smooth at high throughput.

11 Reach for this when…

GPU spend per request is climbing — size weights + KV cache, pick a hardware-matched quantization format, and serve with vLLM instead of the reference implementation.
Long-context requests OOM the server — budget cache bytes per token first, then quantize the KV cache and let PagedAttention reclaim the wasted 60–80%.
Users complain about slow first tokens or stalled streams under load — check whether static batching or giant prefills are the culprit; continuous batching plus chunked prefill is the fix.
