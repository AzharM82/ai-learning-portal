Voice and realtime agents: streaming speech, turn-taking, and latency budgets

A voice agent is not a chatbot with a microphone bolted on. It is a realtime system judged on one number — the gap between the user finishing and the agent audibly starting — where every stage streams, turn-taking is a prediction problem, and the user can talk over the agent at any moment. Get the budget, the endpointing, and the barge-in right, and it feels like a conversation. Get any one wrong, and it feels broken.

02 The one-idea version

Conversation is a latency budget with a social contract. Human turn gaps average around 200 ms; past roughly a second of silence the user assumes the agent is stuck. So a voice agent never waits for anything to finish — audio streams in, transcripts form incrementally, the model starts generating before the turn is even confirmed, speech is synthesized clause by clause, and at every instant the agent must decide: is the user done, still thinking, or interrupting me?

03 The picture: two architectures, one budget

The cascade chains three models you can swap and debug; speech-to-speech collapses them into one realtime model. Either way, the turn gap is spent in the same places.

04 How it works

Six mechanics: pick the architecture, stream everything, predict the end of the turn, spend the budget deliberately, yield on barge-in, and keep tools from creating dead air.

1

Choose the architecture first: cascade, speech-to-speech, or hybrid

A cascade (streaming STT → LLM → streaming TTS) lets you swap each model, inspect the transcript, and reuse your text-agent tools and evals — at the cost of three latencies and losing tone at the text boundary. A speech-to-speech realtime model (OpenAI Realtime, Azure Voice Live, Gemini Live) hears audio and speaks audio in one session: fewer hops, prosody preserved, built-in turn detection — but less debuggability and vendor-shaped control. Hybrids delegate: the realtime model runs the conversation while a backend model or your agent does heavy reasoning and tool work. Decide on latency target, control needs, and telephony vs browser — not on demo wow.

2

Stream every stage — never wait for a stage to finish

Send microphone audio in small frames over a persistent connection (WebRTC in the browser, WebSocket server-side) — never record-then-upload. Consume interim transcripts while the user is still speaking. Start the LLM on the final transcript (or preemptively, see mechanic 5), stream its tokens, and hand TTS the first complete clause while later clauses are still generating. Play audio through a small jitter buffer: large enough to smooth network variation, small enough that stale audio never piles up. The perceived latency is the sum of each stage’s time-to-first-output, not its total runtime.

3

Detect end-of-turn with semantics, not just silence

Voice activity detection (VAD) tells you speech started and stopped — it cannot tell a finished thought from a mid-sentence pause. Layer it: VAD for speech/silence, then a turn detector that reads meaning and acoustics to predict completion — LiveKit’s turn detector model, OpenAI’s semantic_vad (with eagerness), or Azure’s azure_semantic_vad. Bound it with endpointing delays: a minimum wait after silence before closing the turn (LiveKit defaults: min_delay 0.5 s) and a maximum after which you force the turn closed (default 3.0 s). Tune per context — collecting a long account number needs longer pauses than casual chat. Push-to-talk (manual) is the honest fallback when prediction keeps failing.

4

Budget the turn gap stage by stage — and measure p95, not the demo

Write the budget down before you build: endpointing ~200 ms, final transcript ~100 ms, LLM time-to-first-token ~250 ms, TTS time-to-first-audio ~100 ms, network + jitter ~50 ms → first audio in roughly 700 ms. Instrument every stage with one session ID and turn ID, and report p50 and p95/p99 by device, network, and language. A 600 ms median with a 3-second p99 means one turn in a hundred feels broken — and users remember those. When the budget blows, the per-stage numbers tell you which stage to fix; a single end-to-end number tells you nothing.

5

Handle barge-in as a first-class event, and cheat latency honestly

When the user speaks mid-response: stop playback locally and immediately (don’t wait for a server round-trip), cancel the in-flight response, and truncate the conversation history to only the portion the user actually heard — otherwise the model “remembers” saying things the user never heard. Distinguish a real interruption from backchannel (“mm-hmm”, a cough): adaptive interruption handling and filler-word filtering exist precisely for this. To buy back time, use preemptive generation — start the LLM (and optionally TTS) on a likely-final transcript before the turn is confirmed, and discard it if the user keeps talking.

6

Keep tools, keys, and the audio path from breaking the conversation

A tool call that takes three seconds is three seconds of dead air: run tools fast, in parallel where independent, stream a brief spoken acknowledgement for slow ones, and never block the audio loop on a database. Protect the session: mint short-lived ephemeral client secrets server-side for browser clients (OpenAI’s POST /v1/realtime/client_secrets) — never ship a real API key to a client. Clean the audio path: noise suppression and server echo cancellation (so the mic doesn’t hear the agent’s own voice and interrupt it), and resample deliberately — providers expect specific formats (e.g. 16 kHz or 24 kHz PCM), and a mismatch garbles everything downstream.

05 Code sketch

The shape of a streaming cascade turn: interim transcripts flow, generation starts on endpoint, TTS speaks clause by clause, and every stage is timed against the budget. Provider calls are stubs — the orchestration is the lesson.

import asyncio, time
from dataclasses import dataclass, field

BUDGET_MS = {"endpoint": 200, "llm_ttft": 250, "tts_ttfa": 100}

@dataclass
class Turn:
    t_end_of_speech: float = 0.0
    marks: dict = field(default_factory=dict)
    def mark(self, stage): self.marks[stage] = time.perf_counter()
    def gap_ms(self):  # user-finished -> first-audio: THE metric
        return (self.marks["first_audio"] - self.t_end_of_speech) * 1000

async def handle_turn(audio_stream, stt, llm, tts, player, turn: Turn):
    final_text = ""
    async for partial in stt.stream(audio_stream):   # interim hypotheses
        if partial.is_endpoint:        # VAD + semantic turn detector agree
            final_text = partial.text
            turn.t_end_of_speech = time.perf_counter()
            turn.mark("endpoint"); break

    async def speak_clauses():
        buf = ""
        async for token in llm.stream(final_text):  # tokens, not full reply
            if "llm_ttft" not in turn.marks: turn.mark("llm_ttft")
            buf += token
            if buf.endswith((".", ",", "?")):   # clause boundary
                async for frame in tts.stream(buf):
                    if "first_audio" not in turn.marks: turn.mark("first_audio")
                    player.play(frame)   # small jitter buffer inside
                buf = ""

    speaking = asyncio.create_task(speak_clauses())
    async def on_barge_in():              # user talks over the agent
        await audio_stream.wait_for_speech()
        player.stop_now()                 # local stop, no round-trip
        speaking.cancel()                 # + truncate history to heard part
    asyncio.create_task(on_barge_in())
    await speaking
    assert turn.gap_ms() < 1000, f"turn gap {turn.gap_ms():.0f} ms — check stage marks"

06 Failure modes

Five ways voice agents feel broken in production while the demo sounded great — and the one-line fix for each.

1

The silence-timer seesaw: cut off, or comatoseFix: replace fixed silence thresholds with a semantic turn detector plus min/max endpointing delays, tuned per task — and log cut-offs and long gaps as separate metrics.

A short silence_duration_ms makes the agent interrupt every thinking pause; a long one makes every reply feel sedated. Both are the same bug: treating silence as if it meant “finished”. Users adapt by speaking unnaturally fast or giving up.

2

The serial pipeline: three fast APIs, one slow conversationFix: stream all three stages and overlap them — interim STT, token streaming, clause-level TTS — then re-measure time-to-first-audio, not total time.

Each vendor benchmarks well in isolation, but the integration waits for the full utterance, then the full transcript, then the full reply, then the full WAV. Latencies that were supposed to overlap simply add: 2–5 seconds a turn. Nothing is broken; the architecture is.

3

Barge-in blindness — or barge-in hair-triggerFix: stop playback locally on speech start, truncate history to what was heard, and use adaptive interruption handling so backchannel and coughs don’t cancel the response.

Without interruption handling the agent monologues over the user — the single most “robotic” failure there is. With naive VAD-only handling, an “mm-hmm” or a door slam kills the answer mid-sentence. Both extremes come from treating interruption as an afterthought instead of a designed event.

4

The agent interrupts itselfFix: enable echo cancellation (server AEC or a client playback reference) and noise suppression, and test on speakers — not just headsets — before shipping.

On speakerphone, the microphone hears the agent’s own TTS, VAD fires, and the agent stops itself, apologizes to itself, or transcribes its own output as user input. Headset-only testing hides it completely; the first real living-room user finds it in ten seconds.

5

Dead air during tools, hidden by median metricsFix: instrument per-stage p95/p99 with turn IDs, make slow tools acknowledge verbally or run async, and set an alert on turn-gap p95 — not on averages.

The model calls a slow CRM lookup and the conversation just… stops. Meanwhile the dashboard shows a healthy 600 ms median because it only measures model latency, excludes tool time, and averages away the tail. Users experience the p99, not the p50.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

Turn gap
Time from the user finishing a turn to the agent’s first audible response. The core voice-UX metric: human gaps average ~200 ms, ~700 ms feels responsive, past ~1 s feels broken. Budget it per stage, at p95.
VAD
Voice activity detection: classifies audio frames as speech or silence. It detects starts and stops, drives interruption detection — but cannot by itself tell a finished thought from a thinking pause.
Endpointing
Deciding the user’s turn has ended. Tuned with min_delay (wait at least this long after silence) and max_delay (force-close after this long) — LiveKit defaults 0.5 s / 3.0 s — ideally adapted dynamically per speaker.
Semantic VAD / turn detector
A model that predicts end-of-turn from meaning + acoustics, not silence alone: OpenAI semantic_vad (tune eagerness), Azure azure_semantic_vad, LiveKit’s turn detector model. Fewer cut-offs without adding dead air.
Barge-in
The user speaking over the agent mid-response. Correct handling: stop playback locally and immediately, cancel generation, truncate history to the heard portion, and listen. Distinguish it from backchannel (“mm-hmm”).
Cascade pipeline
STT → LLM → TTS as separate streaming models. Modular, debuggable, transcript visible, text tooling reusable — but latencies add and tone is flattened to text in the middle.
Speech-to-speech
One realtime model consuming and producing audio in a single session (OpenAI Realtime, Azure Voice Live, Gemini Live). Fewer hops, prosody preserved, built-in turn detection — traded against control and debuggability.
Preemptive generation
Starting LLM (and optionally TTS) work on a likely-final transcript before the turn is confirmed, discarding it if the user continues. Buys back endpointing latency at the cost of some wasted compute.
Time to first audio (TTFA)
When the first frame of agent speech reaches the speaker. Achieved by summing stage firsts — first token, first clause, first TTS frame — instead of stage totals. The number your budget and your p95 alert should track.

11 Reach for this when…

The interface is a conversation, not a form — phone support, in-car assistants, accessibility-first products, hands-busy workflows. If users would rather talk than type and expect human rhythm, you are in realtime territory and need the budget discipline, not a chat API with TTS stapled on.
Your text agent works but feels dead out loud — multi-second pauses, talking over users, or monologuing through interruptions. The fix is architectural: streaming, semantic endpointing, and designed barge-in, in that order.
You are choosing a voice stack this quarter — decide cascade vs speech-to-speech vs hybrid from your latency target, control/debuggability needs, and channel (WebRTC browser vs telephony) before you fall for a demo; then hold the vendor to a per-stage p95 budget.
