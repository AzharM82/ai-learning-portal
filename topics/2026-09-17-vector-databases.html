Vector databases: indexes, ANN search, and trade-offs

Your embeddings are points in a high-dimensional space; finding the nearest ones is the whole retrieval problem. Exact search doesn't scale, so every vector database is an approximate nearest-neighbor machine — and the index you pick is a bet on the recall–latency–memory triangle.

02 The one-idea version

A vector database answers one question: "which of my million vectors point most like this one?" Checking every vector is exact but O(n) — too slow at scale — so ANN indexes organize vectors so a query only inspects a smart fraction of them. Every index is a trade on the recall–latency–memory triangle: HNSW buys speed with graph hops, IVF buys speed by searching clusters instead of the whole corpus, quantization buys memory by shrinking the vectors themselves.

03 The visual

Three ways to find nearest neighbors: scan everything, partition the space, or descend a layered graph. The query visits less and less of the corpus as you move right.

04 How it works

Six mechanics: why exact search dies, the two indexes that replaced it, the triangle they trade on, and the two things that silently break everything.

1

Exact nearest-neighbor search doesn't survive scale

Brute-force kNN compares the query against every vector: O(n × d) multiply-adds per query. A million 1536-dim vectors is ~1.5 billion operations — milliseconds on a GPU if you're lucky, but it never gets cheaper and doesn't parallelize across shards for free. recall = 100% is the only thing exact search has going for it.

2

HNSW: navigate a layered graph instead of scanning

Hierarchical Navigable Small World builds layers of proximity graphs: the top layer is sparse (long jumps), the bottom layer dense (every vector, linked to its neighbors). A query enters at the top and greedily hops toward the nearest node, zooming in layer by layer — about O(log n) hops. Three knobs: M (links per node, index-time memory), efConstruction (build quality/speed), ef (search-time candidate list: bigger = more recall, more ms). This is the default index in most vector databases for a reason: best recall-per-millisecond on most workloads.

3

IVF: partition the space, search only nearby clusters

Inverted File Index runs k-means over the corpus into nlist clusters; each vector lives in one bucket. At query time, find the nprobe nearest cluster centroids and search only those buckets. nprobe=1 is fast and lossy; nprobe→nlist is exact search with extra steps. Pair it with product quantization (PQ): compress each vector into a short code (e.g. 64 bytes) so a billion vectors fit in RAM — at a small, measurable recall cost.

4

Everything trades on the recall–latency–memory triangle

There is no free lunch, only knobs. More ef / nprobe = more recall, more latency. Bigger M = more recall, more RAM. PQ/SQ quantization = much less memory, slightly less recall. Tune against recall@k — the fraction of the true top-k your index actually returns — measured on your queries, because ANN-benchmarks corpora are not your corpus.

5

The distance metric is part of the index, not a runtime choice

HNSW and IVF indexes are built for one metric — cosine, dot product, or Euclidean. The metric must match how your embedding model was trained (most text models: cosine; normalize vectors first). Build the index with the wrong metric and recall degrades silently — the index still returns k neighbors, just the wrong ones.

6

Metadata filtering is where ANN search goes to die

"Top-5 support docs from 2026" is a filter plus a vector search. Naive post-filtering (search, then discard non-matching) collapses recall when the filter is selective — the true matches were never in the candidate set. Prefer pre-filtering or filtered-aware indexes (most managed DBs handle this internally); always test recall with your filters on, since filtered recall can be dramatically worse than unfiltered.

05 Code sketch

A minimal IVF in 26 lines: partition vectors into clusters, probe the nearest ones, rank candidates by cosine. HNSW is the same idea — a smarter structure — with the same tuning knobs.

import numpy as np

def build_ivf(vecs, nlist=100):
    # partition the corpus into nlist clusters (k-means; sklearn in real code)
    centroids = vecs[np.random.choice(len(vecs), nlist, replace=False)]
    buckets = {i: [] for i in range(nlist)}
    for i, v in enumerate(vecs):
        buckets[int(np.argmin([np.dot(v, c) for c in centroids]))].append(i)
    return centroids, buckets

def search_ivf(q, vecs, centroids, buckets, nprobe=4, k=5):
    # search only the nprobe nearest clusters, then rank exactly
    sims = [np.dot(q, c) for c in centroids]
    probes = np.argsort(sims)[-nprobe:]
    cand = [i for p in probes for i in buckets[int(p)]]
    ranked = sorted(cand, key=lambda i: np.dot(q, vecs[i]), reverse=True)
    return ranked[:k]  # nprobe: recall knob. k: how many you want.

06 Failure modes

Named pitfalls, each with a one-line fix. Number one is completely silent — the index still returns neighbors, just the wrong ones.

✕

Metric mismatch Fix: build the index with the metric your embedding model expects (usually cosine, with normalized vectors); never change it at query time.

HNSW/IVF graphs are built for one distance function. Query-time "switching" to cosine on an L2 index silently degrades ranking — and no error is ever raised.

✕

Default recall settings Fix: raise ef (HNSW) or nprobe (IVF) and measure recall@k on your own queries until the curve flattens.

Defaults are tuned for benchmarks, not your corpus. ef=10 or nprobe=1 can quietly return 80% recall when you assumed 99% — retrieval misses you blame on chunking or the model.

✕

Post-filtering selective metadata Fix: pre-filter, use a filtered-aware index, or over-fetch (larger k) before filtering — and measure filtered recall, not just plain recall.

"Docs from last week" matches 0.1% of the corpus. Post-filtered ANN returns empty or junk because the true matches were never in the probed set.

✕

IVF clusters that never get rebuilt Fix: retrain/rebuild IVF indexes on a schedule (or use HNSW, which inserts incrementally); watch recall decay after big ingests.

IVF partitions are frozen at build time. New documents with shifted distribution land in wrong clusters — recall decays silently as the corpus drifts.

✕

Benchmark-body syndrome Fix: build a recall eval from your own query log; treat public ANN-benchmark numbers as orientation only.

SIFT/GloVe benchmarks don't share your dimensionality, distribution, or filters. An index that wins ann-benchmarks can lose on your data — measure the triangle where you live.

10 Flashcards

Click a card — or tab to it and press Enter — to flip it.

ANN search
Approximate nearest-neighbor search: trades a small, measured recall loss for orders-of-magnitude faster queries than exact O(n) scan.
HNSW
Hierarchical Navigable Small World: layered proximity graphs; queries greedily hop from sparse top layers to dense bottom ones — ~O(log n). The default index for recall-hungry search.
ef (HNSW)
Search-time candidate list size. Bigger ef = more candidates explored = higher recall, higher latency. The first knob to turn when recall is low.
IVF
Inverted File Index: k-means partitions the corpus into nlist clusters; queries search only the nprobe nearest clusters instead of the whole corpus.
nprobe
How many IVF clusters a query searches. nprobe=1 is fast and lossy; nprobe→nlist approaches exact search. IVF's recall knob.
Product quantization (PQ)
Compresses each vector into a short code (tens of bytes) so billions of vectors fit in RAM — at a small, measurable recall cost. A memory knob.
recall@k
The fraction of the true top-k nearest neighbors your index actually returns. The recall side of the triangle — measure it on YOUR queries, not benchmarks.
Distance metric
Cosine, dot product, or Euclidean — built INTO the index, not a runtime choice. Must match the embedding model's training; mismatches silently degrade ranking.
Filtered search
Vector search + metadata filter. Post-filtering selective filters collapses recall — prefer pre-filtering or filtered-aware indexes, and measure filtered recall@k.
The recall–latency–memory triangle
Every index knob buys one corner with another's currency: ef/nprobe trade latency for recall, M trades RAM for recall, PQ trades recall for memory. No free lunch.

11 Reach for this when…

You're choosing a vector store for a RAG system or agent memory — pick the index (HNSW default, IVF+PQ at billion scale) and set recall@k targets before you commit.
Retrieval recall is low and chunking/embeddings already check out — raise ef / nprobe, verify the metric matches the embedding model, and check filtered queries separately.
You're adding metadata filters to vector search — selective filters plus post-filtering is the classic silent recall killer; plan pre-filtering from day one.
