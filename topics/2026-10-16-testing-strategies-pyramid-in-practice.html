Testing strategies: the pyramid in practice

Every test you write buys you confidence and costs you time — and you pay the cost on every run while the value caps out at what the test can actually prove. Testing strategy is therefore a budget question: spend most of it where confidence is cheap (fast unit tests), less where it is expensive (slow end-to-end tests). The pyramid is that budget drawn as a shape.

02 The one-idea version

The pyramid is a budget, not a rule. Each layer trades confidence against cost: unit tests are cheap and fast but prove little about the system; end-to-end tests prove the most but are slow, flaky, and hard to debug. So push every test as far down the pyramid as it can go — the more a layer costs you per run, the fewer tests it deserves.

03 The pyramid is a budget

Read the triangle like a budget sheet: width is how many tests each layer gets, and the two arrows show why. Cost per run climbs as you go up; feedback speed falls. The animated arrow on the right is the only rule that matters — push every test down as far as it can go.

04 How it works: six mechanics

Imperative, concrete, no fluff. These are the moves that turn “we have tests” into a suite that actually ships confidence.

1

Push every test as far down as it can go

Ask of every behavior: can a unit test prove this? If yes, it never belongs in an integration test; if an integration test covers it, it never needs an end-to-end test. The 70/20/10 split is folklore — the direction is the law. And when a top-layer test catches a bug with no corresponding lower-level failure, that is a gap in the lower suite: write the lower test before the fix, so the fast layer owns the regression forever.

2

Unit tests prove behavior through the public interface

A unit test asks “if I enter x and y, do I get z?” — never “did the method call class A, then class B?”. Structure every test as Arrange–Act–Assert (or Given–When–Then), name it like a spec of the behavior, and keep one behavior per test. The test that breaks when you rename a private method is not a test — it is a tax on refactoring, and refactoring is the thing tests are supposed to make safe.

3

Keep units fast and hermetic

A unit test touches nothing shared: no network, no filesystem, no real clock, no sleep(), no randomness it does not seed. Push side effects to the edges (functional core, imperative shell) and inject the seams — clock, RNG, HTTP client — as parameters so tests control them. Google’s size taxonomy makes this the definition: a small test runs in one process with no sleeping, so it is fast and deterministic by construction.

4

Test the seams with integration tests

The database, the queue, the HTTP boundary to a third-party service — this is where units stop proving things and where the most expensive bugs hide. Use the real collaborator where you can afford it (a local database via testcontainers, an in-memory queue where faithful), and cover external APIs with contract tests. Never mock types you do not own: wrap the third-party client in your own interface, mock the seam you own, and let the contract test verify the real one.

5

Reserve end-to-end for the journeys that must never break

E2E is the most expensive layer you have — slow to run, flaky by nature, and every failure is a debugging expedition. Budget it honestly: one test per critical user journey (sign-up, checkout, payment), plus one per important error class. Own the environment: seeded data, deterministic fixtures, no shared staging that someone else is redeploying mid-run. If an e2e test flakes, that is an incident — quarantine it the day it appears.

6

Make the fast loop actually fast

A suite nobody runs is decoration. Units run in watch mode on every save; the full fast suite gates every commit; integration runs on the pull request; e2e runs on release candidates. Parallelize by file, split slow lanes out of the commit path, and keep the pre-push suite under ~5 minutes. Then delete low-value tests on sight — a test that never fails and proves nothing costs runtime on every run while buying zero confidence.

05 Code sketch: pure core, seamed clock

Two patterns in 24 lines of pytest: money math as a pure function (trivially testable), and business logic that takes hour as a parameter instead of calling the clock itself — the seam that keeps the test hermetic.

import pytest

def total(items, tax_rate):
    """Pure function: money math, no I/O — trivially testable."""
    subtotal = sum(i["price"] * i["qty"] for i in items)
    return round(subtotal * (1 + tax_rate), 2)

@pytest.mark.parametrize("items,rate,expected", [
    ([{"price": 10, "qty": 2}], 0.0, 20.0),
    ([{"price": 10, "qty": 2}], 0.1, 22.0),
    ([], 0.1, 0.0),                       # edge: empty cart
])
def test_total(items, rate, expected):
    assert total(items, rate) == expected

# Seam the clock: logic takes "now" as a parameter, never calls it.
def greeting(name, hour):
    return f"Good {'morning' if hour < 12 else 'evening'}, {name}!"

def test_greeting_boundary():
    assert greeting("Azhar", 11) == "Good morning, Azhar!"
    assert greeting("Azhar", 12) == "Good evening, Azhar!"

06 Failure modes: five ways suites die

Each one is a named pitfall plus its one-line fix.

F1

The ice-cream cone Fix: invert it — for every e2e assertion, ask what lower-level test could own it and push coverage down. Keep e2e only for critical journeys; everything else belongs in unit or integration tests.

F2

sleep() waits and real clocks Fix: inject a clock seam (or virtual time), seed the RNG, and replace fixed sleeps with poll-with-timeout on the real condition. Timing-dependent tests pass on your laptop and flake in CI.

F3

Mocking types you don't own Fix: wrap the third-party client in your own interface, mock only the seam you own, and verify the real boundary with a contract test. Your mocks drift from reality and keep passing while production breaks.

F4

Coverage as a target Fix: treat coverage as a smoke detector, not a target. Chasing 100% writes tests for lines instead of behavior, couples tests to implementation, and taxes every refactoring. Diminishing returns set in fast — test what has logic.

F5

The flaky test you "will fix later" Fix: quarantine or delete it the day it appears. A flaky test is worse than no test — it trains the team that red builds are noise, so real failures get re-run into greenness and trust dies.

10 Flashcards

Click or press Enter/Space to flip.

The test pyramid, in one line
Many fast unit tests at the base, fewer integration tests in the middle, a few end-to-end tests at the top. The higher you go, the fewer tests — because cost, runtime, and flakiness all grow with scope.
Push every test down
If a behavior can be verified at a lower level, it belongs there. Direction matters more than any 70/20/10 ratio — and a bug caught at the top with no failing unit test means the unit suite has a gap to close first.
Unit test: what it proves
Observable behavior through the public interface: "if I enter x and y, do I get z?" — never the internal call sequence. A test that breaks on a private-method rename is a tax on refactoring.
Sociable vs. solitary unit tests
Solitary: every collaborator replaced with a test double — perfect isolation. Sociable: real collaborators, doubles only for the awkward ones (slow, nondeterministic, external). Most teams use both.
Hermetic test
Zero dependence on shared state: no network, no real clock, no shared database, no sleep. Fast and deterministic by construction — Google's small/medium/large test-size axis is built on exactly this idea.
Don't mock types you don't own
Wrap third-party clients in your own interface, then mock the seam you own. The real boundary gets a contract test — otherwise your mocks drift from reality and keep passing while production breaks.
Arrange–Act–Assert
The unit-test skeleton: set up the world (arrange), do the one thing (act), check the one outcome (assert). One behavior per test, and the test name reads as a spec of that behavior.
The ice-cream cone
The inverted pyramid: a suite that is mostly UI/E2E tests — slow to run, flaky, expensive to maintain, and it trains the team to ignore red builds. The fix is to invert it back into a pyramid.
A flaky test is…
Worse than no test. It teaches the team that red builds are noise, so real failures get re-run into greenness and trust dies. Quarantine or delete it the day it appears — never "later."
Small vs. medium vs. large tests
Small: single process, no network/disk/sleep — runs on every commit. Medium: localhost, a real database allowed. Large: multi-process or remote services. The size axis predicts flakiness: every capability granted is a way to fail.

11 Reach for this when…

You’re about to write a new test — ask which layer owns this assertion and push it as far down the pyramid as it can go. The cheapest layer that proves the behavior wins.
A test flakes in CI — treat it as an incident: quarantine it today, hunt the non-determinism (clock, network, sleep, shared state), and fix the seam. Never let a flake teach the team that red is normal.
Someone proposes 100% coverage or “just test it in the browser” — reach for the budget: confidence per minute of runtime, not lines per file. Weight the suite toward fast hermetic tests and reserve end-to-end for the journeys that must never break.
