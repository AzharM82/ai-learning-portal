GPU infrastructure: clusters, scheduling, and utilization

A GPU cluster is the most expensive square footage in your stack, and most of it sits idle in three different ways at once. This lesson is the operating model: inventory the topology, expose GPUs to a real scheduler, place multi-GPU jobs gang-style, share small jobs safely — and measure utilization in a way that cannot lie to you.

02 The one-idea version

A GPU earns its cost only when its SMs are doing useful work — allocation is not utilization, and GPU-Util is not proof. A cluster can be 100% allocated, show 100% GPU-Util, and still waste most of its capacity: jobs hold devices they barely touch, a kernel running on one-fifth of the SMs reads as ‘busy’, and free GPUs scattered one-per-node cannot host the next 8-GPU job. Run the cluster as three separate problems — placement (the scheduler), sharing (partitioning), and truth (DCGM SM/tensor/DRAM activity per job) — and optimize each one explicitly.

03 The picture: three utilizations, one truth

Each layer down loses GPUs. The scheduler owns the first gap, the workload owns the second, and only the bottom number is real work.

04 How it works

Seven mechanics: topology first, a real scheduler, honest measurement, and a feedback loop.

1

Inventory the topology before you schedule anything

Record per node: GPU model and memory, GPUs per node, NVLink domains inside the node, and the fabric between nodes (InfiniBand vs Ethernet, rails, spine). Label every node with it (Kubernetes labels / Node Feature Discovery, Slurm node features). A scheduler that cannot see topology will happily split an all-reduce job across the slow fabric — and the job will run at fabric speed, not GPU speed.

2

Expose GPUs to the scheduler — never hand-assign them

In Kubernetes, the vendor device plugin advertises GPUs as an extended resource (nvidia.com/gpu); pods request them in limits only, requests must equal limits, and there is no fractional request by default. The GPU Operator automates driver, toolkit, plugin and DCGM exporter. In Slurm, declare GresTypes=gpu and per-node Gres=gpu:<type>:<count>, let AutoDetect=nvml verify the hardware, and require jobs to ask explicitly (--gres=gpu:2, --gpus-per-node, --cpus-per-gpu). If a human is picking devices by SSH and CUDA_VISIBLE_DEVICES, you do not have a cluster — you have shared workstations.

3

Schedule multi-GPU jobs gang-style and topology-aware

A distributed training job needs all of its GPUs at once or none — partial placement deadlocks or idles the placed half. Use gang scheduling (Volcano, Kueue, Slurm allocations) so the job starts only when the full set fits, prefer GPUs inside one NVLink domain, then one node, then one fabric island. Backfill small, short jobs into the holes a big queued job leaves, with a hard time limit so backfill never delays the big job.

4

Govern with quotas, fair-share, and preemption tiers

Give each team a quota (GPU-hours, not just device count) and a fair-share priority that decays with recent use, so one team’s month-long run cannot starve everyone else. Split capacity into tiers: guaranteed (production inference, deadline training), burstable (experiments that may be preempted), and scavenger (notebooks, evals) that runs only on idle capacity. Preemption is only humane if jobs checkpoint — require checkpointing for anything preemptible.

5

Share a GPU only with the right partition mechanism

Whole-GPU allocation wastes a 80 GB device on a 6 GB inference model. MIG partitions one GPU into hardware-isolated instances with dedicated SMs and memory — predictable performance, the default for multi-tenant production. Time-slicing interleaves processes with no memory or performance isolation — fine for dev and bursty low-stakes jobs, dangerous for latency SLOs. MPS runs processes concurrently in one context — good for many small kernels from cooperative jobs. Pick by isolation need, and reconfigure MIG only when the GPU is idle.

6

Measure three utilizations, per job, with DCGM

Export DCGM and track, per job and per team: (1) allocation — GPU-hours held; (2) SM activity (field 1002) — NVIDIA’s own guidance: ≥0.8 is necessary but not sufficient for effective use, <0.5 likely indicates waste; (3) tensor activity and DRAM activity (1004/1005) plus NVLink/PCIe bytes, to tell compute-bound from memory-bound from starved. Never report the nvidia-smi GPU-Util duty cycle as ‘utilization’ — it only says a kernel was running sometime in the sample window.

7

Close the loop: showback, idle reaping, right-sizing

Publish a weekly per-team report: GPU-hours held vs SM-active GPU-hours, queue wait, and the cost of the gap. Reap allocations with near-zero SM activity past a grace period (warn first, checkpoint if possible). Feed the data back into requests: a job that asks for 8 GPUs and averages 30% SM activity gets a smaller default next time. Utilization improves when it is visible and priced, not when it is exhorted.

05 Code sketch

A tiny Python audit: turn DCGM-style samples into the only report that matters — held vs actually working, per job.

# gpu_waste_audit.py — allocation is not utilization
from collections import defaultdict

# samples: (job, gpu_hours_held, sm_activity 0..1) from DCGM field 1002
samples = [
    ("train-llm-42",  8 * 24, 0.86),
    ("notebook-ana",  1 * 24, 0.03),
    ("infer-embed",   2 * 24, 0.41),
    ("eval-sweep-7",  4 * 24, 0.12),
]

report = defaultdict(lambda: [0.0, 0.0])
for job, held, sm in samples:
    report[job][0] += held            # GPU-hours billed to the job
    report[job][1] += held * sm       # GPU-hours of real SM work

for job, (held, worked) in sorted(report.items()):
    waste = held - worked
    flag = "  <-- REAP / RIGHT-SIZE" if worked / held < 0.5 else ""
    print(f"{job:14} held {held:6.1f}h  worked {worked:6.1f}h  waste {waste:6.1f}h{flag}")
# NVIDIA DCGM guidance: SM activity < 0.5 likely = ineffective use.
# GPU-Util would call every row above 'busy'. This report does not.

06 Failure modes

Five ways GPU clusters quietly burn money — each with a one-line fix.

!

Allocated but idleFix: Notebooks and finished jobs hold GPUs for days at ~0% SM activity. Fix: export DCGM per job, warn at low SM activity, and reap idle allocations after a grace period.

!

Fragmentation blocks the big jobFix: Free GPUs scattered one-per-node cannot host an 8-GPU gang job, so capacity looks free while the queue waits. Fix: gang + topology-aware placement, whole-node reservations for large jobs, and periodic defragmentation drains.

!

GPU-Util says 100%, the job is slowFix: The duty-cycle metric only proves a kernel ran; it may touch a fifth of the SMs. Fix: judge by DCGM SM activity, tensor activity and DRAM activity, then fix batch size, kernels, or data loading.

!

Time-sliced production inferenceFix: Many pods time-share one GPU with no memory isolation — one OOM or noisy neighbour breaks every latency SLO. Fix: use MIG partitions for production tenants and keep time-slicing for dev.

!

GPUs starved by CPUs and storageFix: Dataloaders and slow shared storage leave SMs waiting while the job still ‘owns’ the GPUs. Fix: allocate CPUs/memory per GPU (--cpus-per-gpu), stage data on local NVMe, and watch DRAM/PCIe activity for the stall.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

Allocation vs utilization
Allocation: a scheduler gave the GPU to a job. Utilization: the GPU’s SMs did useful work. Clusters waste money in the gap between the two — always measure both.
Device plugin
The vendor component (e.g. NVIDIA’s) that discovers GPUs on a node and advertises them to the kubelet as an extended resource like nvidia.com/gpu, so the Kubernetes scheduler can place pods on them.
GRES (Slurm)
Slurm’s Generic RESources: declare GresTypes=gpu and per-node Gres counts in slurm.conf, verify with AutoDetect=nvml, and jobs request GPUs explicitly with --gres / --gpus-per-node.
Gang scheduling
All-or-nothing placement: a multi-GPU job starts only when its full GPU set is available together. Prevents partial allocations idling or deadlocking while they wait for the rest.
Topology-aware placement
Placing a job’s GPUs to match the hardware interconnect: same NVLink domain first, then same node, then same fabric island — because collective traffic runs at the speed of the slowest link it crosses.
MIG
Multi-Instance GPU: hardware partitioning of one GPU into isolated instances, each with dedicated SMs, memory and bandwidth. Predictable performance and fault isolation; reconfigurable only when idle.
Time-slicing vs MPS
Time-slicing: processes take turns on the whole GPU — simple, no memory/performance isolation. MPS: processes run concurrently in one merged context — better for many small kernels, still shared fate. Neither isolates like MIG.
SM activity (DCGM 1002)
Fraction of time at least one warp was active on an SM, averaged over SMs. NVIDIA guidance: ≥0.8 is necessary but not sufficient for effective use; <0.5 likely indicates waste. The honest replacement for GPU-Util.
GPU-Util (duty cycle)
The nvidia-smi percentage: share of the sample window in which any kernel was running. A kernel using one-fifth of the SMs all window long reads 100%. Useful for spotting fully idle GPUs, useless as proof of efficiency.
Fragmentation
Free capacity scattered in unusable shapes — one GPU per node when jobs need eight together. Fixed by topology-aware placement, reservations for large jobs, backfill for small ones, and defrag drains.

11 Reach for this when…

GPU queues are long but the bill says the cluster is ‘fully utilized’ — split allocation, GPU-Util and SM activity; the gap tells you whether to fix scheduling, sharing, or the jobs.
Teams are requesting more GPUs / a new cluster — run the held-vs-worked audit first; reaping idle allocations and MIG-sharing small models is cheaper than hardware.
A multi-GPU training job runs far below expected throughput — check placement against NVLink/fabric topology and DRAM activity before touching the model code.
