Git workflows for teams

Git gives every developer a full local copy of history — and then says nothing about how ten developers should share it. A Git workflow is that missing contract: which branches exist, how long they live, and how code travels from a laptop to production. Trunk-based development, GitHub Flow, and Git Flow are three answers to the same question — how long does code stay apart before it comes back together? — and the longer the answer, the more structure you buy and the more painful the merge.

02 The one-idea version

A Git workflow is a team agreement about branch lifetimes — how long code stays apart before merging. Everything else — branch names, pull-request rules, protections — is just enforcement of that one decision. Short branches mean cheap merges and fresh context; long branches buy isolation and release ceremony at the price of merge hell. Pick the lifetime that matches your release cadence, then make the machine protect it.

03 One variable, three workflows

The three models differ in one thing: how long a branch lives before it returns. Dots are commits; the animated paths are code flowing back into the shared line. Longer life, more structure, harder merges.

04 How it works

Seven mechanics. The contract first, the three models next, then history hygiene and enforcement.

1

A workflow is a contract Git itself never enforces

Git gives you branches and merges; it has no opinion about which branches should exist. The workflow is the team’s agreement: which branches are permanent, how long feature branches may live, and how code moves from a laptop to production. If it isn’t written down and enforced, you don’t have a workflow — you have a dozen personal habits sharing one repo.

2

Trunk-based: integrate into main at least daily

Everyone commits to main — directly on tiny teams, through short-lived branches (hours, not days) with fast PR review everywhere else. Work that isn’t user-ready ships dark behind feature flags. Conflicts are small because nobody is far from main, and CI tests the exact combination that will ship. The price: main must be releasable at all times, so a broken build blocks everyone until it’s green — revert first, debug second.

3

GitHub Flow: one permanent branch, the PR is the review unit

Branch off main for each change, push it, open a pull request, discuss, review, merge, delete the branch, deploy from main. Main is always deployable. Branches live hours to days — if a PR quietly grows into a three-week branch, you’ve drifted into long-lived feature branching and lost the model’s whole point. Best default for teams that deploy continuously and support one version.

4

Git Flow: dedicated branches for versioned releases

Two permanent branches: main holds tagged production releases, develop is the integration branch. feature/* branches off and back into develop; release/* branches stabilize a version, then merge into both main (tagged) and develop; hotfix/* is the only branch ever created directly off main, for urgent production patches merged both ways. Fits installable software and versioned releases — at the cost of more process and more painful merges.

5

Merge vs rebase is a history choice — consistency is the rule

Merge commits preserve the honest record: this work happened on a branch. Squash merges compress a PR into one clean commit — a readable changelog, at the cost of losing the branch’s internal history. Rebase replays your local commits onto the latest main for a linear history. Pick one per repo and stick with it. The hard rule: never rewrite history others depend on — rebase only branches you alone own, and if you must force-push, use --force-with-lease.

6

Protect main: turn the contract into machinery

Branch protection is the workflow enforced by the server: require pull requests to change main, require approving reviews, require status checks (CI) to pass, and require the branch to be up to date before merging. Humans will slip — push straight to main at 11 PM, skip a review “just this once” — and the protection is there precisely for those moments. Also protect against accidental deletion of main itself.

7

Keep integration cheap: small PRs, fresh branches, fast reviews

Three habits make any workflow work: keep pull requests small enough to review in one sitting (a few hundred lines, not thousands) — large PRs get rubber-stamped, not reviewed; sync the branch with main daily (merge or rebase locally) so the final merge is a non-event; and review within 24 hours so branches don’t age. On high-traffic repos, a merge queue serializes merges so main stays green.

05 Code sketch

A tiny workflow conscience for a pre-push hook: it blocks direct pushes to main, enforces branch naming, and refuses stale branches. Wire it into .git/hooks/pre-push and the contract enforces itself.

#!/usr/bin/env python3 — workflow_lint.py
import subprocess, sys, re

def git(*a):
    return subprocess.run(["git", *a],
        capture_output=True, text=True).stdout.strip()

branch = git("branch", "--show-current")

# 1. nobody pushes straight to the trunk
if branch == "main":
    sys.exit("Blocked: pushing directly to main. Branch first.")

# 2. branch names follow the convention: type/short-description
if not re.match(r"^(feature|bugfix|hotfix|release)/[a-z0-9-]+$", branch):
    sys.exit(f"Blocked: rename '{branch}' like feature/checkout-validation.")

# 3. a branch 20+ commits behind main is a merge bomb
behind = int(git("rev-list", "--count", f"{branch}...origin/main"))
if behind > 20:
    sys.exit(f"Blocked: {behind} commits behind main — sync first.")

print(f"OK: {branch} is {behind} commits behind main. Pushing.")

06 Failure modes

Five ways teams break their Git workflow, each with the fix.

!

The three-week feature branchFix: integrate at least daily; split the work into shippable slices behind feature flags.

A branch that lives for weeks becomes a merge bomb: by the time it merges, main has moved on and the conflicts are someone else’s rewritten code. The fix isn’t more care during the merge — it’s a shorter branch. If the feature can’t ship in a day, it isn’t one feature; it’s a release plan hiding behind a flag.

!

Rebasing a branch someone else is working onFix: never rewrite shared history — rebase only branches you alone own; if you must force-push, use --force-with-lease.

Rebase rewrites commits; anyone who already pulled the old commits now has a parallel, divergent history that won’t merge cleanly. The teammate’s git pull becomes a puzzle of duplicates. Announce the rebase, agree on it, or just don’t.

!

Pushing straight to main “just this once”Fix: branch protection — require pull requests, approving reviews, and passing CI. Humans slip; the server shouldn’t.

It starts with the emergency fix at 11 PM and ends with “who pushed to main without a review?” on a production incident. Willpower is not a workflow. Protect main and make the right path the only path.

!

The 2,500-line pull request that gets rubber-stampedFix: keep PRs small enough to review in one sitting; stack or split big work across multiple PRs.

Nobody carefully reviews three weeks of work. They skim, they approve, and the bug ships with “LGTM.” The root cause isn’t a lazy reviewer — it’s an unreviewable unit. A 200-line PR gets line-by-line attention; a 2,500-line one gets a prayer.

!

Main is broken and nobody can shipFix: revert first, debug second — restoring green is everyone’s top priority until it happens.

On trunk-based teams a red main is a production freeze; on any team it’s a queue of PRs nobody can merge. Debugging in place keeps the repo red for hours. A revert is one commit and takes minutes — the investigation can continue on a branch, out of everyone else’s way.

08 Sample prompts

Copy-paste these into your AI assistant when you’re setting or fixing a team’s Git workflow.

STRATEGY: PICK THE MODEL

Help my team pick a Git branching strategy: [team size, release cadence — continuous deploy vs scheduled releases, CI maturity and test coverage, how many versions we support in the field, who reviews code and how fast]. Compare trunk-based development, GitHub Flow, and Git Flow for our situation: recommend one with reasons tied to OUR context, name what we'd need to be good at for it to work (feature flags? PR size discipline? merge queues?), and flag the most likely failure mode for our team.

ENFORCE: PROTECT THE CONTRACT

Draft the branch protection and PR checklist for this repo: [which workflow we follow — trunk-based / GitHub Flow / Git Flow, what CI must pass before merge, who must approve]. Give me: (1) the branch protection rules to set on main (reviews, status checks, up-to-date requirement, force-push policy); (2) a PR description template that makes reviews fast (what changed, why, how tested, risk/rollback); (3) the repo convention for merge vs squash vs rebase — one rule, consistently applied.

RESCUE: UNTANGLE THE BRANCH

This branch is a mess and it's mine alone — no one else has pulled it: [paste git log --oneline -15 and git status, plus what's wrong — 60 commits behind main, merge conflicts, a bad rebase]. Plan the recovery: (1) the safest order of operations (backup first — how?); (2) whether to merge main in or rebase onto it, given it's unshared; (3) how to shrink the 40-commit mess into reviewable units before opening the PR. Give exact commands in order.

10 Flashcards

Workflow
A team agreement: which branches exist, how long they live, how code moves to production. Git won't enforce it — branch protection and habit will.
Trunk-based development
Everyone integrates into main at least daily; branches (if any) live hours. Feature flags hide unfinished work; strong CI is mandatory; a broken main blocks everyone.
GitHub Flow
One permanent branch (main), always deployable. Branch per change → pull request → review → merge → deploy → delete the branch. The PR is the review unit.
Git Flow
main holds tagged production releases; develop is the integration branch. feature/* off develop, release/* stabilizes a version, hotfix/* (off main) patches production.
Feature branch
A short-lived branch for one change: create it, integrate often, merge it, delete it. A branch that lives for weeks becomes a merge bomb.
Pull request
A proposal plus a review conversation: describe the change, get feedback, pass CI, merge. Keep it small enough to review in one sitting — hundreds of lines, not thousands.
Merge vs rebase
Merge commits preserve history honestly ("this was a branch"); squash gives a clean linear log. Rebase rewrites local history — never rewrite history others depend on.
Branch protection
Server-side rules on main: require pull requests, approving reviews, passing status checks, and up-to-date branches. The workflow contract, enforced by the machine.
Hotfix branch
The only branch ever created directly off main: an urgent production fix, merged into both main (tagged) and develop so the fix doesn't die on a release line.

11 Reach for this when…

Commits keep colliding, PRs take days to review, and merges are painful — your branches are too long-lived. Shorten them: integrate daily, split the work behind flags, and watch the merge conflicts evaporate.
The team argues about merge vs rebase, or someone pushed straight to main “just this once” — you have a dozen personal habits, not a workflow. Pick one model, write it down, and let branch protection enforce it.
You ship versioned releases and support more than one version in the field — Git Flow’s release and hotfix branches exist for exactly this: stabilize one version while the next one grows on develop.
