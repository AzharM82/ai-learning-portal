Retrieval-augmented generation in production: chunking, ranking, grounding

A demo RAG answers from ten documents. Production RAG must answer correctly, with citations, from millions of chunks — under permissions, latency budgets, and changing data. The difference is not a bigger model: it is chunking that preserves meaning, ranking in two stages, and grounding enforced in code.

02 The one-idea version

Production RAG is a retrieval system with a generator attached — the model can only be as right as the chunks you hand it. If the right chunk was never indexed, was cut in half, was ranked 51st, or was never permitted for this user, no prompt can save the answer. So engineer the pipeline in order: chunking decides what can be found, ranking decides what is found, and grounding decides whether the answer is allowed to claim it.

03 The picture: chunk, rank, ground

Offline, documents become self-contained, permission-tagged chunks. Online, a wide hybrid search is narrowed by a reranker, then generation is checked against the evidence.

04 How it works

Seven mechanics, in pipeline order — each one removes a class of production failure.

1

Chunk by meaning, not by character count alone

Split on structure first — headings, paragraphs, table rows, code blocks — then size. Start around 300–500 tokens with 10–20% overlap for prose; use semantic chunking where boundaries are unclear and hierarchical (parent/child) chunking for nested manuals: retrieve the precise child, hand the model its parent. Never cut a clause, a table header from its rows, or a condition from its exception. Prepend the document title and section path to each chunk so a chunk alone still says what it is about.

2

Stamp every chunk with metadata — and use one embedding model

Store source_id, title, section, updated_at, acl_groups, language, chunk_id, parent_id on every chunk. Metadata is what makes filtering, freshness, citations, and deletion possible later. Embed chunks and queries with the exact same model and version; changing the model means re-embedding the whole corpus, so version the index and cut over atomically, never mix two embedding spaces in one index.

3

Retrieve wide with hybrid search

Run keyword (BM25) and vector search in parallel and fuse them (for example with Reciprocal Rank Fusion). Vectors catch paraphrase and synonyms; BM25 catches exact terms vectors miss — SKUs, error codes, names, numbers. Azure AI Search and Amazon Bedrock both recommend this hybrid pattern for production RAG. Retrieve generously here — top 30–50 — because the next stage exists to narrow. Apply metadata and permission filters during retrieval, not after: a chunk the user may not see must never enter ranking or the prompt.

4

Rerank narrow with a cross-encoder, then budget the context

Re-score the wide set with a cross-encoder / semantic ranker that reads query and chunk together — far more precise than a bi-encoder similarity score, and affordable only on a small set. Keep the top 3–8, drop near-duplicates, drop anything below a relevance threshold, and assemble within a fixed token budget, best evidence first and last. Sending 20 mediocre chunks costs more, is slower, and buries the answer in the middle.

5

Ground in code: citations, thresholds, and an abstain path

Instruct the model to answer only from the supplied chunks and cite the chunk ID for every factual claim. Then enforce it outside the model: verify citations resolve to kept chunks, run a grounding/faithfulness check (for example Bedrock Guardrails contextual grounding or a sampled judge), and if retrieval confidence is low, abstain — “I don’t have that in the sources” — or escalate to a human. A fluent answer with no evidence is a defect, not a fallback.

6

Keep the index fresh and deletable

Index incrementally: diff sources, re-chunk and re-embed only changed documents, and propagate deletions and permission changes promptly — a stale chunk is a wrong answer and a revoked chunk is a security incident. Record corpus and index versions on every answer trace so a bad answer can be replayed against exactly what was indexed at the time.

7

Evaluate retrieval and generation separately, continuously

Maintain a golden set of questions with the chunks that should be retrieved and the facts that should appear. Measure retrieval with recall@k and precision@k, generation with faithfulness, correctness, and citation precision/coverage, plus p95 latency and cost per answer. When a score drops, the split tells you where to fix: missing chunk = chunking/index problem, right chunk ranked low = ranking problem, right chunk in context but wrong answer = grounding/prompt problem. Gate chunking, embedding, and prompt changes on this suite in CI.

05 Code sketch

A minimal production-shaped pipeline in Python: hybrid retrieve, rerank, ground, abstain.

# rag_prod.py — wide retrieve, narrow rerank, grounded answer or abstain
def answer(question, user_groups, index, reranker, llm):
    qvec = embed(question)  # same model+version used at indexing time
    hits = index.hybrid_search(
        text=question, vector=qvec, top=50,
        filter={"acl_groups": {"$in": user_groups}},  # trim BEFORE ranking
    )
    ranked = reranker.score(question, hits)        # cross-encoder re-scores
    kept = [h for h in ranked if h.score >= 0.35][:5]
    kept = dedupe(kept)
    if not kept:
        return {"answer": "I don't have that in the available sources.",
                "citations": [], "abstained": True}
    context = "\n\n".join(f"[{h.id}] {h.title} > {h.section}\n{h.text}"
                           for h in kept)
    out = llm.generate(
        system="Answer ONLY from the sources. Cite [chunk-id] per claim. "
               "If the sources don't say it, say so.",
        prompt=f"Sources:\n{context}\n\nQuestion: {question}")
    cited = verify_citations(out, allowed={h.id for h in kept})
    return {"answer": out, "citations": cited, "abstained": False}

06 Failure modes

Six ways production RAG quietly goes wrong — each with a one-line fix.

!

The split clauseFix: A fixed-size cut separates a rule from its exception, so retrieval returns a confident half-truth. Fix: chunk on structure/semantics, keep tables and conditions intact, add overlap, and prepend title + section path.

!

Vector-only retrieval misses the exact termFix: The answer hinges on a SKU, error code, or name that embeddings rank poorly. Fix: hybrid BM25 + vector with rank fusion, and evaluate on exact-term questions explicitly.

!

Permission check after retrievalFix: Restricted chunks enter the prompt (and can leak through the answer) before anyone filters them. Fix: permission-trim as a retrieval filter, per user/group, and test with a user who should see nothing.

!

Top-k stuffingFix: Twenty chunks are pasted in “to be safe”; cost and latency rise and the key passage is lost in the middle. Fix: rerank to a small kept set, threshold it, dedupe, and budget tokens deliberately.

!

No abstain pathFix: Retrieval finds nothing relevant, so the model answers from memory — fluently and wrongly. Fix: relevance threshold + explicit abstain/escalate response, measured as a first-class outcome.

!

Stale index, silent driftFix: Documents changed or were revoked weeks ago; the index still serves the old chunks and nobody can replay a bad answer. Fix: incremental re-indexing with deletion/ACL propagation, index version on every trace, and a golden-set eval on every change.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

Chunking
Splitting documents into retrievable pieces. Chunk on structure/semantics so each chunk expresses one complete idea; a bad split makes the right answer unfindable or half-true.
Hierarchical chunking
Parent/child chunks: search matches the small, precise child; the model receives the larger parent for context. Best for nested manuals, contracts, and specs.
Hybrid search
BM25 keyword search + vector search in parallel, fused (e.g. Reciprocal Rank Fusion). Keywords win on exact terms; vectors win on paraphrase. Production default.
Reranker (cross-encoder)
A model that scores query and chunk together for a precise relevance judgment. Too expensive for the whole index — apply it to the wide retrieval set (top 30–50) and keep the top few.
Grounding
Constraining the answer to the retrieved evidence: answer only from the chunks, cite each claim, verify citations, and check faithfulness. Anything not in the sources is ungrounded.
Permission trimming
Filtering retrieval by the requesting user’s access (ACL metadata) during search — before ranking and prompting. Filtering after generation is a leak, not a control.
Recall@k vs precision@k
Recall@k: of the chunks that should be found, how many are in the top k? Precision@k: of the top k, how many are relevant? Retrieval eval needs both — wide for recall, reranked for precision.
Faithfulness
Whether every claim in the answer is supported by the retrieved context. The generation-side metric that separates “retrieval failed” from “the model ignored good evidence.”
Abstain path
The designed response when evidence is missing or below threshold: say the sources don’t cover it, or escalate. A production RAG without an abstain path will hallucinate on schedule.
One embedding model rule
Chunks and queries must live in the same embedding space: same model, same version. Changing the model means re-embedding the corpus and cutting the index over atomically.

11 Reach for this when…

A RAG demo works but real users get confident wrong answers — stop tuning the prompt; instrument the pipeline and find whether chunking, retrieval, ranking, or grounding is the failing stage.
You are scaling from hundreds to millions of documents, or adding restricted content — hybrid search, reranking, permission trimming, and incremental indexing stop being optimizations and become requirements.
Answers must be auditable — support, legal, finance, or compliance use — citations on every claim, a grounding check, an abstain path, and versioned traces are the difference between a tool and a liability.
