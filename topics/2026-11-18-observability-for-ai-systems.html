Observability for AI systems: tracing, drift, and quality monitoring

AI systems fail silently — they return fluent, wrong answers while latency and cost creep. Trace every run, watch inputs and outputs for drift, and score quality continuously, so you catch decay before users do.

02 The one-idea version

An AI system has no stack trace for a wrong answer — so you must build one. A trace records what the system actually did (model, retrieval, tools, tokens, latency); drift monitoring records how the world it serves is changing; quality monitoring records whether the answers are still good. Miss any one of the three and the other two will lie to you by omission.

03 The picture: trace, drift, quality — three loops

One request flows left to right. Three monitoring loops watch it at different timescales.

04 How it works

Six mechanics: trace with a standard, account for cost, separate content from metadata, compare windows for drift, score quality on samples, alert on symptoms.

1

Trace every run as a span tree, using the GenAI conventions

Emit one root invoke_agent span per run, a chat span per model call, and an execute_tool span per tool or retrieval step, following the OpenTelemetry GenAI semantic conventions. Always record gen_ai.request.model, input/output token counts, finish reason, and duration — the OpenTelemetry walkthrough shows exactly this tree in a dashboard. Propagate the trace ID across services and agent handoffs so a multi-agent run stays one trace, not five fragments.

2

Keep content out of span attributes by default — capture it deliberately

Prompts and completions are large and often contain PII. The GenAI conventions capture metadata by default and make content opt-in. In production, record content in events or separate, access-controlled storage with only a reference on the span, redact before export, and set a retention window. You need enough content to debug and evaluate — you do not need every user's prompt indexed forever in your tracing backend.

3

Turn traces into metrics: latency, tokens, cost, and errors per slice

Aggregate gen_ai.client.operation.duration and token usage into dashboards sliced by model, prompt version, feature, and customer segment. Price tokens at ingestion so cost is a first-class metric, not a monthly invoice surprise. Track time-to-first-token for streaming, tool error rate, retry count, and empty/refusal rate. Alert on p95 latency, error rate, and cost per successful task — not on raw token volume, which rises happily with growth.

4

Monitor drift as a window comparison — reference vs current, no labels required

Pick a reference window (training data or a known-good week) and compare each new window against it. Evidently's DataDriftPreset does this per column, choosing the test by column type (PSI, KS, Jensen-Shannon, Wasserstein among others) and reporting the share of drifting columns — by default dataset drift at 50% or more. For LLMs, apply the same idea to prompt topics, input length, language mix, embedding centroids, output length, and prediction distribution. Drift is a label-free early warning: it fires the day traffic changes, not months later when labels arrive.

5

Distinguish the three drifts — and do not retrain on autopilot

Data drift: P(X) changes — new users, new phrasing, a new upstream format. Prediction drift: P(prediction) changes — the model answers differently, which may be correct adaptation or decay. Concept drift: P(y|X) changes — the right answer for the same input changed (policy, price, facts). Data drift alone does not prove quality fell, and retraining on drifted data without checking labels can bake in the problem. Use drift to trigger labelling and evaluation first; retrain only when quality evidence says so.

6

Score quality continuously on samples, and close the loop into evals

You cannot hand-grade every output, so sample: run code checks (schema, groundedness against retrieved sources, refusal correctness) on all traffic where cheap, an LLM judge on a stratified sample, and attach user feedback to the exact trace it came from — the LangSmith tutorial's prototyping-to-production flow is built on that trace-plus-feedback loop. Watch judge scores by segment, not just globally. Every confirmed production failure becomes a new case in your regression eval set; that harvest is what makes next month's monitoring smarter than this month's.

7

Alert on symptoms with a drill path, sample traces intelligently

Define SLOs for the user-visible symptoms: success rate, p95 latency, quality score floor, cost per task. Use tail-based sampling — keep 100% of errors, slow runs, and low-quality scores, sample the healthy majority — so storage stays affordable without blinding you to failures. Every alert must land on a filtered trace view and a runbook step (check drift, check deploy/prompt version, check provider status), or it will be muted within a month.

05 Code sketch

Trace a model call with GenAI attributes, then run a drift check comparing this week's traffic to a reference window.

# 1) One trace per run, one span per model call (OpenTelemetry GenAI)
from opentelemetry import trace
tracer = trace.get_tracer("support-agent")

def answer(question, docs):
    with tracer.start_as_current_span("invoke_agent support-bot") as root:
        root.set_attribute("gen_ai.agent.name", "support-bot")
        with tracer.start_as_current_span("chat gpt-4o") as span:
            span.set_attributes({
                "gen_ai.operation.name": "chat",
                "gen_ai.request.model": "gpt-4o",
            })
            reply, usage = call_model(question, docs)  # your client
            span.set_attributes({
                "gen_ai.usage.input_tokens": usage.input,
                "gen_ai.usage.output_tokens": usage.output,
                "gen_ai.response.finish_reasons": [usage.finish],
            })
        return reply

# 2) Drift: current window vs reference window (Evidently preset idea)

06 Failure modes

Five ways AI observability goes wrong — each with a one-line fix.

1

Logging outputs, calling it observabilityFix: emit structured traces (spans, tokens, model, version, tool results) you can slice and alert on — raw text logs are for reading, traces are for querying.

A folder of prompt/response logs tells you what one request said and nothing about rates, segments, latency, or cost. The first real incident becomes an archaeology project.

2

Storing every prompt foreverFix: metadata by default, content opt-in with redaction, separate storage, short retention, and tail sampling that keeps failures at 100%.

Full-content tracing at full volume is a privacy incident and a storage bill waiting to happen — and teams respond by turning tracing off entirely, losing the metadata they actually needed.

3

Watching accuracy while labels lag by monthsFix: monitor inputs, predictions, and embeddings for drift as the early warning, and use sampled judge/feedback scores as the quality proxy until labels land.

For loans, support resolutions, and most LLM tasks, ground truth arrives late or never. A dashboard that only shows labelled accuracy is calm precisely while the system decays.

4

Treating every drift alert as a retraining orderFix: drift triggers investigation and labelling first — retrain only when a quality metric, not just a distribution metric, has moved.

Seasonal traffic, a marketing launch, and a new customer segment all drift legitimately. Auto-retraining on drift alone can train on mislabelled or adversarial new data and make quality worse.

5

One global quality score that hides the broken segmentFix: slice every quality, latency, and cost metric by model, prompt version, language, and customer segment; alert per slice with a minimum volume.

The average stays green while one language, one tenant, or one prompt version collapses — because it is 3% of traffic. Averages are where AI incidents hide.

6

Alerts with no drill pathFix: every alert links to the filtered traces for its window and names the first three runbook checks (drift? deploy? provider?).

A chart that pages at 3 a.m. with no trace link and no owner gets muted, and the next real decay is discovered by a customer instead.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

Trace / span
A trace is one run end-to-end; spans are its timed steps (agent, model call, tool, retrieval). GenAI spans carry model, tokens, finish reason, and duration as attributes.
gen_ai.* conventions
OpenTelemetry's standard attribute names for AI telemetry (gen_ai.request.model, gen_ai.usage.input_tokens, gen_ai.client.operation.duration), so traces look the same across providers and backends.
Data drift
P(X) changed: the input distribution now differs from the reference window. Detectable immediately, without labels — an early warning, not proof that quality fell.
Concept drift
P(y|X) changed: the correct answer for the same input is now different (new policy, price, or facts). The hardest drift — it needs fresh labels or evals to confirm.
Reference window
The baseline distribution every drift check compares against — training data or a known-good period. Choose it deliberately and refresh it on a policy, not on a whim.
PSI / KS / Wasserstein
Distribution distances for drift: PSI bins and compares shares, KS takes the max gap between CDFs, Wasserstein measures the work to morph one distribution into the other. Pick by column type.
Tail-based sampling
Keep 100% of errors, slow runs, and low-quality outputs; sample the healthy majority. Storage stays affordable without blinding you to exactly the traces you need in an incident.
Online evaluation
Scoring live outputs continuously: cheap code checks on all traffic, an LLM judge on a stratified sample, and user feedback attached to its trace. Trends by segment are the quality SLO.
Silent failure
The defining AI failure mode: the system returns a well-formed, fluent, wrong answer with a 200 status. Only tracing, drift, and quality monitoring together can catch it.

11 Reach for this when…

Users report bad answers but every dashboard is green — you have infrastructure monitoring, not AI observability: add GenAI traces, per-segment quality sampling, and drift windows before the next release.
A model, prompt, or provider change is about to ship — baseline the current traces, tokens, cost, and quality scores first, so the change has something to be compared against slice by slice.
Labels arrive late (or never) for your task — stand up reference-vs-current drift on inputs, predictions, and embeddings plus sampled judge scores; that pair is your early-warning system.
