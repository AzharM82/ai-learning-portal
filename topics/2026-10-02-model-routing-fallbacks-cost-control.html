Model routing, fallbacks, and cost control

Your app should never call "the model" — it should call a logical name and let a gateway decide what actually serves it. A router spreads traffic across deployments by strategy (cost, latency, load), retries on transient failures, fails over to backups when a provider is down, and enforces spend budgets per key and team — so an outage becomes a blip and a cost spike becomes a bounded event.

02 The one-idea version

Hard-code a model and you hard-code your failure mode: one provider outage takes you down, and one pricing change rewrites your bill. A routing layer puts a logical name between your app and every deployment: each request is dispatched by strategy (cheapest capable, least busy, fastest), retries absorb transient 429s and 5xx, ordered fallbacks catch hard failures, and budgets cap spend per key and team. Three separate knobs — where the request goes, what happens when it fails, and how much it may cost — managed in one config instead of scattered through your code.

04 How it works

Six mechanics, each one a decision you'd make in production.

M1

Call a logical name, not a provider

Register several deployments under one model_name alias (e.g. support-chat → OpenAI + Azure deployments of the same model). Your code sends the alias; the gateway picks the deployment. Adding a new provider is a config change, not a code deploy.

M2

Route by strategy, per workload

Pick the dispatch rule: cost-based-routing (cheapest capable deployment), latency-based-routing (fastest recently), usage-based-routing (spread load evenly), or least-busy (fewest in-flight). Different model groups can run different strategies — latency for chat, cost for batch.

M3

Retry transient failures, then cool the deployment down

num_retries with exponential backoff absorbs 429s and 5xx. After allowed_fails failures in a minute, the deployment goes into cooldown_time — it stops receiving traffic while the rest carry the load. This is the difference between retrying (polite, bounded) and hammering a sick endpoint (a second outage of your own making).

M4

Fail over through an ordered list

fallbacks: [{"support-chat": ["support-chat-backup", "cheap-llm"]}] — tried in order, first healthy wins. Specialized lists exist for specialized errors: context_window_fallbacks for too-long prompts, content_policy_fallbacks for refusals. Fall back on the error type, not blindly on everything.

M5

Escalate by complexity: cheap first, frontier only when needed

Send every request to the cheap model first, verify its confidence or check the output, and escalate the hard cases up the ladder. Or classify up front and route tiers of requests to tiers of models. Either way, most of your traffic never pays frontier prices — this is where the real cost savings live.

M6

Track spend and hard-cap it with budgets

Every call is logged with model and cost, aggregated per key, user, and team (/key/info shows live spend). Set max_budget per key/team with alerts at 80% and a hard stop at 100%. Budgets turn "we discovered the bill on Monday" into "the key stopped working on Friday."

05 Code sketch

The whole pattern in 25 lines: one logical name, two deployments, an ordered fallback chain, cost-based routing.

import os
from litellm import Router

model_list = [  # two deployments, ONE logical name
    {"model_name": "support-chat",
     "litellm_params": {"model": "openai/gpt-4o-mini",
                            "api_key": os.getenv("OPENAI_API_KEY"),
                            "rpm": 900}},
    {"model_name": "support-chat",
     "litellm_params": {"model": "azure/gpt-4o-mini",
                            "api_base": os.getenv("AZURE_BASE"),
                            "api_key": os.getenv("AZURE_API_KEY"),
                            "rpm": 500}},
]

router = Router(
    model_list=model_list,
    routing_strategy="cost-based-routing",   # cheapest capable first
    num_retries=2,                            # then backoff + cooldown
    allowed_fails=3, cooldown_time=30,     # cool sick deployments
    fallbacks=[{"support-chat": ["support-chat", "cheap-llm"]}],
)

resp = router.completion(model="support-chat", messages=msgs)
print(resp._hidden_params["model_id"])  # which deployment actually served it

06 Failure modes

Named pitfalls, each with a one-line fix.

F1

No fallback configured — one provider outage is your outageFix: every production model_name gets an ordered fallback list, and you test it by injecting a provider error in staging before you need it in production.

F2

Retry storms: retries with no cooldown turn a partial outage into a full oneFix: set allowed_fails + cooldown_time so failing deployments stop receiving traffic, and never retry non-retryable errors like content-policy violations.

F3

Fallback-served answers silently pollute your evals — quality dropped, nobody noticed, because the cheap model answeredFix: log attempted_fallbacks and original_model_group on every request; filter evals by them so you grade what you think you're grading.

F4

Cost-based routing quietly degrades quality — the cheapest deployment wins every request, including the ones it can't doFix: cost routing only among deployments cleared for the task tier; pair it with per-task complexity escalation instead of a global cheapest-wins rule.

F5

No budget guardrails — an agent loop bug discovers a $20k bill on MondayFix: max_budget per key/team from day one, alert at 80%, hard stop at 100%, and a per-call cost view in your dashboards.

10 Flashcards

Click or press Enter/Space to flip each card.

Logical model name
An alias (e.g. "support-chat") your app calls instead of a provider's model string. The gateway maps it to real deployments — you change providers by editing config, not code.
Routing strategy
The rule that picks a deployment per request: cost-based (cheapest capable), latency-based (fastest recently), usage-based (spread load), least-busy (fewest in-flight). Set per model group.
Cooldown
After allowed_fails failures in a minute, a deployment stops receiving traffic for cooldown_time. Retrying without cooldown hammers a sick endpoint into a second outage.
Fallbacks
An ordered list of backup model groups tried in order, first healthy wins. Keep specialized lists: context_window_fallbacks for oversized prompts, content_policy_fallbacks for refusals.
Escalation by complexity
Send everything to the cheap model first, verify, and escalate only hard cases to frontier models. Most traffic never pays frontier prices — the main lever for real cost savings.
max_budget
A hard spend cap per key, user, or team. Pair with an 80% alert and a per-call cost dashboard — budgets turn a Monday-morning bill surprise into a Friday-night stop.
attempted_fallbacks
A spend-log field counting how many fallbacks served a request, plus original_model_group for what was requested. Without these fields, fallback-served answers silently pollute your evals.
Virtual key
A gateway-issued key with its own models, budget, and rate limits. One gateway key per team or feature gives you per-consumer spend tracking and a kill switch for each.
Retry vs failover
Retry = same deployment, transient error (429/5xx), bounded attempts with backoff. Failover = different model group, hard failure, ordered list. Retry first, then fail over.

11 Reach for this when…

Your app depends on one provider and you felt an outage once — a fallback list plus cooldown turns the next outage into a blip instead of a status-page incident.
Frontier models answer most of your traffic at frontier prices — route simple work to cheap models and escalate only hard cases; this is usually the single biggest cost lever in an AI app.
Nobody can say what the LLM bill will be next month — per-key/per-team spend tracking plus max_budget makes cost a configuration, not a surprise.
