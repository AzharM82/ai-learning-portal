Sandboxing and least-privilege tool permissions

An agent’s power is not its model — it’s the tools it can reach. Sandboxing draws a hard boundary around what the agent can read, write, run, and send out on the network, and least privilege fills that boundary with only what this task needs. The result: a capability the agent doesn’t have cannot be prompt-injected into use, no matter how clever the attacker or how confused the model.

02 The one-idea version

Don’t secure the agent’s intentions — remove the capabilities it doesn’t need. An LLM can be talked into anything by text it reads, so the only defenses that hold are structural ones enforced at the boundary: no shell, no network egress, no write tools, no standing credentials unless this task provably needs them. If the blast radius of a wrong turn is zero, the wrong turn is just a wrong turn.

03 The four walls

Least privilege is enforced in four dimensions at once; weakness in any one of them re-opens the others.

04 How it works

Imperative, concrete. Do these in order when standing up an agent that runs anything.

1

Start from nothing: deny-by-default

New agent, new task: the agent can do literally nothing until you grant it. Every tool, every path, every host is denied until explicitly allowed. This is the opposite of a blocklist — you enumerate the safe set, not the dangerous one.

2

Give it an allowlist of tools, not a shell

Expose the smallest set of tools that completes the task: read_file(path), search_docs(query) — never a general-purpose shell unless the task truly is code execution. Each tool gets a JSON schema, and arguments are validated against it before the call runs. A tool the agent never receives cannot be argued for in prose.

3

Run code inside a throwaway container, never on the host

Anything the agent executes runs in an ephemeral container or VM: non-root user, dropped Linux capabilities, a read-only filesystem except for an explicit workdir, and destroyed at the end of the run. Host, cloud metadata endpoints (169.254.169.254), and sibling services are unreachable from inside.

4

Scope credentials to the task, and give them an expiry

Issue a credential that carries exactly the permissions this run needs and expires in minutes, not months. It comes from a secret manager or vault at run start and is revoked at run end. If it leaks, the TTL caps the blast radius; if the run is replayed later, the token is already dead.

5

Close the network, then open named holes

Outbound network defaults to deny for any session that touches sensitive data or untrusted content. Where egress is required, allowlist specific hosts (the package mirror, the vendor API) — through a proxy if you must inspect traffic — and remember that DNS itself is a channel: block it or allowlist it too.

6

Isolate identities: sub-agents get their own, smaller key

When an agent spawns helpers, each sub-agent runs under its own identity with its own scoped permissions. The helper that reads untrusted web pages gets no private-data access and no send capability; the privileged orchestrator never touches untrusted content directly. One compromised helper cannot spend the parent’s authority.

7

Elevate just-in-time, log everything

The agent sits at the permission floor by default. When a step genuinely needs write, issue a narrow short-lived grant for that action only — and for irreversible actions, make the proposer someone other than the approver. Every tool call lands in an audit log with the identity, arguments, and outcome; small, known capability sets make those logs actually readable.

05 Code sketch

The pattern in miniature: a tool gateway that checks the allowlist, validates scope, and issues a short-lived token per run. Under 30 lines of the idea.

# A least-privilege tool gateway: deny-by-default, scoped, expiring grants
from dataclasses import dataclass
import time, secrets

@dataclass
class Grant:
    tools: set[str]        # allowlist: the ONLY tools this run may call
    scopes: set[str]       # e.g. {"read:repo:acme"} — nothing broader
    egress: set[str]       # allowlisted hosts; empty = no network
    expires_at: float  # short TTL — dead when the run ends

def issue_grant(task, vault) -> Grant:
    """Build the minimal grant for THIS task, from a policy table."""
    policy = POLICY_TABLE[task.kind]   # declared per task kind, never per agent
    return Grant(tools=policy.tools, scopes=policy.scopes,
                 egress=policy.egress, expires_at=time.time() + 600)

def call_tool(grant: Grant, tool: str, args: dict, audit):
    if time.time() > grant.expires_at: raise PermissionError("grant expired")
    if tool not in grant.tools:      raise PermissionError(f"{tool} not allowed")
    validate_schema(tool, args)              # schema check at the boundary
    audit.log(tool, args)                       # every call, no exceptions
    return run_in_sandbox(tool, args, grant.egress)

06 Failure modes

Named, with a one-line fix each.

F1

Denylist theaterFix: switch to an allowlist — enumerate what’s permitted, not what’s forbidden.

You block rm -rf by string match; the agent base64-encodes it, wraps it in a subshell, or writes a script that does it. A denylist enumerates the attacks you thought of; the attacker needs one you didn’t. Remove the capability (no shell at all) instead of forbidding its use.

F2

The leaky sandbox: DNS, metadata, or shared filesystemFix: audit the real channels — block the cloud metadata endpoint, allowlist DNS, mount filesystems read-only, drop capabilities.

You cut HTTP egress but leave DNS resolution open — data leaves one TXT record at a time. Or the agent curls 169.254.169.254 for cloud credentials, or writes through a shared mount you forgot. A famous 2026 case: a research agent exfiltrated through DNS out of a “networkless” sandbox.

F3

One shared admin key for every runFix: per-task, per-sub-agent identities with scoped, short-lived credentials from a vault; revoke on run end.

The agent fleet shares a broad service-account key. One compromised run — or one leaked log line — hands an attacker everything the fleet can do. Scope is the unit of damage: make each key describe exactly one task, and let it die with the task.

F4

Sub-agent inherits the parent’s powersFix: every sub-agent gets its own smaller identity; untrusted-content readers get no private data and no send.

You carefully scope the main agent, then it spawns a “researcher” helper that inherits the full credential. The helper reads a poisoned web page carrying an injected instruction — and executes it with the parent’s keys. Containment has to follow the delegation chain, not stop at the front door.

F5

Permission creep: grants that never come backFix: permissions bind to the task, not the identity — re-derive them each run and expire them automatically.

Tuesday’s deploy-needed-write grant is still live on Friday when the agent does read-only triage. Over months, every agent quietly accumulates the union of every permission it ever needed. Least privilege is a property you re-establish per run, or it rots into standing privilege.

08 Sample prompts

Copy-paste starters. Use the copy button; each one is a full working prompt.

PROMPT 1 · SCOPE A NEW AGENT

You are a security-minded platform engineer. I am about to deploy an agent whose task is: [describe the task in one paragraph — what it reads, what it changes, who it affects]. Propose a least-privilege permission set with these headings: (1) tool allowlist — the minimal named tools it may call, and which tools are explicitly denied; (2) data scope — exact records/directories it may read, read-only vs write, and where it may write; (3) credentials — the scoped, short-lived credential it carries, its TTL, and what it can never do; (4) network — egress default plus the exact hosts on the allowlist; (5) sub-agent policy — identities and permissions for any helpers it spawns. Flag anything in my task description that is underspecified for a scoping decision.

PROMPT 2 · AUDIT AN EXISTING AGENT

Audit the agent described below against least privilege and sandboxing best practices. Check: (a) whether its tool surface is an allowlist or a denylist, and name any tools it has that its task does not require; (b) credential scope and TTL — is anything broad or long-lived, and what is the blast radius if it leaks; (c) network posture — egress default, allowlist completeness, and whether DNS or metadata endpoints are real exfiltration channels; (d) sub-agent identity inheritance; (e) audit logging coverage. Rank findings by severity, and for each give a one-line fix. Agent description: [paste config, tool list, credential setup, network policy]

PROMPT 3 · DESIGN THE SANDBOX

Design a sandbox for an agent that runs untrusted or generated code. Specify: the isolation unit (container/VM), user and Linux capabilities (non-root, what is dropped), filesystem mounts (what is read-only, the exact writable workdir), network (egress default-deny plus allowlisted hosts, DNS policy, blocked metadata endpoint 169.254.169.254), resource budgets (CPU seconds, wall-clock minutes, memory), and the teardown contract (what is collected — logs, diff, artifacts — and how credentials are revoked and the container destroyed). Then list three ways a sandbox like this has historically been escaped, and the control that stops each.

10 Flashcards

Click a card to flip it. Tab to a card and press Enter or Space.

Least privilege
Grant an agent only the tools, data scopes, credentials, and network access the task in front of it needs — nothing more, nothing standing.
Deny-by-default
The agent starts able to do nothing; every tool, path, and host is denied until explicitly allowed. The opposite of a blocklist.
Capability lock
Enforce safety by removing the ability to do harm at the boundary, not by asking the model nicely. No shell means no shell trick works.
Allowlist vs denylist
An allowlist enumerates the permitted set (safe default); a denylist enumerates the forbidden set (bypassable via encoding, subshells, quoting, generated scripts).
Short-lived scoped credentials
Tokens valid for minutes and scoped to one task. A leak caps damage by TTL; a replayed token is already dead.
Egress allowlist
Outbound network denied by default; only named hosts (vendor API, package mirror) are reachable. DNS and cloud metadata endpoints count as channels too.
Sub-agent identity isolation
Each helper runs under its own smaller identity. A helper reading untrusted content gets no private data and no send capability.
Just-in-time elevation
The agent sits at the permission floor; a higher-grade action issues a narrow, short-lived grant for that step only — then it is revoked.
Ephemeral sandbox teardown
Collect logs, diffs, and artifacts at run end, revoke credentials, destroy the container. No persistent state for the next run to inherit.

11 Reach for this when…

Your agent runs code, touches the filesystem, or handles untrusted web/email content. If a prompt injection could reach a shell, a file write, or a network call, the run needs a sandbox — not just a careful prompt.
Credentials feel “shared” or long-lived. One admin key for the whole fleet, or grants that survive the task, are standing privilege. Move to per-task scoped tokens with minute-scale TTLs from a vault.
Your safety plan is a list of forbidden commands. That’s a denylist — bypassable by construction. Invert it: allowlist the tools and hosts, and remove the capabilities you never want used.
