Kubernetes and container platforms: operators, autoscaling, multi-tenancy

Kubernetes is not just a container runner — it is a platform you program. Extend it with operators that encode operational knowledge, scale it with three distinct autoscalers, and share it safely with quotas, RBAC, and network policies per tenant.

02 The one-idea version

Kubernetes is a reconciliation engine, and a platform is what you build on top of it. You declare desired state; controllers loop forever making reality match it. Operators extend that loop with your domain knowledge, autoscalers let the loop change how much capacity exists, and multi-tenancy controls decide who is allowed to declare what — and how much they may consume.

03 The picture: declare, reconcile, scale, isolate

One cluster, three platform jobs stacked on the same control loop.

04 How it works

Seven mechanics: extend with operators, reconcile idempotently, scale on three axes, and isolate tenants in layers.

1

Extend the API with a CRD before you write any controller code

Define a CustomResourceDefinition that teaches the API server a new kind — for example SampleDB — with an OpenAPI schema, so invalid objects are rejected at admission. Users then declare the app the way they declare a Deployment: kubectl get SampleDB, edit it, delete it. The Kubernetes operator docs are explicit: operators are clients of the API acting as controllers for a Custom Resource, extending cluster behaviour without modifying Kubernetes itself.

2

Make reconcile level-based and idempotent — never edge-triggered

On every loop, read desired state from the CR and actual state from the cluster, then create, update, or delete the child objects (StatefulSet, PVCs, Jobs, Services) until they match. Running reconcile twice must be safe, because it will run after every watch event, restart, and resync. Handle upgrades, backups, and leader election inside that same loop, and write progress back to the CR's status — never to local memory the next replica will not have.

3

Scale replicas with HPA — and set requests first, or it cannot work

The HorizontalPodAutoscaler is a control loop (default sync every 15 seconds) that computes desiredReplicas = ceil(currentReplicas x currentMetric / targetMetric), with a 10% tolerance and a 5-minute scale-down stabilization window. CPU utilization is usage divided by the container's requests — no requests, no denominator, no scaling. Metrics come from Metrics Server via metrics.k8s.io, or from custom/external metrics APIs for queue depth and latency.

4

Scale size with VPA and nodes with Cluster Autoscaler / Karpenter — never fight HPA

VPA rightsizes a pod's requests from observed history instead of changing replica count. Cluster Autoscaler (or Karpenter) adds nodes when HPA-created pods stay Pending, and removes under-used nodes later. The rule that prevents oscillation: never let HPA and VPA both act on the same CPU/memory metric for the same workload — VPA moving the request moves the denominator HPA divides by.

5

Carve tenants with namespaces — then attach every control at creation

A namespace scopes names, RBAC, quotas, and policies; it is logical isolation, not a security boundary by itself. Stamp out each tenant namespace from one template: RoleBindings (least privilege, namespace-scoped only), a ResourceQuota, a LimitRange, a default-deny NetworkPolicy, and Pod Security labels. The official multi-tenancy guidance is blunt: if a tenant can modify another tenant's API objects, every other policy is negated — authorization comes first.

6

Stop noisy neighbours with ResourceQuota + LimitRange, paired

ResourceQuota caps aggregate requests, limits, pod/PVC/Service counts per namespace; LimitRange sets per-container defaults and maxima. Pair them: once a quota covers requests.cpu, every pod must declare it or be rejected — the LimitRange supplies the default so legitimate pods are not blocked. Leave 20-30% headroom and alert at 80% quota use, so an HPA scale-up during a spike is not killed by the quota meant to protect the cluster.

7

Choose soft vs hard tenancy by trust, and escalate deliberately

Soft tenancy (namespaces + RBAC + quotas + NetworkPolicy + Pod Security) fits trusted internal teams. Hard tenancy — untrusted customers, different compliance domains, tenants who need cluster-scoped resources or their own CRDs — needs virtual clusters (e.g. vCluster) or separate clusters, because tenants still share one API server, one kernel, and one node pool. Network isolation also requires a CNI that actually enforces NetworkPolicy; otherwise the objects are silently ignored.

05 Code sketch

A tenant namespace with quota, an HPA with a real denominator, and the reconcile shape every operator follows.

# Tenant guardrails + autoscaling (apply per namespace)
apiVersion: v1
kind: ResourceQuota
metadata: {name: tenant-quota, namespace: team-a}
spec:
  hard: {requests.cpu: "16", requests.memory: 64Gi, pods: "100"}
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: {name: web, namespace: team-a}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: web}
  minReplicas: 2
  maxReplicas: 20
  metrics:
  - type: Resource
    resource: {name: cpu, target: {type: Utilization, averageUtilization: 70}}
  behavior:
    scaleDown: {stabilizationWindowSeconds: 300}

# Operator reconcile: level-based, idempotent (pseudocode)
def reconcile(cr):
    desired = spec_of(cr)                 # what the user declared
    actual = read_children(cr)            # StatefulSet, PVC, Service
    apply_diff(desired, actual)           # safe to run repeatedly
    write_status(cr, phase=ready_or_progressing(actual))

06 Failure modes

Five ways platform work goes wrong — each with a one-line fix.

1

Building an operator for a stateless app a Deployment already handlesFix: use an operator only when day-2 knowledge (backup, failover, upgrade ordering, leader election) must be encoded — otherwise ship a Helm chart / Deployment.

Operators are the most complex extension point in Kubernetes. Every CRD is a new API you must version, secure, and support forever.

2

HPA shows <unknown> and never scalesFix: install Metrics Server and set CPU/memory requests on every container — utilization has no denominator without requests.

The second most common cause is scaling on a custom metric with no adapter exposing it to the custom metrics API.

3

HPA and VPA fighting over the same metricFix: pick one actor per metric — HPA on CPU with VPA in recommendation (Off) mode, or VPA on size and HPA on a custom metric like queue depth.

VPA raises requests, HPA's utilization falls, HPA scales down, load per pod rises — an oscillation loop with real outage risk.

4

Naked namespaces: isolation assumed, nothing enforcedFix: no namespace ships without RBAC, ResourceQuota + LimitRange, default-deny NetworkPolicy, and Pod Security labels — automate it at namespace creation.

By default pods can talk across namespaces, a tenant with broad RBAC can read another's Secrets, and one runaway workload can starve the node for everyone.

5

Treating namespaces as a hard security boundary for untrusted tenantsFix: escalate to virtual clusters or separate clusters when tenants are untrusted, need cluster-scoped resources, or sit in different compliance domains.

Shared kernel, shared API server, shared nodes: a container escape or a cluster-scoped CRD breaks the namespace story entirely.

6

Quota set to exactly today's usageFix: set quotas with 20-30% headroom, alert at 80%, and review monthly — quota is a fairness ceiling, not a capacity plan.

The first traffic spike fails not on node capacity but on an admission rejection, and the HPA gets blamed for a policy decision.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

Operator
A controller for a Custom Resource that encodes a human operator's domain knowledge — install, upgrade, backup, failover — as a reconcile loop against the Kubernetes API.
CRD / Custom Resource
A CustomResourceDefinition teaches the API server a new kind with a schema; a Custom Resource is one instance of it — the desired state users declare with kubectl.
Reconcile loop
Observe desired vs actual, act to close the gap, repeat forever. Level-based (full state each time) and idempotent — not a one-shot event handler.
HPA formula
desiredReplicas = ceil(currentReplicas x currentMetric / targetMetric), checked every 15s by default, with 10% tolerance and a 5-minute scale-down stabilization window.
HPA vs VPA vs Cluster Autoscaler
HPA changes pod count, VPA changes pod size (requests), Cluster Autoscaler/Karpenter changes node count when pods stay Pending. Never let HPA and VPA act on the same metric.
ResourceQuota / LimitRange
Quota caps aggregate consumption per namespace (requests, limits, object counts); LimitRange sets per-container defaults and maxima. Always pair them.
Soft vs hard tenancy
Soft: trusted teams sharing via namespaces, RBAC, quotas, NetworkPolicy. Hard: untrusted tenants needing virtual or separate clusters — shared kernel/API is not a boundary.
Noisy neighbour
One tenant degrading others by consuming shared CPU, memory, network, or API capacity. Quotas, limits, priority, and node isolation are the mitigations.
Requests are the denominator
HPA CPU utilization = usage / request. No request set means no utilization, no scaling decision — the most common reason an HPA shows <unknown>.

11 Reach for this when…

A database or stateful system needs backups, failover, and ordered upgrades on Kubernetes — that day-2 knowledge is exactly what an operator encodes; a Deployment alone will not do it safely.
Traffic swings and manual replica changes are always late — set requests honestly, add HPA on the signal that leads load, and let node autoscaling follow the Pending pods.
A second team is about to share your cluster — stamp their namespace from the tenant template (RBAC, quota + LimitRange, default-deny NetworkPolicy, Pod Security) before their first pod lands, not after the first incident.
