Human-in-the-loop patterns: approvals, edits, takeovers

The model proposes; a person disposes. Human-in-the-loop is not “a human watches everything” — it’s a decision made per action about which oversight mode it gets: run and log it, run and announce it, stop and ask, or never let the agent do it at all. The pause-and-resume machinery (interrupt → approve/edit/reject → resume) is easy; placing the gates — and designing the review so a human actually reviews — is the craft.

02 The one-idea version

An agent’s actions carry wildly different risk, so oversight must be decided per action, not per agent: cheap reversible work runs freely and gets sampled later, while irreversible or customer-facing work stops for a named person’s yes. The mechanism is a pause (interrupt), a human decision (approve, edit, or reject), and a resume from persisted state — but the machinery only works if the review stays real, which means short approval queues, fail-closed deadlines, and graduated autonomy earned on evidence.

03 Four modes, one gate

Every action passes through the same placement question — can it be undone, and who does it reach? — and lands in exactly one mode.

04 How it works

Seven mechanics. Frameworks (LangGraph, OpenAI Agents SDK, Claude Agent SDK) differ in syntax — the model doesn’t.

1

Choose the oversight mode per action, not per agent

One agent takes many actions with different risk. Every action gets one of four modes: act + log (reversible, internal, high volume), act + notify (reversible, but someone should know), approve before (hard to undo, or reaches customers, money, access, people), never (the permission isn’t granted; a person does it with the agent’s preparation). Most of the value lives in the first two modes.

2

Place each action with two questions

Reversibility: can the action be undone — by whom, at what cost, inside what window? Blast radius: who and what does it reach? Undone-in-seconds plus internal means act + log; cannot-be-undone plus customers/money/access/employment means never at launch. The two answers fit in a meeting, no model expertise required.

3

Pause the run; never block a process

The mechanism is interrupt(): the run halts mid-step, its state is persisted (checkpoint, thread id, or serialized state), and a human answers later — minutes or days. Resume with the human’s decision on the same run, not a new one. A human pause is a durable wait, not a blocked thread.

4

Ship the proposal as a package

An approval request that only says “OK?” trains reflex approvals. Every request carries four things: the proposed action, the evidence the agent used, the reasoning in one or two lines, and the options — approve, edit, or reject. It arrives in the channel the approver already works in, or it will be approved without checking.

5

Treat editing as a first-class decision

Approve-with-changes is its own outcome, not a reject-and-restart. The human amends the draft, the tool call, or the parameters, and the run resumes with the edited values. Most approvals are really corrections: a tone tweak, a different amount, a safer target. An edit path keeps them cheap.

6

Give every gate a name, a deadline, and a default

“Operations approves” is not a design — name the approver and a backup. Every approve-before action gets a response window, and the safe default when the window closes is do nothing and escalate to the backup. A default of “proceed if nobody objects” turns the approval gate into a timer, which provides no oversight at all. Fail closed.

7

Enforce at the tool boundary, not in the prompt

“Never send an email without approval” in the system prompt is a request, not enforcement. The integration must hold the gate whatever the model was told: the tool declares needsApproval, the run pauses, and the side effect cannot execute without a recorded human decision. The model never gets to authorize itself.

05 Code sketch

An approve-before gate in the LangGraph shape. The interrupt carries the full proposal package; resume carries the human’s decision — including an edit.

from langgraph.types import interrupt, Command

def approval_gate(state):
    decision = interrupt({                     # pause; state persisted
        "proposed": state["draft_email"],     # the action
        "evidence": state["order_record"],    # why the agent thinks so
        "question": "Send this customer email?",
    })                                          # returns the human's answer
    if decision.startswith("edit:"):
        return {"draft_email": decision[5:]}  # approve-with-changes
    return {"gate": decision}              # "approved" or "reject"

graph = builder.compile(checkpointer=memory)   # a pause needs persisted state
graph.invoke({"draft_email": draft}, config)  # stops at interrupt()
graph.invoke(Command(resume="approve"), config)  # human said yes; same run

06 Failure modes

Five ways human-in-the-loop quietly stops working — and the fix for each.

1

Review overload breeds reflex approvalsFix: gate by reversibility and blast radius; keep the approve-before list short. Put reversible, internal, high-volume work in act-and-log, and treat the daily approval count as a design number you check every week.

Route hundreds of low-stakes approvals a day to one busy person and you get hundreds of clicks and almost no real reviews. Automation complacency isn’t cured by a more diligent approver — only by a shorter gate list.

2

The gate lives only in the promptFix: declare approval at the tool boundary (e.g. needsApproval), so the pause is enforced by the integration, not requested from the model.

“Never send without approval” in the instructions is just a request. Prompt injections, jailbreaks, or a confident model can route around it. The tool that performs the side effect — or the system it calls — must enforce the authorization itself.

3

Approvals with no deadline or a “proceed” defaultFix: name the approver and a backup, set a response window, and default to do-nothing-and-escalate. The item must never auto-execute on silence.

A gate that waits forever is a queue that quietly fills; a gate that defaults to “proceed if nobody objects” is a timer wearing an approval costume. Both silently downgrade approve-before to nobody-ever-looked.

4

Pausing a run that can’t resumeFix: persist state before the interrupt (checkpointer, thread id, serialized state) and keep all code before the interrupt side-effect-free — the node restarts from the top on resume, and anything before the pause runs twice.

An interrupt without durable state is a cliff: the human approves and there’s nothing to resume. Worse, side effects placed before the pause — logging the charge, sending a partial email — execute again when the node restarts on resume.

5

Gates that never graduate or never come backFix: sample the autonomous tier weekly and record the miss rate; track the approver’s edit/reject rate on gated actions. Move actions between modes on evidence, in both directions, with a named person signing off.

Approve-before is a starting position, not a permanent one — but it fossilizes without a rule for moving. After a month of no approver edits on a narrow action class, graduation to act-and-notify is the honest move; when the edit rate climbs, the action goes back a step.

08 Sample prompts

Copy, adapt, and ask your coding assistant. Each one applies today's skill card.

PROMPT 1 · PLACE THE GATES

Here is a description of an agent workflow: [paste]. List every action the agent takes, and place each one in exactly one human-in-the-loop mode: act-and-log, act-and-notify, approve-before, or never. For each action, state (1) its reversibility (undoable in seconds / undoable with effort / cannot be undone), (2) its blast radius (internal / team / customer, money, access, legal), and (3) why the mode fits. Flag any action where I have not given you enough information to place it, and say what you'd need to ask. Push back on any action that looks like it belongs in "never" at launch.

PROMPT 2 · DESIGN THE REVIEW

This agent action is in approve-before mode: [describe the action, e.g. "send a customer reply"]. Design the review so a real human actually reviews it. Specify: the named approver and a backup; the channel the request arrives in and the four things it must contain (proposed action, evidence, one-or-two-line reasoning, approve/edit/reject options); the response window and the exact fail-closed default when the window closes with no response; what gets logged for every decision; and the evidence rule that would let this action graduate to act-and-notify. Also give a weekly "design number" review: what count do we watch to know the gate list is the right length?

PROMPT 3 · AUDIT THE PAUSE MECHANISM

Review this agent code for human-in-the-loop durability: [paste]. Check: (1) is the interrupt/pause declared at the tool boundary, or only as a prompt instruction? (2) is run state persisted before the pause, and can the run resume days later on the same execution? (3) does any code before the interrupt have side effects that would run twice on resume? (4) is there a timeout on the approval with a stated fail-closed default, or can the gate wait forever? (5) is the decision path limited to approve/reject, or can the human edit the proposed action? List every gap with its consequence and the fix.

10 Flashcards

Click or press Enter/Space to flip. Ten terms worth owning.

Human-in-the-loop
A person approves, reviews, or is notified about specific agent actions — decided per action, not per agent. The design question is where the gates sit, not whether a human exists somewhere in the diagram.
Approve-before
The agent prepares the action with its evidence and stops. A named person approves, edits, or rejects — usually one click. For actions that are hard to undo or reach customers, money, access, or people.
Act-and-log
The agent completes the action and records what it did and why; a person reviews a sample on a schedule. For reversible, internal, high-volume work — where most of the agent's value lives.
Act-and-notify
The agent completes the action and tells a named person, who can reverse it inside a short window. For reversible actions someone should know about — not just the log.
The "never" tier
The agent cannot perform the action — the permission is not granted. The agent prepares the case; a person does it. For irreversible, consequential actions at launch, and whatever sits outside the agent's job.
Interrupt
The pause mechanism: the run halts mid-step and its state persists (checkpoint, thread id, serialized state). The human answers minutes or days later and the same run resumes — no blocked process, no lost work.
Approval payload
The request package that keeps reviews real: the proposed action, the evidence the agent used, the reasoning in one or two lines, and the options (approve / edit / reject) — delivered in the channel the approver already uses.
Edit-in-the-loop
Approve-with-changes as a first-class decision: the human amends the draft, tool call, or parameters and the run resumes with the edited values — instead of rejecting and restarting the whole proposal.
Escalation
Every gate names an approver and a backup, with a response window and a fail-closed default: on timeout, do nothing and escalate. An approval that auto-executes on silence is a timer, not a gate.
Graduation
Moving an action between modes on evidence: after sustained low edit/reject and sampled-miss rates, approve-before graduates toward act-and-notify. When the edit rate climbs, it goes back a step — a named person signs off.

11 Reach for this when…

An agent is about to take irreversible or external actions. Money moves, access changes, customer-facing messages, record deletes: every such action gets a placement decision — and the irreversible ones start behind a human gate.
Your “oversight” is a prompt line like “always ask before sending.” That’s a request, not a gate. Move the authorization to the tool boundary so the pause holds no matter what the model was told — the model never authorizes itself.
Approvals pile up unread or get rubber-stamped in seconds. The review design is broken, not the people: shorten the approve-before list, ship proposals as evidence packages, set fail-closed deadlines, and treat the daily approval count as a design number.
