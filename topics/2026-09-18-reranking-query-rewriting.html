Re-ranking and query rewriting for retrieval quality

Retrieval usually fails at one of two ends: the query is a bad probe for the intent, or the first-stage retriever is a fast, coarse match that can't see fine relevance. The fix is a two-stage pipeline — sharpen the query before it hits the index, then replace cheap similarity with an expensive pairwise judgment over a small candidate set. Cheap and wide at stage one, precise and narrow at stage two.

02 The one-idea version

A vector retriever is a fast bouncer: it embeds your query and the documents separately and admits the nearest 50 on cosine similarity alone — it never reads the query and a document together. A re-ranker is the careful judge: it reads each (query, document) pair jointly and scores true relevance. Rewriting the query first makes the bouncer admit a better shortlist; the judge then picks the winners. Wide and cheap at stage one, narrow and precise at stage two — never the reverse.

03 The visual

One user question fans out into better probes, each retrieves its own candidates, the lists are fused, and a cross-encoder judges every pair. The funnel narrows left to right.

04 How it works

Six mechanics: why stage one is coarse, how stage two judges, and the two ways to fix the probe before it ever reaches the index.

1

First-stage retrieval is coarse by design

Bi-encoders embed the query and each document independently, then rank by one cosine number. That's fast — precompute the doc vectors, encode the query once — but the model never sees the query and a document together, so it can't notice that "cancel my booking" and "voluntary termination of carriage" mean the same thing. Stage one's only job is recall: get the right document into the top-K.

2

Re-rankers are cross-encoders: they read the pair jointly

A cross-encoder takes (query, document) as one input and lets attention flow between every query token and every document token, outputting a single relevance score. That joint reading is why rerankers catch relevance that cosine misses — and why they're 10–100× slower per pair. They run on 50 candidates, never on 5 million documents.

3

The two-stage funnel: retrieve K cheaply, keep 5–10

Retrieve K = 50–200 candidates with the fast bi-encoder (or hybrid BM25 + dense), then rerank the set down to the 5–10 chunks the LLM actually reads. K is the budget knob: bigger K = more recall, more rerank latency and cost. The funnel fails at stage one, not stage two — a reranker only judges what it's shown.

4

Fix the probe: rewrite the query before retrieval

Documents are statements; user queries are short questions — that vocabulary gap is half of all retrieval misses. Three proven rewrites: LLM rewrite ("how do I cancel?" → "cancel my booking and get a refund"); HyDE (have the LLM draft a hypothetical answer and embed that — answers look like documents, and the encoder's dense bottleneck filters out invented details); step-back prompting (retrieve on the general principle behind the specific question).

5

Multi-query + reciprocal rank fusion: hedge your phrasing

One phrasing can miss; five rarely do. Generate several query variants (RAG-Fusion style), retrieve with each, and fuse the ranked lists with reciprocal rank fusion: score each doc by 1/(k + rank) summed across lists. No training, no tuning — docs that appear near the top of multiple lists win, and one bad variant can't sink the result.

6

Know which stage to blame, then measure the funnel

Rewrite when queries are short, ambiguous, or phrased nothing like your documents (the vocabulary gap). Rerank when the queries are fine but ranking is noisy — the right doc is in the top-50 but not the top-5. Judge both stages on a judged query set with NDCG / MRR: a reranker trained on web QA can underperform on your domain, and an LLM rewrite that adds 400ms must earn its latency with measured gains.

05 Code sketch

The whole funnel in 24 lines: coarse bi-encoder retrieval, then precise cross-encoder judgment. The retrieve step returns candidates; the rerank step only ever sees those.

from sentence_transformers import SentenceTransformer, CrossEncoder
import numpy as np

bi = SentenceTransformer("all-MiniLM-L6-v2")          # stage 1: coarse, fast
ce = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")  # stage 2: precise, slow

def retrieve(query, doc_vecs, k=50):
    # bi-encoder: query and docs encoded SEPARATELY — one cosine score
    q = bi.encode(query)
    sims = doc_vecs @ q / (np.linalg.norm(doc_vecs, axis=1) * np.linalg.norm(q))
    return list(np.argsort(sims)[-k:][::-1])  # candidates; k is the recall knob

def rerank(query, docs, cand, top=5):
    # cross-encoder: query+doc read JOINTLY — full token attention
    pairs = [(query, docs[i]) for i in cand]
    scores = ce.predict(pairs)
    return [cand[i] for i in np.argsort(scores)[-top:][::-1]]

cand = retrieve("refund policy for cancelled flights", doc_vecs, k=50)
top5 = rerank("refund policy for cancelled flights", docs, cand, top=5)
# rerank can't rescue docs never retrieved — widen k before blaming the judge.

06 Failure modes

Named pitfalls, each with a one-line fix. Number one is a stage-one failure wearing a stage-two disguise.

✕

Reranking too few candidates Fix: retrieve K=50–100 before reranking; the reranker only judges what it's shown.

The right doc sits at rank 40, your reranker sees the top 10, the answer is wrong — and you blame the judge. A reranker can't rescue documents that never made the candidate set.

✕

HyDE hallucination drift Fix: fuse original-query and HyDE results with reciprocal rank fusion instead of replacing the original query.

The hypothetical answer invents facts ("…refund within 48 hours"), and retrieval chases the invention instead of the question. HyDE is a probe, not a source of truth — always keep the original query in the fusion.

✕

Domain-mismatched reranker Fix: evaluate NDCG on your own judged queries before adopting any reranker; prefer domain-tuned models for specialized corpora.

A reranker trained on web QA (MS MARCO) scores your legal, medical, or code corpus with confident-looking numbers and wrong rankings. Relevance is domain-shaped — the benchmark it aced is not your corpus.

✕

Rewriting every query by default Fix: gate the LLM rewrite — short or ambiguous queries only — or try cheap rewrites (synonym expansion, step-back) first.

An LLM rewrite adds latency and cost to every query, and can degrade already-good queries. The rewrite must earn its milliseconds: measure NDCG with and without it, per rewrite strategy.

✕

Treating reranker scores as calibrated Fix: use scores only to order one query's candidates; set any relevance cutoff from 30–50 representative queries, not from a magic threshold.

Score 0.92 on query A and 0.71 on query B does not mean doc A is more relevant. Reranker scores aren't comparable across queries — they're an ordering within one candidate set, nothing more.

10 Flashcards

Click a card — or tab to it and press Enter — to flip it.

Cross-encoder (reranker)
Encodes the (query, document) pair jointly with full token-level attention, outputting one relevance score. Precise but 10–100× slower per pair — run only on candidates.
Bi-encoder (first stage)
Embeds query and documents independently, ranks by cosine. Fast and precomputable, but never reads query and doc together — coarse by design. Its job is recall.
Two-stage funnel
Retrieve K=50–200 candidates cheaply, rerank down to the 5–10 the LLM reads. K is the budget knob; the funnel fails at stage one — the judge only sees what it's shown.
HyDE
Hypothetical Document Embeddings: the LLM drafts an answer, you embed it instead of the question. Answers look like documents (closing the vocabulary gap); the dense bottleneck filters invented details.
Multi-query + RRF
Generate several query variants, retrieve with each, fuse the ranked lists with reciprocal rank fusion (1/(k+rank) summed). No training — docs ranking high in multiple lists win.
Reciprocal rank fusion
Fuses ranked lists by scoring each doc 1/(k + rank) per list and summing. Simple, parameter-free, and robust — one bad query variant can't sink the result.
The vocabulary gap
Queries are short questions; documents are statements. The phrasing mismatch causes half of all retrieval misses — this is the failure query rewriting exists to fix.
NDCG
Normalized Discounted Cumulative Gain: measures ranking quality on a judged query set — top positions matter most. The metric that proves a rewrite or reranker earns its latency.
Reranker score calibration
Reranker scores order one query's candidates — they are NOT comparable across queries. Never compare a 0.9 on query A with a 0.7 on query B; set cutoffs from your own queries.
Step-back prompting
Retrieve on the general principle behind the specific question (e.g. the policy, not the instance). The broad retrieval grounds the specific answer — a cheap rewrite when HyDE is overkill.

11 Reach for this when…

Retrieval returns near-misses — the right doc hides at rank 20–40 — widen stage-1 K and add a cross-encoder rerank instead of stuffing more chunks into the prompt.
User queries are short or ambiguous while your documents are formal statements — rewrite, HyDE, or multi-query closes the vocabulary gap before the index ever runs.
You're adding context to the LLM and answer quality has stalled — the fix isn't more chunks, it's better-ranked chunks: a reranker on a wider candidate set beats a longer prompt.
