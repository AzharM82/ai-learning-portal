State machines for agents: explicit states beat vibes

A prompt-then-tool-call chain has no concept of “where am I, and what do I do if this doesn’t work.” Model the agent as an explicit state machine instead: named states, declared transitions, cycles you can see, and terminal states for both success and give-up. The graph is not cleverer than the prompt — it is honest about what agentic work actually looks like: iterative, fallible, and in need of a memory of its own progress.

02 The one-idea version

A linear chain encodes progress only as “execution reached line N” — it has no vocabulary for retry, escalate, or resume. A state machine gives every phase of the work a name and every allowed move an edge, so failure becomes a node with options instead of an unhandled exception. The model still reasons, but only inside transitions you approved. If the bug surprised you, ask: what state was the agent in — and did the graph even have a name for it?

03 The shape of a stateful agent

One run of a support-triage agent. Every node is a named state; every arrow is an allowed transition. Note the three things a linear chain has no place to put: the repair cycle, the human-approval branch, and the honest give-up.

04 How it works

Seven mechanics. The framework matters less than the discipline; this works in LangGraph, in XState, or in fifty lines of plain Python.

1

Name the states before you write a single node

Write the state list on paper first: planning, awaiting_tool_result, validating_output, needs_human_input, done. States are finite, enumerable, and speak the domain's language. If you can't list them, you don't have a design yet — you have a prompt and hope.

2

Declare every allowed transition up front

Each state lists its outgoing edges: from tool_failed you may go to repair, fallback_tool, or escalate_to_human — and to nothing else. The agent can only walk edges that exist, so the reachable-behavior space is auditable before the first run. Impossible states become structurally impossible, not handled by nested ifs.

3

Let the model pick the transition, not the destination

Two flavors work: code-routed (a deterministic function reads the state and returns the next node — cheapest, most predictable) and LLM-routed (the model sees the current state plus the list of valid outgoing edges and picks one). Either way the model names a transition, never an arbitrary destination. It cannot invent a state or teleport past your guardrails.

4

Make failure a first-class state, not an exception path

tool_failed is a node with its own edges: retry with a new plan, try the fallback tool, escalate. Because the failure lives in the graph, the repair node inherits the full state — what was tried, what the error was, how many attempts remain — instead of starting from scratch in a bare try/except.

5

Loops are normal; budgets make them safe

Revise-critique-revise is a cycle, and cycles are exactly what state machines (and directed cyclic graphs) model well — chains can't. The guard is a budget tracked in the state: a retry counter, an error buffer, a quality threshold. The conditional edge reads it: attempts remain → loop back; budget exhausted → escalate. A bare while True retry can never tell you the difference.

6

Persist state after every transition

State must live outside the model: serialized, versioned, checkpointed. After each transition, save the snapshot — then a crash, a human-approval pause, or a 2 a.m. process restart resumes from the last good state instead of the beginning. This is also what makes the transition log a real audit trail.

7

Shape the state schema before the topology

The single highest-leverage design decision is not the graph layout — it's the shape of the state object flowing through it. Message history, intermediate results, error counters, retry budgets: decide what each node needs to know to make a correct decision, then wire the nodes and edges that carry it. State shape first, edges second.

05 Code sketch

The whole pattern in plain Python — no framework. States declare their transitions; the router picks the next edge; terminal states end the loop.

def run(states, initial, max_steps=10):
    state, context, steps = initial, {}, 0
    while True:
        node = states[state]
        context.update(node["handler"](context))  # do the work
        if node.get("terminal") or not node["transitions"]:
            return state, context              # terminal: done or gave_up
        steps += 1
        if steps >= max_steps:
            return "gave_up", context      # budget exhausted: honest exit
        state = node["router"](context, node["transitions"])
        assert state in node["transitions"], "illegal transition"

states = {
    "triage":    {"handler": classify,  "router": route_triage,
                     "transitions": ["diagnose", "resolve"]},
    "diagnose":  {"handler": gather,    "router": route_diagnose,
                     "transitions": ["resolve", "tool_failed"]},
    "tool_failed": {"handler": log_err, "router": route_retry,
                     "transitions": ["diagnose", "needs_human"]},
    "needs_human": {"handler": pause,   "router": route_human,
                     "transitions": ["resolve", "gave_up"]},
    "resolve":   {"handler": fix,      "transitions": [], "terminal": True},
    "gave_up":   {"handler": report,   "transitions": [], "terminal": True},
}

06 Failure modes

Five ways the pattern breaks — and the fix for each.

1

Overstuffed stateFix: store summaries, not raw tool dumps; cap history fields; let nodes re-fetch detail on demand.

Every raw tool response gets dumped into the shared state until nodes can no longer see what is relevant — and token costs balloon because the whole state is fed back to the model at every step.

2

Understuffed stateFix: design the schema from each node's decision needs first; add the retry counter and last-error fields before you need them.

The repair node needs the retry count and the last error to decide — but the state never carried them. It re-derives context it should have been handed, or guesses, and the "smart" router becomes a coin flip.

3

Retry in a bare loop instead of in the graphFix: make retry a transition on a failure state; track the attempt budget in state so "still trying" and "exhausted" are different edges.

A while loop around a tool call has no name, no checkpoint, and no audit trail. Twenty minutes of silent retry looks identical to progress from the outside — and there is no state to resume from when it crashes.

4

No honest give-up stateFix: add a terminal state that reports what was tried and returns the evidence trail; treat giving up gracefully as a feature.

With no gave_up state, an agent that can't finish either hangs forever or hallucinates a fake success. An agent that can say "I couldn't complete this, here's what I tried" is far more trustworthy than either.

5

Non-idempotent tool nodesFix: make every tool node safe to re-run — check-then-act, idempotency keys, or dry-run first — so a resumed checkpoint never double-charges or double-books.

Checkpointing only helps if re-running a step is safe. Resume from the last good state and re-execute "book the flight," and without idempotency you've booked it twice.

10 Flashcards

Click or press Enter/Space to flip. Ten terms worth owning.

Finite state machine
A fixed set of named states with declared transitions between them. At any moment the system is in exactly one state; it can only move along an existing edge.
Terminal state
A state with no outgoing transitions. Reaching it ends the run. Design both a success and a give-up terminal — the honest exit beats a hang or a faked success.
Conditional edge
A transition whose destination is chosen at runtime by a router function (code or LLM) reading the current state — "retry if errors, else done."
State schema first
Design the shape of the shared state (messages, results, retry counters, error info) before the graph topology — nodes need data to decide, edges carry it.
LLM-routed transition
The model sees the current state plus the list of valid outgoing edges and picks one. It names a transition, never an arbitrary destination — it cannot invent states.
Checkpoint
A persisted snapshot of state after each transition. It turns "the graph knows its state" into pause, resume, and time-travel — including across restarts.
Directed cyclic graph
A graph that allows edges looping back to earlier nodes. Revise-critique-revise is a cycle, not a line — DAGs can't model real agent work.
Overstuffed state
Dumping every raw tool response into shared state until nodes can't see what's relevant and token costs balloon. Fix: store summaries, re-fetch detail on demand.
Idempotent tool node
A node safe to re-run after a checkpoint resume — check-then-act or idempotency keys — so resuming never double-books, double-charges, or double-sends.
Human-in-the-loop node
A state that pauses execution, persists its state, and waits for a person to approve, reject, or edit. Turns "agent got stuck" into a routine, expected branch.

11 Reach for this when…

An agent's failures have no name. When debugging means reading a wall of prompt/response text, give each phase a state and each failure a node — then the transition log is the trace.
A run must survive interruption. Human approval, crashes, long runs: persist state after every transition so resuming starts from the last good state, never from the beginning.
Retries are hiding in a bare loop. Move the retry into the graph, track the budget in state, and let "still trying" and "exhausted, escalate" be two different, visible edges.
