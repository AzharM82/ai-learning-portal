Model Context Protocol (MCP): servers, tools, resources, and transports

Before MCP, every AI app needed custom glue for every tool — M apps × N tools meant M×N integrations. MCP replaces that with one open protocol: build a server once, and any MCP host can discover what it offers, read its context, and call its tools.

02 The one-idea version

MCP is USB-C for AI applications. The official docs use exactly that analogy: just as USB-C standardizes how devices connect to peripherals, MCP standardizes how AI applications connect to data sources, tools, and workflows. The model never speaks the protocol or runs your code directly — the host does, over JSON-RPC 2.0, after discovering what a server offers.

04 How it works

Six mechanics, in the order you meet them building your first server.

1

Separate the three roles: host, client, server

The host is the AI application the user runs (Claude, ChatGPT, VS Code, Cursor). Inside it, the host creates one MCP client per MCP server — each client owns one dedicated connection. The server is the program that provides context, wherever it runs: local on the user’s machine or remote on a platform. Keeping these roles straight is the architecture: the model proposes, the host decides and executes, the server does the scoped work.

2

Offer the three server primitives — and know who controls each

Tools are executable functions the model can invoke to act (query a database, call an API, write a file) — each with a name, description, and JSON Schema for its inputs. Resources are data sources the application reads as context (file contents, a database schema, API responses), identified by URI. Prompts are reusable, user-chosen templates that structure an interaction (a review workflow, few-shot examples). Tools are model-controlled, resources are application-controlled, prompts are user-controlled — that control split is a safety design, not trivia.

3

Let discovery do the wiring: list first, call second

MCP’s data layer is JSON-RPC 2.0. A client discovers a server’s protocol versions, capabilities, and identity (in the current spec, via server/discover), then lists what is on offer — tools/list, resources/list, prompts/list — before it ever calls tools/call or reads a resource. Because listings are dynamic, a server can add a tool and connected clients can learn about it (with change notifications) without a code change or redeploy of the host. Never hard-code a tool catalog in the client.

4

Pick the transport by where the server lives

Use stdio for local servers: the host launches the server process and talks over its standard input/output — fastest, no network, typically one client. Use Streamable HTTP for remote servers: HTTP POST for client-to-server messages, optional Server-Sent Events for streaming, and standard HTTP auth — the spec recommends OAuth for obtaining tokens. The transport abstracts the wire away: the same JSON-RPC messages work over both, so moving a server from local to remote is a transport change, not a rewrite.

5

Build the server with an SDK — schema first, validation always

Use an official SDK (Python, TypeScript, and others) instead of hand-rolling JSON-RPC. Define each tool from its contract outward: a precise description the model can reason about, a tight input schema, server-side validation of every argument (the model’s output is untrusted input), and structured results or a clear error. Then test the server in isolation with the MCP Inspector — list its tools, call them with good and bad inputs — before any host ever connects to it.

6

Keep authority at the host: auth, approval, least privilege

A remote server must authenticate its clients; a local server inherits the user’s machine, so its file and network reach must be scoped deliberately. Give each server the narrowest tools that do the job (read this folder, query this table — not a general shell), keep credentials with the host/server and never in prompts or resource contents, and put a human approval step in front of irreversible tool calls. Remember the direction of trust: resource contents and tool descriptions are data that can carry prompt injection, so the host treats them as untrusted.

05 Code sketch

A minimal Python MCP server: one tool, one resource, stdio transport. The SDK generates the tool definition from the type hints and docstring.

# weather_server.py — run by the host over stdio
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("weather")

@mcp.tool()
def get_forecast(city: str, days: int = 3) -> str:
    """Get the forecast for a city for the next N days."""
    if days < 1 or days > 10:          # validate: model output is untrusted
        raise ValueError("days must be 1-10")
    return fetch_forecast(city, days)  # your real API call lives here

@mcp.resource("weather://units")
def units() -> str:
    """Context the host can read: how this server reports weather."""
    return "Temperatures in Celsius; times in UTC."

if __name__ == "__main__":
    # stdio: stdout IS the protocol — log to stderr only, never print()
    mcp.run(transport="stdio")

06 Failure modes

Five ways MCP integrations hurt themselves — and the one-line fix for each.

1

Logging to stdout on a stdio serverFix: log to stderr (or a file) only — stdout carries JSON-RPC and nothing else.

The official build-a-server guide warns about this first for a reason: one stray print() corrupts the message stream and the connection dies with a parse error that looks like a protocol bug. It is the MCP equivalent of printing debug output into a binary file format.

2

Shipping a remote server with no authenticationFix: require auth on Streamable HTTP — OAuth as the spec recommends — and scope tokens per client.

A remote MCP server is an internet-facing API whose callers can execute your tools. “It’s just an internal prototype” is how an unauthenticated database-query tool ends up reachable by anyone who finds the URL.

3

Tool poisoning and injected instructions in dataFix: treat tool descriptions and resource contents as untrusted data; pin/review servers, and keep human approval on consequential calls.

A malicious or compromised server can hide instructions in a tool description, and a poisoned document returned as a resource can tell the model to misuse a legitimate tool. MCP gives data a direct line to the model’s context — design as if that data is adversarial, because sometimes it is.

4

One giant, over-privileged toolFix: split it into narrow, named tools with tight schemas — run_query on one table, not execute_anything.

A single run_sql or shell tool makes least privilege, approval prompts, and audit logs meaningless: every call looks the same and can do anything. Narrow tools are safer, and models also choose and parameterize them more accurately.

5

Reinventing a custom protocol instead of using MCP — or using MCP where a plain API call is enoughFix: use MCP when a host/model must discover and invoke capabilities dynamically; call the API directly when your own code already knows exactly what to call.

MCP sits on top of APIs; it does not replace them. Its value is dynamic discovery by an AI application. Hard-coding one known endpoint in your own backend gains nothing from a server, a handshake, and a tool catalog — and a bespoke per-app integration recreates the M×N problem MCP exists to kill.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

Model Context Protocol (MCP)
An open standard for connecting AI applications to external systems — data sources, tools, and workflows — introduced by Anthropic in November 2024. “USB-C for AI applications.”
Host
The AI application the user runs (Claude, ChatGPT, VS Code). It owns the model interaction, creates one client per server, and holds approval and authorization authority.
Client
The component inside the host that maintains one dedicated connection to one MCP server: discovery, listing primitives, and relaying calls and results.
Server
The program that provides context and actions to clients — local (stdio) or remote (Streamable HTTP) — wrapping files, databases, or APIs.
Tools
Executable functions the model can invoke (tools/list, then tools/call), each with a name, description, and JSON Schema inputs. Model-controlled — and effectively arbitrary code execution, so scope and approve them.
Resources
Data sources the application reads as context — file contents, schemas, API responses — identified by URI. Application-controlled.
Prompts (MCP)
Reusable interaction templates a server offers — a workflow or few-shot pattern the user deliberately invokes. User-controlled.
stdio vs Streamable HTTP
stdio: host launches a local server process, messages over stdin/stdout, one client, no network — never log to stdout. Streamable HTTP: remote, many clients, HTTP POST + optional SSE, OAuth recommended.
Discovery
The client learns a server’s versions, capabilities, and primitives dynamically (server/discover, */list) instead of hard-coding them — so servers can evolve without host redeploys.

11 Reach for this when…

You are about to write a one-off integration between an AI app and a tool — if any other host might ever want that tool, build it as an MCP server once instead of glue code per app.
Your agent needs live, private, or changing data — files, a database, an internal API: expose it as resources for context and narrow tools for actions, rather than pasting snapshots into prompts.
The same capability must work across Claude, ChatGPT, VS Code, or your own agent — that cross-host portability is exactly what the standard buys you; a custom integration buys it for one host only.
