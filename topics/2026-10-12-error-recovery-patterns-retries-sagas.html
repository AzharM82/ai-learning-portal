Error recovery patterns: retries, compensation, sagas

Your agent just charged the customer and reserved the inventory — and then the shipping call failed. There is no database transaction to roll back: those were three separate systems. Error recovery patterns answer the question “what now?”: retry what was transient, compensate what already committed, and coordinate the whole mess as a saga with a marked point of no return.

02 The one-idea version

A failure mid-run is not a bug — it is the normal state of distributed work, and a multi-step agent has no database transaction to roll back. So recovery comes in three layers, tried in order: retry the step when the fault is transient (bounded, backed off, jittered, idempotent); compensate completed steps with business inverses in reverse order when forward progress is impossible; and wrap the sequence as a saga — a durable record of steps, compensations, and a pivot point — so crashes resume, and humans get called only for the truly irreversible.

03 The recovery, visually

Forward steps retry; dead steps compensate. The pivot flag marks where undoing stops being possible.

04 How it works

Imperative, concrete. Recovery is a stack of decisions, tried in this order.

1

Classify the fault before you retry

Only transient faults are worth repeating: timeouts, connection resets, HTTP 429, 502/503/504, throttling, deadlocks. HTTP 400/401/403/404/422 and business-rule rejections will fail identically on attempt #47 — report them, never retry them. Retrying a non-transient fault burns capacity and hides the real error behind a wall of identical log lines.

2

Retry bounded: exponential backoff + jitter

Cap the attempts (3–5 for interactive work), grow the delay (1s, 2s, 4s…), and add random spread so a fleet of workers doesn’t retry in lockstep and turn one outage into a thundering herd. Prefer the SDK’s built-in retry or a library like tenacity / Polly over hand-rolled loops — they already implement the backoff math correctly.

3

Make every retried operation idempotent

The lost-response case: the first attempt succeeded, only the reply was lost, and the retry executes the effect twice — double charge, double shipment. Send an Idempotency-Key; the server returns the original result for a repeated key instead of re-executing. Without this, retries are not a recovery strategy, they are a duplication strategy.

4

Pair retries with a circuit breaker for persistent faults

Backoff doesn’t help when a service is down for hours — it just spaces out the damage. The breaker opens after repeated failures so calls fail fast, then lets a trickle of probe traffic through to detect recovery (half-open) before closing. Log transient failures as informational; log only the final exhausted attempt as the real error.

5

Register each step’s compensation BEFORE it executes

If you only register the undo after a successful forward call, a step whose response was lost leaves an orphaned side effect the rollback can’t see. Write the compensation record first, then execute. Design compensation as business logic in reverse (refund, release, cancel) — not as restoring a snapshot: a refund is not a time machine, the customer sees both entries on the statement.

6

Unwind compensations last-in, first-out

The most recent step’s effects are usually the most dependent on earlier ones, so undo in reverse order of completion. Compensations must themselves be retryable and idempotent — a rollback that crashes halfway is worse than none — and the saga’s progress must be persisted durably (event history, outbox) so a crash mid-rollback resumes instead of starting over.

7

Mark the pivot: the point of no return

Some steps are irreversible: money moved, email sent, a legal filing made. Put all validations and compensable steps before the pivot; after it, steps must be retryable-to-completion, never compensable. And if a compensation itself fails irrecoverably, dead-letter it and alert a human — that is an incident, not a log line.

05 Code sketch

A saga runner in miniature: idempotent retried steps, pre-registered compensations, LIFO unwind, dead-letter on compensation failure.

# Saga runner: retry forward, compensate in reverse, never duplicate
import random, time

class TransientError(Exception): pass

class Saga:
    def __init__(self):
        self._undo = []          # stack: unwinds LIFO

    def step(self, name, do, undo, idem_key, attempts=4):
        self._undo.append((name, undo))   # register BEFORE execute:
        for n in range(attempts):          # a lost response may mean it DID run
            try:
                return do(idem_key)           # idempotent: same key, one effect
            except TransientError:
                if n == attempts - 1: raise
                time.sleep(2 ** n * random.uniform(0.8, 1.2))  # exp backoff + jitter
        # non-transient errors are never retried: they raise immediately

    def rollback(self):
        for name, undo in reversed(self._undo):  # last touched, first undone
            try:
                undo()                       # compensation must itself retry
            except Exception as e:
                dead_letter(name, e)         # compensate failed = human incident

06 Failure modes

Named, with a one-line fix each. Most recovery code dies from these, not from bad models.

F1

Retrying what will never succeedFix: classify every failure as transient, business, or terminal — retry only the first kind.

The card is declined with a hard 402; your agent retries it with beautiful exponential backoff eleven times, burning latency and rate-limit budget. Worse, the repeated attempts mask the real problem: a validation issue that needed a human, not a loop. If the answer won’t change, don’t ask again.

F2

Retry without idempotency: the double-chargeFix: every mutating call gets an idempotency key; repeated keys return the original result.

The charge went through; only the response was lost. The retry charged again and the customer now has two holds. This is the single most expensive recovery bug in agent systems — the first attempt wasn’t the failure, the retry was. Idempotency keys turn “at-least-once delivery” into “exactly-once effect.”

F3

The retry storm: synchronized, unbounded retriesFix: bound attempts, exponential backoff with jitter, and a circuit breaker for persistent faults.

Fifty workers all fail against the same struggling service and all retry at once — in lockstep, forever. The recovery traffic becomes a self-inflicted DDoS that prevents the very recovery you’re waiting for. Jitter desynchronizes; the breaker stops the hammering; bounds stop the infinity.

F4

Compensating like a database rollbackFix: write compensation as forward business logic (refund, cancel, release) — and honor dependency order, usually LIFO.

You restore the inventory row to its old value, but the payment service already issued a refund against the new one. Undoing in forward order, or as raw state restoration, corrupts the dependents. Compensation is new business logic: semantically undo the effect, in the order the effects were built.

F5

No pivot: trying to un-send the emailFix: declare compensable vs irreversible steps up front; pivot marks the boundary, validations go before it.

The saga “rolls back” a step that sent a legal notice. You can’t un-notify someone — the compensation is meaningless and the audit trail is a lie. Identify the irreversible steps at design time, keep them after the pivot, and make them retryable-to-completion instead of pretend-undoable.

F6

The orchestrator dies mid-rollbackFix: persist every step and compensation record durably; compensations must be retryable and idempotent; dead-letter failures to a human.

The refund succeeded, the release didn’t, and then the process crashed — now nobody knows what was undone. A compensation you can’t observe, resume, and audit is a hope, not a mechanism. Durable event history turns “did we refund?” into a query instead of an investigation.

08 Sample prompts

Copy-paste starters. Use the copy button; each one is a full working prompt.

PROMPT 1 · DESIGN THE RETRY POLICY

My agent calls this API: [endpoint, method, what it does]. It can fail in these ways: [list error codes / situations, e.g. 429, 503, timeouts, 400, 401, 422]. Design a retry policy for each failure mode: classify it as transient, business, or terminal, and say retry or report. For the retryable ones, set max attempts, base delay, the backoff formula (exponential), and the jitter strategy; say whether the operation is idempotent and, if not, propose an idempotency-key scheme (key scope, TTL, where the server stores it). Recommend whether to use the SDK's built-in retry or tenacity/Polly, and name the conditions under which a circuit breaker should open.

PROMPT 2 · DESIGN THE SAGA

Design a saga for this business operation: [describe the operation and the systems involved]. List the forward steps in order. For each step, name its compensating action — a business inverse (refund, cancel, release), not a data rollback — and label the step compensable, retryable, or irreversible. Mark the pivot point (the point of no return), move all validations before it, and explain why the pivot sits where it does. Recommend choreography vs orchestration for this workflow and why. Then specify: what saga state must be persisted so a crash mid-rollback resumes safely, how compensations themselves retry, and exactly what happens when a compensation fails (dead-letter + human alert path).

PROMPT 3 · CLASSIFY A PRODUCTION FAILURE

A multi-step agent run failed in production. Here is the timeline: [what ran, what failed, what was retried, what state was left behind]. Classify each failure as transient, business, or terminal. Tell me what should have been retried vs compensated vs escalated to a human, and what actually happened instead. Flag any retry-storm risk (synchronized retries, unbounded attempts, missing backoff/jitter, no circuit breaker). Identify the missing pieces: idempotency keys, pivot placement, compensation order, durable saga state. End with the minimal fix list, ordered by blast radius, and for each fix name which failure mode (F1-F6 in today's lesson) it addresses.

10 Flashcards

Click a card to flip it. Tab to a card and press Enter or Space.

Transient fault
A momentary, self-correcting failure: timeouts, 429, 502/503/504, connection resets. The only kind worth retrying.
Exponential backoff + jitter
Delay grows per attempt (1s, 2s, 4s…) with random spread, so a fleet of workers doesn't retry in lockstep and herd.
Idempotency
Repeating an operation with the same key has one effect. What makes the lost-response retry safe instead of a double-charge.
Circuit breaker
Stops calling a persistently failing dependency: open (fail fast) → half-open (probe) → closed (recovered). Pairs with retry.
Retry storm
Synchronized, unbounded retries that amplify an outage into a self-inflicted DDoS. Fixed by bounds, backoff, jitter, breakers.
Compensating transaction
A business inverse (refund, cancel, release) that semantically undoes a committed step. A refund is not a time machine.
Saga
A sequence of local transactions, each with a compensating action, kept eventually consistent — no distributed locks.
LIFO unwind
Compensations run in reverse order of the forward steps: last completed step undone first. Order by dependency.
Pivot transaction
The point of no return. Compensable before it; must-complete (retryable, idempotent) after it. Validations go before the pivot.
Choreography vs orchestration
Choreography: services react to each other's events, no center. Orchestration: a central controller drives steps and compensation.

11 Reach for this when…

Your agent calls external APIs or runs multi-step workflows and sometimes “succeeds” halfway, leaving charges, reservations, or records behind. Recovery isn’t a try/except around the whole run — it’s retry for the transient, compensation for the committed, each decided per step.
You’re about to chain two writes that can’t share a transaction (database + event, payment + shipment, ticket + notification). Failure between them corrupts consistency — design the compensating action before you write the forward step.
A step can irreversibly fail after earlier steps committed (payment captured, email sent, filing made). There is no rollback for that — you need a saga with a declared pivot, business-inverse compensation, and durable state so a crash mid-rollback resumes.
