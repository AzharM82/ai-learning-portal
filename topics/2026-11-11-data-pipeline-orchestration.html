Data pipeline orchestration: Airflow, Dagster, and backfills

Cron knows the clock. It does not know that the extract failed, that the load ran on yesterday’s file, or that Tuesday’s partition was never built. An orchestrator replaces time-only sequencing with a declared graph, a run for every data interval or partition, retries and lineage you can see — and backfills that re-run history on purpose, in range, without duplicating a row.

02 The one-idea version

Orchestration is a graph plus a slice: declare what depends on what, and make every run own exactly one interval of data. In Airflow the graph is tasks in a DAG and the slice is the data interval behind a logical date; in Dagster the graph is data assets and the slice is a partition key. Once a run is addressed by its slice — not by “whenever the clock fired” — retries, reruns, and backfills become the same safe operation: recompute that slice, idempotently, and overwrite only it.

03 The picture: one slice, end to end

A daily pipeline for one partition. A backfill is not a different system — it is this same picture, launched for many slices in a bounded range.

04 How it works

Six mechanics: declare the graph, address the slice, pick a centre of gravity, schedule honestly, bound execution, and backfill like an operator.

1

Declare dependencies in code — never sequence by clock, sleep, or hope

Write the graph down: in Airflow, tasks in a DAG wired with >>; in Dagster, assets whose function inputs are their upstream assets. The scheduler — not cron — starts a step only when its upstream succeeded, parallelises independent branches, and marks downstream work upstream_failed instead of running it on missing data. If ordering lives in five separate cron entries, a slow upstream does not delay anything; it silently corrupts everything after it.

2

Address every run by its data slice, not by wall-clock time

Pass the slice in, never compute “now” inside the task. Airflow gives each DAG run a logical date and a data interval: a daily run for 2026-11-10 usually executes after that day ends, and its tasks must read the interval, not the execution timestamp. Dagster gives each run a partition_key (for example 2026-11-10 from DailyPartitionsDefinition), and the asset reads context.partition_key. Same code path for the scheduled run, a retry, and a backfill three months later.

3

Choose the centre of gravity: Airflow tasks vs Dagster assets

Airflow is task-centric: it asks “did this task succeed for this logical date?” — a huge operator ecosystem, general workflows (not just data), and the incumbent in most platforms. Dagster is asset-centric: it asks “is this table / file / model fresh for this partition?” — lineage, partition status, and materialisation history are first-class, which is how analysts actually ask the question. Pick by the question your team answers at 2 a.m., not by demo aesthetics; both schedule, retry, and backfill.

4

Schedule deliberately: interval, catchup, and readiness

Set start_date and schedule explicitly, and decide catchup on purpose. With catchup on, a scheduler creates a run for every missed interval since start_date — correct for partition-shaped data, a flood for anything else. Airflow 3 defaults catchup to off; earlier defaults surprised many teams. For data that arrives irregularly, do not poll blindly: use a sensor, a deferrable operator, or Dagster asset / automation conditions so a run starts when its input is actually ready, with a timeout that fails loudly.

5

Make every slice idempotent, then bound retries and concurrency

Retries and backfills re-execute code, so a slice must be safe to run twice: write to a staging partition and swap, DELETE / MERGE by partition key before insert, never bare-append. Then bound the blast radius in config: retries with exponential backoff for transient faults only, a timeout per task, and a concurrency cap (Airflow pools / max_active_runs; Dagster run concurrency and backfill policy) so 90 historical runs cannot starve today’s run or the source system.

6

Backfill as a planned operation, and observe by slice

A backfill is a ranged re-run: Airflow airflow dags backfill --start-date … --end-date …, Dagster a backfill over a partition range (one run per partition by default, or a single-run BackfillPolicy when one range query is cheaper). Plan it: prove the new logic on one slice, run a small range, cap parallelism against source rate limits and cost, then expand. Observe per slice — partition status, freshness, row counts — so “the pipeline is green” is replaced by “every partition through yesterday is materialised and checked.”

05 Code sketch

A Dagster partitioned asset: the partition key is the whole contract. The Airflow equivalent is a TaskFlow DAG whose tasks read data_interval_start / end instead of the clock.

import dagster as dg

daily = dg.DailyPartitionsDefinition(start_date="2026-01-01")

@dg.asset(partitions_def=daily, group_name="orders")
def orders_daily(context: dg.AssetExecutionContext) -> None:
    day = context.partition_key                  # e.g. "2026-11-10" — never date.today()
    rows = extract_orders(day)                   # read only this slice
    rows = dedupe(rows, key="order_id")
    write_partition(rows, table="orders", partition=day)  # overwrite, not append

@dg.asset(partitions_def=daily, deps=[orders_daily])
def revenue_daily(context: dg.AssetExecutionContext) -> None:
    day = context.partition_key
    assert_fresh("orders", partition=day)       # fail loudly on a missing slice
    write_partition(aggregate(day), table="revenue", partition=day)

# Schedule fills yesterday's partition daily; a backfill from the UI / CLI
# launches the same two assets for any range, one run per partition.
defs = dg.Definitions(
    assets=[orders_daily, revenue_daily],
    schedules=[dg.ScheduleDefinition(
        job=dg.define_asset_job("daily", selection="*"), cron_schedule="0 2 * * *")],
)

06 Failure modes

Five ways orchestrated pipelines fail in production — each with a one-line fix.

1

The non-idempotent taskFix: write per slice — stage, then overwrite / MERGE that partition atomically; prove it by running one slice twice and diffing.

An append-only load looks fine until the first retry, clear-and-rerun, or backfill doubles the rows. Orchestrators re-run code by design; if twice is not equal to once, every recovery mechanism becomes a corruption mechanism.

2

The catchup floodFix: set start_date and catchup deliberately (off unless the DAG is partition-shaped and a historical fill is actually wanted).

Deploy a DAG with a start_date months in the past and catchup on, and the scheduler dutifully creates hundreds of runs on day one — queue saturated, source hammered, today’s run stuck behind history nobody asked for.

3

The backfill stampedeFix: cap concurrency (pools / max_active_runs / backfill limits), backfill in chunks, and respect source rate limits and cost budgets.

A year-long backfill at unlimited parallelism is a self-inflicted denial-of-service: API quotas exhausted, warehouse credits burned, and the daily pipeline competing with its own history. A backfill is a migration, not a button.

4

Wall-clock date logicFix: derive every filter from the logical date / data interval / partition_key passed to the run — ban date.today() in task code.

A task that reads “yesterday relative to now” processes the right day only when it runs on schedule. Run it late, early, or as a backfill and it silently processes the wrong slice while reporting success — the worst failure shape in data engineering.

5

Big data through the orchestratorFix: pass references (paths, table + partition), never payloads — keep XComs / return values to small metadata only.

Returning a DataFrame between tasks (or shoving rows through XCom) moves your data through the metadata database and memory of the scheduler. It works in the tutorial and dies at real volume; the orchestrator coordinates work, the data plane does the lifting.

DESIGN AN ORCHESTRATED PIPELINE

Design an orchestrated data pipeline for this job: [sources, transformations, destination, cadence, history needed]. Give me: (1) the graph — tasks or assets with explicit dependencies, drawn as a list of edges, (2) the slice — logical date / data interval (Airflow) or partition definition (Dagster) and exactly how each step receives its slice, (3) the schedule and catchup decision, with reasoning, (4) idempotency: how each step overwrites only its slice, proven by a run-it-twice test, (5) retries, timeouts and a concurrency cap, and (6) how we will know every partition through yesterday is present and checked. Argue Airflow vs Dagster for this case in three lines, then commit to one.

PLAN A SAFE BACKFILL

Plan a safe backfill for this pipeline: [pipeline, date range, why we are backfilling — new logic / bug fix / first load, source limits, downstream consumers]. Produce an operator plan, not just a command: (1) preconditions — idempotency proof on one slice, downstream freeze or versioning, (2) the exact Airflow backfill command or Dagster backfill selection, (3) chunking and concurrency caps with the arithmetic against source rate limits and cost, (4) validation per chunk — row counts, checksums, partition status — and the abort threshold, (5) what happens to the normal daily run during the backfill, and (6) rollback: how we restore the old partitions if the new logic is wrong. Flag any step that could double-write.

AUDIT MY DAG FOR PRODUCTION

Audit this orchestrated pipeline like a production reviewer: [paste the DAG / asset definitions and schedule config]. Check in order: (1) date logic — does any task use wall-clock now / today instead of its logical date, data interval, or partition key? (2) idempotency — run every task twice: what duplicates? (3) catchup and start_date — what happens on first deploy and after a week paused? (4) failure shape — retries on non-transient errors, sensors with no timeout, downstream running on missing data? (5) data plane — is any large payload passed between tasks instead of a reference? (6) backfill safety — concurrency caps and source limits. For each finding give severity and the smallest code fix.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

DAG
Directed Acyclic Graph: tasks as nodes, dependencies as edges, no cycles. It declares how work runs — order, retries, timeouts — not what happens inside each task.
Logical date / data interval
Airflow’s name for the slice a run owns: the logical date is the start of the data interval the run processes, not when it executes. A daily run for Nov 10 runs after Nov 10 ends — and must still read Nov 10.
Partition
A named slice of a dataset — usually a day, hour, or region. Dagster’s PartitionsDefinition enumerates the slices; each run materialises one partition_key, tracked independently.
Asset (Dagster)
A data object — table, file, model — plus the code that produces it. Orchestration asks “is this asset fresh for this partition?” and lineage falls out of asset dependencies.
Backfill
A ranged re-run of history: the same graph launched for many slices — Airflow dags backfill over a date range, or a Dagster backfill over a partition range. Used for first loads, bug fixes, and logic changes.
Catchup
The scheduler creating runs for every missed interval since start_date. Correct when a historical fill is intended; a flood when it is a surprise. Set it deliberately — Airflow 3 defaults it off.
Idempotent slice
A slice that is safe to compute twice: the second run overwrites / MERGEs exactly its partition, so retry, rerun, and backfill all converge to the same data. Append-only is the opposite.
Sensor
A task that waits for a condition — a file, an upstream dataset, an API state — before downstream work starts. Always give it a timeout; a sensor with none waits forever, silently.
Pool / concurrency cap
A limit on how many runs or tasks execute at once. It is what keeps a 90-day backfill from starving today’s run and overwhelming the source system it reads from.
XCom trap
Passing data itself between Airflow tasks via XCom / return values routes it through the metadata store. Pass references — a path, a table plus partition — and let the data plane move the bytes.

11 Reach for this when…

Jobs are sequenced by the clock and failing silently — extracts, loads, and reports in separate cron entries with no dependency between them. Declare the graph once; a failed upstream then stops the line instead of poisoning it.
History must be reprocessed — a bug fix, a logic change, or a first load over months of data. If each slice is addressed and idempotent, a backfill is a bounded, validated operation instead of a weekend of manual reruns.
Nobody can answer “is the data fresh?” — green runs, stale tables. Move to per-slice status: partition materialisation, freshness and checks in Dagster’s asset view or Airflow’s dataset / run history, alerted by slice.
