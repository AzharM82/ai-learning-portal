Knowledge graphs for RAG (GraphRAG patterns)

Plain RAG retrieves paragraphs that sound like your question. GraphRAG builds a map of the things inside your corpus — entities as nodes, relationships as edges, clustered into summarized neighborhoods — and answers by traveling that map. When a question spans many documents or asks about a whole corpus, connections beat similarity.

02 The one-idea version

A vector index stores strings: it can find text that sounds like your query, and nothing more. A knowledge graph stores things: the entities in your corpus and the relationships between them, plus which neighborhood each one belongs to. GraphRAG's whole move is to build that map at index time, so at query time the model answers by walking connections — not by fishing for lookalike paragraphs. As Google learned with search in 2012: to master retrieval, map the things under the strings.

03 The visual

Index time builds the map in three passes — extract, cluster, summarize. Query time routes each question to the right search mode: local for entities, global for themes, plain vectors for exact passages.

04 How it works

Seven mechanics: three index-time passes, three query-time modes, and the rule that decides which mode answers.

1

Chunk the corpus, then extract entities, relationships, and claims with an LLM

Slice documents into text units, then have an LLM pull out the things (people, orgs, places, products), the relationships between them, and key factual claims — every triple linked back to its source chunk. This pass is the entire foundation: an under-extracted corpus builds an empty map, and no query mode can rescue it.

2

Cluster the graph into communities (Leiden), then summarize bottom-up

Community detection finds dense neighborhoods — the "Odesa political actors" cluster, the "banking targets" cluster. An LLM writes a summary per community, then summarizes the summaries, building a hierarchy. This is the expensive, one-time work that makes whole-corpus questions answerable in seconds instead of context-window lifetimes.

3

Local search: land on entities, fan out to their neighbors

Link the query's entities to graph nodes, then pull those nodes, their relationships, neighbor entities, and the attached text units. That's multi-hop answering: Microsoft's demo query "What has Novorossiya done?" failed on baseline RAG ("not mentioned") because no chunk contained it — the graph found the entity and walked its edges to the answers, with citations.

4

Global search: map-reduce over community summaries for whole-corpus questions

"What are the top 5 themes in the data?" has nothing in it to point at a chunk — so don't touch raw chunks. Fan out across community summaries (map), answer from each neighborhood, then reduce into one synthesis. Each claim cites its community report, which cites source text: sensemaking with an audit trail.

5

DRIFT: local search primed with community context

The middle mode — start from specific entities, but enrich the fan-out with the communities those entities belong to. Reach for it when the question is about a thing in context: "tell me everything about Novorossiya and the world it moves in." Specific answers, grounded in the neighborhood they live in.

6

Seed with vectors, walk with graphs — hybrid is the default pattern

GraphRAG is a retrieval path, not a religion. The common production pattern: vector or keyword search finds the seed nodes, the graph traversal gathers their neighborhoods, optionally re-rank with a graph algorithm like PageRank. Graphs and vectors are complementary — strings find the entry point, things walk the rest.

7

Basic search: know when the graph adds nothing

For "find the paragraph that says X," plain top-k vector search is cheaper, faster, and better. Every entity, relationship, and community summary costs an LLM call at index time — pay for the map only when questions need connect-the-dots or sensemaking, never for needle-in-haystack lookups.

05 Code sketch

Local fan-out in 19 lines: entities as nodes, relationships as edges, source chunks as provenance. Production would swap the dicts for a graph DB and add Leiden — the shape is identical.

from collections import defaultdict

graph = defaultdict(set)      # entity -> {(relation, entity)}
sources = defaultdict(list)   # entity -> [source chunk ids]

def index_doc(doc_id, text, extract):
    # extract: an LLM call returning (subject, relation, object) triples
    for s, rel, o in extract(text):
        graph[s].add((rel, o)); graph[o].add(("^" + rel, s))  # inverse edge
        sources[s].append(doc_id); sources[o].append(doc_id)

def local_search(query_entities, depth=2):
    # land on entities, fan out; gather the neighborhood + citations
    seen, frontier = set(query_entities), set(query_entities)
    for _ in range(depth):
        nxt = {o for e in frontier for _, o in graph[e]} - seen
        seen |= nxt; frontier = nxt
    cites = sorted({d for e in seen for d in sources[e]})
    return seen, cites  # subgraph + provenance for the LLM context

# global search = same idea at one level up: map-reduce over community
# summaries instead of chunks. raw text is never read at query time.

06 Failure modes

Named pitfalls, each with a one-line fix. Almost all of them are index-time sins surfacing at query time.

✕

An empty map: weak extraction builds a graph of nothing Fix: prompt-tune the extractor with explicit entity types + few-shot examples, and use smaller chunks with overlap so entities don't get cut in half.

The LLM extracted three entities from a 50-page corpus and you wonder why local search returns nothing. GraphRAG's query modes are only as good as the extraction pass — audit node/edge counts per document before tuning anything downstream.

✕

Entity merge collisions: one node, three different "Mercurys" Fix: give the extractor a typed schema (planet / element / company) and disambiguation cues; split on type before merging on name.

"Mercury" the planet, the element, and the car company collapse into one node, and every traversal through it mixes unrelated neighborhoods. The answers look confident and are nonsense.

✕

Global search on every query Fix: route queries — entities → local, corpus themes → global, exact passages → basic vector search. The router is part of the architecture.

Map-reduce over community summaries for "what's the refund policy?" burns tokens and latency for an answer a vector lookup would find cheaper. Global search is for sensemaking questions — everything else is paying for a map you don't need.

✕

A stale graph: the corpus moved on, the map didn't Fix: index incrementally — re-extract only changed text units, re-cluster and re-summarize only affected communities — and timestamp claims so answers say as-of-when.

Documents update daily; a graph built once now cites a world that no longer exists. Provenance to stale sources is worse than no provenance — it looks authoritative while being wrong.

✕

Hub over-traversal: one hop from "United States" returns half the graph Fix: cap fan-out depth at 1–2, cap node counts, weight edges by relationship relevance, and prune or down-weight mega-hubs.

A high-degree node explodes the neighborhood, the context window fills with trivia, and the good signal drowns. Unbounded traversal is a denial-of-service you run on yourself.

10 Flashcards

Click a card — or tab to it and press Enter — to flip it.

GraphRAG
RAG where the retrieval path includes a knowledge graph: the corpus is turned into entities and relationships at index time, and answers come from walking connections — plus vector seeds — instead of similarity alone.
Local search
For entity questions: link query entities to graph nodes, fan out 1–2 hops to neighbors, relationships, and source chunks. The multi-hop answer mode — "what did X do?"
Global search
For whole-corpus questions: map-reduce over pre-computed community summaries — answer per neighborhood, then reduce into one synthesis. Raw chunks are never read at query time.
DRIFT search
The middle mode: start from specific entities, but enrich the fan-out with the communities those entities belong to. Specific answers, grounded in the neighborhood they live in.
Community summaries
After Leiden clustering finds dense graph neighborhoods, an LLM summarizes each community bottom-up — summaries of summaries up the hierarchy. This one-time cost is what makes theme questions cheap to answer.
TextUnit
The analyzable slice of the corpus GraphRAG extracts from — the raw material for entities, relationships, and claims. Every triple links back to its TextUnit for provenance.
Provenance
Every claim cites its source: entity/relationship rows point to source chunks, community reports point to the text behind them. Answers are auditable back to the original documents.
Seed-and-traverse
The default hybrid pattern: vector or keyword search finds the seed nodes, graph traversal gathers their neighborhoods, optionally re-ranked with PageRank. Strings find the entry point; things walk the rest.
Entity merge collision
One node, several real-world things ("Mercury" planet/element/company). Every traversal through it mixes unrelated neighborhoods. Fix: typed entity schemas and disambiguation cues at extraction time.
"Things, not strings"
Google's 2012 knowledge-graph insight, reused by GraphRAG: vectors capture words statistically; graphs capture the entities and relationships the words are about. Mastery comes from mapping the things under the strings.

11 Reach for this when…

Answers live in relationships between documents, not inside any single chunk — multi-hop questions ("who funded the supplier that shipped the faulty part?") that plain RAG answers with "not mentioned."
The question is about the whole corpus — themes, trends, controversies — and there's nothing in the query to point at a chunk. Global map-reduce over community summaries is the only honest way.
Answers must be auditable, explainable, or access-controlled — graph paths can be visualized, cited, and annotated in ways vector similarity never will be, which is the killer feature in regulated or high-stakes domains.
