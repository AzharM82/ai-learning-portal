ML platform engineering: training infrastructure and feature stores

Training a model once is a notebook. Training, retraining, and serving many models reliably is a platform: shared feature definitions, reproducible training infrastructure, GPU scheduling with quotas, and a registry that knows exactly which data and code produced every model.

02 The one-idea version

One definition, two stores, one registry. Define each feature once and serve that same definition to training (offline store, point-in-time joins so no future data leaks in) and to inference (online store, latest values at low latency). Run training on shared, scheduled infrastructure where every run is reproducible from code + data snapshot + config, and register the resulting model with its lineage. That consistency — not GPU count — is what makes an ML platform trustworthy.

03 The picture: from raw data to a registered model

Features flow one way, training pulls history, serving pulls the present, and the registry records everything.

04 How it works

Six mechanics: features as a product, training as scheduled reproducible jobs, and models as registered artifacts.

1

Define features once, in a registry, as code

Register every feature with its entity (user, driver, account), source, transformation, TTL, and owner — versioned in git like feast apply publishes Feast definitions. The registry is the catalog teams search before building a duplicate, and the single definition that both training and serving resolve. A feature with no owner, no TTL, and no description is technical debt with a latency budget.

2

Split storage: offline for history, online for the present

The offline store (warehouse/lakehouse) holds months of timestamped feature values for training and backfills. The online store (Redis/DynamoDB-style key-value) holds only the latest value per entity for low-latency inference. Materialization jobs move values offline → online on a schedule; streaming transforms push fresh values directly. Never serve training from the online store or inference from the warehouse — each fails the other's latency/scale job.

3

Make training datasets point-in-time correct

For each labeled example at time t, join only feature values with event timestamp ≤ t. That one rule prevents label leakage (future values quietly inflating offline metrics) and, paired with the single definition in step 1, prevents training-serving skew. Provide an entity dataframe (keys + event_timestamp) and let the store do the join — hand-written SQL joins per team is where leakage breeds.

4

Run training as scheduled, reproducible jobs — not notebooks on shared boxes

Package training as a containerized job with pinned dependencies, declared resources, and a config file. Platforms like Ray Train express scale declaratively — ScalingConfig(num_workers=8, use_gpu=True) requests one GPU per worker — while Kubernetes operators (Kubeflow Trainer) turn a TrainJob into the right pods, rendezvous, and restart policy. Every run records code commit, data snapshot, config, and seed, checkpoints periodically, and can resume after a preemption or node failure.

5

Schedule GPUs like a scarce shared resource: quotas, priorities, utilization

GPUs are the platform's expensive bottleneck, so admission matters: per-team quotas, priority classes (production retraining preempts experiments), gang scheduling for distributed jobs (all workers start together or none do), and backfill of idle capacity. Measure utilization as GPU-hours actually computing, not allocated — a job holding 8 GPUs at 30% SM utilization is a scheduling and data-loading problem, not a reason to buy more hardware.

6

Register every model with lineage, and promote by alias behind an eval gate

A trained artifact is not done until it is in the model registry: versioned, tagged, and linked to the run, dataset snapshot, feature versions, and eval results that produced it. MLflow's registry model is the pattern: versions under one name, mutable aliases like @champion for the production version, and tags for validation status. Serving loads models:/name@champion; promotion is reassigning the alias after evals pass — never copying files or editing production config by hand.

7

Monitor features and models, and close the retraining loop

Track feature freshness (age of latest value vs its TTL), null/drift distributions offline vs online, serving latency and errors, and model quality on labeled outcomes as they arrive. Wire breaches to action: stale feature → page its owner; drift or quality drop → trigger a retraining run on the same paved road, through the same eval gate. A platform that only trains is half-built; the loop back is the product.

05 Code sketch

Point-in-time training data and low-latency online features from the same Feast definitions.

from feast import FeatureStore
import pandas as pd

store = FeatureStore(repo_path=".")
features = ["driver_stats:trips_7d", "driver_stats:rating_30d"]

# Training: entity rows carry the label time — join is point-in-time correct
entity_df = pd.DataFrame({"driver_id": [1001, 1002],
                          "event_timestamp": pd.to_datetime(
                              ["2026-11-20T08:00Z", "2026-11-20T09:30Z"]),
                          "label": [1, 0]})
train_df = store.get_historical_features(entity_df=entity_df,
                                         features=features).to_df()

# Serving: same feature refs, latest values from the online store
online = store.get_online_features(
    features=features,
    entity_rows=[{"driver_id": 1001}]).to_dict()
print(train_df.shape, online["trips_7d"])

06 Failure modes

Five ways ML platforms quietly fail — each with a one-line fix.

1

Training-serving skew: features computed twice, differentlyFix: one registered definition resolved by both paths; compare offline vs online values in CI and in production monitoring.

The model is perfect offline and mediocre live, with no error anywhere — the batch SQL and the streaming job simply disagree.

2

Label leakage from future feature valuesFix: point-in-time joins keyed on event_timestamp for every training dataset; audit any feature whose offline importance looks too good.

Offline AUC is spectacular because a feature encoded information only knowable after the label — the model learned to cheat.

3

GPU hoarding and starvation: allocated, idle, and blocking othersFix: quotas + priority/preemption, gang scheduling, idle-job reaping, and utilization (not allocation) on the platform dashboard.

One forgotten experiment holds a node for a weekend while the production retrain queues — cost up, throughput down, trust gone.

4

Unreproducible runs: "the good model" nobody can rebuildFix: every run logs code commit, data snapshot, feature versions, config, and seed; the registry entry links to all of them.

Without lineage you cannot debug a regression, satisfy an audit, or retrain the winner — you can only hope.

5

Stale features served silentlyFix: TTL per feature view, freshness monitoring with owner alerts, and a serving fallback (default / previous model) when freshness breaches.

The pipeline broke on Friday; on Monday the model is still confidently predicting on three-day-old features.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

Feature store
An ML data system that transforms raw data into features, stores them offline and online, and serves the same definitions to training and inference — the interface between models and data.
Offline vs online store
Offline: timestamped history in a warehouse/lake for training and backfills. Online: latest value per entity in a low-latency key-value store for inference. Materialization moves values between them.
Point-in-time correctness
Joining, for each labeled example, only feature values with event timestamp at or before the label time. Prevents label leakage from future information.
Training-serving skew
When training and inference compute the same feature differently (two code paths), so live inputs differ from training inputs and quality silently degrades. Cured by one registered definition.
Feature registry
The catalog of feature definitions — entity, source, transform, TTL, owner, version — that teams discover and reuse, and that configures transformation, storage, and serving.
Materialization
The scheduled job that loads feature values from the offline store into the online store so inference sees fresh values; streaming ingestion can push updates directly.
Gang scheduling
Admitting all workers of a distributed job together or not at all. Partial admission wastes GPUs and can deadlock collectives waiting for peers that will never start.
Model registry & alias
A versioned store linking each model to its run, data, and evals. A mutable alias like @champion points at the production version; promotion and rollback are alias reassignments.
Lineage
The recorded chain — code commit, data snapshot, feature versions, config, seed, eval results — that produced a model version, making runs reproducible and auditable.
GPU utilization vs allocation
Allocation is GPUs reserved; utilization is GPUs actually computing. Platforms optimise utilization — low utilization at full allocation signals data-loading or scheduling problems, not a need for more hardware.

11 Reach for this when…

Two or more teams train models on overlapping data — shared feature and model registries stop duplicated pipelines, divergent definitions, and unfindable models.
Offline metrics do not survive contact with production — audit for skew and leakage first: one definition, point-in-time joins, offline-vs-online comparison.
GPUs are expensive, queued, or mysteriously idle — treat training as scheduled platform work: quotas, gang scheduling, checkpoints, and utilization metrics before buying capacity.
