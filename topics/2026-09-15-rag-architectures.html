RAG architectures: naive, advanced, and when to skip RAG

Don't teach the model your data — hand it the right pages at query time. Retrieval-augmented generation grounds answers in your corpus, but the naive pipeline misses answers constantly. Here's how to make retrieval actually work, and when not to bother.

02 The one-idea version

The model's weights are frozen knowledge; your corpus is live knowledge. RAG bridges them: at query time, retrieve the most relevant passages from your corpus and inject them into the context, so the model reasons over your facts instead of guessing from training data. Retrieval does the remembering; the model does the reasoning.

04 How it works

Six mechanics. The first four build the advanced pipeline; the last two decide the architecture.

1

Chunk so that retrieval can win

Retrieval finds chunks, not documents — and chunking is the unglamorous 80% of RAG quality. Cut at semantic boundaries (headings, paragraphs), keep 200–500 tokens per chunk, and attach metadata (source, title, date) so the answer can cite it. Test recall with real user questions, not vibes.

2

Embed query and chunks into one vector space

A good embedding model puts "refund policy" and "can I get my money back?" near each other. Pick one embedding model for the whole corpus, store vectors in an ANN index (HNSW for recall, IVF for speed), and re-embed everything if the model changes — mixed embeddings silently break similarity.

3

Search hybrid: dense + keyword, then fuse

Pure vector search misses exact terms (model numbers, names, error codes); pure keyword search misses synonyms. Run both — dense embeddings + BM25 — and fuse the rankings with reciprocal rank fusion. Each catches what the other misses; hybrid is the single cheapest recall upgrade there is.

4

Retrieve wide, then rerank narrow

Two-stage retrieval: a cheap ANN pass pulls the top 50–100 candidates, then a cross-encoder reranker scores each candidate against the full question and keeps the top 3–5. Most of your retrieval precision lives in the reranker, not the embeddings.

5

Rewrite the query before you search

Users ask ambiguous questions; databases store answers. Expand terse queries, decompose multi-hop questions into sub-queries, and consider HyDE (generate a hypothetical answer, then search with its embedding). One bad query rarely retrieves what a good query would.

6

Generate with citations, then verify groundedness

Require the model to cite which chunk supports each claim, then run a groundedness check: does every answer claim appear in the retrieved passages? The RAG triad — context relevance, groundedness, answer relevance — is how you eval; fail closed (say "I don't know") when the check fails.

7

Choose the retrieval surface deliberately

Not every knowledge problem is a RAG problem. Small corpus that fits in context? In-context dump. Exact answers from structured data? SQL / API calls, not vectors. Stable behavior change? Fine-tuning. Volatile, proprietary, or long-tail facts? That's RAG's home turf.

05 Code sketch

A minimal naive RAG in under 30 lines — then imagine replacing search() with the hybrid + rerank pipeline from section 04.

def answer(question, docs, embed, search, llm):
    # 1. chunk (200-500 tokens, semantic boundaries)
    chunks = [c for d in docs for c in chunk(d, size=400)]
    # 2. embed once, index with ANN (HNSW)
    index = AnnIndex([embed(c.text) for c in chunks])
    # 3. hybrid search: dense top-100 + BM25, fuse ranks
    cands = reciprocal_rank_fusion(
        index.query(embed(question), k=100),
        bm25(question, chunks, k=100))
    # 4. cross-encoder rerank -> top 5
    top = rerank(question, cands, k=5)
    context = "\n\n".join(f"[{c.id}] {c.text}" for c in top)
    # 5. generate with citation requirement
    prompt = (f"Answer using ONLY the sources below. Cite [id] per claim.\n"
              f"If unsupported, say so.\n\n{context}\n\nQ: {question}")
    return llm(prompt)

06 Failure modes

Named pitfalls, each with a one-line fix. Most RAG demos die on number one.

✕

Chunk rot Fix: 200–500 token chunks at semantic boundaries, with source metadata; measure recall on real questions.

Chunks too big bury the answer in noise; chunks too small lose the context that makes them meaningful. Bad chunking makes everything downstream worse.

✕

Retrieval miss Fix: go hybrid (dense + BM25), add a reranker, and track hit-rate — the fraction of questions whose answer is in the retrieved set.

The answer exists in the corpus but never lands in top-k. Embeddings alone miss exact terms; the generator can't answer what it never saw.

✕

Lost in the middle Fix: keep the retrieved set small (3–5 chunks), order the strongest chunk first, and citation-check claims.

The right passage IS in context but the model ignores it — attention spreads thin and the answer leans on parametric memory instead.

✕

Hallucination despite retrieval Fix: "answer ONLY from these sources", require citations, and fail closed when the groundedness check fails.

Retrieved facts don't stop a model from answering from its training weights. Grounding is a constraint you must enforce, not a property you get for free.

✕

RAG when you shouldn't Fix: route — direct prompt for known facts, SQL/API for structured data, fine-tune for stable behavior, RAG for volatile proprietary facts.

Latency, cost, and complexity for a question the model could have answered directly. Retrieval is a tool, not an identity.

10 Flashcards

Click a card — or tab to it and press Enter — to flip it.

Retrieval-augmented generation (RAG)
At query time, retrieve relevant passages from your corpus and inject them into the model's context. Retrieval remembers; the model reasons.
Naive RAG
Chunk → embed → vector top-k → stuff into prompt. The baseline every system starts from — and the one that misses answers most often.
Hybrid search
Running dense (embedding) and sparse (BM25 keyword) search together and fusing rankings — embeddings catch meaning, BM25 catches exact terms.
Reciprocal rank fusion (RRF)
A fusion formula that combines ranked lists by summing 1/(k + rank) across lists — no score normalization needed. The standard hybrid-search combiner.
Reranker (cross-encoder)
A second-stage model that scores the full question against each candidate passage, one by one, keeping the top 3–5. Where most retrieval precision lives.
HyDE
Hypothetical Document Embeddings: have the model draft a hypothetical answer, then search with THAT embedding. Bridges the gap between question-speak and doc-speak.
The RAG triad
The three evals that matter: context relevance (did retrieval fetch the right passages?), groundedness (is each claim supported?), answer relevance (did it answer the question?).
Lost in the middle
Models attend best to the start and end of context; retrieved passages buried in the middle get ignored. Fix: small retrieved sets, strongest chunk first.
Chunking
Splitting documents into retrievable units at semantic boundaries (200–500 tokens, metadata attached). The unglamorous 80% of RAG quality.
When to skip RAG
Model already knows it → direct prompt. Corpus fits in context → dump it. Answer is structured → SQL/API. Stable behavior change → fine-tune.

11 Reach for this when…

Answers must come from your proprietary or volatile data — docs, policies, code, product knowledge that changes faster than training cycles.
Retrieval keeps missing but the answer exists in the corpus — go hybrid + rerank + query rewrite before blaming the model.
You're about to build a RAG pipeline — first ask: direct prompt, in-context dump, SQL, or fine-tune? Retrieval is a tool, not a default.
