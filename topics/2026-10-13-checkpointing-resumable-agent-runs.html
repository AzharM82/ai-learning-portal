Checkpointing and resumable agent runs

Your agent is six steps into an eight-step research task — then the process dies. Without checkpoints, it starts over: re-burning tokens, re-calling tools, re-running side effects. Checkpointing durably records each step’s completed state, so a crashed run resumes from the last checkpoint instead of restarting. Replay restores state; idempotency keys protect the outside world.

02 The one-idea version

A crash mid-run must never mean starting over. A checkpoint is a durable record of what completed and where to resume — the state snapshot plus the pointer to the next un-done step. On restart the runner replays the record to reconstruct state and skips completed steps rather than re-executing tools. Checkpoints restore memory; they do not undo the outside world — that is why every side effect rides an idempotency key.

03 Crash mid-run: the two futures

Same run, same crash at step 4 of 6. One run re-burns everything; the other resumes in seconds.

04 How it works

Imperative, concrete. Crash-safety is designed in, not bolted on.

1

Checkpoint state AND intent at step boundaries

Record three things: the state snapshot (what the run knows so far), the resume pointer (which step comes next — LangGraph calls this next in its StateSnapshot), and the thread identity. State without a pointer tells you what the run knew, not what to do; a pointer without state makes you re-derive everything. Step boundaries — node completions, completed tool batches — are the natural checkpoint unit.

2

Use a durable checkpointer — never in-memory for real runs

InMemorySaver/MemorySaver dies with the process; they are for dev only. Production means a database-backed checkpointer: SqliteSaver for local runs, PostgresSaver for production. Compile once with graph.compile(checkpointer=checkpointer), then every invoke/stream writes checkpoints automatically — one line of durability.

3

Resume means skip, not replay

On restart, load the latest checkpoint for the thread_id, restore state, and skip every completed step — resume with no new input (LangGraph: invoke(None, config)). Replay reconstructs state from the record; it does not re-run tool calls. If your resume logic re-fires an API to “rebuild state,” you wrote a restart, not a resume — and you just re-burned the tokens.

4

Guard every side effect with an idempotency key

A checkpoint restores the run’s memory; it does not un-send the email or un-charge the card. Record the idempotency ledger — which external effects already fired, with which keys — in the checkpoint. On resume, any step that touches the outside world must carry the same key, so the world sees one effect no matter how many times the run restarts.

5

Treat a human approval as a checkpoint with a signal

Pause before the risky step, persist state, then release the worker — do not hold a process open waiting on a person. The human’s decision arrives as ordinary input (approve/reject/edit), the run resumes from the checkpoint, and the audit trail shows exactly what was known at decision time. The graph never blocks on a human; it waits in the database.

6

Version the checkpoint schema and prune old threads

State shapes evolve; resuming an old checkpoint with new code corrupts the run. Stamp a schema version into the checkpoint metadata and refuse (or migrate) on mismatch. Checkpoints also accumulate: prune completed or expired threads on a retention schedule — storage and read latency both grow with a thread’s history.

7

For long-running orchestration, replay from an event history

Temporal’s model: every workflow event is durably logged, and a crashed worker replays that history to rebuild state before continuing. The determinism rule falls out of this: keep LLM calls and API calls in activities (non-deterministic by nature), keep orchestration logic deterministic, and the run can resume after hours, days, or a deploy.

05 Code sketch

A journaled step runner: durable JSON checkpoint, resume skips completed steps, side effects ride an idempotency ledger.

# Checkpointed runner: crash anywhere, resume from the last boundary
import json, os, uuid

CKPT = "run_checkpoint.json"

def save(ckpt):
    tmp = CKPT + ".tmp"
    json.dump(ckpt, open(tmp, "w"))      # atomic write: never a torn file
    os.replace(tmp, CKPT)

def run_resumable(steps, thread_id):
    ckpt = json.load(open(CKPT)) if os.path.exists(CKPT) else {
        "thread_id": thread_id, "schema_v": 1,
        "next": 0, "state": {}, "effects": {},  # idempotency ledger
    }
    assert ckpt["schema_v"] == 1, "stale checkpoint schema; migrate first"
    for i, step in enumerate(steps):
        if i < ckpt["next"]:
            continue                                  # completed: skip, never replay
        key = ckpt["effects"].get(step.name) or str(uuid.uuid4())
        result = step(key, ckpt["state"])            # same key on resume: one effect
        ckpt["effects"][step.name] = key
        ckpt["state"].update(result)
        ckpt["next"] = i + 1                    # pointer advances only after success
        save(ckpt)                                # checkpoint at every boundary
    return ckpt["state"]

06 Failure modes

Named, with a one-line fix each. Most resumability bugs are about what was NOT in the checkpoint.

F1

In-memory checkpointing in productionFix: durable backend for real runs — SQLite locally, Postgres in production.

The demo worked beautifully with InMemorySaver — then the container restarted and three hours of agent work vanished. RAM is not storage. The swap is one line at compile time; the lesson is that your first deploy is where this always breaks.

F2

Checkpointing state but not the side-effect ledgerFix: record every external effect (with its idempotency key) in the checkpoint.

The run resumed perfectly — state restored, pointer correct — and then re-sent the customer email because nothing recorded that it already went out. A checkpoint that forgets the outside world is an amnesiac resume: technically correct, practically a duplicate.

F3

Resume replays tool calls to "rebuild state"Fix: restore state from the record, then skip completed steps; never re-execute.

The resume handler re-runs the search and the LLM calls “to get back to where it was” — burning tokens, drifting results (LLMs don’t repeat), and possibly re-firing non-idempotent effects. If resuming costs the same as restarting, your checkpoints are decoration.

F4

No schema version on checkpointsFix: stamp schema_v into every checkpoint; refuse or migrate on mismatch.

You ship a state-shape change; threads that paused before the deploy resume into a shape the new code doesn’t understand. Keys are missing, types are wrong, and the failure looks like a model hallucination. Versioning turns “stale checkpoint” into a planned path instead of a mystery bug.

F5

Checkpointing inside tight loops or never at allFix: checkpoint at step boundaries — node completions, completed tool batches.

Checkpointing every LLM token costs more in write latency than it saves; checkpointing once per run means one crash loses the whole run. The sweet spot is the unit where re-running is expensive but writing is cheap: after each completed step.

F6

Holding a process open while waiting on a humanFix: interrupt → persist → release the worker; resume on the human’s signal.

The agent pauses before the send-email step and blocks the process — for two days, while the approver is on leave. Workers are expensive and restartable; the database is cheap and durable. A pause that survives a weekend is a checkpoint with a human-shaped resume signal.

Checkpoint
A durable record of what completed and where to resume: state snapshot + resume pointer + thread identity. Written at step boundaries.
Resume pointer ("next")
The recorded identity of the next un-done step. State without a pointer tells you what the run knew, not what to do next.
Checkpointer
Saves thread-scoped graph state as checkpoints (InMemorySaver for dev; SqliteSaver / PostgresSaver for durable runs).
thread_id
The scope a checkpointer writes to: one ID, one continuous run history. Same ID resumes; a new ID starts fresh.
Resume by skipping
Load the latest checkpoint, restore state, and skip completed steps (invoke(None, config)). Replay restores memory; it never re-runs tools.
Idempotency ledger
The checkpoint's record of external effects already fired, with their keys. Checkpoints restore the run's memory — the ledger protects the outside world.
Planned interrupt
A checkpoint with a human-shaped resume signal: pause, persist, release the worker; resume on approve / reject / edit. Never block a process on a person.
Checkpoint schema version
Stamped into checkpoint metadata; refuse or migrate when code and checkpoint disagree. Stops state-shape changes from corrupting paused threads.
Event history replay (Temporal)
Every workflow event durably logged; a crashed worker replays the history to rebuild state, then continues. Non-deterministic calls live in activities.
Checkpoint retention
Checkpoints accumulate: storage and read latency grow with thread history. Prune completed or expired threads on a retention schedule.

11 Reach for this when…

Your agent runs longer than your infrastructure's patience — multi-step tasks, flaky infra, deploys mid-run. Any run that can die between steps needs checkpoints: persist state at step boundaries so a crash resumes instead of restarting.
A human must approve or edit before an irreversible step. Don’t block a process on a person — interrupt, persist the checkpoint, release the worker, and let the decision arrive as ordinary resume input with the full decision-time state attached.
You’re building the run to be long-running by design (hours, days): checkpoint schema versioning, retention policies, and an idempotency ledger for every external effect are what keep a months-old thread resumable instead of a mystery crash.
