Workflow orchestration engines: durable execution that survives crashes

A multi-step agent that dies at step 7 loses everything — the only thing that knew which step it was on was a stack frame that no longer exists. Durable execution hands failure management to the platform: every step’s result is recorded in an event history, and when the process crashes, a fresh worker replays that history to rebuild the state and resumes exactly where it stopped. Write the happy path; let the engine own the recovery.

02 The one-idea version

Durable execution is the guarantee that your code runs to completion even though the machine running it will not. The platform never snapshots memory; it records the result of every step as an ordered event history. Recovery means a new process re-runs your code from the top, and every already-completed step returns its recorded result instantly instead of doing real work again — until execution arrives at the step that never finished, with your local variables exactly where they were. If your agent can't crash and continue, it's not orchestrated; it's hopeful.

04 How it works

Seven mechanics. The engine changes (Temporal, AWS Step Functions, Azure Durable Functions, DBOS) — the model doesn't.

1

Split orchestration from side effects

A Workflow is control flow only: loops, conditionals, and calls, deciding what happens in what order. An Activity is one unit of real work that touches the outside world: an API call, a DB write, an email, a card charge. The split exists so replay stays safe — control flow re-runs for free, side effects never re-run for free.

2

The event history is the state

Every step's result is recorded as an ordered event log on the service — not in your process's memory. The log is the durable record of what happened: which activities completed, what they returned, which timers fired. Debugging starts from evidence instead of reconstruction.

3

Recovery is replay, not restore

Nothing snapshots the stack. A new worker fetches the event history and re-runs the workflow code from the top; each already-completed activity returns its recorded result instantly, with no real work performed. When execution reaches the unfinished step, local variables are exactly what they were. The function "never crashed" — it was seamlessly blocked.

4

Workflow code must be deterministic

Because replay re-runs the workflow, it must produce the same commands every time: no random(), no wall-clock reads, no direct HTTP calls, no thread timing in workflow code. Anything non-deterministic moves into an activity, whose recorded result replays identically.

5

Retries live in configuration, not in code

Each activity declares a retry policy — max attempts, backoff, timeouts — instead of a hand-written retry loop at the call site. A failed activity retries with backoff automatically; an activity whose worker dies is rescheduled. You stop writing recovery code that has nothing to do with your problem.

6

Workers poll; nothing is pushed

A worker is the process that actually runs your code. Workers poll named task queues and pull work; the service never pushes. A worker that is down or saturated stops polling and its tasks wait. Horizontal scale-out is adding more pollers — no load balancer heroics.

7

Long waits are first-class

A workflow can sleep on a durable timer for minutes or months with no process holding the thread — "wait 30 days, then confirm delivery" is one line, not a cron job plus a state table plus a reconciliation sweep. Signals push data into a running workflow mid-flight (human approval!); queries read its state without mutating it.

05 Code sketch

An order pipeline in the durable-execution shape (Temporal-style Python SDK idiom). Look at what’s missing: no retry loops, no checkpoint columns, no state table — just the happy path.

@workflow.defn
class OrderPipeline:
    @workflow.run
    async def run(self, order_id):
        await workflow.execute_activity(validate_order, order_id,
            start_to_close_timeout=timedelta(minutes=2),
            retry_policy=RetryPolicy(maximum_attempts=5))  # config, not code
        await workflow.execute_activity(charge_card, order_id,
            retry_policy=RetryPolicy(maximum_attempts=1))      # charge once, ever
        shipment = await workflow.execute_activity(ship_package, order_id)
        await workflow.sleep(timedelta(days=30))             # waits 30 days, no process
        await workflow.execute_activity(confirm_delivery, shipment)

# If the worker dies during ship_package, another worker replays the
# recorded results of validate_order and charge_card, rebuilds locals,
# and resumes at ship_package. charge_card is never called twice.

06 Failure modes

Five ways durable execution bites — and the fix for each.

1

Side effects inside the workflowFix: workflows orchestrate; activities act. Anything touching the outside world moves into an activity, whose recorded result replays identically.

A direct API call in workflow code runs again on every replay. Charge the card, send the email, write the row — once per recovery instead of once ever. The double-charge is invisible until the invoice arrives.

2

Non-deterministic workflow codeFix: no random(), no wall-clock reads, no iteration order dependence in workflow code — use the engine's deterministic timer and random APIs, or push it into an activity.

Replay must produce the exact same commands as the original run. A random() branch or a time.now() condition makes the replay diverge from the recorded history — and the engine fails the workflow instead of recovering it.

3

Unbounded history growthFix: use Continue-As-New to restart the workflow with the same ID and a fresh history; chunk looping work into child workflows.

A workflow that loops for months accumulates thousands of events, and every recovery replays all of them. Replay stays linear, but a million-event history still makes recovery slow and debugging painful.

4

Giant payloads between stepsFix: store large blobs in object storage or a database and pass a reference through the workflow; keep the history small and queryable.

Every activity result is recorded in the event history — including that 50 MB embedding dump you passed "just for convenience." History bloats, replay slows, and you hit payload size limits mid-run.

5

Deploying new code under running workflowsFix: version your workers (or workflows): running executions finish on the code they started with; only new executions take the new version. Never assume replay semantics are identical across versions.

Recovery replays against the history the original run recorded. If the deployed code changed the workflow's shape mid-flight, replay can diverge — your deploy just became a data-corruption vector for long-running executions.

10 Flashcards

Click or press Enter/Space to flip. Ten terms worth owning.

Durable execution
The guarantee that code runs to completion despite crashes, restarts, and network partitions. The platform preserves execution state so a process failure is a pause, not a loss.
Workflow
Deterministic orchestration code: loops, conditionals, and calls that decide what happens in what order. Never performs side effects directly — it is replayed on recovery.
Activity
One unit of side-effectful work — API call, DB write, email. Plain function, individually retried with a declared policy, and its recorded result replays identically.
Event history
The ordered, durable log of everything that happened in a workflow execution: completed activities and their results, timers, signals. The only state that survives a crash.
Replay
Recovery mechanism: a new worker re-runs the workflow from the top against the event history. Completed steps return recorded results instantly with no real work, rebuilding state to the failure point.
Determinism rule
Workflow code must produce the same commands on every run: no random(), no wall-clock reads, no direct I/O. Non-determinism belongs in activities or engine primitives.
Retry policy
Declared per-activity: max attempts, backoff coefficients, timeouts. Recovery configuration instead of hand-written retry loops — the engine, not your code, owns the retry.
Task queue
A named queue the service fills and workers poll. Nothing is pushed — workers ask for work, so a dead or saturated worker simply stops polling and its tasks wait.
Worker
The process that actually runs workflow and activity code — on your infrastructure. The service schedules work and records history; workers execute. Scales horizontally by adding pollers.
Continue-as-new
Restarting a workflow with the same ID and a fresh event history. The escape valve for unbounded history growth in long-running or looping executions.

11 Reach for this when…

A multi-step process dies and loses everything. When "which step was I on?" lives only in a dead stack frame, the event history turns recovery into replay-and-resume instead of restart-and-pray.
Your code is mostly recovery plumbing. Retry loops, checkpoint columns, state tables, reconciliation jobs: if the business logic is a footnote in its own file, move the durability layer into the platform.
A workflow must wait on the real world. Thirty-day timers, human-approval signals, month-long agent runs: durable waits and mid-flight messaging beat cron jobs plus polling plus a state table, every time.
