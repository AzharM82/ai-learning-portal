Chunking and embeddings: the unglamorous 80%

Two unglamorous decisions determine most of your retrieval quality: how you cut documents into pieces, and how you turn those pieces into numbers. Get them right and retrieval feels magical; get them wrong and no reranker or prompt trick will save you.

02 The one-idea version

Retrieval compares what the user asks against what's in your corpus — but both have to live in the same space, cut at the same scale. Chunking decides the unit of meaning (what can be found) and embeddings decide how meaning becomes geometry (what counts as close). Most retrieval failures are decided here, long before any model is called. Chunking is the cutting; embeddings are the comparing.

03 The visual

The same document chunked two ways, and how the chunks land in vector space. Retrieval is just nearest-neighbor search over the unit you chose.

04 How it works

Six mechanics. The first three cut, the next three compare — and the last one keeps both honest.

1

Cut at meaning boundaries, not token boundaries

Fixed-size splitting cuts sentences in half; recursive splitting tries \n\n → \n → sentence → word until each chunk fits. Prefer 128–512 tokens with 10–20% overlap, and keep structure-aware splitters (markdown headers, HTML tags, code functions) for structured docs.

2

Make every chunk self-contained

A chunk is retrieved without its neighbors — prepend the section header, document title, and source as metadata. Pinecone's rule of thumb: if the chunk makes sense to a human without the surrounding context, it will make sense to the model.

3

Size the chunk to the question

Small chunks give precision (exact facts, error codes); large chunks give context (procedures, explanations). Match chunk scale to query scale — and remember bigger chunks dilute meaning: one noisy sentence in a 2000-token chunk can sink its similarity score.

4

One embedding model for everything, or nothing works

Vectors from different models live in different spaces — mixing them is comparing coordinates on different maps. Pick one model for the whole corpus (e.g. text-embedding-3-small) and re-embed everything if it ever changes. Embeddings are also dimensionally flexible: v3 models can be shortened with the dimensions parameter to trade cost for accuracy.

5

Closeness is an angle, not a length

Cosine similarity measures the angle between two vectors — normalize vectors first so magnitude doesn't pollute the comparison. Scores range from −1 to 1; a score near 1 means "points the same direction," i.e. means nearly the same thing. That's the whole trick behind semantic search.

6

Evaluate chunking like an IR problem, not a vibes problem

Generate real queries over your corpus, mark the relevant tokens, and score chunking strategies by token-level recall and intersection-over-union (the Chroma research team's method). Their finding: defaults like RecursiveCharacterTextSplitter can perform well — but only when parameterized for your data; blind defaults often underperform.

05 Code sketch

Chunk, embed, and cosine-search in under 30 lines — then imagine replacing the sort with an ANN index and the naive splitter with a recursive one.

from math import hypot

def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    return dot / (hypot(a) * hypot(b))  # angle, not length

def build_index(docs, embed, chunk_size=400):
    index = []
    for doc in docs:
        for i, c in enumerate(recursive_split(doc.text, chunk_size)):
            index.append({
                "vec": embed(doc.title + "\n" + c),  # header prepended
                "meta": {"source": doc.title, "chunk": i},
                "text": c,
            })
    return index

def search(query, index, embed, k=5):
    q = embed(query)  # SAME model as index-time, always
    ranked = sorted(index, key=lambda c: cosine(c["vec"], q), reverse=True)
    return ranked[:k]

06 Failure modes

Named pitfalls, each with a one-line fix. Numbers one and two sink more RAG pipelines than every other mistake combined.

✕

Orphan chunks Fix: recursive split at semantic boundaries, 10–20% overlap, prepend the header/title — a chunk must read standalone.

"...applies within 30 days" — of what? Fixed-size cuts strand sentences from their context, and retrieval returns fragments the model can't use.

✕

Mixed embedding spaces Fix: one embedding model for the entire corpus and all queries; re-embed everything on model change.

Indexing with model A and querying with model B gives meaningless similarities — coordinates on two different maps. This failure is completely silent.

✕

Truncation past the context window Fix: keep chunks under the embedding model's input limit (e.g. 8192 tokens for text-embedding-3).

Excess tokens are silently dropped before embedding — the tail of a long chunk never makes it into the vector, so queries about it always miss.

✕

Meaning dilution Fix: shrink chunks to the scale of the answers you need; one noisy paragraph can sink a 2000-token chunk's score.

Oversized chunks smear precise facts across noise. Embeddings capture the average of everything in the chunk — the bigger the chunk, the blurrier the point.

✕

Chunking by vibes Fix: build a recall eval — real queries, relevant tokens marked, chunking strategies compared by token-level IoU.

Defaults feel safe and are often wrong. Chroma's research found popular default chunking settings underperform badly on token-level retrieval measures.

Try paragraph breaks first, then sentences, then words — until each chunk fits. The strong default: respects structure while enforcing size.
Semantic chunking
Embed sentence groups, measure the semantic distance between neighbors, and cut where the topic shifts. Experimental, costlier, but boundary-aware.
Self-contained chunk
A chunk that reads standalone: header, title, and source prepended. If a human can't understand it without the surrounding doc, neither can the model.

11 Reach for this when…

Retrieval keeps missing answers that exist in the corpus — check chunking first (orphans, dilution, unmeasured defaults) before touching the model.
You're picking an embedding model for a new index — one model for corpus and queries, sized dimensions to your budget, and a re-embedding plan before you switch.
You're building the ingestion pipeline for a RAG system or agent knowledge base — chunk at meaning boundaries with metadata attached, then eval with real queries.
