Lakehouse and warehouse engineering: Iceberg, Delta, and table design

Keep data as open files in cheap object storage, then add the warehouse guarantees on top with a table format: ACID commits, snapshots, schema evolution, and partition pruning — so one copy serves SQL, pipelines, and ML without copies drifting into silos.

02 The one-idea version

A lakehouse is not a product — it is files plus a metadata contract. Parquet files hold the rows; the table format (Iceberg's metadata tree or Delta's transaction log) records which files are the table right now, atomically. Swap that pointer and you get a commit; keep old pointers and you get time travel. Everything else — catalog, governance, medallion layers — sits on that one idea.

03 The picture: files, metadata, catalog, engines

Engines never list folders. They ask the catalog, read metadata, then prune to a few files.

04 How it works

Seven mechanics: separate the layers, commit atomically, evolve safely, partition for pruning, maintain files, govern once.

1

Separate storage, table format, catalog, and compute — choose each on purpose

Object storage holds immutable Parquet (or ORC/Avro) files. The table format defines commits and snapshots. The catalog maps a table name to its current metadata and carries permissions and lineage. Compute engines are interchangeable readers/writers. Microsoft's lakehouse principles make the same split: curate data as products, eliminate silos and copies, govern centrally, and prefer open formats so no single engine owns your data.

2

Commit by swapping one pointer — that is the ACID trick

Iceberg writers write new data files, then create a new metadata file and atomically swap the catalog pointer; readers on the old snapshot are unaffected, and a conflicting writer retries on the new base (optimistic concurrency, serializable isolation per the Iceberg spec). Delta does the equivalent with an ordered _delta_log: each commit is the next numbered JSON file, with periodic Parquet checkpoints. If the pointer/log entry did not land, the write did not happen — never partially visible.

3

Pick Iceberg vs Delta by engine mix and interoperability, not fashion

Iceberg is the engine-neutral spec: hidden partitioning, partition evolution, and broad support (Spark, Flink, Trino, Snowflake, BigQuery, DuckDB) via REST catalogs. Delta is Spark/Databricks-native with the tightest Unity Catalog integration, liquid clustering, and UniForm/Iceberg-compat modes that generate Iceberg metadata from a Delta table. Rule: multi-engine or multi-cloud future → Iceberg; Databricks-centred stack that will stay there → Delta is fine. Both give ACID, time travel, and schema evolution — the format war is mostly about who else must read the table.

4

Design tables around the query pattern: partition, sort, and file size

Partition on low-cardinality, always-filtered columns (usually time, via transforms like days(order_ts) in Iceberg's hidden partitioning — users filter on the timestamp, the format maps it to partitions). Sort/cluster within partitions on the next filter columns. Target roughly 128–512 MB files: too small and planning dominates, too large and pruning stops helping. Never partition on a high-cardinality ID — that manufactures millions of tiny partitions.

5

Evolve schema and partitions without rewriting history

Iceberg tracks columns by field ID, so add, drop, rename, reorder, and widen types safely; old files stay readable. Its partition evolution lets new writes use a new spec while old data keeps the old one. Delta enforces schema on write by default and evolves it explicitly (mergeSchema / protocol and table-feature upgrades — note from the Delta docs that upgrading reader protocol can break older readers, so use the lowest protocol that gives you the features you need). In both: additive first, breaking changes as a new table or a versioned view.

6

Run medallion layers as contracts, not folders full of hope

Bronze: append raw data exactly as received, plus source and ingest timestamp — it is your replay log. Silver: typed, deduplicated, conformed to one grain, with quality checks and quarantine for failures; MERGE/upserts live here (copy-on-write for read-heavy, merge-on-read/deletion vectors for write-heavy). Gold: business grains — facts, dimensions, feature tables — pre-aggregated for known consumers. Every gold table must be rebuildable from silver; every silver table from bronze. If a cleaning rule exists only in gold, you have already lost rebuildability.

7

Schedule maintenance like a job, because it is one

Streaming and frequent MERGEs create small files and delete files. Run compaction (Iceberg rewrite_data_files, Delta OPTIMIZE) to bin-pack files, expire snapshots and vacuum/retain history only as long as time-travel and audit actually need (commonly 7–30 days), and remove orphan files. Track file count, average file size, snapshot count, and scan-pruning ratio as table health metrics — a lakehouse degrades silently without them.

05 Code sketch

Create an Iceberg-style table design in Spark SQL, then a Delta MERGE for silver — the two idioms side by side.

# Iceberg: hidden partitioning + evolution-friendly design (Spark SQL)
spark.sql("""
CREATE TABLE lake.silver.orders (
  order_id BIGINT, customer_id BIGINT,
  amount DECIMAL(12,2), status STRING, order_ts TIMESTAMP
) USING iceberg
PARTITIONED BY (days(order_ts))   -- users filter order_ts, not a partition col
TBLPROPERTIES ('write.target-file-size-bytes'='268435456',
               'history.expire.max-snapshot-age-ms'='604800000')
""")

# Delta: idempotent silver MERGE (re-runnable, no duplicates)
from delta.tables import DeltaTable
target = DeltaTable.forName(spark, "lake.silver.customers")
(target.alias("t").merge(updates.alias("s"), "t.id = s.id")
  .whenMatchedUpdateAll().whenNotMatchedInsertAll().execute())

# Maintenance is scheduled, not remembered
spark.sql("CALL lake.system.rewrite_data_files('silver.orders')")
spark.sql("OPTIMIZE lake.silver.customers ZORDER BY (region)")

06 Failure modes

Five ways lakehouses rot — each with a one-line fix.

1

Small-files diseaseFix: batch writes, set a target file size (128–512 MB), and schedule compaction; alert on average file size.

Streaming micro-batches and frequent MERGEs leave thousands of tiny files. Every query pays planning and open-file costs, and the table gets slower while the data barely grows.

2

Partitioning on the wrong columnFix: partition only on low-cardinality columns that appear in almost every query filter; cluster/sort on the rest.

Partitioning by customer_id or a free-text field creates millions of partitions and no pruning benefit — metadata explodes and scans read everything anyway.

3

Schema drift handled by hopeFix: enforce schema on write, evolve additively by field ID / explicit merge, and contract-test producers against the silver schema.

A producer renames or retypes a column, downstream jobs fail days later (or worse, silently read nulls), and no one can say which snapshot introduced the break.

4

Snapshots and history kept foreverFix: set snapshot expiry / vacuum retention to the real audit window (often 7–30 days) and monitor storage by table.

Time travel is kept “just in case” for a year: metadata grows, old files are never deleted, and storage cost quietly doubles while planning slows.

5

Gold tables that cannot be rebuiltFix: keep bronze append-only and all cleaning logic in versioned silver jobs, so gold is always a re-runnable transform of silver.

Analysts patch gold directly, cleaning rules live only in a notebook, and when a bug is found there is no trustworthy path to recompute history.

6

Protocol upgrade that locks out readersFix: use the lowest Delta protocol / Iceberg format version your features need, and test every reader engine before upgrading a shared table.

Enabling a shiny feature raises the reader protocol; a BI tool or older Spark job that shares the table suddenly cannot read it at all.

10 Flashcards

Click a card (or focus it and press Enter / Space) to flip it.

Lakehouse
Open files in object storage plus a table format that adds warehouse guarantees — ACID, snapshots, schema enforcement — so one copy serves BI, pipelines, and ML.
Snapshot
The state of a table at one commit: the exact set of live data files. Readers pin a snapshot; writers create a new one. Old snapshots enable time travel until they expire.
Iceberg metadata tree
Catalog pointer → metadata file → manifest list → manifests → data files. Planning prunes with manifest statistics instead of listing folders — O(1) calls, not O(n).
Delta transaction log
The _delta_log: ordered JSON commit files plus Parquet checkpoints next to the data. The log is the table — replay it to reconstruct any version.
Hidden partitioning
Iceberg derives partition values from a column via a transform (e.g. days(order_ts)). Users filter on the column itself; they cannot forget or misuse a separate partition column.
Partition evolution
Changing the partition spec for new writes without rewriting old data. Old partitions are read under the old spec, new ones under the new — queries span both transparently.
Medallion: bronze / silver / gold
Bronze: raw, append-only, replayable. Silver: cleaned, typed, deduped, one grain, quality-gated. Gold: business grains for BI/ML. Each layer rebuildable from the one below.
Compaction
Rewriting many small files into fewer target-sized files (Iceberg rewrite_data_files, Delta OPTIMIZE). Scheduled maintenance — without it, scan planning cost grows until queries crawl.
Copy-on-write vs merge-on-read
CoW rewrites affected files on update (fast reads, costly writes). MoR writes delete files and merges at read (fast writes, costlier reads; deletion vectors soften this). Pick per table by read/write mix.

11 Reach for this when…

BI and ML keep copying the same dataset into different systems — put one governed copy in a lakehouse table format and let both read it; copies become silos that drift.
A data lake folder needs updates, deletes, or “what did this look like last Tuesday?” — that is exactly the table-format job: MERGE/upsert plus snapshot time travel, not another warehouse migration.
Queries scan everything and the table grows weekly — audit partitioning, file size, and compaction before buying bigger compute; layout, not horsepower, is usually the bottleneck.
