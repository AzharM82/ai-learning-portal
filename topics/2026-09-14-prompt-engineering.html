Prompt engineering: instructions, few-shot, and output contracts

How to write prompts that behave like reliable function calls — clear instructions, well-chosen examples, and an output shape your code can trust.

02 The one-idea version

Think of a prompt as a function signature for the model: the instructions are the contract, few-shot examples are the type examples, and the output contract is the return type. Most "model failures" are really underspecified contracts — fix the signature before you blame the model.

03 The visual

A well-engineered prompt is a pipeline, not a paragraph. Each stage has one job.

04 How it works

Six mechanics. Apply them in order and most prompt problems disappear.

1

Lead with the verb

Start instructions with the action: Classify…, Extract…, Rewrite…. Models weight early tokens heavily — don't bury the task under throat-clearing.

2

One job per prompt

A prompt that classifies and summarizes and formats will do all three badly. Split multi-step work into a chain of single-purpose prompts — each with its own contract.

3

Few-shot: show the mapping, include an edge case

Give 2–5 input → output pairs that obey your own rules. Examples teach format and judgment faster than paragraphs of instruction — and one tricky edge-case example prevents a whole class of errors.

4

Delimit everything

Wrap sections in markdown headers or XML tags (<instructions>, <examples>, <input>). Delimiters turn a wall of text into a parseable structure the model can actually navigate.

5

Specify the output contract

State the exact shape: JSON schema, allowed values, length bounds. "Return JSON" is a wish; a schema plus code-side validation is a contract.

6

Sandwich the non-negotiables

Models attend most to the start and end of a prompt. Put critical rules at the top and repeat them at the bottom. Anything load-bearing that lives only in the middle will be forgotten.

05 Code sketch

A prompt builder that treats the contract as code: versioned, typed, validated.

# prompts.py — prompts live in code, next to the feature they serve
import json

SCHEMA = {"type": "object", "properties": {
    "label": {"enum": ["bug", "feature", "question"]},
    "confidence": {"type": "number"}}, "required": ["label"]}

FEWSHOT = """<examples>
Input: "App crashes on login" -> {"label": "bug", "confidence": 0.95}
Input: "Add dark mode please" -> {"label": "feature", "confidence": 0.9}
</examples>"""

def build(ticket: str) -> str:
    return f"""# Role and objective
Classify the support ticket. One job only.
# Output contract
Return JSON matching this schema, nothing else: {json.dumps(SCHEMA)}
{FEWSHOT}
<input>{ticket}</input>
REMINDER: JSON only, matching the schema above."""

def parse(raw: str) -> dict:  # validate, never trust
    obj = json.loads(raw)
    assert obj["label"] in ("bug", "feature", "question")
    return obj

06 Failure modes

The four ways prompts usually break — each with a one-line fix.

✗

Vague verbsFix: specify audience, length, and format — "Summarize for a busy exec in 3 bullets" beats "Summarize this".

✗

Example driftFix: every few-shot example must obey your own rules — the model copies examples more faithfully than instructions.

✗

Buried constraintsFix: sandwich — state critical rules at the top and repeat them at the bottom; the middle gets skimmed.

✗

No output contractFix: JSON schema + code-side validation + one retry on failure. "Return JSON" alone is a wish, not a contract.

08 Sample prompts

Copy-paste starters. Each one demonstrates a mechanic from section 04.

THE OUTPUT-CONTRACT PROMPT

# Role: you are a precise information extractor. One job only. # Output contract: return a single JSON object with exactly these keys: # {"company": string, "amount_usd": number, "deadline": "YYYY-MM-DD or null"} # Rules: no markdown fences, no commentary, no extra keys. # If a value is absent, use null. Then the reminder: # REMINDER: JSON object only, exactly the three keys above. <input> {{paste the email or document here}} </input>

THE FEW-SHOT CLASSIFIER

Classify the ticket into exactly one of: bug, feature, question. <examples> "Login button does nothing on Safari" -> bug "Can you add SSO support?" -> feature "How do I reset my password?" -> question "Export to CSV gives a blank file, is that expected?" -> bug </examples> Reply with the single label only. <ticket>{{ticket text}}</ticket>

THE INTERN TEST (REWRITE PROMPT)

Rewrite the draft below so a brand-new intern could execute it without asking a single clarifying question. - Replace vague verbs with concrete actions and measurable outcomes. - Add: audience, length limit, output format, and two do/don't examples. - Keep every fact from the original; change only clarity. <draft>{{your vague prompt here}}</draft>

10 Flashcards

Click a card — or tab to it and press Enter — to flip it.

Zero-shot
Asking the model to do a task with no examples — instructions only. Fast and cheap, but risky for unusual formats.
Few-shot
Showing 2–5 input → output pairs so the model copies the exact mapping. Best lever for format reliability.
Output contract
The exact required shape of the response: JSON schema, allowed values, length bounds — enforced by code-side validation.
System prompt
The persistent instruction layer (role, rules, non-negotiables) that frames every user message in the conversation.
Primacy & recency
Models attend most to the start and end of a prompt. Critical rules go at both — the middle gets skimmed.
Example drift
When few-shot examples contradict the instructions, the model follows the examples. Every example must obey your own rules.
Sandwich method
Role and task at the top, context/data in the middle, critical rules repeated at the bottom. Structure that survives long prompts.
The intern test
The single best prompt review: could a brand-new intern follow these instructions without asking one clarifying question? If not, rewrite.
Structured outputs
Constraining generation to a schema (JSON mode, grammars) so outputs are machine-readable by construction, not by luck.

11 Reach for this when…

Outputs are vague or inconsistent — before you blame the model, check whether the contract was ever specified.
Code consumes the model's response — any time a parser touches LLM output, you need a schema plus validation.
A prompt does three jobs at once — split it into single-purpose prompts, each with its own examples and contract.
