01 / LOOP

Engineer the repetition, not just the first answer.

Loop engineering designs the cycle by which an agent observes a result, judges it, and decides what to do next.

The core idea

A prompt gives a model one shot. A loop gives it a process. Instead of “write the code,” the system says: inspect the repository, form a plan, make one change, run the relevant check, study the result, and repeat until a stopping condition is met.

The engineering challenge: make each iteration produce new information. A loop that repeats the same failed action is only an expensive spinner.

A
StateWhat the agent knows now: goal, files changed, errors, test evidence.
B
FeedbackA grounded signal: test output, compiler error, reviewer critique, user response.
C
PolicyThe rule for choosing the next action from the current state.
D
Stop conditionDone, blocked, unsafe, out of budget, or no meaningful progress.
A useful agent loop
ObserveRead the task, environment, and latest evidence.
DecideChoose the smallest action that reduces uncertainty.
ActUse a tool, edit a file, or ask a precise question.
VerifyTest the outcome; stop or feed the result back in.
CODEX-STYLE LEARNING PROMPT · LOOP ENGINEERING
Act as my senior agent-systems mentor. Teach me loop engineering through one realistic coding task.

1. Define the loop's state, actions, feedback signals, and stop conditions.
2. Show one naïve loop and explain exactly why it stalls or thrashes.
3. Redesign it as Observe → Decide → Act → Verify.
4. Trace three iterations using a compact state table.
5. Add failure budgets, retry limits, and an escalation rule.
6. End with a 10-minute exercise where I must repair a broken loop.

Do not move on until I can explain what new information enters on each iteration.
Why it works: it asks for a concrete trace and forces every cycle to earn its cost.
Good loop

Code repair

Edit one fault, run the narrow test, inspect the failure delta, then broaden verification.

Bad loop

Retry blindly

Send the same prompt after every error with no state update or changed hypothesis.

Design test

Ask what changed

If iteration two has no new evidence, the loop needs a better observation or action.

02 / GRAPH

Make the route through the work explicit.

Graph engineering models a workflow as nodes and transitions so branches, approvals, parallel work, and recovery are visible—not buried in a giant prompt.

The core idea

A loop answers “what happens again?” A graph answers “what can happen next?” Nodes represent meaningful states or operations. Edges represent the conditions that move work between them.

Graphs become valuable when the happy path is not the only path: a test may pass or fail, a tool may return partial data, a human may approve or reject, and independent tasks may run in parallel before joining.

CODEX-STYLE LEARNING PROMPT · GRAPH ENGINEERING
Teach me graph engineering by converting this workflow into an explicit state graph: “research a technical decision, challenge the evidence, get approval, implement, and verify.”

For every node, specify:
- purpose and owner
- required input schema
- output schema
- success and failure edges
- retry policy and idempotency risk

Then:
1. Draw the graph in Mermaid syntax.
2. Walk through the happy path and two failure paths.
3. Identify where parallelism helps and where it creates race conditions.
4. Show how state should be checkpointed at each boundary.
5. Quiz me by removing three edge conditions and asking me to restore them.
Why it works: schemas and failure edges turn a vague diagram into an executable design.
Use a graph when

Paths diverge

Different evidence, approvals, or risk levels should lead to different actions.

Avoid complexity when

The path is linear

A three-step deterministic script rarely needs a workflow engine.

Design test

Name every edge

If “otherwise” is doing too much work, an important state is probably hidden.

03 / HARNESS

Build the environment that makes good behavior easier.

Harness engineering surrounds the model with the tools, context, constraints, tests, and observability required to turn capability into reliable work.

The core idea

The model is only one component. The harness decides what it can see, what it can change, how tools are called, which checks must pass, what gets logged, and when a human must intervene.

For coding agents, the repository structure, instructions, tests, sandbox, patch review, and command timeouts often matter as much as the model. Better harnesses reduce ambiguity before asking the model to be “smarter.”

T
Tool contractSmall, typed actions with explicit effects and useful errors.
C
Context contractThe right files and rules, revealed when needed—not a context dump.
V
Verification contractTests and evaluators that can reject plausible-looking failures.
G
Governance contractPermissions, budgets, audit logs, and human checkpoints.
The model sits inside the harness
OBSERVABILITYTrace actions, costs, errors, state transitions, and evidence.
GUARDRAILSPermissions, sandboxes, budgets, approvals, and stop rules.
TOOLS + CONTEXTAPIs, repository instructions, retrieval, schemas, and fixtures.
MODELReasoning and generation inside a controlled operating environment.
CODEX-STYLE LEARNING PROMPT · HARNESS ENGINEERING
Act as a principal engineer reviewing an AI coding-agent harness. Use this scenario: the agent may inspect a repository, edit files, run tests, and propose a pull request—but cannot deploy.

1. Define the tool surface with precise inputs, outputs, and side effects.
2. Design progressive context loading: what is always loaded, retrieved on demand, and never exposed.
3. Specify sandbox, permission, timeout, and budget boundaries.
4. Create a verification ladder from lint → unit tests → integration tests → human review.
5. Add observability fields that would let us reconstruct a failed run.
6. Red-team the harness with five realistic failure modes.
7. Finish with the smallest viable harness and a roadmap for hardening it.
Why it works: it treats reliability as system design, not a clever sentence sent to the model.
Strong harness

Narrow tools

“Apply patch to these files” is easier to govern than unrestricted shell access.

Weak harness

Hidden success

If the agent cannot observe whether its change worked, fluent failure looks complete.

Design test

Replay the run

If an engineer cannot reconstruct the failure, the harness lacks observability.

Prompt studio

Change the prompt to change how you learn.

Use these modes with any of the three topics. They are designed like good Codex tasks: grounded, scoped, verifiable, and iterative.

Visual map prompt

Best when you need a mental model before details.

PROMPT
Teach me [TOPIC] as a visual systems map. Start with one sentence, then show components, flows, feedback, failure points, and boundaries. Use one concrete software example throughout. After the map, ask me to redraw it from memory and correct my version.

Socratic prompt

Best for exposing gaps in your understanding.

PROMPT
Teach me [TOPIC] Socratically. Ask one diagnostic question at a time. Adapt the next question to my answer. Do not reveal the full explanation early. Make me distinguish it from adjacent concepts, predict a failure, and design a fix. End with a concise model answer and my remaining gaps.

Build-it prompt

Best when understanding must survive contact with code.

PROMPT
Teach me [TOPIC] by pairing with me on the smallest working implementation. First define acceptance tests. Then give me one step at a time, waiting for my result. Prefer visible state and deterministic checks. After it works, introduce one failure and make me diagnose it before explaining.

Review-me prompt

Best for turning passive familiarity into durable skill.

PROMPT
Review my explanation or design for [TOPIC] as a strict principal engineer. Separate: correct, incomplete, confused, and risky. Quote the exact sentence or decision you are reacting to. Ask me to repair the top three issues. Re-score only after I respond.

A 90-minute learning sprint.

One small build is worth more than ten abstract summaries.

00–15 MIN

Map

Draw a bug-fixing agent as a loop. Name its state, feedback, and stop rule.

15–35 MIN

Branch

Add graph paths for test pass, test fail, blocked dependency, and review.

35–70 MIN

Harness

Define tools, file permissions, command timeout, and verification ladder.

70–90 MIN

Break it

Inject a flaky test or ambiguous error. Observe the failure and redesign one layer.

Self-check
Can a loop exist without a graph?

Yes. A simple retry or refinement cycle may have one repeated path. It becomes graph-like when the system needs explicit branches, joins, approvals, or recovery routes.

Can a graph replace a harness?

No. A graph describes coordination, but it does not by itself limit permissions, provide tools, expose context, verify results, or log the run. Those are harness responsibilities.

What should you improve first?

Start with the failing layer. Repeated mistakes with no learning suggest the loop. Confused routing suggests the graph. Unsafe actions or unverified outputs suggest the harness. Often, the highest-return fix is better feedback inside the harness.

Where do prompts fit?

Prompts are part of the harness's context and policy, but they are not the whole system. A strong prompt cannot compensate for missing evidence, unsafe permissions, or tests that never run.

The shortest useful mental model.

Loops create learning, graphs create coordination, and harnesses create trust. Mature agent systems need all three—and clear boundaries between them.

feedback × routing × verification
